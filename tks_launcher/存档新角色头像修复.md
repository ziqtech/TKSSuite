# 存档界面新角色头像修复（补丁十五）

> 修复日期: 2026-05-22
> 涉及补丁: [补丁十五]
> 启动器: `tks_launcher.cs`

---

## 一、问题现象

启用启动器（含 WarPC 缓冲区扩展、补丁十一~十四）后，存档列表整体能正常显示（队伍头像、时间、地图、金钱等），但 **新角色（ID 143/144/145）的队伍头像显示异常**：

| 槽位 | 团队 | 实际显示 |
|---|---|---|
| slot 6 | [0, 143, 144, -1, -1, -1] | 主角 + "离开" + "ON"（按钮文字） |
| slot 9 | [0, 143, 144, 145, -1, -1] | 主角 + "离开" + "ON" + "OFF"（按钮文字） |

新角色位置渲染成 GRP 资源中的 UI 按钮文字（"离开/ON/OFF"）而不是头像。

---

## 二、根因深度分析

### 2.1 反编译代码分析

`sub_41AB94` 渲染存档列表队伍头像：

```c
sub_4544EC(
    dword_755AF4,
    71 * v7 + 16,
    150 * i + 46,
    *(char *)(v5 + 6 * (3 * page + i) + 670) + 211,   // ← frame = (char) ID + 211
    a1 + 926,
    -1);
```

frame 计算公式：`(signed char) ID + 211`

### 2.2 实际汇编（dump 后定位）

第一次扫描 `add eax, 0xD3` (`05 D3 00 00 00`) 失败（hook 0 处）。增强诊断后 dump 整个 sub_41AB94 函数体，发现 **只有 1 处 D3**：

```
RVA 0x1AD02:  0F BE 84 41 9E 02 00 00   movsx eax, byte ptr [ecx+eax*2+0x29E]   ; (char) ID
RVA 0x1AD0A:  66 05 D3 00               add ax, 0xD3                            ; ← 16 位加!
RVA 0x1AD0E:  50                        push eax                                ; frame
```

**编译器使用了 16 位的 `add ax, 0xD3` 而不是 32 位的 `add eax, 0xD3`**。这与 `sub_41762C` 中 PortraitCave1 hook 位置 0x17A50 的指令编码完全一致：`66 05 D3 00 50`。

### 2.3 双重 Bug 推导

**Bug 1: Sign-Extension 错位**

```
ID = 143 (= 0x8F as byte)
movsx eax, byte → eax = 0xFFFFFF8F (sign-extended -113)
add ax, 0xD3 → ax = 0x8F + 0xD3 = 0x162 (16-bit overflow, ax = 0x62)
                eax 高 16 位仍是 0xFFFF
push eax → 栈上推入 0xFFFF0062
sub_4544EC 取 frame 低 16 位 = 0x0062 = 98 → 显示 GRP 第 98 帧（"离开"按钮）
```

| ID | (char) ID + 211 (实际 frame) | 渲染结果 |
|---|---|---|
| 0 | 0 + 211 = 211 | ✅ 主角头像 |
| 143 | -113 + 211 = **98** | ❌ "离开" 按钮 |
| 144 | -112 + 211 = **99** | ❌ "ON" 按钮 |
| 145 | -111 + 211 = **100** | ❌ "OFF" 按钮 |

**Bug 2: 没有 WORD[261] 自定义头像查询**

游戏内队伍头像（`sub_41762C` / `sub_417F84`）已通过 `补丁三` 的 `PortraitCave1`/`PortraitCave2` 实现 WORD[261] 优先查询逻辑。

但**存档列表渲染**走的是另一个函数 sub_41AB94，没被补丁覆盖。新角色 (143-145) 的 WarPC.WORD[261] 已设置好（如 0x114/0x115），但存档界面依然走默认 `ID + 211` 公式。

## 三、修复方案

### 3.1 ArchivePortraitCave 设计（48 字节）

参考 PortraitCave1 的 `xchg + jmp eax` 出口技巧（因 hook 替换了 5 字节 `add ax + push eax`，cave 必须自己模拟 push eax 行为）：

```nasm
; 入口约定:
;   eax = movsx 后的 signed char ID (32-bit sign-extended)
;   [esp] = call 推入的返回地址 (= hook+5)

[00] push edx                           ; 保存 edx
[01] push ecx                           ; 保存 ecx
[02] movzx eax, al                      ; 修复 sign-extend → unsigned ID (0..255)
[05] mov ecx, eax                       ; ecx = ID (备用)
[07] imul eax, eax, 1054                ; eax = ID × 1054
[13] add eax, 0x757F08                  ; eax = WarPC[ID]（启动器替换为 newBuf）
[18] movzx edx, [eax + 0x20A]           ; edx = WORD[261]
[25] test dx, dx
[28] jnz +9 → [39]                      ; 非零 → 使用自定义头像
; 默认路径
[30] mov eax, ecx                       ; eax = unsigned ID
[32] add eax, 0xD3                      ; eax = ID + 211 (32 位加, 不溢出)
[37] jmp +2 → [41]
; .use_custom
[39] mov eax, edx                       ; eax = WORD[261]
; .done
[41] pop ecx
[42] pop edx
; 关键: 让栈上留 frame 替代被覆盖的 push eax
[43] xchg eax, [esp]                    ; eax = ret_addr, [esp] = frame
[46] jmp eax                            ; 跳回 hook 下一条指令
```

### 3.2 Hook 模式与定位

**扫描模式**：`66 05 D3 00 50`（5 字节）
- `66 05 D3 00` = add ax, 0xD3
- `50` = push eax

**Hook 替换**：将 5 字节替换为 `E8 XX XX XX XX`（call ArchivePortraitCave）

由于 sub_41AB94 中只有这 1 处 D3，扫描具有唯一性。

### 3.3 WarPC 基址自动重定向

Cave 中的硬编码地址 `0x757F08` 由启动器现有的 `字段级盲扫机制`（在 `ExpandWarPcBuffer()` 中）自动替换为 newBuf 地址，无需在 cave 内做特殊处理。

## 四、关键经验教训

### 4.1 编译器优化导致汇编模式与反编译不一致

反编译的伪代码 `*(char *)(...) + 211` 让人想到 `add eax, 0xD3` 这样的 32 位运算，但**编译器实际用了 16 位 `add ax, 0xD3`**。在游戏代码中这种模式很普遍（编译器优化）。

**经验**：定位 hook 位置时，**不要相信反编译伪代码的运算位宽**，必须 dump 真实字节确认。同一行 C 代码可能编译为多种不同汇编模式：
- `add eax, imm32` (5 字节: 05 D3 00 00 00)
- `add ax, imm16` (4 字节: 66 05 D3 00) ← 本次案例
- `lea eax, [reg + imm32]` (6+ 字节)
- `add eax, imm8 (sign-extended)` (3 字节: 83 C0 ?? — 仅适用 imm8 ≤ 127)

### 4.2 Hook 替换 add+push 组合需要模拟原 push 行为

替换 `add ax, 0xD3 + push eax` (5 字节) 为 `call cave` (5 字节) 时，**call 已经把返回地址 push 到栈上**。Cave 内部必须用 `xchg eax, [esp] + jmp eax` 技巧：

```
入口栈: [esp] = ret_addr (call 推入)
出口栈: [esp] = frame (替代原 push eax 的效果)
        eax = ret_addr (用于 jmp)
```

这与简单的 `add eax, 0xD3` 替换不同（后者只需 `ret` 即可，因为没有 push 行为要模拟）。

### 4.3 Sign-Extension 在 ID >= 128 时的连锁问题

游戏代码用 `(char) ID` 处理队员索引，原本只支持 ID 0-127（队员 ID 总是非负且小，主角=0）。但 WarPC 缓冲区扩展后新角色 ID 达到 143-255，触发 sign-extension：

```
movsx eax, byte → eax = 0xFFFFFF8F (signed -113)
```

后续算术（`+211`、`*527` 等）若用 32 位运算会得到错误的小负数 frame；若用 16 位运算（如 `add ax`）则保留高位 0xFFFF 导致截断后仍错位。

**通用对策**：所有处理新角色 ID 的 hook 都应该在入口先 `movzx eax, al` 修复 sign-extension，再做后续运算。

### 4.4 完整 dump 函数体的诊断价值

第一次扫描 `add eax, 0xD3` 失败时，单纯加"D3 00 位置扫描"也不够（因为 `66 05 D3 00 50` 中 D3 后跟 00 但还要后跟 50）。**完整 dump 函数体到日志**让我能直接读懂所有附近指令：

```
+0x0160: 00-8D-14-49-03-C2-8D-04-40-8B-4D-F4-0F-BE-84-41-9E-02-00-00-66-05-D3-00-50-0F-BF-55-FE-8B-CA-03
                                                 ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                                 movsx eax,byte[ecx+eax*2+0x29E]; add ax,0xD3; push eax
```

只看了一行就完全确认了指令编码、寻址模式、入口约定。**复杂 hook 之前应当先 dump 函数体作为诊断**。

## 五、Cave 字节级验证

补丁十五成功后，日志会显示：

```
RVA=0x..AF00C0  bytes=[52-51-0F-B6-C0-8B-C8-69-C0-1E-04-00-00-05-00-00-F1-07-0F-B7-90-0A-02-00-00-66-85-D2-75-09-8B-C1-05-D3-00-00-00-EB-02-8B-C2-59-5A-87-04-24-FF-E0]
                       ^^                                 ^^^^^^^^^^                                                              ^^^^^^^^^^^^^
                       push edx                           newBuf 地址 (字段级盲扫替换)                                              xchg+jmp 出口
```

注意 cave 中的 `05 00 00 F1 07` 是 `add eax, 0x07F10000` — newBuf 地址被字段级盲扫机制成功替换（原 cave 中是 `05 08 7F 75 00` = `add eax, 0x757F08`）。

## 六、与现有头像补丁的统一性

修复后，三个头像渲染场景使用统一的 WORD[261] 优先逻辑：

| 场景 | 函数 | Cave | Hook 位置 |
|---|---|---|---|
| 游戏内队伍头像（选中） | sub_41762C | PortraitCave1 (41B) | RVA 0x17A50 |
| 游戏内队伍头像（未选中） | sub_417F84 | PortraitCave2 (42B) | RVA 0x17E1A |
| **存档列表队伍头像** | **sub_41AB94** | **ArchivePortraitCave (48B)** | **RVA 0x1AD08（运行时扫描）** |

三个 cave 共享同一套规则：**WORD[261] 非零 → 使用 WORD[261] 作 GRP 帧；为零 → 默认 `ID + 211`**。

存档列表的 cave 比另外两个稍长（48 vs 41/42 字节），原因：
- 多一个 `movzx eax, al` 修复 sign-extend（前两个的 ID 来源不是 movsx byte）
- 多一对 `imul eax, eax, 1054` 代替 `add eax, eax`（前两个的入口 ecx 已是 char_idx*527）
