## 二、DefUnit 链表结构与 DEFINE ID 编码

### 2.1 链表遍历机制

**证据：`sub_4066F0`（`4066F0.c`）反编译代码**

```c
int __cdecl sub_4066F0(int a1, int a2)
{
    // a1 = 实体记录指针（&dword_51AF40[96 * entity_id]）
    // a2 = 子场景选择: 0=A链, 1=B链, 2=C链

    if (a2 == 0)      { v5 = 30; v4 = 39; v3 = 33; }  // max_A, head_A, cur_A
    else if (a2 == 1) { v5 = 31; v4 = 40; v3 = 34; }  // max_B, head_B, cur_B
    else              { v5 = 32; v4 = 41; v3 = 35; }  // max_C, head_C, cur_C

    // 有效性检查：max <= 0 或 cur <= 0 或 max < cur → 返回 -1
    if (entity[v5] <= 0 || entity[v3] <= 0 || entity[v5] < entity[v3])
    {
        entity[44] = -1;   // d44 = -1（无效）
        entity[42] = -1;   // d42 = -1
        return a1;
    }

    // ★ 从 head 出发，沿链表跳转 cur-1 步
    v7 = entity[v4];                          // 取 head 指针
    for (i = 1; i < entity[v3]; i++)          // cur=1 时跳过循环
        v7 = dword_753500[16 * v7 + 12];      // ★ 跳转到 f6（next）指针

    entity[44] = v7;  // ★ d44 = 当前 DefUnit 索引（运行时填充）
    return i;
}
```

**遍历过程（cur_B=1 时不走循环，直接取 head）：**

```
cur_B = 1  →  v7 = head_B = 66  →  d44 = 66
cur_B = 2  →  v7 = head_B = 66
               i=1: v7 = DefUnit[66].f6 = 67
               →  d44 = 67
```

### 2.2 DefUnit 条目结构

**TKDefUnit.dat 格式：每条记录 16 字节 = 8 × uint16**

| 偏移 | 字段 | 含义 |
|------|------|------|
| 0 | f0 | DEFINE ID 低 16 位（block_id） |
| 2 | f1 | 实体 ID（entity_id） |
| 4 | f2 | 保留（通常 0） |
| 6 | f3 | 保留（通常 0） |
| 8 | f4 | 第二槽：DEFINE ID 低 16 位 |
| 10 | f5 | 第二槽：实体 ID |
| 12 | **f6** | **next 指针（链表下一跳）** |
| 14 | f7 | 保留（通常 0） |

> **注意：每条记录有 2 个槽位（f0/f1 和 f4/f5），可编码 2 个脚本引用。B 链遍历时只用第一槽（f0/f1），f6 决定下一跳。**

## 四、cur_B 推进机制 —— SetNowDef 外部切换

### 4.1 为什么子场景 1 不会自动推进到子场景 2

**证据：`40EBD4.c` 中 End 操作码的分发逻辑**

```c
// End(mode) 的 mode 参数决定了链行为：
switch (EndMode)
{
    case 0xFFFF:  // End(1) → cur_A++（A 链递增）
    case 0xFFFE:  // End(2) → cur_B++（B 链递增）
    case 0xFFFD:  // End(3) → cur_C++（C 链递增）
    case 0xFFFC:  // End(4) → cur_A = 0（A 链重置）
    case 0xFFFB:  // End(5) → cur_B = 0（B 链重置）
    case 0xFFFA:  // End(6) → cur_C = 0（C 链重置）

    case 0:       // ★ End(0) → 不修改任何链，只保存 PC
        // 然后一律调用 sub_4066F0(entity, 0)
        // sub_4066F0 带参数 0=处理 A 链，对 B 链无影响
}
```

**End 模式速查表：**

| End 参数 | 行为 | cur_X 变化 |
|----------|------|-----------|
| End(0) | 保存 PC，不修改链 | 不变 |
| End(1) | A 链递增 | cur_A++ |
| End(2) | B 链递增 | cur_B++ |
| End(3) | C 链递增 | cur_C++ |
| End(4) | A 链重置 | cur_A=0 |
| End(5) | B 链重置 | cur_B=0 |
| End(6) | C 链重置 | cur_C=0 |

### 4.2 SetNowDef —— 外部修改 cur_B 的唯一途径

**证据：`sub_40B520`（`40B520.c`，opcode 4）反编译代码**

```c
int *__cdecl sub_40B520(__int16 a1, __int16 a2, __int16 a3)
{
    // a1 = 目标实体 ID（-1=当前上下文, -2=self）
    // a2 = 链选择: 1=A链, 2=B链, 3=C链
    // a3 = 新的 cur 值

    v4 = &dword_51AF40[96 * a1];  // 目标实体记录

    switch (a2)
    {
        case 1:  // A 链
            v4[33] = a3;              // cur_A = a3
            if (v4[33] > v4[30])      // 若超过 max_A → 归零
                v4[33] = 0;
            break;

        case 2:  // B 链
            v4[34] = a3;              // ★ cur_B = a3
            if (v4[34] > v4[31])      // 若超过 max_B → 归零
                v4[34] = 0;
            break;

        case 3:  // C 链
            v4[35] = a3;              // cur_C = a3
            if (v4[35] > v4[32])      // 若超过 max_C → 归零
                v4[35] = 0;
            break;
    }
}
```

**SetNowDef 用法：**
```
SetNowDef(entity_id, chain, new_cur)
SetNowDef(715, 2, 2)   → 将实体 715 的 cur_B 设为 2（切换到子场景 2）
SetNowDef(715, 2, 1)   → 将实体 715 的 cur_B 设为 1（切换到子场景 1）
SetNowDef(715, 1, 3)   → 将实体 715 的 cur_A 设为 3
SetNowDef(-2, 2, 0)    → 将当前实体的 cur_B 重置为 0（禁用 B 链）
```

    // a3 = operator（比较运算符）

}

## 七、如何判断任意实体的 B 链执行条件

基于以上分析，追踪一个实体的 B 链执行条件需要以下步骤：

### 7.1 快速检查清单

1. **读 TKMat.Dat 该实体记录**：确认 `d31 (max_B)`、`d34 (cur_B)`、`d40 (head_B)` 的值
2. **追踪 DefUnit 链**：从 head_B 沿 f6 跳转，找到所有 DEFINE ID（`f1 × 65536 + f0`）
3. **在 TKD.dat 中找到对应 DEFINE 块**：读取脚本内容
4. **检查脚本中的条件命令**：
   - `CheckFlag(flag_id, value, op)` → 检查全局标志
   - `CheckTeam(member1, member2, ...)` → 检查队伍成员
   - `CheckItem(item_id, ...)` → 检查道具
   - `CheckResult(slot, value)` → 检查变量槽
   - `CheckMember(...)` → 检查成员状态
5. **搜索所有 `SetNowDef(实体ID, 2, N)`**：找到哪些外部脚本会修改它的 cur_B
6. **向上追溯触发脚本**：找到对应外部脚本的执行条件（通常也是 CheckFlag）

### 7.2 以实体 715 为例的完整追踪

```
步骤 1: 实体数据
  max_B=2, cur_B=1, head_B=66
  → 2 个子场景，当前在第 1 个

步骤 2: DefUnit 链
  [66] → DEFINE 46858496 (子场景 1)
  [67] → DEFINE 46858497 (子场景 2)

步骤 3: 子场景 1 脚本
  使用 CheckTeam(5,6) 和 CheckResult(0,0/1)
  → 依赖队伍成员和玩家菜单选择
  → 使用 End(0)，不推进 cur_B

步骤 4: 子场景 2 脚本
  纯对话，无条件分支
  → 使用 End(0)

步骤 5: 搜索 SetNowDef
  SetNowDef(715, 2, 2) 在 DEFINE 49152000 中
  → cur_B 推进由"妖狐事件"过场脚本触发

步骤 6: 追溯过场脚本触发条件
  DEFINE 49152000 包含 SetFlag(352, 1)
  可能由其他脚本的 CheckFlag 触发
```

### 7.3 常见的触发模式

| 模式 | cur_B 推进方式 | 典型场景 |
|------|---------------|---------|
| **脚本自推进** | 子场景中使用 `End(2)` | 多段对话依次触发 |
| **外部事件推进** | 外部脚本 `SetNowDef(id, 2, N)` | 剧情过场后 NPC 对话变化 |
| **标志驱动** | `CheckFlag + SetNowDef` 组合 | 任务进度驱动的 NPC 状态 |
| **队伍驱动** | `CheckTeam + SetNowDef` 组合 | 特定角色在队时的对话变化 |
| **道具驱动** | `CheckItem + SetNowDef` 组合 | 持有特定物品后的反应 |
