# 战斗经验锁定（压级）补丁 — 实现方案

## Context

在 TKS Launcher GUI 中增加一个**可选、配置驱动**的补丁「战斗经验锁定（压级）」：允许用户通过 `configs_editor/configs_editor.py` 勾选**战斗队伍槽位 0–5** 中任意若干槽位，被锁定槽位的队员**在战斗胜利结算时不获得任何战斗经验、也不会升级**，从而实现队伍成员的均衡培养。

> **逆向证据基线**：本方案的所有地址、变量、字段偏移均与已验证文档一致，见
> `战斗经验结算逻辑逆向分析` 与
> `战斗经验溢出分析`，
> 核心函数 `sub_43B7FC`（战后经验分配）。

---

## 一、可行性结论

**完全可行。** 依据三点：

1. 战斗经验发放集中在单一函数 `sub_43B7FC`（战斗胜利 `sub_43BFE8(1)` 唯一调用），按**队伍槽位循环**逐个发放。
2. 队伍槽位数 `byte_9DF886` 由战斗初始化 `sub_4307CC` 的 `do { … } while (v28 < 6)` 构建，**上限恰为 6，槽位 0–5**，与需求精确对应。
3. 引擎内**原生就存在**「按槽位索引把某槽经验清零」的逻辑（`if (v13==v5) *v19=0`），压级只是把判定来源从事件标志换成配置掩码。

---

## 二、逆向依据

### 2.1 经验分配循环（sub_43B7FC）

`43B7FC.c L92–L143` 按槽位遍历：

| 变量 | 含义 | 说明 |
|------|------|------|
| `v5` | 槽位索引 (0 … `byte_9DF886`-1) | 循环计数器 |
| `byte_9DF886` | 战斗队伍人数 | 循环上界，≤ 6 |
| `v18 = word_9D7084` | 队员战斗结构指针 | 步长 527 word = 1054 字节 |
| `v19 = dword_9D6F20` | **每槽「本战获得经验」累加器 (int32×6)** | 战斗中击杀奖励已累加于此，战后再加共享池 |

关键片段（保留原始行为，仅标注干预点）：

```c
// 第三阶段：分配 + 加成 + 上限（干预点就在本阶段末尾）
*v19 += dword_9D6F14;                       // L102 加入共享经验池分摊
if (v18[31]) *v19 += (v18[31]* *v19+99)/100;// L104 exp_bonus 加成 (WarPC field[36])
if (dword_755C80 & 0x20) *v19 *= 2;         // L109 全局双倍
if (v13 == v5) *v19 = 0;                    // L111 「经验×2平分」持有者清零（原生按索引清零）
if (v12 >= 0 && v12 != v5) *v19 = 0;        // L113 「经验独得」他人清零
if (*v19 > 30000) *v19 = 30000;             // L115 上限
v11 = *(_WORD *)v19;                        // L116 ★★ 干预点：v11 = 最终获得经验 ★★
for (i = v18-1; *i <= v11; ...) { 升级 }    // L117 v11 驱动升级循环
*(v18 - 2) += v11;                          // L124 写回 current_exp (WarPC field[3])
*(v18 - 1) -= v11;                          // L125 写回 exp_to_next (WarPC field[4])
```

**为什么选 L116（读取 `v11` 处）做干预**：此处位于「上限截断之后、升级循环之前」，压在所有加成/双倍/池分摊之上。干预方式：将**被锁定槽位的 `*v19`（即 `dword_9D6F20[slot]`，每槽获得经验累加器）置 0**：

- 随后 `v11 = *(_WORD *)v19` 读到 0 → 升级循环条件不成立 → **不升级**；写回 `current_exp += 0`、`exp_to_next -= 0` → **经验不变**；
- 结算屏显示函数 `sub_43B2D4` 在本循环之后（L168）运行，其 L55 直接读 `*v6 = dword_9D6F20[slot]` 显示“获得经验”——置 0 后**结算屏也显示 0**。

> 早期方案仅零化本地拷贝 `v11`，实际经验不增但结算屏仍显示原值（因 `dword_9D6F20[slot]` 未动）；改为零化 `*v19` 后两者一致。

即被锁定槽位的经验与等级被完全冻结，且不影响其他任何逻辑（JP/金钱/掉落均在别处，不受影响）。锁定只可能**减少**升级，绝不会引发异常升级。

### 2.2 干预点真实机器码（VA 0x43BAF3）

从内存转储 `memory/00401000--00481000.txt` 反汇编核对：

```
0x43BADF: 8B 10 81 FA 30 75 00 00 7E 0A …  ; exp_cap_unsigned_fix 占用区 (至 0x43BAF2)
0x43BAF3: 8B 44 24 1C        mov  eax,[esp+1C]  ┐ 拟偷取 7 字节
0x43BAF7: 66 8B 10           mov  dx,[eax]      ┘ (mov eax=v19; mov dx=*v19)
0x43BAFA: 66 89 54 24 06     mov  [esp+06],dx   ; v11 = dx  ← hook 返回后在此落地
```

- 与相邻的 `exp_cap_unsigned_fix`（结束于 `0x43BAF2`）**零重叠**，两补丁可共存。
- 槽位索引 `v5` 全程存于 `[esp]`（word）；`v19` 存于 `[esp+1C]`。

### 2.3 槽位与结构对应（引用既有验证）

| 语义 | WarPC 索引 | 战斗结构（`word_9D7084` 基址） | 证据 |
|------|-----------|------------------------------|------|
| current_exp | field[3] | `v18[-2]` | 结算逻辑文档 §一 |
| exp_to_next | field[4] | `v18[-1]` | 结算逻辑文档 §一 |
| 每槽获得经验 | — | `dword_9D6F20[v5]` (int32×6) | 结算逻辑文档 §一 |

> WarPC 索引 = 战斗结构索引 + 5，已由既有文档多处交叉验证。

## 三、Cave Hook 设计（字节级）

### 3.1 Hook 安装

在 VA `0x43BAF3` 偷取 7 字节 `8B 44 24 1C 66 8B 10`，替换为：

```
E8 <rel32>   ; call cave         (5 字节)
90 90        ; NOP 填充           (2 字节)
```

`call` 压入返回地址 `0x43BAF8`（落在 NOP 上）；cave `ret` 后执行 2× NOP，再到 `0x43BAFA` 的 `mov [esp+06],dx`，把 cave 计算好的 `dx` 存入 `v11`。

### 3.2 Cave 代码（28 字节，入口 esp 已 +4）

```asm
; 入口: [esp]=返回地址; 原 [esp+1C](v19) → [esp+20]; 原 [esp](v5) → [esp+04]
8B 44 24 20        mov   eax, [esp+20h]       ; eax = v19 指针 (重放被偷指令1)
0F B7 4C 24 04     movzx ecx, word [esp+04h]  ; ecx = v5 = 槽位 (0..5)
B2 <MASK>          mov   dl,  <MASK>          ; dl = 锁定掩码 (imm8, 由配置写入; bit i=锁定槽 i)
D2 EA              shr   dl,  cl              ; dl >>= 槽位
F6 C2 01           test  dl,  1
74 06              jz    .keep                ; 未锁定 → 不改动
C7 00 00 00 00 00  mov   dword [eax], 0       ; 锁定 → dword_9D6F20[slot]=0 (显示&逻辑均 0)
.keep:
66 8B 10           mov   dx,  [eax]           ; 重放被偷指令2: dx=*v19 (锁定则 0)
C3                 ret                         ; 返回 0x43BAF8 (NOP,NOP → mov [esp+06],dx)
```

- 仅用 `eax / ecx / dx`（返回后原代码均会重载 `eax/ecx/edx`，`dx` 即刻被存入 `v11`），无需 push/pop，栈平衡不受影响。`eax`(v19 指针) 全程不被篡改，`mov dword[eax],0` 与收尾 `mov dx,[eax]` 均基于它。
- `<MASK>` 处的 imm8 字节偏移 = cave_offset + 10（`CAVE_EXP_LOCK_MASK_OFFSET`），由 `apply_exp_lock()` 依配置计算后写入。
- 槽位 ≥ 6 时（不应发生）掩码高位为 0，视作未锁定，安全。

### 3.3 Cave 区容量

`patcher_worker.py` 通过 `VirtualAllocEx(…, 1024, …)` 申请，但系统按页粒度提交整页（4 KB）。现有最高 cave 为 `team_member_leave_routing`（offset 1152，长 158 字节，占用至 1310）；本 cave 取 **`cave_offset = 1344`（0x540）**，28 字节占用至 1372，与所有既有 cave 零重叠，且远在 4 KB 页内。

## 四、配置文件

`configs/exp_lock.json`：

```json
{
  "lock_slots": [false, false, false, false, false, false]
}
```

| 字段 | 值域 | 说明 |
|------|------|------|
| `lock_slots` | 长度 6 的 bool 数组 | 索引 = 战斗队伍槽位 0–5；`true` = 锁定该槽经验 |

- 掩码计算：`mask = Σ (1 << i)  for i where lock_slots[i] == true`。
- `mask == 0`（无任何锁定）→ 补丁跳过，游戏原版行为不受影响。

`_registry.json` 追加：

```json
"exp_lock": {
  "description": "战斗经验锁定（压级）：锁定队伍槽位0-5指定槽的战斗经验增长",
  "category": "launcher",
  "schema": "key_value",
  "primary_editor": "configs_editor",
  "consumers": ["tks_launcher_gui"],
  "merge_strategy": "key_override",
  "user_editable": true
}
```

> **语义提示**：锁定按「战斗队形槽位 0–5」生效（引擎遍历顺序），随队形位置而非角色。压级培养的直觉用法即：把已练满的角色放入锁定槽。

## 六、启动器补丁

### 6.1 `tks_patches.json` 新增条目

```json
{
  "_group": "── 战斗经验锁定（压级）──",
  "type": "patch_exp_lock",
  "id": "exp_lock",
  "name": "战斗经验锁定（压级）",
  "desc": "锁定队伍槽位0-5指定槽的战斗经验：被锁定槽位战斗胜利不获经验、不升级 (sub_43B7FC @0x43BAF3 cave hook; 需配置 configs/exp_lock.json)",
  "optional": true,
  "default_checked": false,
  "json_file": "configs/exp_lock.json",
  "hook_pattern": "8B 44 24 1C 66 8B 10 66 89 54 24 06",
  "hook_size": 7,
  "hook_expect_count": 1,
  "fallback_rva": "0x43BAF3",
  "cave_offset": 1344
}
```

- `hook_pattern` 12 字节含两处 `66` 前缀，唯一性强，`expect_count=1` 强制校验；扫描失败时回退 `fallback_rva`。
- `cave_offset = 1344`：在既有 cave（最高 team_member_leave_routing 1152+158=1310）之后，零重叠。

### 6.2 `core/patch_engine.py`

1. 新增 cave 模板常量 `CAVE_EXP_LOCK`（§3.2 字节，`<MASK>` 处占位）。
2. `build_cave_template()` 增加 `"exp_lock"` 分支返回模板。
3. 新增 `apply_exp_lock(defn, code_buf, code_start_addr, base_addr, h_proc, cave_addr, variables, log_func, config_override)`：
   - 读取 `exp_lock.json`（支持 MOD 覆盖，回退 `configs/`）；
   - 计算 `mask`；`mask == 0` → 记录并跳过；
   - 复制 `CAVE_EXP_LOCK`，把 `<MASK>` imm8 写为 `mask`；
   - 写 cave 到 `cave_addr + cave_offset`；
   - 模式扫描 `hook_pattern`（`expect_count=1`，失败回退 `fallback_rva`）→ 在命中处写 `E8 rel32 + 90 90`；同步回写 `code_buf`。
4. 在配置补丁分发处（`apply_config_patches`）为 `type == "patch_exp_lock"` 路由到 `apply_exp_lock`。

## 八、验证方法

1. **编辑器可用性**：启动 `configs_editor.py`，确认「压级(经验锁定)」标签页正常加载、勾选后保存 `exp_lock.json` 内容正确。
2. **掩码计算**：勾选槽位 0、2、4 → `mask = 1|4|16 = 0x15`；面板保存后 JSON 为 `[true,false,true,false,true,false]`。
3. **无锁定回归**：`lock_slots` 全 false → 补丁跳过，战斗经验与原版一致。
4. **锁定生效**：锁定某槽 → 该槽队员战斗胜利后 `current_exp`/等级不变，其余槽位正常获得经验并可升级。
5. **共存性**：与 `exp_cap_unsigned_fix`、`battle_writeback` 同时启用无冲突（地址不重叠）。
6. **配置异常**：JSON 缺失/格式错误 → 补丁跳过，不影响原版逻辑与其他补丁。

## 九、风险与边界

1. **仅覆盖战斗胜利经验**（`sub_43B7FC`）。剧情/道具直接改经验（如 `sub_434510` 环境探索）不在范围内——但那不属于「战斗经验」，符合本功能定义。
2. **不锁 JP（技能点）**：JP 走 `dword_9D6F38` / `v18[26]` 独立路径，本补丁不触碰，被锁槽位仍正常获得技能点（符合「压级 = 抑制等级」的语义）。
3. **锁定单位是槽位而非角色**：调整队形会改变锁定对象，属预期行为，已在配置与面板文案中说明。
4. **升级方向单调**：`v11=0` 只会阻止升级，不会造成经验倒扣或异常降级。
