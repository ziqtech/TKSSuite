# TKS 技能数量扩展可行性分析

## 一、当前数据结构总览

> **逆向核对**：本节数据结构均已逐条验证——TKSkill 94×350=32900（`4173F8:20`，word_7861CA）、skill_learn 字节级从 0x757FB8 起（= 0x757F08+0xB0，word index 88/byte offset 176）、344 字节（索引 0~343）、WarPC 1054×143=150722（`4173F8:18`/`412688:22`）、存档 Frame1 TKMat 2304000 + Frame2 (3432+5768+150722)=159922（`410ED4:22,26-30`/`41103C:24-37`）。扩展方案均基于这些已核实的结构。

### 1.1 TKSkill.dat — 技能数据文件

| 属性 | 值 | 来源 |
|------|------|------|
| 记录大小 | 94 字节 (47 × int16) | SKILL_REC = 94 |
| 技能总数 | 350 个 | SKILL_CNT = 350 |
| 原始文件大小 | 32,900 字节 | 350 × 94 = 32,900 |
| 存储方式 | LZSS 压缩 | sub_45343C 解压加载 |
| 内存基址 | 0x7861CA (word_7861CA) | sub_4173F8 加载目标 |

**技能索引范围**: 0 ~ 349，其中：
- 0 ~ 343: 可学习技能（与 WarPC 技能学习数组对应；JP/物品学习路径覆盖范围）
- 344 ~ 349: 系统保留技能（不参与学习系统，被 skill_scan_bound 补丁排除在 JP 扫描外；但物品 use_learn 等直接索引路径不受此补丁保护）

**TKSkill 字段布局**（47 words / 94 bytes，已通过反编译验证的关键字段）：
- word 2 (byte 4) = 技能类型：1=被动属性加成、2=反应技能、3=主动技能
- word 8 (byte 16) = 起始子技能索引（被动组技能用，参考 word_7861D2）
- word 21-23 = 被动属性加成字段（HP/属性百分比等）
- word 25-30 = 属性加成系数（sub_422BBC 用于百分比加成计算）
- word 34-35 = 反应/被动位掩码（每 bit 对应一种状态效果）
- word 44 (byte 88) = 子技能组关联（word_786224），-1=无子技能、0=单技能、>0=子技能组
- word 46 (byte 92) = 子技能组中数量

### 1.2 WarPC.dat — 角色数据文件

| 属性 | 值 | 来源 |
|------|------|------|
| 记录大小 | 1054 字节 (527 × int16) | WARPC_REC = 1054 |
| 原始角色数 | 143 个 | WARPC_ORIG_COUNT = 143 |
| 原始文件大小 | 150,722 字节 | 143 × 1054 |
| 内存基址 | 0x757F08 (word_757F08) | 运行时加载目标 |
| 存储方式 | LZSS 压缩 | sub_45343C 解压加载 |

**WarPC 记录内存布局**（1054 字节）：

```
偏移(字节)    字索引        用途
─────────────────────────────────────────────────────
0-137        [0]-[68]      身份/属性/基础字段
138-145      [69]-[72]     ★ 装备物品槽 (TKItem 索引 0-3)
146-163      [73]-[81]     装备权限/战斗状态字段（含被动装备判断位 word 79-81）
164-171      [82]-[85]     ★ 装备技能槽 (TKSkill 索引 0-3，对应 word_757FAC/AE/B0/B2)
172-175      [86]-[87]     ★ 被动技能槽 (TKSkill 索引 1-2)
176-519      字节 176 起    ★ 技能学习状态数组 (344 字节，每技能 1 字节)
520-1053     [260]-[526]   补丁专用字段（角色关联/事件 ID 等）
```

**关键说明**：
- **装备物品槽（word 69-72，字节 138-145）**：存储 TKItem 索引（非 TKSkill）。反编译证据：sub_417F84 `v8 = (__int16 *)(1054 * a3 + 7700370)` (7700370=0x757F92=字节138)，并通过 `sub_4067E8(word_77CBCE[32 * *v8])` 查找 TKItem 数据；sub_42234C 中 `v9 = &word_77CBCA[32 * *v5]` 也确认这些槽位指向 TKItem。
- **装备技能槽（word 82-85，字节 164-171）**：存储 TKSkill 索引。反编译证据：sub_41F318/422EF4 中 `word_757FAC[527 * a2]`、`word_757FAE[527 * a2]`、`word_757FB0[527 * a2]`、`word_757FB2[527 * a2]`。
- **被动技能槽（word 86-87，字节 172-175）**：存储 TKSkill 索引。反编译证据：sub_42234C 中 `sub_422BBC(a1, a2, a2[86])` 与 `sub_422BBC(a1, a2, a2[87])`。
- **装备技能槽 0 的初始化陷阱**：sub_42234C 在每次角色初始化时，通过 `v6[16]=0` 循环（v6=a2+51，循环 16 次）会清零 word 51-66 与 word 67-82（即 equip_skill0）。该函数随后只对 equip_skill2/3 与 passive1/2 调用 `sub_422BBC` 重新应用效果，不重新应用 equip_skill0/1。这意味着 equip_skill0/1 的实际数值依赖游戏逻辑后续设置（如 sub_41F318），而 equip_skill2/3 与被动技能每次初始化都会按 TKSkill 数据重算。

**技能学习状态数组** 关键特征：
- 字节级访问（非 int16），每个技能占 1 字节
- 起始地址：`byte_757FB8`（= 0x757F08 + 0xB0 = 字节 176）
- 数组大小 = 344 字节 → 对应技能索引 0 ~ 343
- 状态值: 0=不会, 1-9=等待学, 10=可以学, 20=已学会, 30=子技能自动学会, 40=已使用（消耗）

> **符号说明**：反编译代码中 `byte_757FB8`/`byte_757FAC`/`byte_757FAE` 是 IDA 对绝对地址的字节视图自动命名，原始符号为 `word_757FAC`/`word_757FAE`（word_757F08 + 字偏移 82/83）。`pointers.txt` 中只列出 word 符号，byte 形式由编译器根据访问模式推导。

**现有补丁**: `skill_scan_bound` — 修改可装备技能列表扫描上限

这意味着游戏在 **3 个位置** 使用 `350` 作为技能扫描上限。补丁将其改为 `344` 以匹配学习数组边界。

### 2.5 技能数据访问模式

**逆向证据** (decompile/422BBC.c):
```c

```

技能数据以 `47 × int16 = 94 字节` 步长索引，基址 `word_7861CA`。如果扩展技能数量，需确保内存缓冲区足够容纳所有记录。

**TKSkill 字段读取反编译证据**（sub_422BBC, 关键字段）：
```c
v6 = &word_7861CA[47 * a3];
if ( v6[2] == 1 )          // type 1: 被动属性加成
{
    a2[12] += v6[25] * a2[11] / 100;   // v6[25] 百分比加成
    ...
    if ( ((unsigned __int16)v6[34] & (1 << v5)) != 0 )  // v6[34-35] 状态位掩码

    ...
}
else if ( v6[2] == 2 )     // type 2: 反应技能
{
    if ( a3 < 303 || a3 > 305 )   // 反应类型判定（按索引区间分支）
    ...                            // a3 范围 303-330 分别对应 1-10 类反应
    a2[42] = v6[44];              // 子技能组起始索引
}
else if ( v6[2] == 3 )     // type 3: 主动技能（属性/特殊效果）

    a2[24] += v6[30];
    ...
}
```

**TKSkill 关键字段汇总**（按反编译验证）：
- word 2 (byte 4) — 技能类型 (1=被动、2=反应、3=主动)
- word 8 (byte 16) — 起始子技能索引（被动组用，word_7861D2）
- word 21 (byte 42) — HP 加成百分比（sub_422BBC）
- word 23 (byte 46) — MP 加成百分比
- word 25-30 — 各属性百分比/数值加成
- word 31 (byte 62) — 命中率加成（a2[32]）

- word 34-35 (byte 68-71) — 反应/被动位掩码
- word 44 (byte 88) — 关联子技能组（word_786224），-1=无、0=单技能、>0=组起始
- word 46 (byte 92) — 子技能总数（word_786226）

## 三、扩展方案分析

### 方案 A: 扩展 WarPC 记录大小（扩展技能学习数组）

**原理**: 在每条 WarPC 记录的技能学习数组区域增加字节，扩大可学习技能数。

**所需修改**：

| 修改项 | 复杂度 | 说明 |
|--------|--------|------|
| 记录步长 1054→N | ★★★★★ | 代码中所有 `527 *`(int16步长) 和 `1054 *`(字节步长) 引用 |
| 字段偏移重定位 | ★★★★ | 技能数组后的所有字段偏移 (520+) 需后移 |
| 文件大小常量 | ★★ | 已有补丁支持 |
| 存档格式兼容 | ★★★★ | 旧存档迁移、新旧存档混用问题 |
| 技能扫描上限 | ★ | 修改 skill_scan_bound 的目标值 |

**致命问题**：
1. **步长常量分布极广**: `527 *` 和 `1054 *` 出现在战斗系统、存档系统、装备系统、召唤系统等几十个函数中，无法通过简单的 value_scan 定位（因为 527 作为乘法因子可能编译为 `imul` 指令的立即数，与其他指令混合）
2. **乘法编译多态性**: 编译器可能将 `× 527` 优化为 `lea/shift/add` 组合，无统一的二进制模式可扫描
3. **尾部字段偏移硬编码**: 补丁字段 `[260]-[263]` 等使用固定偏移 (如 `0x208`、`0x20A`)，cave 模板中有硬编码的字节偏移
4. **旧存档不兼容**: 现有存档使用 1054 字节记录，扩展后需要迁移工具

**结论**: ❌ **不可行** — 需要修补的位置过多且无法自动化定位。

---

### 方案 B: 保持记录大小不变，仅扩展 TKSkill.dat（推荐）

**原理**: 保持 WarPC 记录 1054 字节不变，技能学习数组保持 344 字节。扩展 TKSkill.dat 技能总数，但新增技能**不参与学习系统**（仅通过编辑器直接装备/通过补丁授予）。

**适用场景**：
- 新增"装备即用"型技能（被动技能、反应技能）
- 为新增角色设计独有技能
- 通过 WarPC 编辑器的 `equip_skill` / `passive` 字段直接装备

**所需修改**：

| 修改项 | 复杂度 | 说明 |
|--------|--------|------|
| SKILL_CNT 扩展 | ★ | 技能编辑器修改常量 |
| TKSkill.dat 大小补丁 | ★ | 已有 tkskill_size 补丁自动处理 |
| 技能内存缓冲区 | ★★ | 需扩展 word_7861CA 缓冲区 |
| skill_scan_bound | ★ | 保持 344 不变 |
| 存档兼容 | ✓ | 完全兼容，WarPC 记录未变 |

**限制**：
- 新增技能索引 > 343 的技能**无法通过 JP 学习**
- 新增技能只能通过 WarPC 编辑器的 `equip_skill[0-3]` / `passive[1-2]` 字段装备
- 每个角色仍然最多装备 4+2=6 个技能（4 主动 + 2 被动）

**缓冲区问题**: 游戏加载 TKSkill.dat 到固定地址 `word_7861CA`，如果文件大于 32900 字节，会溢出到后续内存区域。**需要与 WarPC 类似的运行时缓冲区重定位方案**。

**结论**: ✅ **可行，推荐方案** — 但新增技能无法通过 JP 学习。

### 方案 C: 外挂技能学习表 + Cave Hook（高级方案）

**原理**: 保持 WarPC 记录大小 1054 不变，在游戏内存中分配独立的"扩展技能学习表"，通过 cave hook 拦截所有技能学习状态的读写操作，当索引 ≥ 344 时转向外挂表。

**架构设计**：

```
┌─────────────────────────┐    ┌──────────────────────────┐
│  WarPC 原始记录 (1054B)  │    │  扩展技能学习表           │
│  skill_learn[0..343]    │    │  ext_learn[角色数][新技能数]│
│  (保持不变)              │    │  (VirtualAllocEx 分配)    │
└─────────────────────────┘    └──────────────────────────┘
           │                              │
     ┌─────┴─────────────────────────────┐
     │  Cave Hook: skill_learn_accessor   │
     │  if (skill_idx < 344)              │
     │    → 原始 WarPC 数组               │
     │  else                              │
     │    → 扩展表[char_idx][skill_idx-344]│
     └───────────────────────────────────┘
```

**需要 Hook 的位置分析**:

| 代码位置 | 功能 | 访问模式 |
|----------|------|----------|
| sub_422EF4 (0x422EF4) | 装备技能→学习状态更新 | `byte[1054*a2 + v10]` |
| sub_447BA8 (0x447BA8) | 技能学习界面 | `i[1054*char + 176]` |
| sub_42234C (0x42234C) | 装备初始化/学习触发 | `*((_BYTE*)a2 + v9[22] + 176)` |
| sub_43BF20 (0x43BF20) | 战后经验/JP分配 | 遍历技能学习数组 |
| 其他未确认位置 | 存档读写等 | 多种模式 |

**复杂度评估**：

| 修改项 | 复杂度 | 说明 |
|--------|--------|------|
| 定位所有访问点 | ★★★★ | 需逆向确认所有 skill_learn 访问位置 |
| Cave Hook 编写 | ★★★ | 多个 hook 点，需处理不同寄存器上下文 |
| 外挂表存档集成 | ★★★★ | 需额外存档扩展机制 |
| 启动器集成 | ★★ | 已有 cave hook 框架 |
| 向后兼容 | ★★★ | 需处理无扩展存档的降级 |

**致命问题**：
1. **访问模式不统一**: 游戏代码使用 `byte_757FB8[1054*i + skill_idx]` 等多种写法，hook 点多且分散
2. **存档不携带扩展数据**: 旧存档无法保存 ≥344 的学习状态
3. **JP 学习逻辑硬编码**: 技能树遍历 (`v6 = 4 * a1 + 181` 等) 与 344 紧密耦合

**结论**: ⚠️ **理论可行但工程量极大** — 适合作为远期目标。

## 四、推荐实施路径

### 第一阶段: 方案 B — 扩展 TKSkill.dat（可立即实施）

#### 4.1 技能编辑器修改

```python
# skill_editor_v2.py
SKILL_REC = 94
SKILL_CNT = 400  # 从 350 扩展到 400（示例）
```

- 编辑器支持 400 个技能定义
- 新增技能使用索引 350~399
- 保存时生成 400 × 94 = 37,600 字节的 TKSkill.dat

#### 4.2 WarPC 编辑器修改

**无需修改 WarPC 记录结构**。编辑器已有的字段可直接使用：

```python
# warpc_editor_v2.py 中已有字段
EQUIP_SKILL_FIELDS = [
    ("equip_skill0", 164, "装备技能0", ...),  # 值可 ≥ 344
    ("equip_skill1", 166, "装备技能1", ...),
    ("equip_skill2", 168, "装备技能2", ...),
    ("equip_skill3", 170, "装备技能3", ...),
    ("passive1",     172, "被动技能1", ...),
    ("passive2",     174, "被动技能2", ...),
]
```

- `equip_skill[0-3]`: 可填入任何技能索引（包括 ≥ 344 的新技能）
- `passive[1-2]`: 可填入被动技能索引
- 编辑器需更新技能选择列表的范围验证

**注意**: 新增技能索引 ≥ 344 时，`skill_learn[]` 数组中对应位置不存在，游戏的装备校验函数 (sub_42234C) 不会检查学习状态，因为装备技能的加载是直接读取 `equip_skill` 字段值。

#### 4.3 启动器兼容性

已有补丁机制完全覆盖：

| 补丁 | 作用 | 状态 |
|------|------|------|
| `tkskill_size` | TKSkill.dat 大小常量修补 | ✅ 已支持 |

## 五、关键风险与缓解

### 5.1 TKSkill 内存缓冲区溢出

**风险**: `word_7861CA` 缓冲区大小固定为 32,900 字节，扩展后的数据写入会覆盖后续内存。

**缓解**: 
- 在启动器中实现 `expand_tkskill_buffer()`，类似已有的 `expand_warpc_buffer()`
- value_scan 扫描 `0x7861CA` 地址引用并重定位
- 此缓冲区位于 .bss 段（0x7861CA 在 TKS.exe 地址空间 0x700000-0x800000 范围），重定位方案与 WarPC 一致

### 5.2 技能索引越界

**风险**: 游戏代码使用 `47 * skill_idx` 计算技能记录偏移，如果 skill_idx 超出缓冲区会崩溃。

**缓解**:
- 确保新缓冲区大小 ≥ 新技能数 × 94
- `skill_scan_bound` 补丁保持 344，防止装备界面越界
- `equip_skill` 字段的值由 WarPC 编辑器确保有效

### 5.3 召唤系统技能索引

**风险**: 召唤表补丁引用特定技能索引（222, 224~231, 251），新增技能不会干扰。

**缓解**: 无需处理，召唤系统的索引引用是角色索引而非技能索引。

### 5.4 启动器 warpc_expander 兼容

**风险**: 现有 WarPC 扩展机制假设记录大小为 1054。

**缓解**: 方案 B 中 WarPC 记录大小未变，完全兼容：
- `prepare_warpc_for_game()`: 按 WARPC_REC_SIZE=1054 截断 ✅
- `expand_warpc_buffer()`: 所有重定位基于 1054 步长 ✅
- `inject_warpc_data()`: 读写 WORD[260]/[261] 偏移正确 ✅

### 9.3 关键发现: 物品不能从零教会技能

**核心逻辑约束**:

```
条件1: byte_757FB8[1054 * char_idx + skill_idx] >= 1  (必须已在学习状态)
条件2: byte_757FB8[1054 * char_idx + skill_idx] < 20  (必须尚未学会)
```

| 当前状态 | 物品效果 | 说明 |
|----------|----------|------|
| 0 (不会) | ❌ 无效果 | **条件1失败** — state < 1 |
| 1-9 (等待学) | ✅ → 10 | 加速为"可以学" |
| 10 (可以学) | ✅ → 10 | 无实际变化 |
| 20+ (已学会) | ❌ 无效果 | 条件2失败 — state >= 20 |

**结论**: 物品使用学习技能的**硬性前提**是角色在 WarPC.dat 中已对该技能有 1-9 的预设状态。如果 WarPC.dat 中该角色该技能的 skill_learn 值为 0，则物品使用**完全无效**。

**注意**：本文档作者在旧版本中曾推测 byte 520+ 字段含义为 `awk_sprite_id` / `portrait_menu_id` / `history_text_id` / `entity_link` / `growth_early` / `jp_reward` 等。**经核查反编译代码，这些字段名在 `逆向工作区` 目录中没有任何对应符号**，为文档作者推测添加，不应继续作为可信依据使用。

#### 后果分析

1. **读取时**：代码检查该字节是否在 1-19 范围。如果对应字段的字节值恰好满足（如某个保留字段的低字节为 7），条件成立（即 `item_use_learn` 触发时会"误以为"该角色已对该技能处于学习中状态）。

2. **写入时**：代码将该字节强制设为 10。**这会直接破坏对应 WarPC 字段的字节数据**——具体被破坏的字段依赖存储布局，需根据 `4173F8.c` 中实际读取该偏移位置的逻辑确认，不能仅凭推测命名。

3. **skill_scan_bound 保护**：现有补丁将扫描上限改为 344，阻止了 JP 学习界面扫描到这些越界位置。但**物品使用路径（sub_41E40C / sub_422EF4）不受此补丁保护**——物品的 `use_learn` / `equip_learn` 字段直接使用技能索引，没有上限检查！所以越界索引的物品学习仍可能触发写入风险。

### 9.7 存档持久性分析

| 机制 | 存档行为 | 说明 |
|------|----------|------|
| skill_learn[0-343] 状态变化 | ✅ 完整保存 | 在 WarPC 记录字节 176-519，随存档持久化 |
| equip_skill[0-3] 装备技能 | ✅ 完整保存 | 在 WarPC 记录字节 164-170，随存档持久化 |
| passive[1-2] 被动技能 | ✅ 完整保存 | 在 WarPC 记录字节 172-174，随存档持久化 |
| skill_idx ≥ 344 的"学习状态" | ❌ 破坏性写入 | 实际写入的是其他字段的字节，数据损坏 |

**结论**: 通过 `equip_skill` / `passive` 字段配置的扩展技能**可以被存档正确保留**。但如果通过物品学习机制试图设置索引 ≥ 344 的技能状态，只会**破坏该字节偏移处的 WarPC 字段**。

### 9.8 综合结论

#### 问题1: 物品学习的技能能否出现在角色技能列表中？

**对于技能索引 0-343 (原始范围)**:
- ✅ 可以 — 但前提是 WarPC.dat 中该角色该技能的 skill_learn **已预设为 1-9**
- 物品使用将状态从 1-9 提升为 10（出现在 JP 学习界面）
- 玩家需额外花费 JP 将其学会（状态 10→20），才能在战斗中使用
- 如果 WarPC 中未预设（state=0），物品使用完全无效

**对于技能索引 ≥ 344 (扩展范围)**:
- ❌ 不可以 — 因为：
  1. `skill_scan_bound` 补丁阻止 JP 界面扫描到 ≥344 的索引
  2. 即使没有此补丁，访问的字节不是技能状态而是其他字段数据
  3. 写入操作会破坏角色 byte 520+ 处的字段

#### 问题2: 存档能否保留物品学习的技能？

**对于技能索引 0-343**: ✅ 能保留 — skill_learn 数组完整存入存档

**对于技能索引 ≥ 344**: ❌ 无法正确保留 — 写入的是错误的字段位置

#### 问题3: 扩展技能如何安全地让角色使用？

**唯一安全路径**: 通过 WarPC 编辑器直接设置 `equip_skill[0-3]` 或 `passive[1-2]`：

```
1. 在技能编辑器中创建新技能 (索引 350+)
2. 在 WarPC 编辑器中为角色设置:
   - equip_skill[2-3] = 新技能索引 → 主动技能效果生效
   - passive[1-2] = 新技能索引 → 被动技能效果生效
3. sub_422BBC 直接读取 TKSkill 数据表应用效果 (不检查 skill_learn)
4. equip_skill/passive 字段随 WarPC 记录保存到存档 ✅
```

**注意**: 通过 `equip_skill` 设置的技能，其**被动效果**（属性加成等）会正常生效，但在战斗中是否显示为可选技能取决于该技能是否为**指令技能组**（type=0）的一部分。单独的主动/被动技能通过此方式设置后，效果会静默生效，不需要在战斗菜单中选择。

| 4 | sub_41E248 | 技能树进度传播 | `*((char*)&word_757F08[527*a2+88] + *v4)` | R+W | ★★ |
| 5 | sub_422EF4 | 装备/卸装技能状态变更 | `byte_757FB8[1054*a2 + v10]` | R+W | ★★★ |
| 6 | sub_422EF4 | 子技能遍历 | `(char*)&word_757F08[527*a2+88] + idx` | R | ★★ |
| 7 | sub_4189BC | JP学习界面技能列表 | `(char*)&word_757F08[527*a2+88] + v12` | R | ★★★ |
| 8 | sub_447BA8 | 战斗技能菜单(子技能) | `i[1054*word_9D6F58 + 176]` | R | ★★ |
| 9 | sub_438F28 | 战斗技能菜单(详细) | `i[1054*word_9D6F58 + 176]` | R | ★★ |
| 10 | sub_442D44 | 战斗中状态触发检查 | `algn_9D70D0[1054*a1 + 16 + a2]` | R | ★ |

**访问模式分类**:

```
模式A — 全局数组 + 绝对偏移:
  byte_757FB8[1054 * char_idx + skill_idx]
  = (WarPC基址 + 176) + 1054 * char_idx + skill_idx
  出现: sub_41E40C, sub_422EF4, sub_41E248

模式B — 记录指针 + 相对偏移:
  *((_BYTE *)a2 + skill_idx + 176)
  其中 a2 = &word_757F08[527 * char_idx]
  出现: sub_42234C

模式C — 迭代器递增:
  v8 = (char *)&word_757F08[527*a2 + 88] + start_idx;
  while (v12 < 350) { check *v8; ++v8; ++v12; }
  出现: sub_4189BC

模式D — 战斗副本:
  i = (char *)word_9D707A + skill_idx;
  check i[1054 * char_idx + 176]
  出现: sub_447BA8, sub_438F28
```

### 11.3 外挂表内存布局设计

```
┌─────────────────────────────────────────────┐
│  ExtSkillTable (VirtualAllocEx 分配)         │
│                                             │
│  结构: ext_learn[MAX_CHARS][EXT_SKILLS]     │
│  其中: MAX_CHARS = 200 (支持扩展角色)       │
│        EXT_SKILLS = N (扩展技能数量)        │
│                                             │
│  每个字节 = 1个技能的学习状态 (同原始语义)   │
│  总大小 = 200 × N 字节                      │
│                                             │
│  映射关系:                                   │
│    原始: skill_learn[char][idx] (idx 0-343)  │
│           → WarPC记录内 byte[176 + idx]      │
│    扩展: skill_learn[char][idx] (idx ≥ 344)  │
│           → ExtTable[char][(idx - 344)]      │
│                                             │
│  示例: N=56 (技能350~405)                   │
│  总大小: 200 × 56 = 11,200 字节             │
└─────────────────────────────────────────────┘
```

### 11.4 Cave Hook 设计

#### 核心拦截逻辑 (通用子程序)

```x86
; skill_learn_accessor — 统一访问入口
; 输入: ECX = char_idx, EAX = skill_idx
; 输出: EDX = 指向目标字节的指针
; 保证: 不破坏 ECX, EAX
skill_learn_get_ptr:
    cmp eax, 344
    jb  .original                ; idx < 344 → 原始路径
    ; 扩展路径
    push ebx
    sub eax, 344                 ; offset = idx - 344
    mov ebx, EXT_SKILLS          ; 每角色扩展字节数 (imm32)
    imul ecx, ecx, ebx           ; char_offset = char_idx × ext_skills
    add eax, ecx                 ; total_offset = char_offset + (idx-344)
    lea edx, [EXT_TABLE + eax]   ; edx → &ext_table[char][idx-344]
    pop ebx
    ret
.original:
    ; 计算原始 WarPC 内地址
    imul ecx, ecx, 1054          ; char_byte_offset
    add ecx, eax                 ; + skill_idx
    lea edx, [WARPC_BASE + ecx + 176]  ; → &warpc[char].skill_learn[idx]
    ret
```

预计大小: ~50 字节

#### 各 Hook 点适配

| Hook 目标 | 原始指令 (字节) | Hook 大小 | Cave 逻辑 |
|-----------|----------------|-----------|------------|
| sub_41E40C:103 | `cmp byte[...], 1` (7B) | 7 | 调用 accessor, 比较 *edx |
| sub_42234C:78 | `cmp byte[...], 40` (7B) | 7 | 调用 accessor, 比较 *edx |
| sub_41E248:17 | `mov byte[...], 20` (7B) | 7 | 调用 accessor, 写 *edx=20 |
| sub_422EF4:87 | `cmp byte[...], 20` (7B) | 7 | 调用 accessor, 比较 *edx |
| sub_4189BC:61 | `while v12<350` (6B) | 6 | 修改上限 + 迭代重定向 |
| sub_447BA8:32 | `cmp byte[...], 20` (7B) | 7 | 调用 accessor (战斗副本) |

**注意**: 战斗系统使用独立的 WarPC 副本 (word_9D707A)，其初始化时从原始 WarPC 做 memcpy。外挂表需在战斗初始化时也同步到战斗副本对应位置。

### 11.5 存档持久化方案

#### 方案选择: 边车文件 (Sidecar File)

```
原始存档: save/sav.1, save/1.sav
扩展存档: save/sav.1.ext (新增文件)
```

**优势**:
- 不修改原始存档格式，完全向后兼容
- 无需 hook sub_410ED4/sub_41103C 内部逻辑
- 启动器在读档后从 .ext 文件恢复扩展数据

**格式设计**:
```
[ext_skill_save 文件格式]
偏移  大小   内容
0     4B     魔数 "TKSE" (0x45534B54)
4     2B     版本号 (1)
6     2B     角色数 (N)
8     2B     扩展技能数 (M)
10    2B     保留
12    N×M B  扩展技能学习状态数组
```

#### 启动器集成流程

```
游戏启动:
1. VirtualAllocEx 分配 ExtSkillTable
2. 检测 save/sav.*.ext 是否存在
3. 安装 cave hooks (拦截 skill_learn 访问)
4. 安装存档看门狗 (监控存档写入事件)

读档触发 (hook sub_41103C 返回后):
1. 从 sav.X.ext 读取扩展数据
2. memcpy 到 ExtSkillTable

存档触发 (hook sub_410ED4 返回后):
1. 从 ExtSkillTable 读取当前数据
2. 写入对应 sav.X.ext 文件
```

### 11.6 战斗系统同步

**问题**: 战斗开始时，游戏将 WarPC 数据复制到战斗区域 (word_9D707A)。扩展技能数据不在 WarPC 记录内，不会被自动复制。

**解决方案**: Hook 战斗初始化函数 (sub_444FD4 中的 `qmemcpy(..., 0x41Eu)`)，在战斗副本创建后将 ExtSkillTable 的对应数据注入战斗区域的"虚拟扩展区"。

或者，更简单地：**战斗中的 skill_learn 检查 hook 直接从 ExtSkillTable 读取**，不依赖战斗副本。因为战斗中 skill_learn 是只读的（不会在战斗中学习新技能），这种方案安全可靠。

### 11.8 难点与风险

| 难点 | 说明 | 缓解措施 |
|------|------|----------|
| Hook 点数量多 | 需要 6-8 个独立 hook 点 | 使用共享 accessor 子程序减少重复 |
| sub_4189BC 迭代器 | 该函数使用指针递增遍历, 不是索引访问 | 需修改扫描上限 + 在 >=344 时切换基址 |
| 战斗副本 word_9D707A | 战斗数据是独立副本 | 战斗中 hook 直接读 ExtTable |
| 寄存器冲突 | cave 中使用的寄存器可能与调用者冲突 | 每个 hook 需单独分析寄存器上下文 |
| 向后兼容 | 无扩展时不应影响原始行为 | idx < 344 完全走原始路径, ExtTable 未分配时跳过 |
| 存档一致性 | .ext 文件可能与主存档不同步 | 存档时间戳比对; .ext 丢失时优雅降级 |
| 多版本 EXE 兼容 | 不同版本 EXE hook 位置可能不同 | 使用模式扫描定位 (已有框架) |

### 11.9 sub_4189BC 特殊处理 (最复杂的 Hook)

sub_4189BC 是技能列表显示的核心函数，使用指针递增遍历技能：

```c
v8 = (char *)&word_757F08[527 * a2 + 88] + v12;  // 初始指针
while ( v13 < 9 && v12 < 350 )  // ← 扫描上限
{
    if ( (char)*v8 >= v10 && (char)*v8 < v9 && *v7 == v11 )  // 读取 *v8
    {
        // 添加到列表
    }
    ++v12; v7 += 47; ++v8;  // 指针递增
}
```

**Hook 策略**:
1. 将 `v12 < 350` 修改为 `v12 < NEW_LIMIT` (如 400)
2. 在 `*v8` 读取处: 当 v12 >= 344 时，从 ExtTable 读取替代值
3. 在指针递增处: 当 v12 >= 344 时，v8 不再递增原始数组指针

**实现复杂度**: ★★★★ — 这是整个方案中最难的部分，因为需要在循环内部拦截并维护两套指针。

**替代简化方案**: 不 hook sub_4189BC 内部循环，而是在其**调用前**将 ExtTable 中 state=10~19 的技能预填入 WarPC 记录的空闲技能槽（idx 0-343 中 state=0 的位置）。这样原始扫描逻辑无需修改。

### 11.12 与方案 B 的关系

外挂学习表方案 (方案C) **不是方案 B 的替代**，而是其**上层扩展**:

```
方案B (基础层, 先实施):
  TKSkill.dat 扩展 + TKSkill 缓冲区重定位
  → 让游戏能加载 >350 个技能定义

方案C (学习层, 后追加):
  ExtSkillTable + Cave Hooks
  → 让扩展技能能参与 JP 学习系统
  → 依赖方案B 提供的 TKSkill 缓冲区重定位
```

方案C 必须建立在方案B 已实施的基础之上（因为 sub_422BBC/sub_42234C 读取技能效果数据时需要 TKSkill 缓冲区包含扩展技能的记录）。
