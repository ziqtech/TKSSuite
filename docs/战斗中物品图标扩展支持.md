# 战斗中物品图标支持 Mu.JVG 扩展图标 (tkitem_expand.battle_icon)

> 结论：战斗内三处物品图标绘制按 **Mu2.JVG** 取帧（帧号 = 图标值，而 Mu2 只有 107 帧），
> 而 MOD 扩展图标只追加在 **Mu.JVG**（帧号 = 图标值 + 130）。因此扩展图标在菜单/商店正常、
> 战斗内空白。修复方式：在战斗初始化把当次刚载入的 Mu2 对象**原地重载为 Mu.JVG**，
> 把 JVG 帧表整体前移 130 帧（对象内帧号 = 图标值 = "菜单帧号 − 130"），并**成对交换两组
> 状态图标表项**，抵消 Mu 与 Mu2 之间状态 11/12 的次序差异 → 物品图标与菜单/商店同源，
> 状态图标与原版逐像素一致。

---

## 一、现象与定位

MOD 把扩展图标追加进 `Mu.JVG` 并把物品图标值设为扩展值后：

| 场景 | 结果 |
| --- | --- |
| 菜单 / 商店物品页 | 正常（Mu.JVG 帧 = 图标值 + 130） |
| 战斗道具菜单详情图标 | 空白 |
| 战场地面掉落/拾取物品图标 | 空白 |
| 战斗结算页物品图标 | 空白 |
| 上述三处使用原版图标值 0..75 | 正常 |

### 1.1 战斗内物品图标的三处绘制（对象 = `dword_755AF4`，帧 = 图标值原样）

| 函数 | 绘制调用点 | 取帧表达式 |
| --- | --- | --- |
| `sub_434188` | `0x4344AA` | `*(WORD*)(item + 8)`（掉落/拾取物记录，`a1` 即 `sub_42F8D4` 查到的记录） |
| `sub_439750` | `0x4399B6` | `word_9DF8AC[4*槽]`（由 `sub_436AD0` 从 `word_77CBD2` = item+8 抄录） |
| `sub_43B648` | `0x43B6D4` | `item[4]`（= 记录字节 +8，`sub_42F8D4` 查表得到的记录） |

对整段 `.text` 扫描 `0x00755AF4` 立即数并跟踪其后 40 字节内的绘制调用可确认：战斗模块
（`0x42F000-0x450000`）只有这些点位从该全局取帧 —— 战斗初始化 `sub_42FEE0`（载入）、
清理 `sub_436DC0`（释放）、上面三个**物品图标**点，以及 `sub_433690`×2 / `sub_437664`×2
四处**状态图标**绘制（帧 = `word_9D6F76 + statusID − 1`，硬编码 `a2 = 21..30` 与
`+(char)statusID − 1` 两种公式）。

### 1.2 `dword_755AF4` 在战斗中指向 Mu2.JVG

战斗初始化 `sub_42FEE0` 载入 `Mu2.jvg`（`decompile/42FEE0.c:151-153`，字符串 `0x4EB945`），
并立刻计算状态图标基准帧 `word_9D6F76 = sub_45408C(obj, 44) = 76`（0x43020F）。
`sub_45408C(obj, block)` = 该块首帧号（前序块帧数之和），所以 76 即「Mu2 第 44 块首帧」。

### 1.3 Mu2.JVG 的帧号语义（逐帧字节比对实测）

`Mu2.JVG`（57 块 / 107 帧）与 `Mu.JVG`（99 块 / 274 帧）比对结果：

| Mu2 帧 | Mu 帧 | 内容 |
| --- | --- | --- |
| 0..75 | 130..205 | **物品图标**（30×30），即图标值 0..75，逐帧字节完全相同 |
| 76..106 | 242..272 | **状态图标** 1..31（30×30），29 帧相同 + 状态 11/12 次序相反 |

即物品区严格满足 `Mu2[帧] == Mu[帧 + 130]`；状态区满足 `Mu2[76+i] == Mu[242+i]`（i≠10,11）。
两处例外（实测 `Mu2[86] == Mu[253]`、`Mu2[87] == Mu[252]`，且 `Mu[252] ≠ Mu[253]`）：

| 状态 | Mu2 帧（原版战斗） | Mu 帧（菜单/编辑器 `STATUS_ICON_BASE = 242`） |
| --- | --- | --- |
| 11 无视 | 86（树桩） | 252（草叶） |
| 12 伪装 | 87（草叶） | 253（树桩） |

原版 `TKItem.dat` 600 条的图标值实测恰为 **0..75**（最大值 75），所以原版战斗物品图标
全部可解析；MOD 的扩展图标（图标值 ≥ 144 → Mu 帧 ≥ 274）在战斗内帧号 = 图标值 ≥ 144 > 107，
被 `sub_4544EC` 的 `if (a5 < a2[6])` 挡下 → 空白。

> 注：Mu2 并非"只有状态图标"——它同时提供战斗用的物品图标（帧 0..75）与状态图标
> （帧 76..106）；菜单/商店则统一走 Mu.JVG 的 `图标值 + 130` 帧。

### 1.4 两条可选路线（补丁 or 纯数据）

战斗取帧 = 图标值、菜单取帧 = 图标值 + 130，两个消费者读**不同对象**，因此同一个图标
画面要在两个文件里各存一份位置不同的副本。由此有两种做法：

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| A. 只改 Mu.JVG + 本补丁 | 扩展图标只追加在 Mu.JVG 帧 `图标值 + 130`（现状），战斗由 cave 重载 Mu.JVG 解决 | 依赖启动器/烧录 exe 注入补丁 |
| B. 纯数据（补全 Mu2.JVG） | 把每个扩展图标**同时**补进 Mu2.JVG 帧 `图标值`（107 帧原版内容保持不动，跳过的帧号用极小占位帧填满），Mu.JVG 侧照旧 | 图标存两份、Mu2 体积增大、每次改图要同步两个文件；但**不用任何补丁**，可与任意启动器/原版 exe 共用 |

补丁对路线 B 自动让路：门控（见 2.0）只在「图标值 ≥ Mu2 总帧数」时才注入，Mu2 补全后
该条件不成立 → 不注入 cave，战斗直接读 Mu2 的自定义帧，状态图标也保持原版帧 76..106。

## 二、修复

`tkitem_expand` 由单一 `patch_data_expand` 改为组合补丁（bundle），`prepare.py` 展开为两个操作：

1. `tkitem_expand.table` — 物品表扩容（原有行为，自身按数据大小门控）。
2. `tkitem_expand.battle_icon` — 战斗图标取帧修正（按 2.0 的精确判据注入）。

### 2.0 注入判据（`prepare.py`）

战斗内越界判据就是 `sub_4544EC` 的 `a5 < a2[6]`，而 `a2[6]`（obj+0x18）是载入器从
JVG 头 +0x10 写入的总帧数（实测 `Mu2.JVG` 头 +0x10 = 107、逐块帧数之和也是 107；
Mu.JVG = 274、MOD Mu.JVG = 764，三份文件均吻合）。于是门控直接算：

```
需要 cave  ⟺  物品表里存在「图标值 ≥ Mu2.JVG 总帧数」的条目
           且 Mu.JVG 存在 (cave 的素材来源)
```

* 只在 Mu.JVG 追加扩展图标（图标值 ≥ 144）→ 原版 Mu2(107) 必然越界 → 注入；
* 已把图标补进 Mu2.JVG（帧号 = 图标值，路线 B）→ 取值合法 → **不注入**，纯数据方案不被干扰；
* `Mu2.JVG` 读不到时按原版 107 帧判定；`Mu.JVG` 缺失 → 不注入（无素材可载）；
* 图标值按 int16 有符号读，负值（空槽 -1）不算越界；数据损坏 → 保守跳过，不阻断扩容。

### 2.1 cave 语义

hook：战斗初始化 `sub_42FEE0` 内 `0x430218` 的 6 字节 `mov edx,[0x755AF8]`
（pattern 起点 `0x43020F`，hook_offset 9；该 18 字节 pattern 全 `.text` 唯一）；
落在 `word_9D6F76` 赋值之后，因此 cave 内改写状态基准不会被随后的初始化覆盖；
被替换指令是 `word_9D6F78 = sub_45408C(wm.jvg, 11)` 的取对象指令，cave 结尾原样重放。

cave（141 字节，逐字节清单见 `tks_launcher_gui/patches/tkitem_expand/icon_cave.py`）：

```
pushad ; cld
eax = [0x755AF4] ; 为空则跳过
sub_453BD0(eax, "Mu.jvg")        ; 对象已存在, 内部 sub_4538B4 先释放 Mu2 数据/关文件
若返回 0 (文件缺失/非 JVG) → 跳过 (对象内容保持 Mu2, 行为等同原版, 一字节都不改)
sub_45410C(obj, -1, 0)           ; 全量载入各块 (sub_4544EC 不按需载块)
[obj+8]  += 130*2                ; 帧→块表指针前移 130 帧
[obj+0xC]+= 130*2                ; 帧→子帧表指针前移 130 帧
[obj+0x18]-= 130                 ; 总帧数 -130 (必须 imm32: 83 /5 的 imm8 0x82 会符号扩展成 +126)
交换帧→块表 / 帧→子帧表的下标 252/253 两项 (对象内帧 122/123 = 状态 11/12)
word_9D6F76 = 112                ; 状态图标基准 = Mu 帧 242 - 130
popad ; 重放 mov edx,[0x755AF8] ; ret
```

之后帧号 v 映射 Mu.JVG 帧 v + 130：

| 图标值 | 战斗内绘制 | 菜单/商店绘制 |
| --- | --- | --- |
| 0..75 | Mu 130..205（原版图标，与 Mu2 帧 0..75 逐字节相同） | 同一帧 |
| 76..143 | Mu 206..273（原版为立绘等非图标帧） | 同一帧 |
| ≥144 | Mu 274+（MOD 追加的扩展图标） | 同一帧 |

**状态次序还原**：`word_9D6F76 = 112` → 帧 112..142 = Mu 帧 242..272；交换表项 252/253 后，
对象内帧 122/123（状态 11/12）分别取到 Mu 帧 253/252，即 Mu2 帧 86/87 的原版画面 →
31 个状态图标与 `Mu2.JVG` 逐像素一致，本补丁对状态图标零影响。
（不交换时状态 11/12 会与菜单一致但与原版战斗相反，属于补丁引入的可见变化，故必须交换。）

### 2.2 为什么不改绘制点 / 不保留 Mu2 对象

* 替换对象后三处物品绘制与四处状态绘制**同时**正确，只需 1 个 cave；若改为「另建对象 +
  三处改址」，需要在三处立即数位点写入运行时地址，还要另分配并维护第二个 JVG 对象。
* 只把帧号改成 `图标值 + 130`（曾试过的做法）会打在 Mu2 对象上，帧号 ≥130 全部越界 →
  连原版图标也会消失，因此必须连对象一起换。
* 保留 Mu2 只做物品重定位不可行：Mu2 只有 0..106 帧，扩展开关只能靠换对象获得。

### 2.3 对象所有权

对象本身由战斗初始化 `operator new(0x28)` 分配、战斗结束 `sub_436DC0` 以
`sub_45388C(obj, 3)` 释放；cave 只重载其内容，且所有内部缓冲（记录表、帧表、各块数据、
调色板、文件句柄）都由游戏自己的加载器重建 → 释放路径与原生一致，无新增内存、无泄漏、
无悬垂指针。每次战斗重新载入 `Mu.JVG`（进战斗一次性 I/O），战斗结束由游戏释放。

    状态基准 112、两张帧表各一次 `add ecx,244` + `rol edx,16` 的表项交换；
  * 真实 `TKS.exe` 中 hook pattern 全 `.text` 唯一、落在 `0x430218`、被替换的 6 字节
    正好是 cave 结尾重放的指令；
  * `validate_runtime_plan` 在原版 exe 代码缓冲上通过（运行时预检）；
  * 计划门控：图标值 < Mu2 总帧数 → 只注入扩容；≥ 总帧数且 `Mu.JVG` 存在 → 注入图标操作；
    `Mu2.JVG` 缺失按 107 判定；`Mu2.JVG` 已补全（帧数 > 图标值）→ 不注入；缺 `Mu.JVG`
    → 不注入；补丁 `disabled` → 两条操作都不产生；数据损坏 → 保守跳过；
  * **unicorn 执行级**：桩函数替换 `sub_453BD0`/`sub_45410C`，验证三条路径的寄存器恢复、
    栈平衡、参数顺序（cdecl `[esp+4]` 为第一参）、帧表 +260、总帧数 −130、状态基准 112、
    表项交换**只**发生在下标 252/253（其余 762 项逐项比对），失败/未载入路径零改动；
  * 运行时注入：E8 rel32 指向 cave、cave 内容正确、`hook_size` 之外字节零改动；
  * 离线烧录（生成启动器）：`.test` 节含 cave、hook 点 E8 指向该节；
  * **真实 JVG 数据**（原版目录 Mu/Mu2）：物品区 `Mu2[0..75] == Mu[130..205]` 逐帧比对；
    状态区差异恰为 `[11, 12]` 且 `Mu2[86]==Mu[253]`、`Mu2[87]==Mu[252]`；
    重定位视角下逐帧核对物品帧与状态帧的取图来源；
  * **MOD 目录 Mu.JVG**：追加区 30×30 图标的图标值全部 ≥107（原版 Mu2 帧数，即修复前
    必然空白）且 < `总帧数 − 130`（重定位后可解析）。
* 完整补丁选择端到端（用户 `launcher_config.json` 勾选 + `游戏目录（改版）`）：
  * 数据图标值 ≤75 → 计划只含 `tkitem_expand.table`；把一条图标改为 300 → 计划自动加入
    `tkitem_expand.battle_icon`，`validate_runtime_plan` 通过；
  * 模拟所有非 cave 补丁的字节写入后，hook pattern 仍全 `.text` 唯一、hook 点
    仍为 `mov edx,[0x755AF8]` → 不会与其它补丁互相踩踏。

## 四、已知局限

1. 状态图标次序按**原版 Mu2** 固定：状态 11 读 Mu 帧 253、状态 12 读 Mu 帧 252（交换后）。
   若 MOD 想用 Mu 帧 242..272 重新绘制状态图标，需按此对应关系作画；只替换画面内容
   （不关心 11/12 归属）则无需理会。
2. 对象总帧数由 107 变为 `Mu 总帧数 − 130`，因此越界 statusID（≥32）不再被帧数上限
   挡下而会画出越界帧。正常数据 statusID 为 1..31，行为不变；`war_status_icons`
   的 `maxst = 总帧数 − 基准 + 1` 判定会同步放宽（该补丁对正常数据零影响）。
3. 扩展图标帧的尺寸应与原版 30×30 一致（绘制按帧原尺寸直出）。
4. `Mu.JVG` 缺失/损坏时 `sub_453BD0` 返回 0，cave 直接放弃，战斗行为等同原版
   （原版战斗本就依赖 `Mu2.JVG`）。
5. 注入门控基于**物品表数据 + 本目录 Mu2.JVG 头**（见 2.0）：图标值都小于 Mu2 帧数时
   不注入（日志里不会出现 `[tkitem_expand.battle_icon]`）。因此改动物品图标（或补全
   Mu2.JVG）后需要重新启动/重新生成一次，让计划重新判定；启动日志中出现
   `[tkitem_expand.battle_icon]: ... 补丁已应用` 即表示本次战斗把 Mu2 对象重载成了
   Mu.JVG 取帧。
6. 路线 B（补全 Mu2.JVG）时 Mu2 必须保持「原版帧 0..106 不变 + 扩展图标放在帧
   `图标值`」。战斗只按帧号取值，所以占位帧（跳过的帧号）内容任意；但若某条目用了
   帧号未补全的图标值，仍会回到 1.1 的空白现象（此时补丁会因该值越界而自动接管）。
