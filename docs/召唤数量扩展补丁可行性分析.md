## 1. 背景与目标

原版游戏战斗中存在召唤系统，但**玩家通过技能最多只能同时召唤 2 个角色**（槽位变量硬编码为 2 个）。本文档分析：

- 召唤数量限制为 2 的底层实现原理
- 通过 tks_launcher_gui 的 `.tkspatch` 补丁形式扩展召唤数量的可行性
- 扩展的上限约束与具体补丁注入点

---

## 2. 召唤系统逆向分析

游戏内实际存在**两套共享同一角色数组的召唤系统**：

### 2.1 玩家技能召唤（上限 2，本次扩展目标）

由技能 222 / 224-231 / 251 触发（召唤术类技能），完整调用链：

```
sub_43CA64 (主战斗循环)
  └─ sub_447DAC (玩家输入/技能处理)
       └─ sub_4458B0 (技能效果执行)
            └─ sub_444BB0 ★ 召唤技能处理（满槽检查）
                 └─ sub_431094 ★ 创建召唤物单位（槽位分配）
```

#### 满槽检查 — `sub_444BB0`（0x444BB0）

文件：`decompile/444BB0.c` 第 25-30 行：

```c
if ( byte_9DF88E[0] >= 0 && byte_9DF88F >= 0 )   // 两个召唤槽都已占用
{
    sub_451780(1);
    sub_451C38(0);
    return sub_433A38(a1, (int)&unk_4EBBDC, 18); // 播放"召唤已满"消息
}
```

**这就是"只能召唤 2 个"的直接限制点。**

召唤物 ID 由技能决定（第 35-54 行）：

| 技能 ID (`word_9D6C7C`) | 召唤物 ID | 说明 |
|---|---|---|
| 222 | 58 | 固定召唤物 |
| 224-231 | 查表 `stru_4EB6F0` | 按技能选择不同召唤物 |
| 251 | 96 或 98（随机） | `sub_452AC0(100) >= 0x32` 决定 |

#### 槽位分配 — `sub_431094`（0x431094）

文件：`decompile/431094.c` 第 17-26 行，**硬编码两个 if/else 分支**：

```c
if ( byte_9DF88E[0] == -1 )        // 槽 1 空
{
    v6 = byte_9DF883;              // 召唤物角色索引 = 初始角色数 + 0
    v5 = 0;                        // 槽位号 0
}
else if ( byte_9DF88F == -1 )      // 槽 2 空
{
    v6 = byte_9DF883 + 1;          // 召唤物角色索引 = 初始角色数 + 1
    v5 = 1;                        // 槽位号 1
}
// （无 else：两槽全满时函数继续用未初始化的 v5/v6 —— 调用方 444BB0 已提前拦截）
```

随后第 61 行写回槽位：`byte_9DF88E[v5] = v6;`

该函数同时完成（第 27-60 行）：

- `qmemcpy` 从模板区 `0x7570A8 + 1054*v7` 复制 1054 字节（0x41E）角色数据到 `word_9D707A[527*v6]`
- 加载精灵动画（`dword_9DF43A` / `dword_9DF43E` 系列）
- 初始化特殊技能（`word_9D6C9A` / `word_9D6C9C`）
- 注册到战场：`byte_9D705A[byte_9DF882++] = v6;`
- 写入坐标并登记 32×32 格占位表 `byte_951D42`

#### 槽位初始化 — `sub_436BD4`（0x436BD4）

文件：`decompile/436BD4.c` 第 25-26 行（战斗初始化时清空两槽）：

```c
byte_9DF88E[0] = -1;
byte_9DF88F = -1;
```

#### 槽位清除 — `sub_43C734`（0x43C734）

文件：`decompile/43C734.c` 第 18-25 行（召唤物死亡/移除时清除槽位）：

```c
if ( a1 == byte_9DF88E[0] )
    byte_9DF88E[0] = -1;
else if ( a1 == byte_9DF88F )
    byte_9DF88F = -1;
```

### 2.2 技能175「囔嚷」——骗敌上场机制（每场累计上限 6，共享角色数组尾部）

> 2026-08-15 更正：此前误称"敌方援军系统"。经核实游戏内并无此概念——该路径是**辩才类技能 175「囔嚷」**的技能效果，且仅在特殊战斗模式下生效。

辩才类技能 172-175（說服/勸誘/和解/囔嚷，名称来自 `docs/tksexe/warpc_skill_tkkon_mapping.csv` 与游戏内文本"嚷嚷失敗"）在 `sub_4458B0` 中同组处理（`4458B0.c:537-653`）：

| 技能 | 名称 | 成功效果 |
|---|---|---|
| 172 | 說服 | 目标 HP 归零退场（`word_9D7084=0`） |
| 173 | 勸誘 | 目标倒戈：阵营改为 20（我方召唤物阵营），敌方计数 -1 |
| 174 | 和解 | 清空战斗状态，战斗直接结束 |
| **175** | **囔嚷** | **v29≥v36：被抵抗（显示 &unk_4EBC87）；v29<v36：调用 sub_445564 从本场敌方编制表随机骗 1 个未上场敌人上战场（满 6 次时 sub_445564 返回 0，显示 &unk_4EBC63「嚷嚷失敗」）** |

生效前提（`4458B0.c:574-595`，注意方向勿反）：

```c
v36 = 施法者等级 * (176 - word_9D6C7C) + 30;   // 175 号技能: 等级×1+30
if ( !word_9DF894 )                              // 特殊战斗模式标志
    v36 = 0;                                     // 非特殊战斗 → 成功率恒 0，永远被抵抗
if ( v29 >= v36 )  /* 随机数 ≥ 阈值：技能被抵抗 → 显示 &unk_4EBC87（"敵人抵抗"类反馈） */
else               /* 随机数 < 阈值：技能成功 → 调用 sub_445564 骗敌 */
{
    ...
    if ( word_9D6C7C == 175 && !sub_445564() )   /* sub_445564 返回 0（已满 6 次）→ 显示 &unk_4EBC63（"嚷嚷失敗"） */
}
```

`word_9DF894` 由 `4084E0.c:67` 置 1（数据表驱动的特殊战斗入口，随即调用 `sub_40EB10` 启动战斗），`40EBD4.c:555` 清零。**普通战斗中 v36 被强制为 0 → 任何 v29 (0..449) 均 ≥ 0，技能 100% 被抵抗，压根进不到 sub_445564 —— 这就是玩家通常见不到该机制的原因。**

> **与文档初版对比**：初版注释 `/* 抵抗分支，显示"嚷嚷失敗" */` 方向写反。实际 `&unk_4EBC63`（"嚷嚷失敗"）只在「骗敌满 6 次」时显示，而「随机抵抗」分支显示的是 `&unk_4EBC87`（具体文本未在 strings.txt 导出，估计为"敌人不为所动"之类反馈）。

「囔嚷」生效后的执行路径 `sub_445564 → sub_444FD4`：

**次数上限检查** — `decompile/445564.c` 第 22 行（每场战斗累计 6 次）：

```c
if ( byte_9DF887 >= 6 )
    return 0;
```

**上场索引计算** — `decompile/444FD4.c` 第 45 行：

```c
v12 = byte_9DF887 + byte_9DF883 + 2;   // 跳过玩家召唤的 2 个槽位！
```

`sub_444FD4` 从本场**敌方编制表**（`word_9537FA`/`byte_953830`/`byte_95381E` 等 18 项，由 `4307CC.c` 战斗初始化同一表生成初始敌人）中筛选"模板有效、子类型 0、阵营<10"的未上场条目，随机取一个复制模板（+35 敌方模板区，与初始敌人完全同源）创建新敌方单位并随机放置。

⚠️ **关键联动**：上场索引公式中的常量 `+2` 正是玩家召唤槽数。若扩展玩家召唤数而不改此公式，「囔嚷」上场的敌人会与玩家召唤物索引重叠、数据互踩。

## 3. 战场角色数组容量：32 槽硬上限

所有战场角色（队员/敌人/召唤物/「囔嚷」上场的敌人）存储在一组**按 32 槽设计**的并行数组中，索引 0-31：

### 3.1 容量证据（memset 大小 + 地址间距相互印证）

| 数组符号 | 地址 | 证据 | 推算容量 |
|---|---|---|---|
| `word_9D707A`（角色主数据，1054B/角色） | 0x9D707A | `memset(word_9D707A, 0, 0x83C0u)` = 33728B（`4307CC.c:40`）；33728 ÷ 1054 = **32** | 32 |
| `dword_9DF43A`（精灵句柄，20B/角色） | 0x9DF43A | `memset 0x280u` = 640B（`4307CC.c:41`）；640 ÷ 20 = **32** | 32 |
| `byte_9D705A`（战场角色索引列表） | 0x9D705A | 到下一变量 `word_9D707A` 间距 = 0x20 = 32B | 32 |
| `byte_9DF781` | 0x9DF781 | 到 `byte_9DF7A1` 间距 0x20；`memset(byte_9DF781, 0, sizeof)` | 32 |
| `byte_9DF761`（阵营标记，<10 为敌方侧） | 0x9DF761 | 到 `byte_9DF781` 间距 0x20 | 32 |
| `word_9DF6BA` / `word_9DF7C2` / `word_9DF802+804`（坐标等） | — | 各与下一变量间距 0x40/0x80，均为 32 项 | 32 |

### 3.2 槽位占用账本（零余量）

| 占用方 | 数量 | 索引区间 |
|---|---|---|
| 队伍成员（`byte_9DF886` 上限 6） | ≤6 | 0-5 |
| 敌人（`word_9D6F66` 硬编码 18，`4307CC.c:209`） | ≤18 | 紧接队员 |
| **初始角色合计 `byte_9DF883`** | **≤24** | 0-23 |
| 玩家召唤槽 1/2 | 2 | 24、25 |
| 「囔嚷」上场的敌人（`byte_9DF887` 每场累计上限 6） | ≤6 | 26-31 |
| **战场总数 `byte_9DF882` 最大值** | **32** | **恰好占满** |

代码中**没有任何 `byte_9DF882 >= N` 的显式上限检查**——第 33 个角色会直接越界写坏相邻全局变量。因此：

> **扩展约束：玩家召唤数 N + 「囔嚷」上场敌人数上限 ≤ 8**（即 `2+6` 池内重新分配）
> - N=4 → 「囔嚷」上限降为 4（行为影响中等）
> - N=6 → 「囔嚷」上限降为 2（特殊战斗中该技能可骗出的敌人减少）

### 3.3 为什么不能突破 32 槽

1. 角色主数据 memset 33728B 恰好 32×1054，精灵/坐标/状态等 8+ 个并行数组全部按 32 设计
2. `byte_9DF882`（战场总数）为单字节，虽有富余，但所有数组无余量
3. 突破 32 须迁移并扩容全部并行数组、hook 几十处 `[527 * idx]` / `[20 * idx]` / `[2 * idx]` 访问点，工程量与稳定性风险巨大，**不建议**

## 4. 关键内存布局（0x9DF882 起）

槽位变量 `byte_9DF88E` 仅 2 字节，且**其后内存全部被占用**，无法原地扩容：

| 地址 | 符号 | 大小 | 用途 |
|---|---|---|---|
| 0x9DF882 | `byte_9DF882` | 1 | 战场总角色数 |
| 0x9DF883 | `byte_9DF883` | 1 | 初始角色数（召唤物索引基址），唯一写入点 `4307CC.c:315-317` |
| 0x9DF884 | `byte_9DF884` | 1 | 我方阵营计数 |
| 0x9DF886 | `byte_9DF886` | 1 | 队伍成员数（上限 6） |
| 0x9DF887 | `byte_9DF887` | 1 | 「囔嚷」上场敌人计数（每场累计上限 6） |
| 0x9DF888 | `byte_9DF888[6]` | 6 | 队伍成员 ID 列表 |
| **0x9DF88E** | **`byte_9DF88E[0]`** | 1 | **召唤槽 1**（-1=空，存角色索引） |
| **0x9DF88F** | **`byte_9DF88F`** = `byte_9DF88E[1]` | 1 | **召唤槽 2**（同一数组的别名） |
| 0x9DF890-93 | `byte_9DF890..893` | 4 | 阵营计数器（`4307CC.c:45-48` 初始化、`43C734.c` 递减） |
| 0x9DF894 | `word_9DF894` | 2 | 标志位 |
| 0x9DF896-9DA | `word_9DF896..89C` | 10 | 光标坐标 X1/Y1/X2/Y2（`4359A4.c` 大量使用） |
| 0x9DF89E-A5 | `unk_9DF89E` 等 | 8 | 被引用数据（`pointers.txt` 多处命中） |
| 0x9DF8A6 起 | `word_9DF8A6[]` | — | 召唤物物品列表数组（道具召唤 UI） |

> **结论**：扩展后的 N 槽数组（N>2）无法放在 0x9DF88E 原地，需迁入 **WarPC 扩展内存**（见下节）。

## 5. Launcher 补丁机制能力评估

`tks_launcher_gui` 现有机制**完全覆盖**本方案全部需求：

| 需求 | 现有机制 | 位置 |
|---|---|---|
| 重写槽位分配/满检/清除逻辑 | `cave_hook` + 外置 `cave_code`（自定义 x86 机器码） | `core/patch_engine.py` `apply_cave_hook()` (L997) |
| 存放新 N 槽数组 | WarPC 扩展内存（`discover_warpc_base` 自动发现 + `0x757F08` 占位符运行时重定位） | `core/scanner.py` (L340)、`replace_addr_in_bytes()` |
| 改「囔嚷」索引常量/次数上限 imm | `patch_bytes` / `patch_imm32` | `apply_patch_bytes()` (L790) 等 |
| 进程挂起时应用补丁 | CREATE_SUSPENDED 启动 → 挂起 → 补丁 → resume | `workers/patcher_worker.py` `_do_run()` (L88) |
| Cave RWX 内存 | `VirtualAllocEx` 1024B，各补丁以 `cave_offset` 分区共用 | `patcher_worker.py` (L505) |

**同类先例**（证明复杂度可控）：

- `CAVE_TEAM_MEMBER_LEAVE_ROUTING`（158 字节，主角离队槽位右移逻辑）
- `CAVE_SUMMON_RANDOM` / `CAVE_SUMMON_RANDOM_222_251`（召唤多随机，占位符 `0x52414E44` 重定位）
- `CAVE_WEAPON_CAUSE_MASK`（含 pushad 保护、空槽检查、范围校验的完整 cave）

补丁以单个 `.tkspatch`（ZIP 容器：`patch.json` + 外置 `cave_code` 十六进制串）交付，无需改引擎代码。

## 6. 补丁实现方案（6 个注入点）

```
战场 32 槽布局（补丁后 N=4 示例）：
[初始角色 ≤24][玩家召唤 ×N=4][「囔嚷」敌人 ≤8-N=4]
 索引 0..23      24 25 26 27     28..31
```

| # | 函数 | 原逻辑（上限 2） | 补丁方案 | 类型 |
|---|---|---|---|---|
| 1 | `sub_436BD4` (0x436BD4) | 初始化：槽1=槽2=-1 | hook 初始化 WarPC 中 N 槽数组全部为 -1 | cave_hook |
| 2 | `sub_444BB0` (0x444BB0) | 满检：槽1≥0 且 槽2≥0 → 拒绝 | hook 遍历 N 槽判满（计数 ≥N 才拒绝） | cave_hook |
| 3 | `sub_431094` (0x431094) | 分配：硬编码 2 分支，索引=9DF883+slot | hook 循环找空槽 0..N-1，索引=9DF883+slot。**核心难点：需正确重建局部变量 v5/v6（角色索引、槽位号）的寄存器/栈状态，供函数后续代码使用** | cave_hook |
| 4 | `sub_43C734` (0x43C734) | 死亡清除：2 个 if | hook 遍历 N 槽，匹配则清除 | cave_hook |
| 5 | `sub_444FD4` (0x444FD4) | 「囔嚷」敌人索引 = 9DF887 + 9DF883 + **2** | imm 常量 2 → N（与 #3 联动，防索引重叠） | patch_bytes |
| 6 | `sub_445564` (0x445564) | 「囔嚷」次数上限：9DF887 ≥ **6** | imm 常量 6 → 8−N | patch_bytes |

### 6.1 Cave 机器码要点（参照现有模板规范）

- 进入时 `pushad`/保存寄存器，退出恢复；cave 末尾 `ret`
- cave 内**重放被 hook 覆盖的原始指令**
- E8 call hook 场景下，cave 开头 `pop edx` 移除多余返回地址（参照 `CAVE_DUEL_COUNTER_SELF_FIX`）
- WarPC 基址占位符 `0x757F08` 由引擎运行时 `replace_addr_in_bytes()` 重定位

### 6.2 UI 无需改动的验证

战场渲染（`sub_444BB0` 第 66-137 行、`sub_445564` 第 47-93 行）均按 32×32 格占位表 `byte_951D42` 遍历全部角色，新增召唤物**自动显示**，无需额外 UI 补丁。

另经核实两处疑似限制与召唤无关，**无需处理**：

- `411E84.c:36` 的 `dword_755B58 >= 2`：角色模板 ID 检查（剧情分支）
- `43B2D4.c:64` 的 `< 26`：敌方状态 UI 每屏最多 26 行的显示上限

## 7. 风险点与约束

| 风险 | 说明 | 缓解 |
|---|---|---|
| **sub_431094 cave 难度最高** | 2 分支改循环，需精确保存/恢复 v5（槽位号）/v6（角色索引）供原函数后续 qmemcpy、战场注册使用 | 逐条对照反编译汇编手动核对机器码；先在调试器（x64dbg）单步验证 |
| **「囔嚷」联动必须同步改** | 漏改 #5/#6 会导致玩家召唤与「囔嚷」敌人索引重叠（26 起），数据互踩 | #5/#6 与 #1-#4 放同一补丁包，原子生效 |
| **「囔嚷」上限下降是行为变化** | N=6 时「囔嚷」从 6 次降到 2 次，特殊战斗中该技能骗出的敌人减少。注意：普通战斗中「囔嚷」本就无效（`word_9DF894=0` 时成功率恒 0），实际影响面仅限少数特殊战斗 | 首版 N=4；在补丁描述中明示 |
| **槽位数组迁移 WarPC** | 新 N 槽数组地址与原全局变量不同，4 处 cave 必须统一引用 | 占位符机制已有，一处定义 |
| **版本兼容** | 加密版/终极版 EXE 指纹不同 | 引擎已有 `detect_exe_profile` + `fallback_rva` 回退机制 |
| 32 槽越界 | 若 N + 「囔嚷」上限 > 8，第 33 角色越界写坏光标坐标等全局变量 | 补丁内对 N 做上限校验（N ≤ 6） |

## 8. 结论与建议

1. **可行**：通过 tks_launcher_gui 的 `cave_hook` + `patch_bytes` 组合补丁，可将玩家召唤数从 2 扩展到最多 6。
2. **天花板**：32 槽角色数组零余量，约束为 `玩家召唤 N + 「囔嚷」上场敌人 ≤ 8`；突破 8 需迁移全部并行数组，不值得。且「囔嚷」仅在 `word_9DF894=1` 的特殊战斗中生效，普通战斗不受 #5/#6 联动修改的影响。
3. **推荐路线**：首版 **N=4**（「囔嚷」上限 6→4，行为影响最小）→ 实测稳定 → 再放宽 N=6。
4. **交付形式**：单个 `.tkspatch`（ZIP 容器），含 4 个 cave_hook（外置 cave_code 机器码）+ 2 个 patch_bytes，不修改引擎源码。
