# 生成启动器差异补丁开发经验总结

## 一、目标与最终结论

本次优化在当前 `feat-skill` 分支推进，没有参考其他分支。目标不是单独生成一个修改版 EXE，也不是复制一份完整游戏，而是生成能够覆盖到指定原版上的独立差异包。

最终原则：

> 从当前游戏目录读取已有内容，叠加所选 MOD、补丁和兼容工具，再与用户手选的原版基准比较；输出新增或内容变化的文件，以及生成的 `TKS_MOD.exe`。

这里的“差异包”是**文件级覆盖包**：有变化的文件以完整成品输出，并非需要专用安装器还原的二进制增量补丁。

## 二、需求演进暴露的问题

| 阶段 | 当时的处理 | 暴露的问题 | 得到的经验 |
| --- | --- | --- | --- |
| 只烧录 EXE | 将所选补丁写入程序 | MOD 数据、图形、字体等仍依赖启动器部署 | EXE 独立不等于整个 MOD 内容独立 |
| 输出 MOD 声明文件 | 整合 MOD 涉及的目标文件并输出 | 当前游戏目录可能已经被手工编辑，未被 MOD 声明的修改会漏发 | MOD 元数据不是当前游戏内容的完整清单 |
| 输出全部运行文件 | 把当前目录的运行数据全部带上 | 大量与原版相同的资源被重复分发，不符合补丁原则 | 内容完整性和输出精简必须同时满足 |
| 三目录差异输出 | 分离原版对照、当前内容来源和输出位置 | 可以保留已有改版内容，同时省略与原版一致的文件 | 缺少独立基准时，不能准确判断哪些文件需要分发 |

### 关键诊断：能读取，不代表会输出

前期漏发 `WarPC.dat` 的原因不是启动器没有传入改版目录。

当时主窗口已经传入所选游戏程序路径，数据解析也能读到该目录里的文件；真正的问题是输出清单只收录 MOD 声明的目标。

因此，排查生成类问题必须分别检查：

1. 输入目录是否正确。
2. 数据合并实际读取哪个文件。
3. 补丁容量和依赖根据哪份数据计算。
4. 哪些文件进入发布候选集。
5. 最终哪些文件真正写到输出目录。

不能仅凭“解析函数找到了文件”，就认定覆盖包已经包含它。

## 三、最终界面约定

弹窗仅提供三个文件夹路径，均可修改：

| 路径 | 默认值 | 用途 |
| --- | --- | --- |
| 基准目录 | 留空，导出前手动选择 | 原版游戏目录，只作为内容差异对照 |
| 游戏目录 | 启动器当前所选程序的父目录 | 提取当前游戏程序和运行数据，可以是原版或改版 |
| 输出目录 | 游戏目录下的 `dist` | 存放差异文件、生成程序和清单 |

具体行为：

- 三个浏览按钮均使用文件夹选择器，不再要求选择输入或输出 EXE 文件。
- 从游戏目录读取 `TKS.exe`，生成程序固定命名为 `TKS_MOD.exe`。
- 没有主窗口游戏路径时，不擅自猜测其他游戏安装目录。
- 修改游戏目录时，仍处于默认值的输出目录跟随更新。
- 用户手动指定过输出目录后，不因切换游戏目录而覆盖其选择。
- 基准目录不会跟随游戏目录自动变化，也不会默认等同于游戏目录。
- 基准和游戏目录允许相同，此时仍可输出 MOD 或补丁造成的变化。
- 没有数据差异时，仍允许输出程序和生成清单。

“基准目录”和“游戏目录”必须分开命名。把实际内容来源称为“原版”或“基准程序”，容易让使用者误以为工具会忽略已有改版内容。

## 四、正确的生成顺序

```text
选择基准目录、游戏目录、输出目录
  → 校验路径及输入保护边界
  → 重载所选 MOD / 合集并解析依赖
  → 收集游戏目录现有运行文件，在临时目录建立工作副本
  → 在工作副本中整合 MOD 差分与完整资源
  → 与基准比较，得到准备阶段的差异清单
  → 根据完整整合数据准备补丁、扩容容量及配置
  → 用户确认
  → 烧录临时 TKS_MOD.exe
  → 汇总游戏成品、补丁资源与兼容工具
  → 按最终内容再次与基准比较
  → 事务发布差异文件、EXE 和清单
  → 清理本次临时目录
```

### 1. 基准只参与比较，不参与数据兜底

MOD 合并必须基于游戏目录，而不是原版基准目录。否则会丢失用户已通过编辑器修改的字段。

例如当前 `WarPC.dat` 已修改字段甲，MOD 再修改字段乙，正确结果应同时保留甲、乙，再与原版比较。

同样，补丁需要读取的文件在游戏目录中缺失时，不能偷偷从基准目录补齐，掩盖当前游戏内容不完整的问题。

### 2. 补丁容量必须根据完整整合数据计算

`WarPC.dat`、`TKSkill.dat` 等文件可能已经扩容，也可能在 MOD 合并后才扩容。

容量判断必须读取暂存的最终数据，不能读取：

- 原版基准的数据大小；
- 上次生成遗留在 `dist` 的数据；
- 已经被差异过滤后的不完整输出集合。

因此，完整暂存数据和待输出差异清单是两个不同概念。文件与基准相同、无需分发，并不意味着补丁准备阶段不再需要读取它。

### 3. 差异必须在最终覆盖顺序确定后判断

准备阶段的差异清单只能作为预览，不能直接当作最终发布清单。

可能发生两种反转：

- 游戏文件不同于原版，但 MOD 或兼容工具将其改回原版内容，最终不应输出。
- 游戏文件与原版相同，但所选工具覆盖后发生变化，最终必须输出。

兼容工具沿用启动器最后部署的顺序，默认选择也应沿用主窗口。不能仅因为工具目录中存在 `cnc-ddraw`，就在导出时擅自启用它。

## 五、文件与配置处理经验

### EXE 烧录不等于把 DAT 内容嵌入 EXE

现有扩容实现通过 PE 的 BSS 空间声明运行时缓冲区，游戏仍会从外部文件加载数据。

因此，“已经烧录扩容补丁”不能替代部署对应的数据文件。覆盖包中的 EXE 和差异数据必须作为同一套产物使用。

### 扩展状态文件不能误判为普通存档

`WarPC.dat.tksx` 是扩展技能初始状态资源，不能因为它与存档机制有关，就按玩家存档或缓存排除。

它应与其他游戏运行数据一样参与收集和内容比较：基准没有则新增，内容不同则输出，相同则省略。

### 成对资源要完整参与整合，但不必重复分发

GRP 差分通常需要配套 IDX。合并时必须确保两者可用，不能只拿 GRP 处理。

最终发布仍按每个文件的内容决定：

- GRP 和 IDX 都变化：输出两者。
- GRP 变化、IDX 与基准一致：只输出 GRP，使用目标原版已有的 IDX。

### 数据配置和文件资源不是同一种部署方式

MOD 白名单配置应传给对应配置补丁并烧录，不能仅复制一个 JSON 就声称脱离启动器。

如果 MOD 提供了配置，但对应补丁未启用或无法处理，应明确中止，而不是静默忽略。

`ddraw.ini` 等运行时工具配置则属于直接部署的文件，需参与最终差异比较。

### 自动收集需要明确边界

当前自动收集依据已支持的游戏资源类型，包括 DAT、TKSX、GRP、IDX、JVG、GXP、SRP、媒体、字体及部分运行配置等，并保留相对目录结构；显式 MOD 资源仍按其声明处理。

不是把目录里的任意文件都视为游戏必需内容。存档、缓存、日志、旧输出、备份及编辑器工程不自动混入分发包。

新增游戏格式时，应补充资源识别与回归测试，不能把现有筛选集合当成永久完备的清单。

## 六、差异比较与发布安全

### 内容比较不能只看时间或大小

实现采用流式 SHA-256 与实际读取长度比较，不依赖修改时间，也不依赖跨次文件比较缓存。

必须覆盖以下情况：

- 大小相同、修改时间相同，但字节不同：需要输出。
- 修改时间不同，但字节完全相同：不输出。
- 大文件仅最后一个块不同：需要输出。
- 读取中途失败：中止，不能当作文件相同或无差异。

### 两个输入目录均只读

生成阶段不应临时改写真实游戏目录后再恢复。现有合并器有直接写盘行为，因此只能在隔离工作副本上复用。

路径保护还包括：

- 拒绝越界相对路径、绝对资源路径、Windows 设备名和备用数据流形式。
- 拒绝会越过保护边界的符号链接或目录链接。
- 防止输出覆盖游戏或基准目录。
- 游戏树内输出限定在 `dist` 及其子目录；独立基准树内不允许输出。
- 发布使用替换而非写穿原有文件，避免硬链接间接破坏输入。

### 编辑器备份与运行残留要区分

普通 `.bak` 是编辑器备份：不分发，但不应因此拒绝读取对应的当前数据文件。

`.orig`、`.mod_orig`、`.mod_new`、`.toolbak`、`.expanded` 等运行残留则可能表示数据处于临时替换或截断状态，应明确提示处理，不能自行恢复、删除或猜测哪份才是正确数据。

### 发布成功必须意味着整套文件成功

数据整合、EXE 烧录、资源复制或比较失败，都不能显示“生成成功”。

使用 `tks_build_manifest.json` 记录实际产物；重新生成时仅清理上次清单管理且本次不再需要的文件，不删除未知文件。

发布失败需要回滚已覆盖和已清理的旧输出。若回滚也失败，必须保留备份位置并报告，不能继续清理掉恢复依据。

## 七、验证方法与本次结果

### 自动化验证应围绕产物，而不是成功提示

本次定向验证覆盖：

- 三个文件夹选择器、取消操作、默认路径联动和输入校验。
- 无 MOD 时已有手工编辑数据仍参与差异输出。
- 原版与游戏相同、同大小不同内容、MOD 改回原版等情况。
- GRP/IDX、完整资源、资源子目录、配置覆盖与 EXE 替换。
- 工具最终覆盖后差异清单和成功计数更新。
- 基准与游戏目录不变、异常中止、事务回滚和重复生成清理。

## 八、必须保留的能力边界

1. **差异覆盖包不是完整游戏。** 必须覆盖到与基准版本一致的游戏目录，不能直接在输出目录独立运行。
2. **覆盖不表达删除。** 基准有而当前游戏没有的文件，不会通过复制补丁自动删除；不能承诺覆盖后两棵目录完全相同。
3. **未知旧输出会保留。** 建议使用专用输出目录，分发时以生成清单为准，避免混入未受管理的旧文件。
4. **原版纯净性由使用者确认。** 路径存在且包含 `TKS.exe`，不等于程序已经证明它是官方原版。
5. **源 EXE 必须与补丁兼容。** 改版程序不一定仍具有补丁预期的模式或位点，匹配失败应中止，不能强行烧录。
6. **运行时重建文件要注意。** `TKDef.txt`、`TKTalk.txt` 存在时，游戏可能重建 TKD/TKT；保留它们时需提示，不能忽略其对数据加载顺序的影响。
7. **静态一致性不等于实机等价。** 本次没有启动游戏或废弃 CLI；战斗、技能、存读档等实际效果仍需使用者复测。
8. **输出精简不等于无临时复制。** 当前仍建立完整工作副本并在发布前暂存，磁盘空间与耗时需按候选数据规模考虑，不能按最终差异包大小估算。

以后遇到“启动器正常、生成版不一致”，优先检查：

- 是否选中了正确的原版基准和当前游戏目录。
- 是否沿用了相同的 MOD、补丁高级选项及工具选择。
- 漏发文件是否进入自动收集或显式资源候选集。
- 补丁容量是否来自整合后的游戏数据，而非基准或旧输出。
- 最后一次内容覆盖发生在何处，是否在其后重新比较。
- 输出清单是否包含真实需要的新增、变化文件。
- 是否存在运行残留、文件删除需求或启动时重新生成数据的行为。
- 当前证据属于字节校验、合成测试还是实机结果，避免混淆验证层级。
