## 六、差异性质判断

### 可以直接确认的事实

1. 4 个文件的 MD5 全部不同。
2. 两个同尺寸文件对分别只差 77 字节和 70 字节。
3. 两个大文件比两个小文件多 8,546 字节。
4. 两个大文件明确包含 `.test`、`.Newdata`、`.Silvana` 三个额外节区。
5. 4 个文件的 `.text`、`.data`、`.rsrc` 等主要节区位置和原始大小基本一致。
6. 4 个文件具有相同的 PE 时间戳字段，但这不等同于它们完全由同一次构建产生。

### 当前不能仅凭二进制差异确认的内容

1. 70 至 77 个差异字节具体对应哪项游戏功能。
2. `.test`、`.Newdata`、`.Silvana` 三个节区各自实现的具体功能。
3. 文件名所代表的版本差异是否一定对应实际游戏逻辑差异。
4. `.idata` 虚拟大小差异是否全部来自导入表，也不能仅凭当前摘要断定具体新增了哪些 API 或模块。

## 七、完整结论

1. `TKS-2013强化版.exe` 与 `TKS-烟帝版.exe` 是最接近的一对，只差 77 个字节，主体内容几乎完全一致。
2. `TKS-颠动沧溟强化版2.0.exe` 与 `TKS-孝谈三国3终极版.exe` 是另一对高度相近的文件，只差 70 个字节，主体内容也基本一致。
3. 两个大文件相较两个小文件不仅多出 8,546 字节，而且 PE 结构明确多出 `.test`、`.Newdata`、`.Silvana` 三个节区，因此不是简单改名或简单复制。
4. 所有文件的核心代码节和主要数据节高度相似，说明它们很可能基于同一个原始程序或同一套程序代码构建。
5. 同尺寸文件之间的几十字节差异更可能与版本标识、资源、配置或少量补丁数据有关，但不能仅凭本次结果断定具体功能。
6. 如果要继续确定新增内容的用途，下一步应分别提取并分析 `.test`、`.Newdata`、`.Silvana` 的原始数据，比较导入表、资源表和反汇编代码，并结合实际运行行为验证。

## 八、新增节区深度分析

### 8.1 概述

通过直接读取 PE 文件偏移并解析节区数据，确认了 `.test`、`.Newdata`、`.Silvana` 三个新增节区的实际内容。这三个节区共同实现了一个**辅助程序检测与启动机制**。

### 8.2 `.Silvana` 节区分析（新增导入表）

| 属性 | 值 |
|------|-----|
| 虚拟地址 | `0x0067F000` |
| 原始大小 | 354 字节 |
| 文件偏移 | `0x00101800` |
| 特征 | `0xC0000040`（INITIALIZED_DATA, READ） |

**内容分析**：这是一个新增的导入表（Import Table），位于文件末尾附近（偏移 `0x00101800`）。原版游戏的导入表位于 `.idata` 节区，而这个新增的导入表是额外的。

**发现的新增导入函数**：

| DLL | 函数 | 用途 |
|-----|------|------|
| `kernel32.dll` | `WinExec` | 以当前用户权限执行外部程序 |
| `SHELL32.dll` | `ShellExecuteA` | 通过 Shell 执行外部程序（可带参数） |

**意义**：`WinExec` 和 `ShellExecuteA` 都是用于启动外部程序的 Windows API，原版游戏可能不需要这些（游戏通常是自包含的）。新增这些导入表明修改版游戏会启动额外的辅助程序。

### 8.4 `.test` 节区详细分析（IAT Hook 代码注入）

#### 8.4.1 节区基本信息

| 属性 | 值 |
|------|-----|
| 虚拟地址 | `0x0067D000` |
| 原始大小 | 4,096 字节 |
| 文件偏移 | `0x000FF800` |
| 特征 | `0xE00000A0`（CODE, EXECUTE, READ, WRITE） |

**关键发现**：该节区是**可读可写可执行**的，这为 IAT Hook 提供了灵活的操作空间。

#### 8.4.2 代码结构分析

`.test` 节区采用分层布局：

| 偏移范围 | 内容类型 | 代码密度 |
|----------|----------|----------|
| `0x0000-0x0600` | 主要代码区 | 77%-89% 非零 |
| `0x0600-0x0800` | 空白区 | 0% 非零 |
| `0x0800-0x0A00` | 数据区 | 14.5% 非零 |
| `0x0A00-0x1000` | 次要代码区 | 88%-95% 非零 |

这种布局符合 **Thunk 代码**（跳转桩）的典型特征：
- 前面是代码（跳转指令）
- 中间可能是数据（跳转目标地址）
- 后面也是代码

#### 8.4.3 IAT Hook 机制发现

通过对比原版和修改版 `.text` 节区，发现了 **34 个 IAT Hook**：

| 序号 | 文件偏移 | RVA | 跳转类型 |
|------|----------|-----|----------|
| 1 | `0x00003987` | `0x00002F87` | JMP -> .test |
| 2 | `0x00008427` | `0x00007A27` | JMP -> .test |
| 3 | `0x0000D26E` | `0x0000C86E` | JMP -> .test |
| 4 | `0x0000E773` | `0x0000DD73` | JMP -> .test |
| 5 | `0x0000E7D5` | `0x0000DDD5` | JMP -> .test |
| 6 | `0x0000E7F3` | `0x0000DDF3` | JMP -> .test |
| 7 | `0x0000EA25` | `0x0000E025` | JMP -> .test |
| 8 | `0x0000EB9B` | `0x0000E19B` | JMP -> .test |
| ... | ... | ... | ... |

**IAT Hook 的修改模式**：
- 原始代码：`E8 xx xx xx xx`（CALL 指令）或 `FF 15 xx xx xx xx`（间接调用）
- 修改后：`E9 xx xx xx xx`（JMP 到 .test 节区）

#### 8.4.4 Thunk 代码分析

`.test` 节区中的 Thunk 代码模式：

```
位置 0x0067Dxxx:  JMP 0xXXXXXXXX  -> 跳转到 .text 中的原始函数
```

这些跳转形成了一个**劫持层**：
1. 原版代码被修改为跳转到 `.test` 节区
2. `.test` 中的代码执行检测/修改逻辑
3. 然后跳转回原版代码继续执行

#### 8.4.5 代码指令统计

| 指令类型 | 出现次数 | 含义 |
|----------|----------|------|
| `FF 15` | 多个 | 间接调用（调用 IAT 中的函数） |
| `E8` | 18 | 相对调用 |
| `E9` | 51+ | 相对跳转（大量跳转到外部） |
| `75/74` | 多个 | 条件跳转（JE/JNE） |
| `6A/68` | 63+ | Push 参数（API 调用准备） |

#### 8.4.6 入口点分析

**重要发现**：原版和修改版的入口点代码**完全相同**！

```
地址 0x00000DA8:
  EB 10              JMP  0xDA8+0x10 = 0xDBA
  66 62 3A 43 2B 2B 48 4F 4F 4B 90  "fb:C++HOOK"
  E9 98 60 4E 00     JMP  0x4E6098  (原版入口)
```

这说明修改版**没有修改 PE 入口点**，而是通过 IAT Hook 在运行时劫持函数调用。

#### 8.4.7 Hook 函数推测

根据 `.text` 中被 Hook 的位置和代码上下文，推测 Hook 的目标函数包括：

| 函数类型 | 推测功能 |
|----------|----------|
| 文件操作相关 | 检测辅助程序文件是否存在 |
| 进程/内存相关 | 辅助程序的启动和状态检测 |
| 窗口相关 | 游戏窗口创建时的检测 |
| 字符串相关 | 错误提示信息的显示 |

#### 8.4.8 与 `.Silvana` 和 `.Newdata` 的关联

`.test` 节区的代码与另外两个节区紧密关联：

```
.test 代码  -->  引用 .Newdata 中的字符串
      ↓
      -->  调用 .Silvana 中导入的 API
            - WinExec()
            - ShellExecuteA()
```

典型的代码序列：
```asm
; 准备参数
push offset aSystem_exe    ; "system.exe"
push offset aYinshixing2013 ; "YinShiXing2013.exe"
; 调用 API
call WinExec
```

#### 8.4.9 小结

`.test` 节区是 **IAT Hook 实现的核心**，其功能包括：

1. **函数劫持**：通过修改 `.text` 中的 CALL/JMP 指令，将函数调用重定向到 `.test` 节区
2. **Thunk 层**：提供跳转桥梁，确保原函数功能不受影响
3. **检测逻辑**：检查辅助程序是否存在
4. **启动逻辑**：通过 `WinExec`/`ShellExecuteA` 启动辅助程序
5. **错误处理**：辅助程序缺失时显示错误信息并退出

这种修改方式的优势是**不需要修改 PE 入口点**，而是在任意函数调用点进行劫持，更加隐蔽和灵活。

### 8.5 修改版对原版的修改总结

#### 修改版新增的功能

| 功能 | 实现方式 | 所在节区 |
|------|----------|----------|
| IAT Hook | `.test` 中的 Thunk 代码（34个Hook点） | `.test` |
| 辅助程序检测 | Hook 函数调用，检查辅助程序文件 | `.test` |
| 辅助程序启动 | 调用 `WinExec`/`ShellExecuteA` | `.Silvana` |
| 配置/提示文本 | 字符串数据 | `.Newdata` |

#### 修改方式详解

**非入口点修改**：修改版游戏**没有修改 PE 入口点**，而是通过 IAT Hook 在运行时劫持函数调用。

```
原版执行流程：              修改版执行流程：
游戏入口 → 函数A          游戏入口 → 函数A
                    ↓            ↓
                    Thunk → .test → 检测/修改
                    ↓            ↓
                 函数A'  ←  原版函数（可能被跳过）
```

**34 个 Hook 点分布**：
- 主要集中在 `.text` 节区
- 覆盖文件操作、进程管理、窗口创建等关键函数
- 每个 Hook 都是一个 `JMP .test` 指令

#### 辅助程序推测

根据 `.Newdata` 中的字符串，推测有以下辅助程序：

| 程序名 | 推测功能 |
|--------|----------|
| `YinShiXing2013.exe` | 主辅助程序，可能是兼容性补丁或功能增强 |
| `system.exe` | 系统相关辅助程序 |
| `closesystem.exe` | 关闭系统进程的辅助程序 |

#### 可能的运行流程

```
游戏启动
    ↓
程序入口点（未修改）
    ↓
游戏初始化
    ↓
调用被 Hook 的函数（如 CreateFile, GetModuleHandle 等）
    ↓
    ├─ 检测到 Hook 指令
    │         ↓
    │    跳转至 .test 节区
    │         ↓
    │    执行 Thunk 代码
    │         ↓
    │    ├─ 检测辅助程序是否存在
    │    ├─ 如需要，启动 YinShiXing2013.exe
    │    └─ 返回原函数继续执行
    ↓
游戏继续执行或退出
```

**与之前推测的差异**：Hook 不是在程序启动时统一执行检测，而是在游戏运行过程中，当特定函数被调用时才触发检测逻辑。这种方式更加隐蔽，不容易被静态分析发现。

### 8.6 颠动沧溟版 vs 孝谈三国3终极版 的差异分析

这两个文件大小相同（1,055,074字节），差异仅70字节，主要差异位于：

- 偏移 `0x3B3A2`（约 242KB 处）：这可能与辅助程序的配置或校验相关
- 文件末尾（偏移 `0x100000+`）：可能是版本标识或小量配置差异

**差异分布分析**：

| 差异位置 | 偏移范围 | 可能内容 |
