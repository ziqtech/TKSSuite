**FileRead TKAct.dat buffer too small 事故（2026-09-10 深夜，用户实测后定位）**：

- **现象**：用生成器（源=基准目录）产出的 TKS_MOD.exe 放入改版目录（TKAct.dat 已被

- **根因**：`_build_data_section`/`_read_data_file_size` 只从**所选原版 TKS.exe 目录**读
  数据文件——基准目录 TKAct.dat 为原版 509600 → tkact_expand 被 SKIP → 生成的 exe

  26240）与 WarPC.dat（解压 211854）同样处于"生成时被 SKIP"状态。
- **修复**：① 新增 `resolve_data_file(输出exe, 原版exe, 文件名)`——优先**输出 exe 所在
  目录**（游戏实际运行目录），回退原版目录，`_build_data_section` 与
  `_read_data_file_size`（imm32 变量 `{*_actual_size}` 等）统一走它；② 新增
  `pad_section_data`——注入数据补零到 64KB 对齐，缓冲区留余量，部署目录数据小幅
  增长无需重新生成（FileRead 只要求 文件大小 <= 缓冲区大小，尾部保持补零）。
- **验证**：`_datafile_test.py`（解析优先级/补齐/回退 + tkkon 65536 重定向 + 字段锚定）；

## 一、引擎级缺陷（最高优先级）

### 1.1 exe_builder 写 E9 jmp，与 cave 代码的 E8 CALL 约定不兼容 【生成启动器产物必坏】

- `core/exe_builder.py:912` 统一写 `E9 rel32`（jmp）；而 `core/patch_engine.py:855/1050`（运行时）统一写 `E8 rel32`（call）。
- **全部 22 个 cave_hook 补丁的 cave 代码按 E8 约定编写**：入口读 `[esp+4]`/`[esp+0x20]`（exp_lock）、结尾 `ret` / `add dword[esp],N; ret`（war_status_icons、trap 两补丁）/ `xchg [esp],eax; jmp`（portrait）等。E9 下无返回地址入栈 → `ret` 弹出垃圾、栈槽映射全错 → 崩溃或随机写内存（如 exp_lock 的 `mov dword[eax],0`，eax 来自错误栈槽）。
- **summon_extend cave3（alloc）** 以 `mov [esp],esi` 复用 E8 返回地址槽、精确复刻 `push esi; push edi` 后的栈布局（[esp+8]=调用者返回地址）——E9 下该写法覆写调用者活跃栈/local（[ebp-8..ebp-5]，含刚写入的 v5/v6）→ 栈损坏。
- 反向例外：summon_extend cave1/2/4（pushad…popad + E9 跳回）与 capacity cave 在 E9 下"栈恰好正确"，但 capacity 在运行时 E8 下有 esp−4 漂移（见 1.3）。
- **修复**：exe_builder 改写 E8 CALL + NOP 填充（与 patch_engine 对齐）。文档 `生成启动器功能实现.md` 的"jmp hook"表述需一并更正。
- 附带：`CavePatchItem` **无 hook_offset 字段**，`generate_exe_dialog.py:336-343` 不传 → awk_sprite_cave3/4（json 声明 `hook_offset: 2`）在生成的 exe 中 hook 写在 `EB 05`（jmp +5）指令上，破坏指令边界与 ==36 特判分支 → 必崩。exe_builder 需补 hook_offset 支持。

### 1.2 summon_extend clear hook 入口错位 16 字节 【运行时召唤物死亡必崩】

- `patch.json` clear 的 `cave_entry_offset: 1904`（0x770），但 `cave_code.py` 把 cave4 代码放在 `CAVE_4_OFFSET = 0x680 + 224 = 1888`（0x760）；docstring 自称 [0x770,0x7B0) 自相矛盾。
- 引擎按 entry 1904 发 E8/call → 落在 cave4 首指令 `0F B6 54 0E FF` 的第 2 字节 → `mov dh,0x54; push cs; …` 执行垃圾。clear 触发时机 = 召唤物死亡/移除（必经路径）。
- **修复**：patch.json entry 1904 → 1888（推荐；若改 CAVE_4_OFFSET=+240 则与 SLOTS_OFFSET=0x7A0 重叠，需连动改布局）。
- 已复核其余 4 个 entry（1664/1696/1744/1968）与常量一致。

### 1.3 summon_extend capacity cave 运行时 esp 漂移 【E8 约定下】

- capacity cave 结尾 `popad; jae/E9 跳回`，不消费 E8 压入的返回地址 → 回到 0x44558E 时 esp = 原值 −4。
- 续接点 `8D 54 24 04`（lea edx,[esp+4]）为 **esp 相对寻址**（sub_445564 是 esp 帧函数，`83 C4 E8` 无 ebp）→ 局部缓冲地址整体错 4 字节，后续 call 收到错误指针。
- 对照：cave1/2/4 续接点（0x436C7B `push×3+call+add esp,0xC`、0x444C1B、0x43C768 `mov [ebp-2]`）为 push/pop 对称或 ebp 相对，且宿主函数 436BD4/444BB0/43C734 为 ebp 帧（`55 8B EC`）→ 漂移在该处无害（侥幸设计）。cave3 显式复用返回地址槽、精确平衡。
- **修复**：capacity cave 结尾改为消费返回地址（如 `mov [esp+0x1C],eax` 写 pushad 的 EAX 槽后 popad + `ret` 回 0x445589，或在 cave 内对 4 个出口统一 `add esp,4` 后跳回）。需实测验证。

### 1.4 exp_lock fallback_rva 口径错误 【潜伏】

- json `fallback_rva: "0x43BAF3"` 是 VA 口径（正确 RVA = 0x3BAF3，与注释、模式命中一致）；其余全部补丁的 fallback_rva 均为 RVA 口径。
- 运行时（patch_engine.py:1543 `fb_off = fallback_rva − 0x1000`）→ 0x43AAF3 越界 → 回退保护失效（跳过）；exe_builder 路径 `rva_to_offset(0x43BAF3)` 落入 .data 区间 → 静默错改。当前模式必命中故为潜伏缺陷。
- **修复**：改为 `0x3BAF3`。

### 2.1 summon_exp_jp_accumulation_fix — 遗漏个人经验越界写

### 实测联调修复（2026-09-11 晚，GUI + cnc-ddraw 端到端）

本轮把宽屏补丁从"应用成功但黑屏/停摆"调到"窗口 16:9 且游戏正常运行"，根因链（按发现顺序）：

1. **启动器挂起态检测失效 → 补丁晚打 1 秒**：`get_module_base` 用 Toolhelp，对 CREATE_SUSPENDED 进程返回 ERROR_PARTIAL_COPY(299)（psapi 同样失败），启动器误判"加密版"→ 恢复进程后走后备检测 → DD 初始化/DFM 流式/缓冲分配都已按旧值完成 → "窗口不变"。修复：`memory.py` 增加 PEB 直读回退（NtQueryInformationProcess → PEB.ImageBaseAddress，64 位宿主查询 WOW64 时在 +0x10；MZ/PE 校验），并支持从 PE 头读 SizeOfImage。现在稳定走"已挂起"路径，全部补丁在游戏启动前写入。
2. **patch_sites 的 E8 rel32 漏加模块基址**（运行时与生成器两侧）：`target - (rva+5)` 应为 `target - (image_base+rva+5)`，原实现把 cave 调用跳到 `image_base` 之外的零内存 → 游戏线程异常退出 → 黑屏。已修 `patch_engine._resolve_sites_writes`（新增 code_start_addr 参数）与 `exe_builder._apply_sites_patch`。
3. **cave 未遵守 memcpy 的 size 参数**（停摆的直接原因）：存在 size=0 的页画布调用（src=NULL），原版 memcpy 立即返回；cave 硬拷 480 行 → 从 NULL 读 → 访问违例。重写为按 size 分块、`size==0` 直接返回、末行按剩余 dwords 拷贝。
4. **cave 其余约定**：保存/恢复 EBX（callee-saved，破坏会让页面状态机错乱）、`cld`（rep movs/stos 依赖 DF，原 memcpy 为 SSE 实现不受影响）、返回 dst（memcpy 语义）、行步进从 `unk_A2ACC8+0x10` 读 lPitch（实测 856x480 时为 1712；曾误改到 +0x20=0）。
5. **宽度 854 → 856**：cnc-ddraw 实际 pitch = 1712 = 856x2（854x2=1708 被 16 字节对齐成 1712，按 854 步长绘制会每行错位 2px）。856 与实测 pitch 精确一致且仍接近 16:9。
6. **`optional`/`default_checked` 必须显式声明**：loader 对缺失的 default_checked 默认 True，导致补丁在 GUI 中恒被勾选（用户历次测试其实都带着它）。已显式 `optional=true, default_checked=false`。
7. **撤掉"强制窗口协作模式"位点**（widescreen 里的 `push 1->0`）：它让游戏自己开窗口，绕过 cnc-ddraw 的独占全屏接管，表现为"cnc-ddraw 没生效 / 直接进入系统窗口"。已移除。
8. **注入后落盘校验**（`patcher_worker._settle_tool_files`）：逐文件比对大小、失败重试、再留 0.6s 稳定期再启动，避免游戏加载到未就绪的 ddraw.dll。
9. 测试注意：GUI 的补丁勾选状态来自**按游戏路径的 profile**（`launcher_config.json.profiles[*].patches`），改顶层 `patches` 不生效。

### 页面绘制步长动态化（2026-09-11 深夜，菜单错位修复）

现象：标题/菜单呈横向拖影错位（截图确认）。原因：页面对象内嵌画布是 640x480
(行距 1280B)，而拓宽补丁把绘制原语的步长常量改成了 856，页面控件因此按 856
步长落笔到 640 宽画布。

方案（与 TKSRemake"普通页面保持 640 逻辑画布"一致）：**步长改为运行时全局**。

- 全局槽：`0x660800` (步长) / `0x660804` (暂存返回地址)，位于 .data BSS 尾部
  空闲区（全 .text 无任何 disp32 引用），由补丁在 DD 初始化时置为 856。
- 21 处步长惯用形改写为 `imul rA, [0x660800]`（0F AF /r 内存形 7B，比原立即数
  形 6B 长 1 字节，仍在 17B 改写跨度内）。
- 页面状态机进入前切 640、返回后恢复 856：把 3 个调用点（0xD644→42131C、
  0xD977→4240B8、0x12D95→426164）的 `call page_fn` 换成 `call wrapper`。
- DD 初始化调用点（0x31B5→44EC0C）同样包一层，保证首次绘制前全局已生效。

⚠ 关键教训（实测 Access violation）：wrapper **不能**用 `call page_fn`——会多压
一个返回地址，使 page_fn 的参数整体错位 4 字节（表现：sub_44EC0C 在 0x44EC67
读野指针 AV）。正确形态是**尾调用 + 替换自身返回地址为桩**：

    [esp]=ret_caller → 存 g_ret, 把 [esp] 改成桩地址(相对 call $+5 计算), jmp page_fn;
    page_fn 的 ret 落到桩 → 桩恢复步长 856 并 jmp 回 ret_caller（参数未被触碰）。

DD 初始化 wrapper 无需恢复动作，直接尾调用即可。cave 块 338B（6 入口）。

验证：296/296 位点 → 无错误框、帧节拍持续前进、步长全局在页面帧后为 856、
页面调用点 g_ret 指向调用点后地址（返回地址替换生效）。

### 16:9 光标拖影 + 标题菜单失效根因与修复 (2026-09-11 深夜, 实测闭环)

用户实测反馈「鼠标重叠绘制无法游戏」。用 `ReadProcessMemory` 现场取真值 + 在 cave 内埋计数器
(临时, 已移除) 定位到两个独立缺陷:

1. **擦除链的 `lea` 未乘二 (拖影根因)**。`cave_code.build_cursor_scratch` Phase A 与
   `grab_erase` 里算 scratch 行指针时写的是 `emit(b'\x8D\x00')`，注释却是
   `lea eax,[eax+eax]`。`8D 00` 实为 `lea eax,[eax]` (无 ×2)，正确编码是 `8D 04 00`。
   scratch 是 16bpp，像素索引必须 ×2 才是字节偏移，于是 Phase A/grab_erase 读到的
   scratch 全部错位 → 逐像素判定 `dst==scratch` 永不成立。现场计数器显示
   `scratch_entry=46 帧 / 恢复像素=0`，而 scratch 内确有 654 个光标像素 (解码链路正常)，
   证明"解码对、擦除读错地址"。改为 `8D 04 00` 后快扫不再留串。
   ⚠ 教训: 手写机器码的 `lea` 变体 (2B `lea r,[r]` vs 3B `lea r,[r+r]`) 极易写错，生成后
   必须 capstone 反汇编核对寄存器语义，不能只看注释。

2. **Phase A 由整矩形校验改为逐像素归属恢复**。原实现要求整个光标矩形仍精确等于上帧
   绘制结果才整块恢复；游戏每帧只局部重绘 (动画/悬停高亮) 时校验必然失败 → 整块放弃 →
   未被覆盖的光标像素永久残留。改为只恢复"仍等于我们写入值"的像素:
   `scratch != SENTINEL 且 dst == scratch → dst = BKBUF`，被游戏碰过的像素一律不动。
   `grab_erase` 同步改为逐像素 (顺带修掉其 `8B DE`=`mov ebx,esi` 误作 `mov ebx,ebp`，
   正确为 `8B DD`，否则 BKBUF 行指针变垃圾)。

3. **标题菜单 hover/点击失效 (页面 wrapper 桩破坏 EAX)**。未提交的"字体半行距"改动在
   `build_page_wrapper` 的返回桩里加了 `mov eax,[0x755B08]; mov [eax+0x28],428`，没有保护
   EAX。标题循环是 `dword_4E8064 = sub_426164(...)`，返回值被覆盖成字体对象指针 (非零)，
   `if (dword_4E8064) break;` 首帧跳出标题状态机 → `word_4E8058=0`、菜单 `sub_425F3C`
   悬停/`sub_426004` 点击全不执行。桩内加 `push eax ... pop eax` 后，监控实测
   `hover` 索引随鼠标在 1/2 间切换、点击后 `a1[461]` 由 0→10 (进入新游戏流程)。

输入映射复核 (本次确认正确，无需改动): FormMouseMove/MouseDown 钩子把 raw 存 `[0x824278]`，
同步 `PAGE_X=clamp(raw-108,0,639)`；页面态读点已重定向到 `PAGE_X`/`PAGE_REC_X`。实测
鼠标 (495,360) → `PAGE_X=387` (=495-108)，`hover` 与点击记录均正确。

验证: GUI/CLI + cnc-ddraw 实机 — 光标快扫无拖影、标题三项可 hover/点击、
`patch.json` 的 cave_code/cave_entries 与 `cave_code.py` 重生成结果逐字节一致。

### 16:9 菜单字体错位根因与修复 (2026-09-11 深夜)

现象: 进入游戏后各菜单页 (含存档页) 字体大小/位置错误, 部分文字在 +108 处重复。

### 16:9 地图/战斗精灵网格碎片根因与全量修复 (2026-09-12)

现象: 大地图主角移动形象呈"网格长条碎片"。

根因: 绘制原语 (4544EC..45B20C) 的 JVG RLE 解码是**沿 640 宽平面的反向线性扫描**
(`sub_4544EC` 0x45460A: 目标指针 `dst+2*(Y*640+X)`, 之后逐像素 `sub [ptr],2` 左移,
跨行靠 640 平面内存连续隐式回绕)。屏幕加宽到 856 后只改进位常量会让 x=0 再减 2
落到上一行 x=855, 而 RLE 流期望 x=639 → 每行漂 216px, 即网格碎片。常量替换无法消除,
必须像 TKSRemake 那样"先解码进 640 平面缓冲, 再按真实 stride blit"。

修复 (v4): 18 个原语统一入口加壳, 每函数一个极简跳板 (`pop fn+5` → 执行原序言 →
`jmp` 共享入口), 共享入口:
1. 保存 `ret/obj/X/Y/frame/dst` (18 个原语 ABI 一致: a5=[ebp+0x18]=dst);
2. `sprite_prep` 读帧几何 (V1/inner/fd), 取锚点 `X0=max(0,w-1-xMax)`/`Y0` 保证整帧
   落在 640x480 平面内, 并把帧矩形填哨兵色;
3. 把 [ebp+0xC/0x10/0x18] 换成 (X0,Y0, 独立 640 平面), `g_stride/g_end` 临时切 640,
   用"替换 [ebp+4] 为共享 after"的方式跑原函数体 (序言已执行);
4. after 恢复原 stride/end, 调 `sprite_blit` 按真实 stride 把帧矩形写回原 dst
   (哨兵透明), 再 `jmp [ret]`。

要点: ① 独立平面 (SPR_SCRATCH) 与光标 scratch 分开, 否则地图上精灵解码会踩掉
光标上一帧解码、导致光标擦除失效 (拖影复现); ② `454D90/4553A4` 会回调 `4544EC`,
用深度计数器 (SPR_DEP) 让嵌套调用走原路径; ③ 几何非法时回退原路径 (不重定向),
行为与补丁前一致, 不崩; ④ `cursor_scratch` 内部调用 `4544EC` 前置 SPR_BYP 旁路。
⑤ cave 总量 3497 → 超 8192 预算, `cave_total_size` 提到 16384。

验证: 456/456 位点写入, 游戏启动/心跳正常, 深度计数归零 (嵌套平衡)。

#### 修正: 锚点公式与 454944 误加壳 (主角地图行走图)

1. **锚点错误**: 原体裁剪要求"右缘 `X=X0+xMax ≥ w`"才走完整 RLE 绘制分支, 否则进入
   贴边/部分绘制分支 (0x4546FC: 从 `X-w` 起, 按越界重新算源指针)。之前取
   `X0=max(0,w-1-xMax)` 使 `X=xMax=w-1 < w`, 恰好命中部分分支 → 主角解成虚线状碎片。
   正确: `X0=clamp(w-xMax, 0, 639-xMax)` (Y 同理 `h-yMax / 479-yMax`), 使
   `X ∈ [w,639]`, `Y ∈ [h,479]` 走完整分支, 左缘落在 scratch x=1。
   注: 光标走 BYP 旁路 (自管锚点 320,240), 不受此式影响。
2. **454944 不是屏幕渲染器**: 其唯一调用者 `sub_406864:118` 传的目标是
   `&word_78E276` (拾取缓冲), 即"拾取链", 不能按 856 步长回贴 (会写坏拾取缓冲)。
   已从外壳列表移除。主角由 `sub_406864:42 sub_4544EC(754814, X, Y, frame, a1, -1)`
   绘制, 走 4544EC 外壳。

     (`mov edx,[ecx+0x1C]` / `[ecx+0x20]` = obj[7]/obj[8])。
  3. 因此失效不在解码器, 而在"这些原语是 UI/菜单/图标/光标**共用**的" —— 整体替换
     波及了所有调用方。

**v7 做法**: 不动 18 个原语, 只在 `sub_406864` 的 **10 个实体绘制 call 位点**把目标
改成 cave 处理器 (每点一条跳板, 把模式号放进 edx):

| call 位点 | 原目标 | 模式 |
| --- | --- | --- |
| 0x4069B7 / 0x406AB9 | 458020 (影子 / d24=3) | 3 减法 |
| 0x406A10 | 4544EC | 0 不透明 |
| 0x406A4A | 454D24 | 1 alpha |
| 0x406A86 | 4559D0 | 2 加法 |
| 0x406AE7 | 459168 | 4 灰度 alpha |
| 0x406B16 | 458D08 | 5 灰度写入 |
| 0x406BA3 / 0x406C76 | 45AA08 (遮挡影子 / d24=3) | 7 遮挡减法 |
| 0x406C19 | 459EF4 | 6 遮挡不透明 |

处理器分流 `entity_only=True`: 这些位点最后一参恒为 -1, 直接走 `blk[60]` 层索引,
不再按模式猜 flag 栈偏移 (v6 的隐患之一)。遮挡 wx/wy/depth 仍在 [ebp+0x1C/0x20/0x24]。
UI/菜单/物品图标/光标继续走原版混合, 零改动、零回归。位点 expect 为现场取的真实
E8 5 字节, 与镜像逐一相符; 448 位点解析全通过、无重叠; cave 3797B。

**注意**: 位点 `rva` 必须是 `VA - 0x400000` (0x406A10 → `0x6a10`), v6 曾误写完整 VA
导致整补丁中止 (表现为 16:9 消失)。

**跳板 pop 层数 (实测读档进图崩溃的根因)**: 挂"函数入口"时栈上是
`[fn+5][调用者 ret][args]`, 跳板必须 `pop eax` 丢掉 fn+5; 挂"调用点"时栈上
**只有一层返回地址** `[调用者 ret][args]`, 跳板再 pop 会把第一个参数 obj 弹掉,
参数表整体左移一位 (obj 读到 X, reader 变野指针) → 读档进图崩溃。故 `build_block`
新增 `pop_ret` 开关: 实体调用点用 `pop_ret=False` (跳板 10 字节 `BA mode E9 rel32`,
无 pop), 原语入口用 `pop_ret=True`。

**防崩溃护栏**: 处理器增加 obj != 0、g_stride ∈ (0,4096]、遮挡模式 mb != 0
且 `0 < mw <= 0x10000` 的前置检查, 任一不满足直接跳过绘制。

**"只有影子、身体不显示"根因 (2026-09-12 实测)**: 之前照 TKSRemake 加了
`row<h && col<w` 的像素过滤, 但**原版全量分支根本不做该判断** —— 它按 640 线性
回绕行走, 会画到 w×h 窗口之外。真实帧里存在这类像素, 于是身体被成片过滤掉,
只剩影子 (影子帧小、恰好都在窗口内)。已删除该过滤; 同时 `fx/fy` 计算必须显式
装载 row/col (删过滤时误带掉了 `ld(0,L_ROW)`/`ld(1,L_COL)`, 导致 fx/fy 取到脏寄存器,
已在测试中暴露并修正)。修正后**与原版全量分支在一致/任意 RLE 下都逐字节一致**
(mode0 4544EC、mode3 458130, diff=0)。

**w/h 不再做合法性判断**: 原版全量分支不使用 w/h 做像素定位, 加 `0<w,h<=4096`
会把某些真实帧整帧跳过, 故移除 (防崩只保留指针类护栏)。

### 16:9 菜单 hover 花屏根因: 4 个 memcpy 位点被错误改道 (2026-09-12 深夜)

### 三、经验教训

1. **禁止臆测, 读现场.** 本环境无法启动图形程序, 但可用 ReadProcessMemory 取解包镜像/抓帧,
   配合反编译与反汇编对照. 之前凭推断做的方案 (原语整体加壳、PAGE_MODE 光标步长) 都造成回归;
   凡"读现场"的结论 (真实函数差分、调用点参数、抓帧) 才成立.
2. **老代码普遍"窄值塞宽槽".** 调用点用 `mov ax/cx/al` 取值后整体压栈, 高 16 位是残留;
   被调函数只读 word/byte. 已确认三类: 帧号(16 位有符号)、alpha(16 位)、遮挡深度(8 位).
   凡是"按 dword 读参数"的地方都要先核原版宽度.
3. **改道/挂钩前必须核对"调用方"实参语义.** 菜单花屏根因: 补丁把按"856 屏幕源"写的 grab_copy
   挂到了 4 个"640 页画布->备份画布"的拷贝上 —— 同名形参 `Src` 在不同函数里含义相反.
4. **等长改写要验指令边界.** 优化后的算式常量常非独立立即数 (如 `34*v+1` 是 shl/add/inc 多段),
   需用等长序列等价改写 (imul/nop/add imm), 并确认前后指令边界不错位 (v11 的写法见上).
5. **位点 `rva` = VA - 0x400000.** 误写完整 VA 会让整个补丁静默失败 (表现为"16:9 消失").
6. **改一处、验一处, 不顺带.** "顺手"改光标步长直接弄坏了两个场景的光标; 未确证的改动一律回退.
7. **区分"未适配"与"改坏了".** 战斗单位未挂钩、幕帘未居中、淡变计数、菜单热区属功能缺口;
   由自己改动引起的属于回归, 必须立即回退再定位.
8. **固定长度补丁 + 全量 expect 校验 + 无重叠**是硬约束; 每次改完都要跑
   cave 同步 / 解析 / 去重 / schema / 仿真, 再交给用户做视觉验收.

### 结算页背景"拉伸+右侧裁切"根因：GXP 表面从未加宽（2026-09-13）

对截图做像素级测量（856x480）：

- 修序后黑边正确，但背景仍呈"拉伸 + 右侧被裁"：原图竖直分隔线在 `x=412`，
  截图中在 `x=661`。`412+108 = 520`（1:1 应为 520），而 `108 + 412*1.3375 = 661`
  → **背景被整幅拉伸 640→856（1.3375 倍），因此右 25% 落到画面外。**

根因：`gxp_pad_decide` / `gxp_upload` 两个 cave 虽然一直存在于 `cave_code.py`，
但**在全部历史提交中都没有任何位点引用它们**（dead code）。因此全屏 640x480 的
GXP 表面仍按 640 宽创建，而每帧的 `Blt(后备[856], 0, 背景[640], 0, 0, 0)`
两矩形为 NULL → cnc-ddraw 按整面拉伸到 856。

本轮把这两个 cave 真正接上（并修正其自身的两处缺陷）：

- `gxp_pad_decide`（hook RVA 0x50397，`mov [ebp-0x90],edx`，6B）：补回原指令后，
  若 `ddsd.dwWidth==640 && ddsd.dwHeight==480` 则把 dwWidth 改为 856 并置
  `g_pad=1`；否则 `g_pad=0`。`ret` 回到 site+5 继续原流程。

  参数且退出前不清理，`ret` 会跳到参数值（必然崩），这也是它从未被接上的原因。

### 小游戏文字：画布宽 vs 换行边界是两个字段（2026-09-14）

### 文字位移 wrapper 的 MOV/ADD 编码错误（2026-09-14）

小游戏页所有文字仍挤在左侧 ~x=108 处。逐字节核对 wrapper：

```python
b'\xC7\x44\x24\x0C' + imm32   # C7 /0 = MOV  dword [esp+0xC], 108
b'\xB8' + 0x44E49C + b'\xFF\xE0'
```

注释写的是 "add dword [esp+0xC],108"，但 `C7` 是 **MOV**：不是把文本 X 加 108，
而是**直接把 X 覆盖成 108**。所有挂了该 wrapper 的文本因此全被挤到 x=108 附近 ——
这正是实测现象（帮助文本、下注金額、100兩、關寶全部落在 x≈108~118）。

同一处错误也存在于 `build_text_shift_a2`（结算页右对齐/页码 wrapper），这也是当初
"结算页内容被挤在一起"的一个原因。

修复（等长，5→8 字节不变）：

```python
C7 44 24 0C imm32   ->   81 44 24 0C imm32     # mg_text_shift   (x=[esp+0xC])
C7 44 24 08 imm32   ->   81 44 24 08 imm32     # text_shift_a2   (x=[esp+8])
```

反汇编确认：`add dword ptr [esp + 0xc], 0x6c`。

回归测试：`tests/test_widescreen_context.py::TextShiftWrapperTests`。

### 拾取链 (实体/出入口命中) 与 856 画布的坐标一致化 (2026-09-14)

用户实测两点: ① 鼠标在出入点区域内移动会闪烁 (手型↔常规来回切); ② 部分实体
(洛阳市集 #780) 原版可对话, 打补丁后鼠标移上去没反应。逐条反查确认是**两处独立
成因**, 都在"实体命中"这条链上。

**成因 A: 拾取缓冲只覆盖屏幕 x<640, 而实体整体右移了 108**

- `sub_406864` (地图实体渲染) 以屏幕坐标 `X = obj.worldX - 8242A8` 写拾取缓冲
  `word_78E276` (经 `sub_454944`, 内部硬编码 640 平面裁剪/行距), 鼠标侧
  `sub_410B74` 用 `[0x824278]` 读同一缓冲 (索引 `Y*640 + X`);
- 856 画布下视口原点 `8242A8` 左移 108 (actorX-428 而非 -320) → 实体屏幕坐标
  整体 +108, 于是"原版可见区" (现在 x∈[108,748)) 的实体一旦落到 x≥640 就
  **没有写进缓冲**;
- 读侧又把 X 钳到 639 (旧 MG_MAP) → 读到边缘列里**别的实体 id / -1** → 悬停状态
  随之跳变 (闪烁)、点不动。

洛阳市集 #780 正是 x≥640 的情形: 原版它落在 x∈[532,640) 可见可点, 加宽后被推出
缓冲范围 (文档已知局限⑥ "x≥640 单位不可拾取" 的真实表现)。

**成因 B: 相机 cave 重建视口后没有同步鼠标世界坐标**

- 原版 `sub_406CE0` 只在 `a1[1] == 当前场景` 守卫成立时才写 `824280/824284`

### 16:9 硬编码 640/480 全面排查 (2026-09-14, 用户要求)

**方法**（三层, 兼顾"别漏"与"别瞎报"）:

1. **指令级立即数扫描**: capstone 解码后只统计**立即数操作数**（含 66 前缀 16 位形式）,
   排除"某条 4 字节位移/数据恰好等于 0x280"这类假阳性 —— 上一版纯字节搜索就吃过这个亏;
2. 按函数归类, 再与 `patch.json` 位点区间求交 → 得出"已挂 / 未挂";
3. **结构孪生比对**: 绘制原语族 (`0x544EC..0x5B20C`, 87 个函数) 内裁剪结构相同的孪生体
   （定点间距, 如 45AA8C 与 45B20C 相差 `0x780`）必须拥有**同一组**位点。这一步能抓出
   "非 640 立即数"的漏项, 例如 `add eax,0x95b00`（= 479×1280, 640 平面末行偏移）。

**结果**（"未挂" = 该立即数未被任何位点覆盖）:

| 常量 | 立即数引用 | 已挂 | 未挂 | 判定 |
| --- | --- | --- | --- | --- |
| 640 = 屏宽 | 245 | 218 | 27 | 10 处 = 拾取写原语 `454944`（**640 平面, 设计如此**）; 8 处 = `45B20C`（**本轮补齐**）; 其余为位移/数据假阳性与库函数 |
| 639 | 3 | 1 | 2 | 位移假阳性（`46451C` / `4A1FA0` 属库/数据） |
| 320 = 半宽 | 18 | 3 | 15 | 3 处已挂（字幕 `40B2D0`、地图阈值 `411308`、战场 `42FA50`）; 2 处为库内图像宽 (`471500`); 13 处结构体偏移假阳性 |
| 480 / 479 = 屏高 | 99 | 4 | 95 | **高度不变, 全部合法**（裁剪/边界） |
| 1280 = 640×2 行距 | 42 | 3 | 39 | 3 处已挂（天气 `405744`）; 1 处库内图宽 (`4B0987`); 38 处位移/数据假阳性 |
| 614400 = 640×480×2 | 25 | 0 | 25 | 1 = 拾取缓冲清零（**640 平面, 设计如此**）; 24 = **页画布**（640×480 内嵌画布, 其"画布<->屏幕"拷贝已由 `push_copy`/`grab_copy` 居中） |
| 307200 = 640×480 | 2 | 1 | 1 | 已挂 = 淡变像素数; 未挂 = 数据区字符串 |
| `add …,0x95B00` = 479×1280 | 20 | 19 | 1 | 未挂 = `454944`（640 平面）; 其余 19 处已挂 `blit_end_eax` |
| `dword_4E7CC8` 视口宽（.data 初值） | — | 1 | 0 | 初值 640→**856**; 该全局**只被读**（24 处）无写入 → 全链一致 |
| `dword_4E7CCC` 视口高（.data） | — | 0 | 0 | 480 不变 ✓ |
| 16 位（66 前缀）640/480/320/639 | 0 | — | — | 二进制里不存在 |

**本轮唯一实修: `sub_45B20C` 孪生补齐（9 处）**

45AA8C 与 45B20C 是同一裁剪结构的孪生绘制原语, 但 45B20C 只挂了 5/14 个位点 —— 它在
856 画布上仍按 640 换行/裁剪, 走它的精灵会逐行漂 216px:

```
0x5B417 / 0x5B781 / 0x5B7B6 / 0x5B7FF   cmp edx,640      -> cmp edx,[g_stride]  (4 处)
0x5B5EA / 0x5B725                        cmp eax,640      -> blit_cmp_eax_w 钩子 (2 处)
0x5B6FA / 0x5B78B                        add [ebp+0xc],640-> blit_wrap_add  钩子 (2 处)
0x5B630                                  add eax,0x95b00  -> blit_end_eax    钩子 (1 处, 非 640)
```

补齐后孪生组 `45AA8C↔45B20C` 与其余 4 组（`456720↔4573A0`, `456D50↔4579D0`,
`458130↔45871C`, `459F78↔45A4C0`）全部 **0 不一致**。

**顺带修正**: 23 个位点的 tag 把 856 误写成 "854"（实际 repl 字节一直是
`58 03 00 00` = 856, 只有注释错）, 已统一为 856 / `y*g_stride`, 避免下一轮照错注释排查。

**验证**: 796 位点 expect 对原版 exe 全对（PE 节区映射逐条读取）; 无重复 RVA、列表按
RVA 升序; 427 个 `call` 位点 rel32 全部落在各自 cave 入口; 41 项测试通过（新增
`PrimitiveTwinCoverageTests`）。位点 787 → 796, cave 7689 字节不变。

### 出入点/实体命中: 修复"边带短路"跳过 bbox 兜底 (2026-09-14, 用户反馈)

用户实测: 洛阳市集**最右侧的出入点**鼠标移上去没有悬停效果 (原版有)。

**根因**: 上一轮为"856 屏幕左右边带没有拾取缓冲内容"加的守卫, 把整个拾取读函数
`sub_410B74` 在**入口** (`call sub_410B74`) 直接短路成 -1 —— 但该函数的 bbox 兜底是
**函数内部** a1==2 分支的一部分, 入口短路把它一起跳过了:

```
v4 = word_78E276[640*Y + X];                 // 缓冲里的实体 id
if (a1 == 2) {
  for (i = 可见实体列表; ...) {
    if (list[i] == v4) return list[i];                       // ← 缓冲命中
    if (!v7[9] && (1 & flags) && (4 & flags)                 // ← bbox 兜底
        && bbox 含鼠标世界坐标 && 掩码匹配) return list[i];
  }
}
```

于是边带区域既没有缓冲命中、又拿不到兜底 → 出入点/实体没有悬停 (手型) 与提示文字。

**修复**: 把守卫从"读函数入口"移到**缓冲读取指令本身** (RVA 0x10BAF, 8B:
`movsx edx, word ptr [edx*2 + 0x78E276]`): 边带 (raw-108 ∉ [0,640)) 只把**读出来的
id** 换成 -1 (真实实体 id 恒 >= 0, 永不命中), 原函数继续执行后续的
"id 命中可见列表 / 逐实体 bbox + 标志 + 掩码" 判定 —— 与原版"缓冲没命中时"的行为
完全一致。中心区仍按原指令读缓冲 (与原版逐列等价)。

关键吻合: 实体渲染**写**缓冲的条件 (`flags & 1 && flags & 4`) 与 bbox 兜底的条件
(`dword_4E7138 = 1` / `dword_4E7140 = 4` 两个标志位) **是同一组位**, 所以凡是被写进
缓冲的实体都能通过 bbox 兜底被找到 —— 这正是"有像素但落在 640 视图之外"的出入点
所需要的路径。

**验证**: 796 位点 expect 对原版 exe 全对; 新位点 `0x10BAF → E8 rel32 + 3×NOP`
(8B 等长, 返回地址 = site+8); 427 个 `call` 位点 rel32 全部落在各自 cave 入口;
41 项测试通过 (`PickupMappingTests` 新增"不得再出现读函数入口短路位点"断言)。
位点 796 (净 0: -0x123A2 +0x10BAF), cave 7689 → 7717 字节。

### HWND 全面扫描: 工具提示方形底色的真因与修复 (2026-09-14, 用户要求)

用户反馈"提示框还有 HWND 的矩形背景 + 换行不一致"。前者一路查下来, 真因与最初
判断不同, 记录完整证据链。

**项目里其实有三套圆角机制** (扫描时才理清):

| 机制 | 位置 | 作用对象 | 实测效果 |
| --- | --- | --- | --- |
| QSS `border-radius` | `editor_themes/templates/base.qss.tpl` | 所有控件 (含弹层) | 只裁剪"边框/背景绘制", **不裁剪窗口本身** |
| DWM 角偏好 | `ui_helpers._round_popup_win11_corners` | `Qt.Popup` (+ 本次补的 ToolTip) | 系统抗锯齿圆角, `DWMWCP_ROUND(2)` ≈ 8px |
| 原生窗口 region | `combo_box._apply_rounded_window_region` (SetWindowRgn) | RoundedComboMenu / EditorComboListPopup | 硬裁剪, RADIUS=8 |

**扫描方法** (运行时, 非读代码): 真建出项目里每一类顶层窗口, 读它的 HWND 真实状态 ——
`DwmGetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` + `GetWindowRgn`/`PtInRegion`
(逐像素量出角被裁几 px) + `WA_TranslucentBackground`:

| 窗口 | winType | 半透明 | DWM 角 | 窗口 shape | QSS 圆角 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| QToolTip | 13 ToolTip | 否 | ROUNDSMALL(3) → **ROUND(2)** | **region 裁 1px** → **无 region** | 8px | ❌→✅ 本次修复 |
| QMenu 菜单 | 9 Popup | 否 | ROUND(2) | 无 region | 8px | ✅ 一致 |
| EditorComboListPopup | 9 Popup | 否 | ROUND(2) | region 裁 7px | 8px | ✅ 一致 |
| QComboBox 内建弹层 | 9 Popup | 否 | ROUND(2) | 无 region | 8px | ✅ 一致 |
| 浮动 QDockWidget | 11 Tool | 否 | ROUND(2) | 无 region | — | ✅ 无圆角需求 |
| QMessageBox / QDialog / QMainWindow | 3/3/1 | 否 | ROUND(2) | 无 region | — | ✅ 原生边框 |
| GameOverlay (游戏内提示) | 11 Tool | **是** | DEFAULT | 无 region | 自绘 6px | ✅ 透明窗自绘, 无需系统圆角 |

**真因 (与首轮判断不同, 以实测为准)**:

- Qt 给 tooltip 设了 `SH_ToolTip_Mask` 窗口遮罩, **实测只裁 1px**;
- 而 QSS 画的是 radius_md=**8px** 圆角 → 8px 描边被 1px 遮罩切断,
  **圆角之外那圈方形填充色露出来** —— 这才是"矩形背景";
- 关键: **窗口 region 的优先级高于 DWM 圆角**。只把角偏好设成 ROUND(2) 时,
  region 仍是 1px → 仍然无效 (实测: DWM=2 且 region 裁 1px)。首轮只改 DWM 的版本
  因此**没有真正解决问题**, 必须同时清掉遮罩。

**修复** (`ui_helpers._shape_tooltip_window`, 由全局过滤器在 Show/Resize 调用):

1. `tip.clearMask()` 清掉 Qt 的 1px 遮罩;
2. 延迟一拍 (`QTimer.singleShot(0)`) 再执行 —— Qt 的处理在过滤器之后, 同步清会被
   覆盖 (实测同步 clearMask 后 processEvents 遮罩又回来);
3. 设 DWM `ROUND(2)` —— 清掉遮罩后由系统接管, tooltip 与 QMenu **完全同形态**
   (无 region + DWM ROUND)。

Show 与 Resize **都要做**: Qt 在 Resize 里会重设遮罩。实测三段:
`显示后=无region ✓ → resize 后=有region(裁1px) ✗ → 过事件循环=无region ✓`。

**修复前后对照 (两个独立进程实测)**:

```
未装过滤器(修复前): region=有 region, 顶部裁 1px   DWM角=ROUNDSMALL
装了过滤器(修复后): region=无 region (整窗, 交给系统) DWM角=ROUND
```

**换行问题** (同一轮修复): Qt tooltip 只在文本宽度超过"屏幕宽度一定比例"时才软换行
(实测 800px 屏阈值约 496px) → 屏幕越宽越不容易换行, 133 字的说明一条到底, 228 字的
反而换行。改为 `ui_helpers.wrap_tooltip_text()` 按固定 480px 预换行, 补丁表/模组表
两处 tooltip 接入。

**扫描结论**: 除工具提示外, **未发现其它 HWND 圆角/遮罩问题** —— 其余顶层窗口的
系统圆角(ROUND≈8px)与 QSS radius_md(8px) 一致, 或本就半透明/无圆角需求。
遗留取舍 (未改, 记录备查): Win10 无 `DWMWA_WINDOW_CORNER_PREFERENCE`, 上述弹层会退化为
"方窗 + 圆角描边" (与项目既有取舍一致); 只有走 SetWindowRgn 的 EditorComboListPopup
在 Win10 上也正常。

**验证**: `tests/test_tooltip_popup.py` 9 项 (含 DWM 覆盖类型、Resize 重清、换行宽度、
启动器最长说明已换行); 启动器 53 项单测通过; `tests/test_editor_smoke` 5 项通过
(18 个 GUI 入口 × 4 主题, 因改动落在共享 `ui_helpers`)。

### 战场血条贴在屏幕边缘 (单位滚出后残留) 修复 (2026-09-15, 用户反馈)

现象: 屏幕滚动时, 单位已经滚出屏幕上方, 血条却一直贴在屏幕顶边 (y=0) 不消失。

**根因**: cave 里 `y0 = sy-132` 之后带一条 `test eax,eax / jns +2 / xor eax,eax` —— 把负数
**钳到 0** (v4 手写版起就有, v6 构建器照搬)。于是只要 `sy < 132`, 血条就被画在第 0 行;
而**下方**边界用的是无符号 `ja`, 所以只有"向下出屏"会消失, "向上出屏"会永久残留在顶边
(单位滚到 sy=-500 照样在画)。

**同源对照 (关键线索)**: `war_status_icons` 的 ytop 判定本来是无符号越界
(`cmp edx,0x1A3; ja`) —— `ytop<0` 直接被无符号比较挡掉, 图标会正常消失; 只有血条因为多

### 武器附加状态修复: 根因不在 cave, 而在"装备重算把掩码赋值了" (2026-09-15, 用户反馈)

**现象**: 角色只装备带状态的武器时, 普攻能附加该状态; 一旦再装备衣服或饰品, 普攻再也不附加。

**根因 (原版 `sub_42234C` 装备重算@0x42234C)**: 它遍历 4 个装备槽 (单位记录字偏移 69..72 =
字节 0x8A..0x90), 对每个**非空**槽取该装备 TKItem 的字 26/27 (cause_mask 低/高, 字节 52/54),
写进单位记录字偏移 67/68 (字节 0x86/0x88):

```
 42263f  66 8b 41 34        mov ax, [ecx+0x34]      ; TKItem.cause_mask1
 422643  66 89 82 86 00..  mov [edx+0x86], ax      ; ★ 赋值 (本应是 or)
 422650  66 8b 41 36        mov ax, [ecx+0x36]      ; TKItem.cause_mask2
 422654  66 89 82 88 00..  mov [edx+0x88], ax      ; ★ 赋值 (本应是 or)
 42265b  66 ff 45 fc        inc word [ebp-4]        ; 下一个槽
```

循环入口前 `42244e/42245a` 已把这两个字清零, 说明设计意图就是"各槽累加";
结果写成赋值 → **最后一个非空槽覆盖前面所有槽**: 单武器 → 掩码 = 武器;
再装衣服/饰品 → 武器掩码被覆盖成它们自己的 (通常 0) → 普攻带不出武器状态。

**消费点证据 (普攻命中附加状态在哪读这两个字)** — `sub_4400DC` @0x441C08~0x441C5B:

```
 441c08  66 83 7d 08 00           cmp word [ebp+8], 0        ; 攻击者有效?
 441c0d  7c 54                    jl  441c63
 441c0f  66 83 3d 7c 6c 9d 00 ff  cmp word [0x9d6c7c], -1     ; 仅普通攻击
 441c17  75 4a                    jne 441c63
 441c2f  66 8b 14 45 02 71 9d 00  mov dx, [eax*2+0x9d7102]    ; 单位字 68 = cause2
 441c48  66 8b 14 45 00 71 9d 00  mov dx, [eax*2+0x9d7100]    ; 单位字 67 = cause1
 441c5b  e8 20 24 ff ff           call sub_434080            ; 状态入队
```

`word_9D7100/9D7102` = 战斗单位数组 (0x9D707A) + 0x86/0x88 —— **正是 sub_42234C 写的那两个字**。
`sub_434080` 里 `if (a6+a5+a4+a3)` 四个掩码全 0 时直接不入队, 所以被覆盖成 0 时连队列都进不去。

**旧 cave 为何治不了**: 旧 `weapon_cause_mask_hook` (hook 0x4400F6) 是把武器掩码 OR 进
`word_9D6C3C/0x9D6C3E` —— 那是 sub_4400DC 开头从 TKKon 复制来的"本次攻击参数块", 只被
AI 评估 (`43E980`, 经 `4359A4`) 与函数尾部目标循环 (@442A77) 使用, 与普攻命中附加状态
(0x441C5B 读单位 67/68) **不是同一条链路**; 而且该 cave 用"战斗单位号"索引持久 WarPC 数组
0x757F08, 而战斗记录 0x9D707A 是 `qmemcpy` 自 `WarPC[队伍槽+35]` (见 4307CC.c:227 前一段),
两者索引并不相同 → 实际读到的是别人的记录, 既治不了根因, 还可能带上别的角色的武器状态。

**修复** (`patches/weapon_cause_mask_hook/patch.json`, 由 cave_hook 改为 patch_bytes):

| 项 | 值 |
| --- | --- |
| pattern | `66 89 82 86 00 00 00 8B 4D F8 8B 55 0C 66 8B 41 36 66 89 82 88 00 00 00` (24B, 含相邻取值指令) |
| expect_count | 1 (原版 exe 唯一命中: 文件 0x22043 = RVA 0x22643) |
| replace | `{"1": "09", "18": "09"}` → 两条 `mov` (opcode 89) 变 `or` (opcode 09) |

等长替换、只改 opcode: 各装备槽 cause_mask 取并集。单武器行为与原版逐字节一致;
武器+衣服/饰品恢复正常。旧 cave 及其 `cave_code.py` 一并撤除 (该补丁本就是必选)。

**验证** (`tests/test_weapon_cause_mask_fix.py`, 6 项, 全部通过):

1. 定义自检: 类型已改为 patch_bytes、无 cave/hook、旧 `cave_code.py` 已移除、replace 指向
   两条目标指令的 opcode。
2. 模式解码: 两条指令确为 `mov word [edx+0x86],ax` / `mov word [edx+0x88],ax`; 改后变成
   同操作数的 `or`, 其余指令逐条不变。
3. **消费点证据链**: 在 exe 上唯一命中普攻守卫 (0x441C08)、读单位字 67/68 (0x441C2F/0x441C48)、

   并断言 `0x9D707A+0x86 == 0x9D7100` (消费点读的就是被写的那两个字)。
4. 语义模型: 复刻槽循环, 断言"单武器修前修后一致"; "武器+衣服"修前丢失、修后保留;
   "武器+饰品"修后为并集; 空槽/顺序无关。
5. 离线烧录实测: 全文件仅 2 字节变化 (RVA 0x22644 / 0x22655, 0x89 → 0x09)。
6. 与全部现有补丁写入区间零重叠 (含宽屏补丁 796 个 patch_sites 位点与多模式补丁)。
