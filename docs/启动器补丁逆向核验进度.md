## 一、引擎级缺陷（最高优先级）

### 1.1 exe_builder 写 E9 jmp，与 cave 代码的 E8 CALL 约定不兼容 【生成启动器产物必坏】

- `core/exe_builder.py:912` 统一写 `E9 rel32`（jmp）；而 `core/patch_engine.py:855/1050`（运行时）统一写 `E8 rel32`（call）。
- **全部 22 个 cave_hook 补丁的 cave 代码按 E8 约定编写**：入口读 `[esp+4]`/`[esp+0x20]`（exp_lock）、结尾 `ret` / `add dword[esp],N; ret`（war_status_icons、trap 两补丁）/ `xchg [esp],eax; jmp`（portrait）等。E9 下无返回地址入栈 → `ret` 弹出垃圾、栈槽映射全错 → 崩溃或随机写内存（如 exp_lock 的 `mov dword[eax],0`，eax 来自错误栈槽）。
- **summon_extend cave3（alloc）** 以 `mov [esp],esi` 复用 E8 返回地址槽、精确复刻 `push esi; push edi` 后的栈布局（[esp+8]=调用者返回地址）——E9 下该写法覆写调用者活跃栈/local（[ebp-8..ebp-5]，含刚写入的 v5/v6）→ 栈损坏。
- 反向例外：summon_extend cave1/2/4（pushad…popad + E9 跳回）与 capacity cave 在 E9 下"栈恰好正确"，但 capacity 在运行时 E8 下有 esp−4 漂移（见 1.3）。
- **修复**：exe_builder 改写 E8 CALL + NOP 填充（与 patch_engine 对齐）。文档 `生成启动器功能实现.md` 的"jmp hook"表述需一并更正。
- 附带：`CavePatchItem` **无 hook_offset 字段**，`generate_exe_dialog.py:336-343` 不传 → awk_sprite_cave3/4（json 声明 `hook_offset: 2`）在生成的 exe 中 hook 写在 `EB 05`（jmp +5）指令上，破坏指令边界与 ==36 特判分支 → 必崩。exe_builder 需补 hook_offset 支持。

### 1.2 summon_extend clear hook 入口错位 16 字节 【运行时召唤物死亡必崩】

- `patch.json` clear 的 `cave_entry_offset: 1904`（0x770），但 `cave_code.py` 把 cave4 代码放在 `CAVE_4_OFFSET = 0x680 + 224 = 1888`（0x760）；docstring 自称 [0x770,0x7B0) 自相矛盾。
- 引擎按 entry 1904 发 E8/call → 落在 cave4 首指令 `0F B6 54 0E FF` 的第 2 字节 → `mov dh,0x54; push cs; …` 执行垃圾。clear 触发时机 = 召唤物死亡/移除（必经路径）。
- **修复**：patch.json entry 1904 → 1888（推荐；若改 CAVE_4_OFFSET=+240 则与 SLOTS_OFFSET=0x7A0 重叠，需连动改布局）。
- 已复核其余 4 个 entry（1664/1696/1744/1968）与常量一致。

### 1.3 summon_extend capacity cave 运行时 esp 漂移 【E8 约定下】

- capacity cave 结尾 `popad; jae/E9 跳回`，不消费 E8 压入的返回地址 → 回到 0x44558E 时 esp = 原值 −4。
- 续接点 `8D 54 24 04`（lea edx,[esp+4]）为 **esp 相对寻址**（sub_445564 是 esp 帧函数，`83 C4 E8` 无 ebp）→ 局部缓冲地址整体错 4 字节，后续 call 收到错误指针。
- 对照：cave1/2/4 续接点（0x436C7B `push×3+call+add esp,0xC`、0x444C1B、0x43C768 `mov [ebp-2]`）为 push/pop 对称或 ebp 相对，且宿主函数 436BD4/444BB0/43C734 为 ebp 帧（`55 8B EC`）→ 漂移在该处无害（侥幸设计）。cave3 显式复用返回地址槽、精确平衡。
- **修复**：capacity cave 结尾改为消费返回地址（如 `mov [esp+0x1C],eax` 写 pushad 的 EAX 槽后 popad + `ret` 回 0x445589，或在 cave 内对 4 个出口统一 `add esp,4` 后跳回）。需实测验证。

### 1.4 exp_lock fallback_rva 口径错误 【潜伏】

- json `fallback_rva: "0x43BAF3"` 是 VA 口径（正确 RVA = 0x3BAF3，与注释、模式命中一致）；其余全部补丁的 fallback_rva 均为 RVA 口径。
- 运行时（patch_engine.py:1543 `fb_off = fallback_rva − 0x1000`）→ 0x43AAF3 越界 → 回退保护失效（跳过）；exe_builder 路径 `rva_to_offset(0x43BAF3)` 落入 .data 区间 → 静默错改。当前模式必命中故为潜伏缺陷。
- **修复**：改为 `0x3BAF3`。

## 二、补丁逻辑遗漏（运行时行为问题）

### 2.1 summon_exp_jp_accumulation_fix — 遗漏个人经验越界写

- 已验证：门槛 0x441832 movsx / 0x441839 cmp 0x64 / 0x44183C jnz；召唤物阵营 20（431094.c:53）；cave 恰为 20 映射 100；43B7FC 分配循环上界 byte_9DF886 ≤6 确不含召唤物——注释此部分全部属实。
- **遗漏**：放行后奖励块 0x4418FF `add dword_9D6F20[ecx*4],eax`（个人经验，ecx=movsx arg_0）对召唤槽 ≥6 越界写：槽 6-11 落入 dword_9D6F38（队员个人 JP 战斗累计器 → 经 43B7FC.c:105/134 `v18[26]+=*v20` 变永久 JP 污染），槽 ≥12 落入 unk_9D6F50 升级旗标等。trap_exp_jp_personal_fix 只处理 arg_0==−1，不覆盖 ≥6。
- **修复方向**：本补丁 cave 需同时处理 0x4418FF（召唤槽直接跳过该条写入）。

### 2.2 tkkon_expand — 遗漏 0x9D069E 基址+6 引用

- 19 处 0x9D0698 引用全部核实为真 TKKon 表引用；old_size 26000=40×650 正确（40 字节记录由 `rep movsd`×10 实锤）。
- **遗漏**：4434BC.c:67 `word_9D069E[20*i]` 编码为 `movsx eax, word [ecx*8+0x9D069E]` @0x443544（disp32 = 基址+6）——精确基址替换改不到。重定向后该处读 BSS（0）→ TKAct[0]，若内存呈 0xFF 则 movsx=−1 → `784×(−1)+新基址` 越界拷贝。此为 WarPC→TKKon→TKAct 主战斗动画查找链（常态分支）。
- **修复**：追加对 0x9D069E 的重定向（或按 warpc_expander 的字段启发式处理该处）。

### 2.3 warpc_base_refs — 生成 exe 路径缺字段锚定引用处理

- 已验证：29 处基址 + 5 处大小引用全数核实；**存档 150722 引用安全**（malloc 尺寸由 0xD68+0x1688+0x24CC2 三栈变量运行时相加，改 0x24CC2 后自动跟随，旧存档读档按存档内尺寸，无溢出）——这是本批最高风险点的排除结论。
- **遗漏（仅 exe_builder 路径）**：只精确替换 0x757F08/0x24CC2，改不到 `word_757F0C` 等 ~24 个函数的字段锚定引用（WarPC 记录内偏移 2/4 的绝对地址全局量）。运行时由 `warpc_expander.py:264-315`（base+4 修补 + [base, base+1054) 扫描 + `75 00` 标记启发式）兜底；exe_builder 无等价逻辑 → 独立 exe 中这些引用读 BSS 零。
- **修复**：exe_builder 复刻 warpc_expander 的字段扫描（tkkon_expand 的 0x9D069E 同理可由此机制覆盖）。
