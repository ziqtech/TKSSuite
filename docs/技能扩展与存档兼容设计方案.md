# 技能扩展与存档兼容设计方案

> 整理日期：2026-09-16  
> 适用范围：TKSSuite 编辑器、原版 TKS 补丁、TKSRemake 重制版  
> 状态：基于源码与反编译的设计方案，尚未实现或完成实机扩容验证

## 一、结论与设计目标

### 1.1 推荐结论

推荐采用 **“保留原版二进制布局，外置新增技能的状态与效果映射”**，而不是扩大每条 WarPC 记录中的技能数组。

具体分离为三个层次：

1. **技能定义**：技能名称、类型、费用、关联技能、默认效果等，属于 MOD 资源。
2. **角色技能配置**：角色有哪些技能、初始学习状态、角色专属效果覆盖，属于角色模板资源。
3. **游戏进度**：玩家实际学习状态、装备选择，以及确实会变化的扩展状态，属于运行时和存档。

原版程序通过补丁接入这一模型；重制版通过 C++ 访问接口接入；编辑器通过统一的数据适配层编辑。

目标是把扩容成本从“每增加一批技能，就修改记录布局和存档格式”，转变为“完成一次架构改造后，增加技能通常只增加数据”。

### 1.2 本方案解决的问题

- 技能数量不再决定 WarPC 记录的宽度。
- 角色技能配置不再依赖手工维护数百个原始字段。
- 新增指令技能同时具备学习状态和可用的 TKKon 效果映射。
- 旧存档能够在明确的迁移规则下被新版加载。
- 原版补丁和重制版可以共享资源语义及测试用例。
- 后续扩展数量时，不必反复迁移全部角色记录。

### 1.3 不承诺的事项

- 不承诺未打补丁的原版程序能够使用新增技能。
- 不承诺增加 TKSkill 条目就能增加任意新战斗机制。
- 不承诺所有第三方 MOD 的二进制补丁都能直接兼容。
- 不承诺只修改少量上限常量就能完成完整扩容。
- 不在本阶段同时改造装备槽数量、战斗单位数量或任意技能树结构。

## 二、已核实的结构与关键纠正

### 2.1 存档不包含 TKSkill 定义表

原版存档写入函数 `sub_410ED4` 写入两个压缩帧：

| 区域 | 原版解压后大小 | 内容 |
|---|---:|---|
| Frame 1 | 2,304,000 字节 | TKMat 实体运行数据 |
| Frame 2 / Block A | 3,432 字节 | 脚本及全局状态 |
| Frame 2 / Block B | 5,768 字节 | 队伍、背包等状态 |
| Frame 2 / WarPC | 150,722 字节 | 143 条完整角色记录 |
| Frame 2 合计 | 159,922 字节 | 上述三段拼接 |

TKSkill 则由资源加载函数单独从 `TKSkill.dat` 读取。

因此，需要纠正的前提是：

> 存档中保存的是完整 WarPC 及其技能相关状态，不是完整 TKSkill 技能定义表。

证据：

- [原版写档：410ED4.c:22](../../TKS/反编译产物/decompile/410ED4.c#L22)
- [原版读档：41103C.c:24](../../TKS/反编译产物/decompile/41103C.c#L24)
- [TKSkill 资源加载：4173F8.c:18](../../TKS/反编译产物/decompile/4173F8.c#L18)
- [存档编辑器布局：save_editor.py:76](../save_editor/save_editor.py#L76)

以上大小描述原版基线；启用现有人物扩容后，WarPC 总长度可能增加，但本方案仍要求每条记录保持 1054 字节。

### 2.2 WarPC 没有内嵌完整技能定义，但内嵌了按技能索引访问的数据

| 项目 | 当前结构 | 扩容影响 |
|---|---|---|
| WarPC 单条记录 | 1054 字节，即 527 个 int16 | 直接改变会影响跨记录寻址与复制 |
| 装备技能引用 | 字索引 82～87，共六个引用槽 | 能存索引不代表对应技能已经可执行 |
| 当前编辑器学习区 | 字节 176～519，共 344 字节 | 每技能一个状态字节 |
| 学习区后字段 | 字索引 260 起 | 已有角色扩展字段等用途，不能直接覆盖 |
| 技能效果相关区域 | 字索引 273 起 | 战斗按技能编号直接计算位置，尾部另有特殊用途 |

### 2.3 344、350 与 252 是不同的边界

这几个数字不能混为一个“技能上限”。

| 数字 | 实际含义 |
|---:|---|
| 350 | 原版 TKSkill 记录数，原版部分菜单循环也扫描到这个数量 |
| 344 | 当前编辑器及补丁采用的常规学习区边界，覆盖技能 0～343 |
| 252 | 原版数据中连续指令技能 0～251 对应的常规效果位置数量 |

原版 `sub_4189BC` 的循环上限确实是 350，并不是 344；当前补丁将扫描范围收窄，避免把字节 520～525 等已有用途的数据当成常规学习状态。

本次只读解析原版 `TKSkill.dat` 得到：

- 总大小 32,900 字节，共 350 条，每条 94 字节。
- `type == 0` 的编号区间为 0～251、344～349。
- 344～349 的名称字段为 0，不能据此把这些条目直接当成六个可自由使用的学习槽。

建议保留全部旧编号 0～349 的既有约定，第一批新增技能从 350 开始；344～349 走明确的旧逻辑或系统用途分支，不以 `skill_id >= 344` 一概判断“新增技能”。

重制版目前仍保留 350 项计数及旧字节偏移，不能假定它已经采用当前编辑器的 344 边界。

证据：

- [原版菜单扫描：4189BC.c:59](../../TKS/反编译产物/decompile/4189BC.c#L59)
- [当前扫描补丁：skill_scan_bound/patch.json:1](../tks_launcher_gui/patches/skill_scan_bound/patch.json#L1)

### 2.4 完整扩容必须解决 TKKon 映射，不只是学习状态

原版战斗路径包含这样的寻址关系：

```text
效果索引 = 战斗角色记录[273 + 技能编号]
效果数据 = TKKon[效果索引]
```

因此，对新增技能 350，直接套用旧公式会访问字索引 623，已经超出单条记录的 0～526 范围。

同时，记录尾部并不是 254 个通用技能槽：

- 字索引 273～524 对应常规技能 0～251。
- 字索引 525 存在普通攻击或动作类覆盖等特殊读取。
- 字索引 526 在战斗侧有头像帧用途。

当前编辑器通过筛选 `type == 0` 的条目构造显示列表，这种显示顺序不能被当成可任意扩展的引擎索引协议；改变技能类型或直接追加列表，不会让原版的 `273 + skill_id` 自动变成新映射。

TKKon 也不应只理解为动画编号：战斗会复制整条效果数据用于后续处理，角色专属效果映射属于技能执行链的一部分。

### 2.5 技能状态不是布尔值，也不是单纯的 JP 数值

| 状态 | 当前已观察到的语义 |
|---|---|
| 0 | 不会或不参与当前学习路径 |
| 1～9 | 等待条件满足，关联技能可以累加进度权重 |
| 10～19 | 可进入学习候选范围，但还要单独检查 JP 等条件 |
| 20 | 已学习状态之一 |
| 30 | 关联或子技能状态，菜单有特殊处理 |
| 40 | 装备关联技能失效等路径会使用的状态 |

不能把 `1～9` 简化为“已经投入的 JP”，也不能把 `10` 理解为“JP 一定足够”；`sub_41E248` 会传播关联进度，`sub_4189BC` 则另外判断学习费用。

初期扩展状态应保持字节级语义，不要同时引入布尔化或位压缩；旧档中的原始状态要可无损保留，新增状态规则只采用已经核实的值。

证据：

- [学习及关联进度传播：41E248.c:17](../../TKS/反编译产物/decompile/41E248.c#L17)
- [候选状态与 JP 判断：4189BC.c:63](../../TKS/反编译产物/decompile/4189BC.c#L63)
- [卸装状态变更：422EF4.c:83](../../TKS/反编译产物/decompile/422EF4.c#L83)

### 2.6 战斗单位是独立副本

原版召唤路径会以 `0x41E`，即 1054 字节，复制一条 WarPC 到战斗记录区；重制版也明确维护独立的战斗单位记录数组。

所以不能把所有扩展状态都只挂到全局角色索引上，然后认为战斗会自然同步。

必须区分：

- 持久角色身份。
- 战斗单位实例。
- 实例来源的角色模板或持久角色。
- 战斗期间的临时变化。
- 哪些变化需要在结算时回写。

证据：

## 三、方案比较

| 方案 | 优点 | 主要代价或限制 | 判断 |
|---|---|---|---|
| 扩大 WarPC 内部学习数组 | 表面上继续沿用原公式 | 改变后续字段偏移、记录步长、复制长度、存档格式 | 不推荐作为原版补丁主线 |
| 在每条 WarPC 尾部追加字段 | 旧字段相对偏移可保持 | 记录步长仍改变，所有跨记录访问与副本复制仍需处理 | 不能绕过核心问题 |
| 仅扩大 TKSkill 定义表 | 少量属性型技能可能较容易验证 | 不解决学习、指令效果映射、菜单或编号特判 | 只能作为受限阶段 |
| 复用旧技能并改变角色效果映射 | 原版布局改动小 | 增加的是技能变体，不是真正独立的新技能及进度 | 适合少量角色差异化 |
| 每角色局部槽映射到全局技能库 | 可限制角色自身状态占用 | 每角色槽数仍受限，编号语义及所有使用路径需转换 | 特定需求可研究，不作为默认方案 |
| 外置学习状态与效果映射 | 保持原版记录布局，后续数量扩展更稳定 | 需要一次性补齐访问路径、生命周期和存档支持 | 推荐 |
| 仅在重制版重建技能系统 | 可直接修改源码，验证更便利 | 不会自动让原版程序兼容 | 推荐作为模型验证底座 |

### 3.1 为什么不推荐修改记录步长

原版中既有按字节计算的 `1054 * index`，也有按字计算的 `527 * index`，以及复制完整记录的常量。

即使把新增字段放在记录尾部，也仍需处理：

- 全局角色数组寻址。
- 战斗角色数组寻址。
- 角色进入战斗、召唤与初始化时的复制。
- 存档缓存与读写长度。
- 已有补丁中的字段引用和记录步长。
- 第三方 MOD 对旧布局的依赖。

这不是理论上绝对不可行，而是修改面广、遗漏风险大，不适合作为维护成本较低的原版扩展路线。

### 3.2 为什么局部槽映射不是免费解法

如果允许每个角色最多使用固定数量的技能，可以设想让旧状态槽表示“该角色的第几个技能”，再映射到全局定义。

但原版很多路径将数值直接当作全局技能编号，包括技能树、装备、效果、AI 和特殊分支；有些查询位置也没有直接携带角色上下文。

这种方案需要广泛转换编号语义，且更换映射时必须保证旧存档中的槽位不会变成另一项技能。

如果要求所有新增技能都能拥有独立、持久的学习状态，就不能指望在完全不增加持久化信息的前提下无限扩展。

## 四、推荐的数据模型

以下名称均为设计概念，不表示仓库已经存在对应类、文件或接口。

### 4.1 数据职责划分

| 数据 | 建议归属 | 是否需要进入扩展存档 |
|---|---|---|
| 技能名称、类型、消耗、关联关系 | 技能定义资源 | 通常不需要 |
| 新技能默认 TKKon 映射 | 技能定义资源 | 通常不需要 |
| 某角色可学习的技能及初始状态 | 角色技能配置资源 | 初始化依据，不代替实际进度 |
| 某角色的专属 TKKon 覆盖 | 角色配置资源 | 静态覆盖通常不需要 |
| 实际学习状态 | 持久角色运行数据 | 需要 |
| 已装备技能 | 原有引用槽或明确新增的状态结构 | 引用槽能表达时继续使用旧槽 |
| 战斗临时状态 | 战斗实例数据 | 普通非战斗存档不直接保存临时副本 |
| 剧情永久改变的扩展效果覆盖 | 持久运行数据 | 仅在确认存在此需求时保存 |
| MOD 身份、数据版本及映射信息 | 资源清单与存档元数据 | 需要用于一致性检查 |

本方案不要求原有全部字段立刻脱离 WarPC；先外置新增部分，避免为了扩容同时重写所有旧逻辑。

### 4.2 逻辑结构

```text
技能定义注册表
  技能标识 -> 原有 94 字节定义 + 扩展元数据

角色技能配置
  角色标识 -> 技能清单、初始状态、角色专属效果覆盖

持久角色扩展状态
  角色标识 -> 技能标识 -> 学习状态字节

战斗单位扩展状态
  战斗槽位 -> 来源身份、独立的技能状态工作副本

效果解析
  角色或战斗实例 + 技能标识 -> TKKon 标识
```

### 4.3 稳定标识与编号政策

第一阶段建议采用最保守的编号策略：

1. 原有技能 0～349 不重排、不挪用。
2. 新增技能从 350 起追加。
3. MOD 内技能编号一旦进入存档，就不能因排序、删除或插入而静默复用。
4. 角色编号同样需要稳定；若继续使用 WarPC 行号作为身份，角色重排必须被视为需要迁移的操作。
5. 跨 MOD 不把相同数字当成同一个技能，存档同时记录 MOD 身份及数据版本。
6. 删除技能时保留编号占用或提供显式迁移，不把旧进度移交给新技能。

不能直接宣称支持 65535 个技能：原版多处使用有符号 int16，部分命令路径又以 1000、2000 等数值区分非技能操作。

第一阶段先验证新增编号 350；后续容量上限根据完整调用路径审计确定，而不是根据文件能存多少条决定。

证据：

- [有符号技能参数及类型分支：422BBC.c:9](../../TKS/反编译产物/decompile/422BBC.c#L9)
- [小于 1000 的技能分类判断：435D68.c:33](../../TKS/反编译产物/decompile/435D68.c#L33)
- [战斗菜单命令标记：447DAC.c:60](../../TKS/反编译产物/decompile/447DAC.c#L60)

### 4.4 建议的统一访问边界

| 概念接口 | 职责 |
|---|---|
| `GetSkillDefinition(skill_id)` | 查询技能定义，屏蔽表基址与记录数 |
| `GetLearnState(subject, skill_id)` | 查询持久角色或战斗实例的学习状态 |
| `SetLearnState(subject, skill_id, state)` | 写入正确的数据源 |
| `ResolveSkillEffect(subject, skill_id)` | 解析角色专属或默认 TKKon 效果 |
| `InitializeActorSkills(actor_id)` | 按资源配置初始化新角色 |
| `CreateBattleSkillState(unit, source)` | 建立独立的战斗扩展状态 |
| `CommitBattleSkillState(unit, actor)` | 按已核实规则回写持久变化 |

对原版而言，这些是需要通过补丁建立的逻辑边界，并不存在一个现成函数可以一次性接管所有访问。

对重制版而言，可以先在源码中集中这些访问，再替换后端存储。

### 4.5 旧数据与扩展数据的路由

```text
学习状态
  旧常规技能 0～343 -> 原 WarPC 学习区
  旧特殊编号 344～349 -> 保留旧约定，不进入通用新增技能路径
  已注册的新技能 >=350 -> 外置角色或战斗状态
  未注册编号 -> 配置错误，不能继续按偏移读取

效果查询
  旧指令技能 -> 保持原有映射及特殊规则
  新增指令技能 -> 角色覆盖优先，否则使用技能默认映射
  没有合法效果映射 -> 禁止作为可执行技能发布
```

这里的效果覆盖优先级是建议，不代表原版已有这套规则。

### 4.6 稀疏配置与运行时数组可以并存

编辑器、资源和存档可以用“角色—技能”的记录集合表达关系，避免把所有角色都展开成巨大的可编辑矩阵。

原版补丁运行时则可按实际规模将这些记录展开成连续数组，降低查询和 Hook 的复杂度；逻辑模型无需绑定具体的字典或数组实现。

无论采用何种存储，都应保留完整状态字节，且区分：

- 技能不在该角色配置中。
- 技能存在，但当前状态明确为 0。
- 技能是本次资源升级新加入、尚未执行迁移的条目。

## 五、原版程序的改造范围

### 5.1 技能定义表扩容与重定位

当前 `tkskill_size` 补丁只修改加载大小常量，描述中也明确说明它不是完整扩容。

完整处理至少需要：

- 为 TKSkill 分配足够容量的独立区域。
- 重定位表基址及字段基址引用，而不仅是单个表头地址。
- 调整加载长度和已经核实的遍历边界。
- 检查重新加载资源时是否仍写回旧地址。
- 检查已有补丁或第三方 MOD 对原地址的依赖。
- 在修改前验证可执行文件版本、指令特征和预期匹配数量。

现有 `patch_data_expand` 可以作为基础设施参考，但它不会自动证明所有技能访问都已覆盖。

证据：

- [当前技能大小补丁：tkskill_size/patch.json:1](../tks_launcher_gui/patches/tkskill_size/patch.json#L1)
- [通用数据扩容：patch_engine.py:1158](../tks_launcher_gui/core/patch_engine.py#L1158)
- [物品扩容参考：tkitem_expand/patch.json:1](../tks_launcher_gui/patches/tkitem_expand/patch.json#L1)

不能把修改循环上限视为充分条件：例如菜单虽然能显示新技能，但技能书仍可能向旧 WarPC 的后续字段写入。

### 5.3 技能组与编号特判

第一阶段应保持原有技能组语义，包括连续子技能区间和固定数量的关联记录，不同时改为任意图结构。

还需单独处理两类限制：

- **临时数组容量**：`sub_438F28` 有固定大小的菜单清空操作，不能因为总技能数增加就允许一个技能组无限增加子项。
- **按编号决定行为**：`sub_422BBC` 对反应技能按 303～330 等编号范围分类，新增同类型记录不等于新增正确的反应行为。

可以先选择不依赖新机制的普通指令技能做验证；新增反应类别、特殊战斗机制另列后续范围。

### 5.4 战斗状态的生命周期

| 时机 | 必须明确的处理 |
|---|---|
| 新游戏或新角色创建 | 从角色配置初始化扩展状态 |
| 普通角色进入战斗 | 从持久状态建立战斗工作副本 |
| 敌人或召唤单位创建 | 从对应模板建立实例状态，不错误绑定玩家进度 |
| 同一模板出现多个单位 | 每个实例具有独立临时状态 |
| 战斗槽位被复用 | 清除前一个单位的扩展状态 |
| 战斗结束 | 仅回写实际应持久化的变化 |
| 读档或切换 MOD | 清除上一局、上一档或上一 MOD 的运行缓存 |

战斗槽号不能作为跨战斗持久身份，指针地址也不能直接写入存档。

如果未来支持战斗中存档，需要单独序列化战斗实例及其关联关系，不属于仅扩展普通存档的自然结果。

## 六、存档扩展设计

### 6.1 推荐独立文件尾扩展块

建议保留现有两个压缩帧的协议，在第二帧结束之后追加独立扩展封套：

```text
sav.N
  [Frame 1 压缩长度][Frame 1 压缩数据]
  [Frame 2 压缩长度][Frame 2 压缩数据]
  [扩展头][技能扩展负载]
```

注意这里是 **两个压缩帧之外的文件尾部**，不是第二帧解压内容中的 WarPC 尾部。

理由：

1. 当前编辑器把 `Frame2[9200:]` 全部当成 WarPC。
2. 在该区域混入扩展技能字节，会破坏角色数量推导，或被错误解释为角色数据。
3. 原版读档函数为第二帧分配固定大小的解压缓冲区，直接扩大第二帧内容可能造成越界写入。
4. 文件尾独立块使旧数据区域和新增数据区域具有明确边界。

原版读档函数在读取第二帧后关闭文件，这说明独立尾块具有可利用的容器兼容性；但这不代表原版能够理解新增技能，也不代表所有编辑器会保留尾块。

证据：

- [原版固定缓冲区与关闭文件：41103C.c:29](../../TKS/反编译产物/decompile/41103C.c#L29)
- [当前 WarPC 段切分：save_editor.py:422](../save_editor/save_editor.py#L422)
- [角色编辑器对记录整除的要求：warpc_editor.py:261](../warpc_editor/warpc_editor.py#L261)

### 6.2 扩展封套需要表达的信息

以下为协议设计要求，字段宽度、魔数取值及负载编码需在实施阶段统一冻结，不能视为已有文件格式。

| 信息 | 用途 |
|---|---|
| 固定魔数 | 区分扩展块与无关尾部数据 |
| 格式版本 | 决定解析与迁移规则 |
| 头部长度、负载长度 | 明确边界，支持完整性检查 |
| 负载校验值 | 检测意外损坏，不作为防篡改认证 |
| MOD 标识及资源版本或指纹 | 防止用错误资源解释同一编号 |
| 角色、技能身份映射版本 | 识别编号迁移需求 |
| 角色与技能状态记录 | 恢复实际扩展进度 |
| 必要的持久扩展覆盖 | 仅保存已确认会变化的额外状态 |

负载不应再次复制全部 TKSkill 静态定义。

初版优先使用可明确校验的简单记录结构；不要直接转储 C++ 对象、指针、容器内存或带编译器填充的结构体。

### 6.3 读取顺序

1. 校验并解码两个既有压缩帧。
2. 依据帧头中的压缩长度计算第二帧结束位置。
3. 检查是否存在扩展封套。
4. 验证版本、长度、记录数量和校验信息。
5. 验证 MOD 身份以及角色、技能引用。
6. 在临时对象中构造完整待加载状态。
7. 所有检查通过后，再替换当前运行状态。

不能先覆盖当前游戏，再发现扩展块不可用后继续运行半套状态。

### 6.4 没有扩展块不一定意味着“正常旧档”

无扩展块可能有两种来源：

- 真正的原版或旧版存档。
- 扩展存档被不支持扩展的编辑器重写，导致尾部丢失。

如果原有装备槽已经引用新增技能，而扩展块不存在，应判为不完整或需要明确迁移处理，不能静默清零。

如果没有任何可识别的新技能引用，仅凭旧格式本体未必能判断尾部曾经存在；界面应明确提示“按旧档导入”，不要声称能够可靠恢复已经丢失的扩展进度。

### 6.5 旧档初始化与迁移规则

导入旧档时：

- 保留已有角色属性、装备和旧技能进度。
- 按对应 MOD 的角色技能配置建立新增状态。
- 区分“尚不可学”“等待条件”“可学习”“已经掌握”，不要统一填 0 或统一设为已学会。
- 若新技能的开放条件依赖剧情，使用明确迁移规则，不能凭空推断玩家是否满足条件。
- 迁移完成后写入当前扩展版本，使后续加载不重复授予或重复初始化。

新增资源版本时：

- 已有扩展技能以存档进度为准。
- 新加入的技能才执行新增条目初始化或版本迁移。
- 删除、重命名或改变编号的技能必须有明确策略。
- 明确记录的状态 0 不能被误当成“没有存档状态”，从而在每次更新后重新开放。

### 6.6 保存一致性

建议的最终写入流程：

1. 生成同一时点的旧格式数据与扩展状态快照。
2. 将两个压缩帧及扩展块完整写入同目录临时文件。
3. 检查写入结果，并进行必要的解析回读。
4. 使用平台支持的替换操作提交文件，保留原档备份。
5. 替换失败时保留可用旧档，不宣布保存成功。

仅在原版写档结束后再次打开正式文件追加尾块，仍有“旧部分已更新、扩展部分尚未写入”的中断窗口；这只能作为临时验证方式，不能被描述成完整的事务保存。

游戏另有槽位摘要文件时，摘要不应成为扩展状态的唯一依据；其更新与主存档提交的先后关系也需要纳入失败恢复测试。

### 6.7 为什么不优先采用旁路存档文件

旁路文件如 `sav.N.ext` 便于早期调试，但带来额外配对问题：

- 用户复制主存档时可能漏掉扩展文件。
- 覆盖、备份或回滚两个文件时可能来自不同时间点。
- 主存档写成功、扩展文件写失败会产生状态不一致。

若验证阶段采用旁路文件，必须绑定主存档身份或内容摘要，并在不匹配时拒绝静默合并；正式格式优先采用单文件扩展块。

## 七、兼容性边界

| 组合 | 建议行为 |
|---|---|
| 旧存档 + 新版运行时 + 匹配 MOD | 明确导入，保留旧进度并初始化新增状态 |
| 扩展存档 + 同版本运行时和资源 | 完整恢复并校验引用 |
| 扩展存档 + 可迁移的新资源版本 | 执行有版本记录的迁移 |
| 扩展存档 + 缺少技能或不同 MOD | 阻止正常加载，提示缺失依赖或需要迁移 |
| 扩展存档 + 未打补丁的原版 | 不保证可用，不能仅凭旧帧可解压宣称兼容 |
| 扩展存档 + 旧版编辑器写回 | 可能丢失尾块，应明确禁止或警告 |
| 扩展存档 + 支持扩展的新编辑器 | 修改所需字段，同时保留其余有效状态 |
| 未识别的扩展版本 + 新编辑器 | 默认不允许有损写回 |
| 无扩展块但含新增技能引用 | 视为不完整或需专门迁移，不静默继续 |

**“新版能读旧档”与“旧版能读新档”是两个不同目标。**

原版程序即使忽略文件尾块，仍可能读取旧 WarPC 装备槽中的新增编号，从不存在的技能表位置取数据，因此不能保证安全降级。

若未来需要“导出原版兼容存档”，应作为显式的有损转换功能，清理不支持的引用并告知进度损失，而不是正常保存时自动执行。

## 八、编辑器侧改造

### 8.1 保留二进制格式适配，改变上层编辑模型

建议将 WarPC 原始读写保留为兼容适配层，上层角色技能页面不再直接依赖“第几个原始字段就是第几个技能”。

职责可以分为：

- 原版 WarPC 编解码。
- 动态技能定义目录。
- 角色技能配置与运行状态访问。
- 统一存档容器读写。

不要求把现有整个编辑器重写，只集中改造技能相关路径。

### 8.2 角色技能页面的建议交互

以角色技能清单为主要编辑入口：

| 列 | 内容 |
|---|---|
| 技能 | 名称与稳定编号 |
| 类型 | 指令、属性、反应、移动等 |
| 初始状态或实际状态 | 区分模板模式与存档模式 |
| 装备槽 | 现有槽位引用，不顺便扩大槽位数 |
| 默认效果 | 技能资源提供的 TKKon 映射 |
| 角色覆盖 | 仅显示与默认效果不同的配置 |
| 来源 | 原版数据、扩展配置或存档状态 |

配合搜索、类型筛选、批量赋予技能组，可以减少维护完整矩阵的负担。

原始字段视图仍可保留用于逆向和高级调试，但不再作为扩展技能的主编辑方式。

### 8.3 技能定义编辑器

当前 `skill_editor` 的加载与保存使用固定 350 条限制，需要改为：

- 依据实际完整记录数或资源清单读取。
- 保存时不截断新增条目。
- 校验记录长度、编号、关联技能与效果资源引用。
- 增加条目时保持旧编号稳定。
- 对当前引擎不支持的类型、编号或技能组结构明确提示。

仅把 `SKILL_CNT` 改成另一个固定数字，不是最终扩展接口。

证据：[skill_editor.py:158](../skill_editor/skill_editor.py#L158)。

### 8.4 WarPC 编辑器

重点改造以下位置：

- 技能名称目录的 `range(350)`。
- 技能关系解析的 `min(350, ...)`。
- 学习页面固定 344 项的生成方式。
- 效果页面通过活动技能列表顺序推导原始字段的方式。
- 表格模式及批处理工具中重复的学习和效果映射逻辑。

不要只修改主窗口，遗漏表格模式、批量修改和存档模式。

证据：

- [学习页面：warpc_editor.py:1244](../warpc_editor/warpc_editor.py#L1244)
- [技能目录与关系解析：warpc_editor.py:1786](../warpc_editor/warpc_editor.py#L1786)
- [表格模式：warpc_table_mode.py:122](../warpc_editor/warpc_table_mode.py#L122)
- [批处理映射：batch_skill_learn.py:79](../warpc_editor/batch_skill_learn.py#L79)

### 8.5 两个编辑器都需要保留扩展块

当前两个保存入口只写回两个压缩帧：

- [save_editor.py:431](../save_editor/save_editor.py#L431)

因此，新存档不能只改游戏的写档函数；必须统一更新这些入口，使修改金币、属性或装备时不会意外删除技能扩展状态。

对于不认识的扩展版本，至少应阻止有损保存；若未来支持原样保留未知块，也需要明确哪些编辑操作会破坏块与旧数据的关联。

## 九、重制版的改造路线

### 9.1 当前状态

重制版并未天然摆脱旧布局：

- 战斗效果仍读取 `273 + cmd`。
- 战斗单位仍是 `32 * 527` 个字的记录数组。
- 存档仍构建原版大小的状态块。

- [存档写入：SceneSave.cpp:441](../../TKSRemake/src/game/scene/SceneSave.cpp#L441)

### 9.2 建议顺序

1. 用统一接口包住现有技能定义、学习状态和效果访问，先保持旧行为。
2. 通过旧资源与旧存档回归测试确认结果不变。
3. 将新增部分放入独立运行时结构。
4. 接入共享的资源模型与扩展存档协议。
5. 再逐步减少旧格式对内部运行时的约束。

应让旧二进制格式主要承担导入与兼容职责，而不是永远作为所有 C++ 游戏逻辑的数据模型。

### 9.3 为什么优先用重制版验证

重制版能够直接调试访问接口、索引检查、状态迁移和实例复制，适合尽早验证模型是否完整。

但重制版验证通过只证明模型与该实现可用，不证明原版 Hook 已经覆盖所有路径；原版仍需独立的指令级核验和实机测试。

共享目标应是资源语义、协议和测试样例，而不是要求 Python 与 C++ 共享某种进程内内存布局。

## 十、分阶段实施与交付条件

### 阶段 0：冻结基线与补齐访问审计

工作：

- 固定待支持的 EXE 版本、补丁组合及原始资源样本。
- 建立旧角色、旧技能及特殊编号清单。
- 补齐学习状态、效果映射、编号特判和战斗复制路径。
- 明确第一阶段新增技能类型及允许编号范围。
- 冻结资源模型、存档协议和迁移规则。

完成条件：关键访问路径均有证据，没有用“应该没问题”代替未核实的索引行为。

### 阶段 1：在重制版贯通一个新增技能

选择编号 350 的普通指令技能，复用已知合法 TKKon 效果，不同时开发新战斗机制。

验证闭环：

```text
编辑资源 -> 初始化角色 -> 满足学习条件 -> 消耗 JP 学习
-> 装备或选择 -> 进入战斗 -> 施放效果
-> 保存 -> 退出并重启 -> 读档 -> 状态与效果一致
```

完成条件：不占用旧字段、不串角色、不依赖重启前的内存残留。

### 阶段 2：完善编辑器及存档往返

工作：

- 动态加载技能目录。
- 编辑角色技能清单和效果覆盖。
- 两个编辑器支持扩展块。
- 实现旧档导入及资源版本检查。
- 建立固定的往返样本。

完成条件：用编辑器修改不相关字段，不丢失新增技能的学习进度或效果配置。

### 阶段 3：接入原版补丁

工作：

- 技能定义表重定位。
- 学习及装备读写路径接入。
- 战斗实例和效果查询接入。
- 存读档扩展接入。
- 验证与现有人物、物品扩容补丁的组合。

完成条件：原版完成与阶段 1 相同的闭环，并通过旧功能回归测试。

### 阶段 4：扩大数量与覆盖类型

工作：

- 从单技能扩至多角色、多技能组。
- 验证分页、数组容量、AI 与召唤单位。
- 按需增加反应类、移动类等支持。
- 验证新增、删除及升级资源后的迁移。

完成条件：容量上限有完整路径依据，新增资源不要求再次改变 WarPC 记录布局。

## 十一、验收测试清单

### 11.1 资源与编辑器

- [ ] 原版 350 条技能加载、保存不截断、不改变编号。
- [ ] 新增 350 号技能能够完整保存并重新读取。
- [ ] 非完整 94 字节记录、重复编号、无效引用被明确拒绝。
- [ ] 344～349 不被错误初始化为普通新增学习槽。
- [ ] 表单、表格与批处理对同一技能的状态解释一致。
- [ ] 模板初始状态和存档实际状态在界面中明确区分。
- [ ] 修改技能显示顺序不会改变已有存档引用。
- [ ] 新技能缺少合法 TKKon 映射时不能作为可执行配置发布。

### 11.2 学习与装备

- [ ] 关联技能能够正确增加新增技能的解锁进度。
- [ ] 状态达到可学习范围但 JP 不足时，不错误允许学习。
- [ ] 确认学习只扣除一次 JP。
- [ ] 旧技能关联新技能、新技能关联旧技能均正确。
- [ ] 技能书作用于新增技能时，不覆盖 WarPC 后续字段。
- [ ] 装备和卸装附带技能正确处理相关状态转换。
- [ ] 保存后重启仍保留新增技能的学习及装备状态。

### 11.3 战斗与效果

- [ ] 新增指令技能使用外置效果映射，不访问旧记录之外的位置。
- [ ] 角色效果覆盖优先级符合约定。
- [ ] 玩家与 AI 都能正确选择或处理新增技能。
- [ ] 同模板多个单位的临时状态不会互相污染。
- [ ] 召唤、退出、再次召唤和槽位复用不会留下旧状态。
- [ ] 战斗结束只回写规定的持久变化。
- [ ] 技能组达到临时列表容量边界时不越界。
- [ ] 普通攻击、旧反应技能及旧特殊技能保持原行为。

### 11.4 存档与失败恢复

- [ ] 旧档导入不改变原有经验、装备及技能进度。
- [ ] 旧档新增技能按迁移规则初始化，不一律填 0 或直接学会。
- [ ] 扩展存档经过两个编辑器修改无关字段后仍完整。
- [ ] 未识别版本、截断负载、异常长度和损坏校验均被识别。
- [ ] 缺少 MOD 或技能定义时不给出貌似成功的加载结果。
- [ ] 不完整扩展档不会静默当成正常旧档覆盖保存。
- [ ] 保存中断或文件替换失败后仍有可恢复的旧档。
- [ ] 资源升级不会覆盖已有明确状态 0，也不会重复授予技能。
- [ ] 两份不同进度的存档切换时，没有缓存残留。
- [ ] 启用现有人物或物品扩容后，上述往返仍成立。

本清单是后续验收要求，不表示这些测试已经执行或通过。

## 十二、对既有分析文档的使用说明

仓库已有以下相关资料：

- [技能数量扩展可行性分析](技能数量扩展可行性分析.md)
- [外挂技能学习表实现指南](外挂技能学习表实现指南.md)
- [补丁十六 skill_learn 扩容方案分析](tks_launcher/补丁十六_skill_learn扩容方案分析.md)

这些文档可用于查找历史讨论和候选入口，但其中的结论与示例不能直接视为已实现事实。

本次核查特别修正以下理解：

| 容易误用的说法 | 本方案的解释 |
|---|---|
| 存档包含整套 TKSkill 定义 | 实际写入 TKMat 和 WarPC 等状态，TKSkill 独立加载 |
| 原版学习循环天然以 344 为界 | 原版部分循环扫描 350，344 是当前补丁及编辑器采用的边界 |
| 外置学习数组即可完成全部扩容 | 还必须处理 TKKon 映射、战斗实例和编号语义 |
| 只需增加一个技能表重定位补丁 | 只能说明定义表容量问题，不能证明完整技能可用 |
| 每条 WarPC 末尾追加数据不会影响旧访问 | 字段偏移可不变，但记录步长仍改变 |
| WarPC 后面追加扩展字节就自然兼容旧档 | 若混入 Frame 2，会影响解析边界及原版解压缓冲区 |
| `skill_id >= 344` 都是新增技能 | 344～349 属于旧编号范围，应单独保留约定 |
| word 类型意味着可以扩到 65535 | 有符号解释、命令标记和其他数组还有额外约束 |
| 只有几个 Hook 就一定足够 | 一个函数可能有多个访问点，必须以完整审计为准 |
| 已具备前置扩容能力 | 需以当前补丁实现和测试为准，不能根据指南中的前置声明判断 |

本次只新增设计文档，不重写这些历史资料，也不把任何尚未验证的 Hook 示例升级为可直接部署方案。

## 十三、待实施前确认的问题

1. 首批扩展是否只包含普通指令技能，还是需要立即支持反应与移动技能。
2. 第一阶段需要覆盖哪些 EXE 版本及第三方 MOD。
3. 新技能是否需要通过旧剧情进度自动解锁，具体规则是什么。
4. 角色与技能编号在编辑器中是否允许删除、重排及复用。
5. 哪些角色专属效果是静态资源，哪些确实可能在游戏中永久改变。
6. 是否要求跨原版补丁与重制版双向交换扩展存档，以及旧部分各字段是否已经一致。
7. 是否需要战斗中存档；若需要，必须另行定义战斗实例序列化。
8. 扩展协议如何标识必需版本，以及不兼容时如何提示和停止写回。

这些问题应在实施阶段结合目标 MOD 冻结，不影响当前推荐的结构分离方向。

## 十四、最终建议

优先顺序是：**先分离技能定义、角色配置和实际进度，再打通一个新增技能的完整生命周期，最后扩大数量与类型。**

原版保持 1054 字节 WarPC 记录，新增学习状态和效果映射走独立扩展层；重制版先建立统一访问接口，再逐步让旧格式退回兼容边界。

真正需要长期稳定的不是某个新的技能数量常量，而是技能身份、状态归属、效果解析和存档协议。
