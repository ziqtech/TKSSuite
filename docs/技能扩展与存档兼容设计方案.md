# 技能扩展与存档兼容设计方案

> 复核日期：2026-09-17；最近复验：2026-09-19
>
> 适用范围：TKSSuite 编辑器、原版 TKS 补丁与启动器；TKSRemake 仅作原版逻辑的只读参考，不修改、不扩展、不作为先行验证平台
>
> 状态：用户已确认新游戏及角色 #0、#200 的技能列表恢复正常；技能菜单修复通过 89 项回归，经验总结见第二十二节。存档页读档及完整游戏内人工闭环尚未单独确认，不据此扩大验收范围。

## 一、结论与设计目标

### 1.1 推荐结论

推荐采用 **“保留原版二进制布局，外置新增技能的状态与效果映射”**，而不是扩大每条 WarPC 记录中的技能数组。

具体分离为三个层次：

1. **技能定义**：技能名称、类型、费用、关联技能、默认效果等，属于 MOD 资源。
2. **角色技能配置**：角色有哪些技能、初始学习状态、角色专属效果覆盖，属于角色模板资源。
3. **游戏进度**：玩家实际学习状态、装备选择，以及确实会变化的扩展状态，属于运行时和存档。

原版程序通过补丁接入这一模型，编辑器通过统一的数据适配层编辑。重制版只能辅助理解原版逻辑，不承担本方案的实现或验证。

目标是把扩容成本从“每增加一批技能，就修改记录布局和存档格式”，转变为“完成一次架构改造后，增加技能通常只增加数据”。

本次交付必须同时满足：

1. 扩大 TKSkill 技能定义总数，并扩大每个角色独立可学习的技能数量；不只是复用旧技能槽或增加显示条目。
2. 保持 WarPC 单条记录 1054 字节，兼容项目已有的 200+ 角色及 500 槽扩容。原版 143 条只用于描述未扩容基线，不是本项目角色上限。
3. 审计 `tks_launcher_gui/patches` 下全部补丁。互斥原型必须在选择阶段明确阻止，不能靠说明文字避免冲突；生产补丁之间须完成组合验证。
4. 同时覆盖 `tks_launcher_gui/main.py` 的 GUI 注入启动和 GUI 生成启动器两条链路；禁止使用或新增对 `tks_launcher_gui/cli_launcher.py` 的兼容。
5. 验收全部在 TKSSuite 与原版 TKS 上完成，不修改重制版，也不以重制版测试代替原版测试。

### 1.2 本方案解决的问题

- 技能数量不再决定 WarPC 记录的宽度。
- 角色技能配置不再依赖手工维护数百个原始字段。
- 新增指令技能同时具备学习状态和可用的 TKKon 效果映射。
- 旧存档能够在明确的迁移规则下被新版加载。
- 编辑器配置、原版运行时与扩展存档采用一致的资源语义。
- 后续扩展数量时，不必反复迁移全部角色记录。

### 1.3 不承诺的事项

- 不承诺未打补丁的原版程序能够使用新增技能。
- 不承诺增加 TKSkill 条目就能增加任意新战斗机制。
- 不承诺所有第三方 MOD 的二进制补丁都能直接兼容。
- 不承诺只修改少量上限常量就能完成完整扩容。
- 不在本阶段同时改造装备槽数量、战斗单位数量或任意技能树结构。

## 二、已核实的结构与关键纠正

### 2.1 存档不包含 TKSkill 定义表

原版存档写入函数 `sub_410ED4` 写入两个压缩帧：

| 区域 | 原版解压后大小 | 内容 |
|---|---:|---|
| Frame 1 | 2,304,000 字节 | TKMat 实体运行数据 |
| Frame 2 / Block A | 3,432 字节 | 脚本及全局状态 |
| Frame 2 / Block B | 5,768 字节 | 队伍、背包等状态 |
| Frame 2 / WarPC | 150,722 字节 | 143 条完整角色记录 |
| Frame 2 合计 | 159,922 字节 | 上述三段拼接 |

TKSkill 则由资源加载函数单独从 `TKSkill.dat` 读取。

因此，需要纠正的前提是：

> 存档中保存的是完整 WarPC 及其技能相关状态，不是完整 TKSkill 技能定义表。

证据：

- [原版写档：410ED4.c:22](../../TKS/反编译产物/decompile/410ED4.c#L22)
- [原版读档：41103C.c:24](../../TKS/反编译产物/decompile/41103C.c#L24)

- [存档编辑器布局：save_editor.py:76](../save_editor/save_editor.py#L76)

以上大小描述原版基线；启用现有人物扩容后，WarPC 总长度可能增加，但本方案仍要求每条记录保持 1054 字节。

### 2.2 WarPC 没有内嵌完整技能定义，但内嵌了按技能索引访问的数据

| 项目 | 当前结构 | 扩容影响 |
|---|---|---|
| WarPC 单条记录 | 1054 字节，即 527 个 int16 | 直接改变会影响跨记录寻址与复制 |
| 装备技能引用 | 字索引 82～87，共六个引用槽 | 能存索引不代表对应技能已经可执行 |
| 当前编辑器学习区 | 字节 176～519，共 344 字节 | 每技能一个状态字节 |
| 学习区后字段 | 字索引 260 起 | 已有角色扩展字段等用途，不能直接覆盖 |
| 技能效果相关区域 | 字索引 273 起 | 战斗按技能编号直接计算位置，尾部另有特殊用途 |

### 2.3 344、350 与 252 是不同的边界

这几个数字不能混为一个“技能上限”。

| 数字 | 实际含义 |
|---:|---|
| 350 | 原版 TKSkill 记录数，原版部分菜单循环也扫描到这个数量 |
| 344 | 当前编辑器及补丁采用的常规学习区边界，覆盖技能 0～343 |
| 252 | 原版数据中连续指令技能 0～251 对应的常规效果位置数量 |

原版 `sub_4189BC` 的循环上限确实是 350，并不是 344；当前补丁将扫描范围收窄，避免把字节 520～525 等已有用途的数据当成常规学习状态。

本次只读解析原版 `TKSkill.dat` 得到：

- 总大小 32,900 字节，共 350 条，每条 94 字节。
- `type == 0` 的编号区间为 0～251、344～349。
- 344～349 的名称字段为 0，不能据此把这些条目直接当成六个可自由使用的学习槽。

建议保留全部旧编号 0～349 的既有约定，第一批新增技能从 350 开始；344～349 走明确的旧逻辑或系统用途分支，不以 `skill_id >= 344` 一概判断“新增技能”。

重制版目前仍保留 350 项计数及旧字节偏移，不能假定它已经采用当前编辑器的 344 边界。

证据：

- [原版菜单扫描：4189BC.c:59](../../TKS/反编译产物/decompile/4189BC.c#L59)
- [当前扫描补丁：skill_scan_bound/patch.json:1](../tks_launcher_gui/patches/skill_scan_bound/patch.json#L1)

### 2.4 完整扩容必须解决 TKKon 映射，不只是学习状态

原版战斗路径包含这样的寻址关系：

```text
效果索引 = 战斗角色记录[273 + 技能编号]
效果数据 = TKKon[效果索引]
```

因此，对新增技能 350，直接套用旧公式会访问字索引 623，已经超出单条记录的 0～526 范围。

同时，记录尾部并不是 254 个通用技能槽：

- 字索引 273～524 对应常规技能 0～251。
- 字索引 525 存在普通攻击或动作类覆盖等特殊读取。
- 字索引 526 在战斗侧有头像帧用途。

当前编辑器通过筛选 `type == 0` 的条目构造显示列表，这种显示顺序不能被当成可任意扩展的引擎索引协议；改变技能类型或直接追加列表，不会让原版的 `273 + skill_id` 自动变成新映射。

TKKon 也不应只理解为动画编号：战斗会复制整条效果数据用于后续处理，角色专属效果映射属于技能执行链的一部分。

### 2.5 技能状态不是布尔值，也不是单纯的 JP 数值

| 状态 | 当前已观察到的语义 |
|---|---|
| 0 | 不会或不参与当前学习路径 |
| 1～9 | 等待条件满足，关联技能可以累加进度权重 |
| 10～19 | 可进入学习候选范围，但还要单独检查 JP 等条件 |
| 20 | 已学习状态之一 |
| 30 | 关联或子技能状态，菜单有特殊处理 |
| 40 | 装备关联技能失效等路径会使用的状态 |

不能把 `1～9` 简化为“已经投入的 JP”，也不能把 `10` 理解为“JP 一定足够”；`sub_41E248` 会传播关联进度，`sub_4189BC` 则另外判断学习费用。

初期扩展状态应保持字节级语义，不要同时引入布尔化或位压缩；旧档中的原始状态要可无损保留，新增状态规则只采用已经核实的值。

证据：

- [学习及关联进度传播：41E248.c:17](../../TKS/反编译产物/decompile/41E248.c#L17)
- [候选状态与 JP 判断：4189BC.c:63](../../TKS/反编译产物/decompile/4189BC.c#L63)
- [卸装状态变更：422EF4.c:83](../../TKS/反编译产物/decompile/422EF4.c#L83)

### 2.6 战斗单位是独立副本

原版召唤路径会以 `0x41E`，即 1054 字节，复制一条 WarPC 到战斗记录区；重制版也明确维护独立的战斗单位记录数组。

所以不能把所有扩展状态都只挂到全局角色索引上，然后认为战斗会自然同步。

必须区分：

- 持久角色身份。
- 战斗单位实例。
- 实例来源的角色模板或持久角色。
- 战斗期间的临时变化。
- 哪些变化需要在结算时回写。

证据：

- [原版召唤复制：444FD4.c:43](../../TKS/反编译产物/decompile/444FD4.c#L43)

## 三、方案比较

| 方案 | 优点 | 主要代价或限制 | 判断 |
|---|---|---|---|
| 扩大 WarPC 内部学习数组 | 表面上继续沿用原公式 | 改变后续字段偏移、记录步长、复制长度、存档格式 | 不推荐作为原版补丁主线 |
| 在每条 WarPC 尾部追加字段 | 旧字段相对偏移可保持 | 记录步长仍改变，所有跨记录访问与副本复制仍需处理 | 不能绕过核心问题 |
| 仅扩大 TKSkill 定义表 | 少量属性型技能可能较容易验证 | 不解决学习、指令效果映射、菜单或编号特判 | 只能作为受限阶段 |
| 复用旧技能并改变角色效果映射 | 原版布局改动小 | 增加的是技能变体，不是真正独立的新技能及进度 | 适合少量角色差异化 |
| 每角色局部槽映射到全局技能库 | 可限制角色自身状态占用 | 每角色槽数仍受限，编号语义及所有使用路径需转换 | 特定需求可研究，不作为默认方案 |
| 外置学习状态与效果映射 | 保持原版记录布局，后续数量扩展更稳定 | 需要一次性补齐访问路径、生命周期和存档支持 | 推荐 |

### 3.1 为什么不推荐修改记录步长

原版中既有按字节计算的 `1054 * index`，也有按字计算的 `527 * index`，以及复制完整记录的常量。

即使把新增字段放在记录尾部，也仍需处理：

- 全局角色数组寻址。
- 战斗角色数组寻址。
- 角色进入战斗、召唤与初始化时的复制。
- 存档缓存与读写长度。
- 已有补丁中的字段引用和记录步长。
- 第三方 MOD 对旧布局的依赖。

这不是理论上绝对不可行，而是修改面广、遗漏风险大，不适合作为维护成本较低的原版扩展路线。

### 3.2 为什么局部槽映射不是免费解法

如果允许每个角色最多使用固定数量的技能，可以设想让旧状态槽表示“该角色的第几个技能”，再映射到全局定义。

但原版很多路径将数值直接当作全局技能编号，包括技能树、装备、效果、AI 和特殊分支；有些查询位置也没有直接携带角色上下文。

这种方案需要广泛转换编号语义，且更换映射时必须保证旧存档中的槽位不会变成另一项技能。

如果要求所有新增技能都能拥有独立、持久的学习状态，就不能指望在完全不增加持久化信息的前提下无限扩展。

## 四、推荐的数据模型

以下名称均为设计概念，不表示仓库已经存在对应类、文件或接口。

### 4.1 数据职责划分

| 数据 | 建议归属 | 是否需要进入扩展存档 |
|---|---|---|
| 技能名称、类型、消耗、关联关系 | 技能定义资源 | 通常不需要 |
| 新技能默认 TKKon 映射 | 技能定义资源 | 通常不需要 |
| 某角色可学习的技能及初始状态 | 角色技能配置资源 | 初始化依据，不代替实际进度 |
| 某角色的专属 TKKon 覆盖 | 角色配置资源 | 静态覆盖通常不需要 |
| 实际学习状态 | 持久角色运行数据 | 需要 |
| 已装备技能 | 原有引用槽或明确新增的状态结构 | 引用槽能表达时继续使用旧槽 |
| 战斗临时状态 | 战斗实例数据 | 普通非战斗存档不直接保存临时副本 |
| 剧情永久改变的扩展效果覆盖 | 持久运行数据 | 仅在确认存在此需求时保存 |
| MOD 身份、数据版本及映射信息 | 资源清单与存档元数据 | 需要用于一致性检查 |

本方案不要求原有全部字段立刻脱离 WarPC；先外置新增部分，避免为了扩容同时重写所有旧逻辑。

### 4.2 逻辑结构

```text
技能定义注册表
  技能标识 -> 原有 94 字节定义 + 扩展元数据

角色技能配置
  角色标识 -> 技能清单、初始状态、角色专属效果覆盖

持久角色扩展状态
  角色标识 -> 技能标识 -> 学习状态字节

战斗单位扩展状态
  战斗槽位 -> 来源身份、独立的技能状态工作副本

效果解析
  角色或战斗实例 + 技能标识 -> TKKon 标识
```

### 4.3 稳定标识与编号政策

第一阶段建议采用最保守的编号策略：

1. 原有技能 0～349 不重排、不挪用。
2. 新增技能从 350 起追加。
3. MOD 内技能编号一旦进入存档，就不能因排序、删除或插入而静默复用。
4. 角色编号同样需要稳定；若继续使用 WarPC 行号作为身份，角色重排必须被视为需要迁移的操作。
5. 跨 MOD 不把相同数字当成同一个技能，存档同时记录 MOD 身份及数据版本。
6. 删除技能时保留编号占用或提供显式迁移，不把旧进度移交给新技能。

不能直接宣称支持 65535 个技能：原版多处使用有符号 int16，部分命令路径又以 1000、2000 等数值区分非技能操作。

第一阶段先验证新增编号 350；后续容量上限根据完整调用路径审计确定，而不是根据文件能存多少条决定。

证据：

- [有符号技能参数及类型分支：422BBC.c:9](../../TKS/反编译产物/decompile/422BBC.c#L9)
- [小于 1000 的技能分类判断：435D68.c:33](../../TKS/反编译产物/decompile/435D68.c#L33)
- [战斗菜单命令标记：447DAC.c:60](../../TKS/反编译产物/decompile/447DAC.c#L60)

### 4.4 建议的统一访问边界

| 概念接口 | 职责 |
|---|---|
| `GetSkillDefinition(skill_id)` | 查询技能定义，屏蔽表基址与记录数 |
| `GetLearnState(subject, skill_id)` | 查询持久角色或战斗实例的学习状态 |
| `SetLearnState(subject, skill_id, state)` | 写入正确的数据源 |
| `ResolveSkillEffect(subject, skill_id)` | 解析角色专属或默认 TKKon 效果 |
| `InitializeActorSkills(actor_id)` | 按资源配置初始化新角色 |
| `CreateBattleSkillState(unit, source)` | 建立独立的战斗扩展状态 |
| `CommitBattleSkillState(unit, actor)` | 按已核实规则回写持久变化 |

对原版而言，这些是需要通过补丁建立的逻辑边界，并不存在一个现成函数可以一次性接管所有访问。

接口覆盖与语义必须以原版反编译、实际指令和补丁执行结果核验，不能依赖修改重制版来补足原版路径。

### 4.5 旧数据与扩展数据的路由

```text
学习状态
  旧常规技能 0～343 -> 原 WarPC 学习区
  旧特殊编号 344～349 -> 保留旧约定，不进入通用新增技能路径
  已注册的新技能 >=350 -> 外置角色或战斗状态
  未注册编号 -> 配置错误，不能继续按偏移读取

效果查询
  旧指令技能 -> 保持原有映射及特殊规则
  新增指令技能 -> 角色覆盖优先，否则使用技能默认映射
  没有合法效果映射 -> 禁止作为可执行技能发布
```

这里的效果覆盖优先级是建议，不代表原版已有这套规则。

### 4.6 稀疏配置与运行时数组可以并存

编辑器、资源和存档可以用“角色—技能”的记录集合表达关系，避免把所有角色都展开成巨大的可编辑矩阵。

原版补丁运行时则可按实际规模将这些记录展开成连续数组，降低查询和 Hook 的复杂度；逻辑模型无需绑定具体的字典或数组实现。

无论采用何种存储，都应保留完整状态字节，且区分：

- 技能不在该角色配置中。
- 技能存在，但当前状态明确为 0。
- 技能是本次资源升级新加入、尚未执行迁移的条目。

## 五、原版程序的改造范围

### 5.1 技能定义表扩容与重定位

当前 `tkskill_size` 补丁只修改加载大小常量，描述中也明确说明它不是完整扩容。

完整处理至少需要：

- 为 TKSkill 分配足够容量的独立区域。
- 重定位表基址及字段基址引用，而不仅是单个表头地址。
- 调整加载长度和已经核实的遍历边界。
- 检查重新加载资源时是否仍写回旧地址。
- 检查已有补丁或第三方 MOD 对原地址的依赖。
- 在修改前验证可执行文件版本、指令特征和预期匹配数量。

现有 `patch_data_expand` 可以作为基础设施参考，但它不会自动证明所有技能访问都已覆盖。

证据：

- [当前技能大小补丁：tkskill_size/patch.json:1](../tks_launcher_gui/patches/tkskill_size/patch.json#L1)

### 5.3 技能组与编号特判

第一阶段应保持原有技能组语义，包括连续子技能区间和固定数量的关联记录，不同时改为任意图结构。

还需单独处理两类限制：

- **临时数组容量**：`sub_438F28` 有固定大小的菜单清空操作，不能因为总技能数增加就允许一个技能组无限增加子项。
- **按编号决定行为**：`sub_422BBC` 对反应技能按 303～330 等编号范围分类，新增同类型记录不等于新增正确的反应行为。

可以先选择不依赖新机制的普通指令技能做验证；新增反应类别、特殊战斗机制另列后续范围。

### 5.4 战斗状态的生命周期

| 时机 | 必须明确的处理 |
|---|---|
| 新游戏或新角色创建 | 从角色配置初始化扩展状态 |
| 普通角色进入战斗 | 从持久状态建立战斗工作副本 |
| 敌人或召唤单位创建 | 从对应模板建立实例状态，不错误绑定玩家进度 |
| 同一模板出现多个单位 | 每个实例具有独立临时状态 |
| 战斗槽位被复用 | 清除前一个单位的扩展状态 |
| 战斗结束 | 仅回写实际应持久化的变化 |
| 读档或切换 MOD | 清除上一局、上一档或上一 MOD 的运行缓存 |

战斗槽号不能作为跨战斗持久身份，指针地址也不能直接写入存档。

如果未来支持战斗中存档，需要单独序列化战斗实例及其关联关系，不属于仅扩展普通存档的自然结果。

## 六、存档扩展设计

### 6.1 推荐独立文件尾扩展块

建议保留现有两个压缩帧的协议，在第二帧结束之后追加独立扩展封套：

```text
sav.N
  [Frame 1 压缩长度][Frame 1 压缩数据]
  [Frame 2 压缩长度][Frame 2 压缩数据]
  [扩展头][技能扩展负载]
```

注意这里是 **两个压缩帧之外的文件尾部**，不是第二帧解压内容中的 WarPC 尾部。

理由：

1. 当前编辑器把 `Frame2[9200:]` 全部当成 WarPC。
2. 在该区域混入扩展技能字节，会破坏角色数量推导，或被错误解释为角色数据。
3. 原版读档函数为第二帧分配固定大小的解压缓冲区，直接扩大第二帧内容可能造成越界写入。
4. 文件尾独立块使旧数据区域和新增数据区域具有明确边界。

原版读档函数在读取第二帧后关闭文件，这说明独立尾块具有可利用的容器兼容性；但这不代表原版能够理解新增技能，也不代表所有编辑器会保留尾块。

证据：

- [原版固定缓冲区与关闭文件：41103C.c:29](../../TKS/反编译产物/decompile/41103C.c#L29)
- [当前 WarPC 段切分：save_editor.py:422](../save_editor/save_editor.py#L422)
- [角色编辑器对记录整除的要求：warpc_editor.py:261](../warpc_editor/warpc_editor.py#L261)

### 6.2 扩展封套需要表达的信息

以下为协议设计要求，字段宽度、魔数取值及负载编码需在实施阶段统一冻结，不能视为已有文件格式。

| 信息 | 用途 |
|---|---|
| 固定魔数 | 区分扩展块与无关尾部数据 |
| 格式版本 | 决定解析与迁移规则 |
| 头部长度、负载长度 | 明确边界，支持完整性检查 |
| 负载校验值 | 检测意外损坏，不作为防篡改认证 |
| MOD 标识及资源版本或指纹 | 防止用错误资源解释同一编号 |
| 角色、技能身份映射版本 | 识别编号迁移需求 |
| 角色与技能状态记录 | 恢复实际扩展进度 |
| 必要的持久扩展覆盖 | 仅保存已确认会变化的额外状态 |

负载不应再次复制全部 TKSkill 静态定义。

初版优先使用可明确校验的简单记录结构；不要直接转储 C++ 对象、指针、容器内存或带编译器填充的结构体。

### 6.2.1 当前 v1 代码协议

当前实现位于 `editor_utils/skill_extension.py`，已经冻结 64 字节小端头：

| 偏移 | 大小 | 字段 |
|---:|---:|---|
| 0 | 4 | Magic `TKSX` |
| 4 | 2 | 协议版本，当前为 1 |
| 6 | 2 | 头长度，当前为 64 |
| 8 | 4 | 负载长度 |
| 12 | 4 | 负载 CRC32 |
| 16 | 4 | MOD 身份指纹 |
| 20 | 2 | 角色数量 |
| 22 | 2 | 起始技能编号，当前为 350 |
| 24 | 2 | 扩展技能数量 |
| 26 | 2 | 稀疏覆盖数量 |
| 28 | 2 | 标志位 |
| 30 | 2 | 保留 |
| 32 | 4 | 映射版本 |
| 36 | 2 | 角色容量 |
| 38 | 2 | 技能容量 |
| 40 | 24 | 保留，必须为零 |

负载先存放 `角色数量 × 扩展技能数量` 的字节学习状态矩阵，再存放固定 8 字节的稀疏覆盖：
`actor_id(uint16) + skill_id(uint16) + tkkon_id(int16) + flags(uint16)`。

Python 解析器已校验魔数、版本、长度、CRC、头部末尾 24 字节、重复覆盖和矩阵索引，空尾部返回旧档标记。但偏移 30 的保留字段被解包为 `_reserved0` 后未检查，不能宣称所有保留字段都已校验。

`migrate_skill_extension()` 拒绝缩小矩阵；原版专用包装却以 `max(实际数量, 固定容量)` 传参，因此尚不能证明当前资源确实包含存档引用的全部角色和技能。Python 可接受的容量、覆盖数量和效果值也未与游戏补丁完全对齐，具体差异见第十五节。

### 6.3 读取顺序

1. 校验并解码两个既有压缩帧。
2. 依据帧头中的压缩长度计算第二帧结束位置。
3. 检查是否存在扩展封套。
4. 验证版本、长度、记录数量和校验信息。
5. 验证 MOD 身份以及角色、技能引用。
6. 在临时对象中构造完整待加载状态。
7. 所有检查通过后，再替换当前运行状态。

不能先覆盖当前游戏，再发现扩展块不可用后继续运行半套状态。

### 6.4 没有扩展块不一定意味着“正常旧档”

无扩展块可能有两种来源：

- 真正的原版或旧版存档。
- 扩展存档被不支持扩展的编辑器重写，导致尾部丢失。

如果原有装备槽已经引用新增技能，而扩展块不存在，应判为不完整或需要明确迁移处理，不能静默清零。

如果没有任何可识别的新技能引用，仅凭旧格式本体未必能判断尾部曾经存在；界面应明确提示“按旧档导入”，不要声称能够可靠恢复已经丢失的扩展进度。

### 6.5 旧档初始化与迁移规则

导入旧档时：

- 保留已有角色属性、装备和旧技能进度。
- 按对应 MOD 的角色技能配置建立新增状态。
- 区分“尚不可学”“等待条件”“可学习”“已经掌握”，不要统一填 0 或统一设为已学会。
- 若新技能的开放条件依赖剧情，使用明确迁移规则，不能凭空推断玩家是否满足条件。
- 迁移完成后写入当前扩展版本，使后续加载不重复授予或重复初始化。

新增资源版本时：

- 已有扩展技能以存档进度为准。
- 新加入的技能才执行新增条目初始化或版本迁移。
- 删除、重命名或改变编号的技能必须有明确策略。
- 明确记录的状态 0 不能被误当成“没有存档状态”，从而在每次更新后重新开放。

### 6.6 保存一致性

建议的最终写入流程：

1. 生成同一时点的旧格式数据与扩展状态快照。
2. 将两个压缩帧及扩展块完整写入同目录临时文件。
3. 检查写入结果，并进行必要的解析回读。
4. 使用平台支持的替换操作提交文件，保留原档备份。
5. 替换失败时保留可用旧档，不宣布保存成功。

仅在原版写档结束后再次打开正式文件追加尾块，仍有“旧部分已更新、扩展部分尚未写入”的中断窗口；这只能作为临时验证方式，不能被描述成完整的事务保存。

游戏另有槽位摘要文件时，摘要不应成为扩展状态的唯一依据；其更新与主存档提交的先后关系也需要纳入失败恢复测试。

### 6.7 为什么不优先采用旁路存档文件

旁路文件如 `sav.N.ext` 便于早期调试，但带来额外配对问题：

- 用户复制主存档时可能漏掉扩展文件。
- 覆盖、备份或回滚两个文件时可能来自不同时间点。
- 主存档写成功、扩展文件写失败会产生状态不一致。

若验证阶段采用旁路文件，必须绑定主存档身份或内容摘要，并在不匹配时拒绝静默合并；正式格式优先采用单文件扩展块。

## 七、兼容性边界

| 组合 | 建议行为 |
|---|---|
| 旧存档 + 新版运行时 + 匹配 MOD | 明确导入，保留旧进度并初始化新增状态 |
| 扩展存档 + 同版本运行时和资源 | 完整恢复并校验引用 |
| 扩展存档 + 可迁移的新资源版本 | 执行有版本记录的迁移 |
| 扩展存档 + 缺少技能或不同 MOD | 阻止正常加载，提示缺失依赖或需要迁移 |
| 扩展存档 + 未打补丁的原版 | 不保证可用，不能仅凭旧帧可解压宣称兼容 |
| 扩展存档 + 旧版编辑器写回 | 可能丢失尾块，应明确禁止或警告 |
| 扩展存档 + 支持扩展的新编辑器 | 修改所需字段，同时保留其余有效状态 |
| 未识别的扩展版本 + 新编辑器 | 默认不允许有损写回 |
| 无扩展块但含新增技能引用 | 视为不完整或需专门迁移，不静默继续 |

**“新版能读旧档”与“旧版能读新档”是两个不同目标。**

原版程序即使忽略文件尾块，仍可能读取旧 WarPC 装备槽中的新增编号，从不存在的技能表位置取数据，因此不能保证安全降级。

若未来需要“导出原版兼容存档”，应作为显式的有损转换功能，清理不支持的引用并告知进度损失，而不是正常保存时自动执行。

## 八、编辑器侧改造

### 8.1 保留二进制格式适配，改变上层编辑模型

建议将 WarPC 原始读写保留为兼容适配层，上层角色技能页面不再直接依赖“第几个原始字段就是第几个技能”。

职责可以分为：

- 原版 WarPC 编解码。
- 动态技能定义目录。
- 角色技能配置与运行状态访问。
- 统一存档容器读写。

不要求把现有整个编辑器重写，只集中改造技能相关路径。

### 8.2 角色技能页面的建议交互

以角色技能清单为主要编辑入口：

| 列 | 内容 |
|---|---|
| 技能 | 名称与稳定编号 |
| 类型 | 指令、属性、反应、移动等 |
| 初始状态或实际状态 | 区分模板模式与存档模式 |
| 装备槽 | 现有槽位引用，不顺便扩大槽位数 |
| 默认效果 | 技能资源提供的 TKKon 映射 |
| 角色覆盖 | 仅显示与默认效果不同的配置 |
| 来源 | 原版数据、扩展配置或存档状态 |

配合搜索、类型筛选、批量赋予技能组，可以减少维护完整矩阵的负担。

原始字段视图仍可保留用于逆向和高级调试，但不再作为扩展技能的主编辑方式。

### 8.3 技能定义编辑器

当前工作区的 `skill_editor` 已按实际完整记录数加载、保存，并允许追加条目；这解决了原先固定 350 条的截断问题，但还需要：

- 统一编辑器与原版补丁允许的技能容量，不能编辑器无限追加而游戏固定扫描到 696。
- 校验编号、关联技能与效果资源引用。
- 增加条目时保持旧编号稳定。
- 对当前引擎不支持的类型、编号或技能组结构明确提示。
- 验证新增、复制、修改类型、应用和保存的完整交互，而不只测试底层文件往返。

仅把 `SKILL_CNT` 改成另一个固定数字，不是最终扩展接口。

证据：[skill_editor.py](../skill_editor/skill_editor.py)、[动态目录测试](../tests/test_skill_editor_dynamic.py)。

### 8.4 WarPC 编辑器

当前工作区已动态加载技能目录和关系，并在模板表单提供新增技能状态页，但仍须补齐：

- `WarPC.dat.tksx` 到原版游戏的实际加载链路。
- 存档模式、表格模式和批量工具对扩展状态的统一支持。
- 角色重置、复制、移动、导入、导出时，原记录与扩展状态及效果覆盖的一致性。
- 旧效果区的真实索引与特殊字段映射，不以筛选后的显示序号代替技能编号协议。
- 默认效果与角色覆盖的编辑及资源合法性检查。

不能只修改主窗口而遗漏其他编辑入口，也不能把伴随文件写出当成配置已被游戏使用。

证据：[warpc_editor.py](../warpc_editor/warpc_editor.py)、[warpc_table_mode.py](../warpc_editor/warpc_table_mode.py)、[batch_skill_learn.py](../warpc_editor/batch_skill_learn.py)。

### 8.5 两个编辑器都需要保留扩展块

当前两个编辑器已经接入尾部解析和写回，现有测试覆盖了合法扩展块的往返保留。这是必要条件，但不代表旧档初始化、资源迁移、角色结构变化和保存失败恢复都已正确。

修改金币、属性或装备时，必须保留已有学习进度与效果配置，不能隐式授予新增状态；模板保存还需要保证 `WarPC.dat` 与 `.tksx` 伴随配置成对备份、成对提交。

对于不认识的扩展版本，至少应阻止有损保存；若未来支持原样保留未知块，也需要明确哪些编辑操作会破坏块与旧数据的关联。

## 九、原版交付与启动模式

### 9.1 重制版只作参考

`TKSRemake` 仅供只读理解原版菜单、学习、效果和战斗副本的逻辑，不纳入本次修改、扩展、运行验收或扩展存档交换要求。本文保留的重制版源码链接只是辅助证据；涉及原版地址、布局、Hook 和补丁兼容性时，以原版工程和 EXE 实际指令为准。

### 9.2 两种必须支持的入口

| 模式 | 必须验证的实际链路 |
|---|---|
| GUI 注入启动 | `tks_launcher_gui/main.py` → GUI 启动工作线程 → 共享补丁流水线 → 原版进程 |
| GUI 生成启动器 | 同一 GUI 的生成入口 → `GenerateExeDialog` → `ExeBuilder` → 独立启动生成的 EXE |

禁止使用或兼容 `tks_launcher_gui/cli_launcher.py`。直接调用构建器或模拟器可以定位问题，但不能替代上述两条实际交付链路的验收。

两条链路必须保持角色与技能容量、配置资源加载、补丁依赖、重定位、初始状态及存档协议一致。尤其需要分别检查原代码和注入 cave 中的 WarPC、TKSkill、TKKon 地址；一条链路能构建或注入，不代表另一条也正确。

### 9.3 全部补丁的兼容验收

对 `tks_launcher_gui/patches` 全目录建立清单并记录写入范围、依赖及冲突，不能只用六个扩容补丁的组合代替全量检查。重点组合包括人物/物品/效果表扩容、装备学习、菜单容量、存档修复、战斗回写、召唤扩展及宽屏。

需要同时验证补丁选择、排序、位点匹配、注入后的地址和行为；“没有重叠写入”也不等于语义兼容。若旧原型已被统一补丁取代，必须明确其互斥关系，并由 GUI 与构建链路阻止重复启用。

## 十三、待实施前确认的问题

1. 首批扩展是否只包含普通指令技能，还是需要立即支持反应与移动技能。
2. 第一阶段需要覆盖哪些 EXE 版本及第三方 MOD。
3. 新技能是否需要通过旧剧情进度自动解锁，具体规则是什么。

5. 哪些角色专属效果是静态资源，哪些确实可能在游戏中永久改变。
6. 角色和技能配置采用何种资源版本及迁移规则，在两种 GUI 交付链路中如何保持一致。
7. 是否需要战斗中存档；若需要，必须另行定义战斗实例序列化。
8. 扩展协议如何标识必需版本，以及不兼容时如何提示和停止写回。

这些问题应在实施阶段结合目标 MOD 冻结，不影响当前推荐的结构分离方向。200+ 角色兼容、全部现有补丁审计、两种 GUI 链路与重制版只读参考已是明确约束，不再列为待确认选项。

## 十四、最终建议

优先顺序是：**先分离技能定义、角色配置和实际进度，再在原版打通一个新增技能的完整生命周期，最后扩大数量与类型。**

原版保持 1054 字节 WarPC 记录，沿用现有人物数量扩容；新增学习状态和效果映射走独立扩展层。所有实施及验收均在原版补丁和编辑器完成，重制版只作原版逻辑参考。

真正需要长期稳定的不是某个新的技能数量常量，而是技能身份、状态归属、效果解析和存档协议。

## 十五、本次实现复核结果（2026-09-17）

### 15.1 总体判断

**本节是 2026-09-17 修复前的复核快照，不表示当前工作区仍未修复。** 当时实现不能表述为“已兼容全部补丁和两种启动模式，只差实机验证”：已有有效的协议、编辑器和补丁基础，但还存在可复现的功能断链、组合失败及角色索引错误。修复结果见第十六节。

| 目标 | 当前结论 |
|---|---|
| 扩大技能总数 | 动态读写和定义表重定位已有实现；原版状态层固定覆盖新增编号 350..696，不能宣称任意扩展 |
| 扩大每角色可学数 | 矩阵设计为 344 个旧常规状态加 347 个新增状态，理论共 691 个；模板配置尚未进入游戏，不能视为闭环完成 |

### 15.2 已存在且有测试支持的基础

- `skill_editor` 已取消固定 350 条读写截断，WarPC 技能目录也改为动态加载。
- Python 的 64 字节 `TKSX` v1 封套支持学习矩阵、稀疏覆盖及 CRC；两个编辑器的底层往返会保留合法扩展尾部。
- `tkskill_expand` 可以把定义表放入独立 PE 数据段；最小六补丁组合可以构建。
- 统一补丁包含学习、物品、装备、菜单、效果和存档等访问入口，既有 Unicorn 用例能执行其部分路径。

这些是后续修复的基础，不应因存在缺陷而推翻；但单入口测试和最小组合不能证明正常 GUI 交付链路正确。

### 15.3 阻断交付的确定问题

#### 原版执行入口的首要阻断

下列问题来自当前 `patch.json` 的实际机器码，不只是设计或实机测试尚未覆盖；核对的生成汇编片段与内嵌机器码一致。

1. **新游戏 Hook 破坏返回栈。** 统一补丁 `patch.json:339` 在 RVA `0x128A3` 用 `call` 替换原函数尾部，但 `init_new_game_state`（cave `+0x1740`）直接执行 `add esp,0x18; pop edi; pop esi; ret`，没有处理新增返回地址。按真实栈布局模拟，最终跳到原保存的 ESI 值，复现非法取指。生成汇编：`tools/upgrade_skill_ext_capacity.py:430`。
2. **学习菜单从错误地址读取状态。** 扫描入口把 `[ebp-4]` 的两个相邻 short 当作 dword；原函数 `[ebp-2]` 列表计数初值为 -1，因此计算出的源地址偏移 64KB。两个原位点又有不同的输入寄存器约定，却共用同一入口。按原版局部变量布局模拟出现非法内存读取；现有测试将整个 dword 写成 0，掩盖了问题。证据：统一补丁 `patch.json:13`、`:20`；生成汇编 `tools/upgrade_skill_ext_capacity.py:47`；原版 `4189BC.c:21`、`:24`；测试 `tests/test_skill_learn_state.py:143`。
3. **实际装备路径仍使用旧的 143×1 状态寻址。** `patch.json:220` 起使用的 mapped 入口调用 cave `+0x88B`，容量升级只重定向了另一入口 `+0x648`。角色 9 装备技能 350 实际写入 `EXT+9`，而不是 `EXT+9×347`；角色 ≥143 或技能 ≥351 会落入已被大矩阵覆盖的旧“无效地址”，造成串写。部分状态读取位点原本要求 EAX／EDX 输出，却替换为仅输出 ECX 的 helper，关联进度也会用到残留指针。必须按实际位点调用链逐项修正，不能只测未被调用的 helper。
4. **AI 效果读取仍多出 `0x222` 偏移。** 两个 AI 入口共用玩家的 `scratch - 2×skill` 返回值，而原 AI 后续指令还加 `0x222`。技能 350 的 scratch 虽为 590，实际效果读取却为 0。证据：统一补丁 `patch.json:297`、`:304`；生成汇编 `tools/upgrade_skill_ext_capacity.py:525`。测试应执行到原位点后续读取，不能只检查 scratch。
5. **初始化只写 500 字节，而不是 500×347 字节。** `init_extension_defaults`（cave `+0x1700`，生成汇编 `tools/upgrade_skill_ext_capacity.py:417`）未清空完整矩阵和战斗映射。模拟中预置的角色 499／技能 696 状态 30、战斗槽 2 映射值 123，在初始化后均原样残留；旧档无尾块也调用同一入口，形成跨档污染。

应先修复调用约定、真实访问路径和完整初始化，再谈扩容技能在游戏内可用。

#### A. 模板配置没有进入游戏

`warpc_editor/warpc_editor.py:1856`、`:3469` 读写 `WarPC.dat.tksx`，但启动器 Python 实现中没有该配置或 `skill_extension` 的消费入口。把某角色技能 350 设为已学并保存，不会自动使新游戏采用该配置。存档模式还在 `:1361` 隐藏附加技能页。

必须让两种 GUI 链路实际加载同一份模板状态与效果配置，并把模板初始化与存档进度恢复分开；不能依赖测试直接填充游戏内存。

#### B. 战斗映射截断角色编号

统一补丁活跃入口 `record_battle_map`（cave `+0x1C00`，关键写入从 `+0x1C09` 开始）将 `actor_id + 1` 写入一个字节，读取端同样按 byte 解码。边界执行结果如下：

| 角色编号 | 映射字节 | 新技能状态读取（预期 20） |
|---:|---:|---:|
| 200 | 201 | 20 |
| 254 | 255 | 20 |
| 255 | 0 | 0 |
| 256 | 1 | 0 |
| 299 | 44 | 0 |
| 499 | 244 | 0 |

错误来自角色映射而非 WarPC 记录长度，不能通过扩大矩阵再解决一次。映射应使用足以表示 0..499 和无效哨兵的类型，并同步修改所有读写端。证据入口：`tks_launcher_gui/patches/skill_ext_learn_state/patch.json:290`、`:368`。

生命周期也没有闭合：当前只在 `sub_444FD4` 的一条增援路径记录来源，常规队伍、初始敌人及召唤的其他复制入口未同步建立映射。映射未随开战、读档清理，菜单还会通过映射改读持久 WarPC，而非独立战斗副本。原版证据为 `decompile/4307CC.c:114`、`:224` 和 `decompile/431094.c:16`；因此仅扩大映射字段仍不足以避免实例串状态。

#### C. GUI 注入顺序与补丁预期相矛盾

加载器按目录名排序（`core/tkspatch_loader.py:548`），运行时按该顺序应用（`core/patch_engine.py:2616`）。`skill_ext_learn_state` 先于 `skill_scan_bound` 执行，却在 RVA `0x18BB1` 等三处要求扫描上限已经从 350 改为 344（统一补丁 `patch.json:34`）。实际注入模拟在第一处报 expect 不符，统一补丁失败。

此外，`tkskill_expand` 先改写加载地址及大小，随后 `tkskill_size` 的完整旧锚点匹配数变为 0。两条链路必须统一依赖和处理次序，不能把离线构建的分类型顺序当成运行时顺序。

#### D. 与必选菜单保护直接冲突

统一补丁和 `skill_menu_cap` 同时接管 RVA `0x39049`、`0x47C6B`（统一补丁 `patch.json:205`；菜单补丁 `patch.json:9`）。`skill_menu_cap` 在生成界面是锁定勾选的必选项（`ui/generate_exe_dialog.py:398`）；默认组合加统一补丁构建时，在 `0x47C6B` 发生字节校验失败。

简单取消菜单保护不是修复：战斗列表仍只有 12 项，必须把扩展状态读取与容量保护合并到同一条正确路径。旧 `skill_ext_effect_resolver` 另与统一补丁冲突六处效果位点，界面也未实现互斥约束。

#### E. GUI 运行时 WarPC 分配出两份数据源

这是既有流程问题，但直接阻断本次兼容目标。`core/launcher_pipeline.py:489` 先分配缓冲 A，并通过 `:603` 把 A 传给 cave；随后 `warpc_base_refs` 进入通用数据扩容处理，再分配 B 并重定位原代码。

500 条 WarPC 的模拟中，技能 cave 保留 7 个 A 引用，原代码出现 29 个 B 引用、0 个 A 引用。原代码、扩展学习 Hook、既有人物 Hook 和存档不能因此保证访问同一份状态。必须统一唯一 WarPC 分配及所有后续引用。

#### F. 新补丁即使未勾选，也挤掉运行时宽屏

`core/patch_engine.py:340`、`:360` 对全部补丁预分配 cave，筛选勾选项却发生在之后的 `:2620`；默认预算只有 16384 字节（`core/config_loader.py:24`）。当前完整目录布局中，宽屏需要到 `0x35D0 + 7717 = 21493` 字节，因超预算被跳过。

未勾选的 8704 字节统一技能 cave 仍占用预算，因此这是对现有宽屏使用的回归，不仅影响启用技能扩展的人。应按实际启用集合计算布局与容量，并在启动前明确报告无法容纳的组合。

#### G. 编辑器与游戏协议允许范围不一致

`editor_utils/skill_extension.py:85` 允许最多 65535 条覆盖，`:103` 允许负效果索引，`:320` 的原版专用迁移用 `max` 放大容量而不限制上限。补充执行探针中，下列数据都能通过 Python 序列化/解析，却被游戏加载入口拒绝并执行 `ExitProcess(1)`：

- 65 条稀疏覆盖（游戏上限是全局 64 条，不是每角色 64 条）；
- 覆盖中 `TKKon == -1`；
- 348 个扩展技能；
- 501 个角色。

反方向也有漏检：当前游戏加载入口接受 `mod_id = 12345` 和 `mapping_version = 999`，不验证它们是否匹配当前资源；非负 TKKon 32767 也可通过，而验证样本实际只有 650 条效果。标志位、部分保留字段及重复覆盖同样没有完整对齐。原文“非零 MOD 一律拒绝、严格校验映射版本”的断言不符合当前机器码。

保存入口还忽略 `fwrite` 和 `fclose` 的失败返回，模拟短写／关闭失败时正常返回，不能宣称保存成功或具备事务一致性。证据：`tools/upgrade_skill_ext_capacity.py:253`、`:289`、`:365`，对应当前内嵌存读档代码。

原版专用配置、迁移及保存入口应统一容量、MOD/映射版本与实际效果范围校验，并在完整写入、成功关闭后提交文件；不能把通用封套可表达的值等同于当前原版补丁可用的值。

#### H. 跨角色编辑会丢失或错配扩展状态

- `_reset_edit()`（`warpc_editor.py:3279`）重置当前角色时，把整个扩展草稿替换成已应用矩阵，其他角色待应用的新增状态也被撤销。
- `_move_record()`（`:3380`）立即交换已应用 WarPC 字段，却只交换草稿学习矩阵。随后保存时选择放弃草稿，会保留角色移动、撤销技能移动，造成错配；稀疏效果覆盖也没有随角色交换。
- 模板保存（`:3466`）只备份 `WarPC.dat`，没有配对备份 `.tksx`；伴随文件写失败也会留下不一致组合。

应以同一角色身份同步操作原记录、已应用状态、草稿状态和效果覆盖，保存时成对备份及提交。

### 15.4 其他已确认的缺口

- 初始化语义不一致：Python `create_original_game_extension()`（`editor_utils/skill_extension.py:344`）把角色 0 的所有新增状态设为 10，其余角色设为 1；当前补丁执行结果并不一致。例如角色 0 技能 351 是游戏 1／编辑器 10，角色 199 技能 350 是游戏 0／编辑器 1。WarPC 存档模式加载无尾块旧档会自动创建这份矩阵，普通属性编辑也可能改变新增技能开放状态。
- 默认效果只覆盖技能 350 → TKKon 590；其余新增技能没有通用默认效果资源，仍依赖数量有限的稀疏覆盖。尚不能支撑所有角色大量新增指令技能的正常配置。
- 存档写入的 MOD 身份仍为固定值，读取又未核对实际资源身份，不能宣称已实现多 MOD 身份兼容。
- `warpc_editor.py:1443` 新过滤排除了旧普通攻击条目的效果入口；`:1476` 仍按筛选序号而非真实技能编号定位旧字段，表格/批量规则又未同步。
- `skill_editor.py:1398` 的既有枚举应用问题直接影响新增技能：类型解析后 `continue` 而未写回，`-1-近战攻击` 又会因按 `-` 切分而触发 `ValueError`。这是既有缺陷，不归因为本次新增，但新增技能交互验收必须覆盖它。
- 表格、批处理和存档模式没有完整接通新增状态；角色导入还能绕过新增/复制操作的 500 条限制（`warpc_editor.py:3431`）。
- 351 条 TKSkill 的离线产物虽然分配了 64KB，加载大小仍固定为构建时的 32994 字节；随后只换成 352 条资源并不等于可以直接加载，应重新构建或实现一致的动态长度协议。

## 十九、进入游戏卡死的根因与外科式修复（2026-09-18）

实机（`python main.py` 注入启动，测试目录 `游戏目录（改版）`）反馈：标题页与
存档页正常，但进入新游戏或加载存档一律卡死。这正是第十八节“把 `sub_404024`
入口改成 `xor eax,eax; ret`”引入的回归：该函数不仅执行越界的解压写入，还负责
`free`/`fclose` 后删除 `tmp.dat` 并正常返回。整函数置空同时抹掉了删除与返回，
异步 WarPC 写回/回读握手因此无法收尾，进入场景的等待循环卡死。

根因定位（原版机器码，`sub_404024 @ 0x404024`）：

```text
004040BC  68 08 7F 75 00   push 0x757F08     ; 解压目标 WarPC（基址引用已被重定向到新缓冲）
004040C2  8B 55 C4         mov edx, [ebp-0x3c]
004040C5  52               push edx
004040C6  E8 49 EA 04 00   call 0x452B14     ; 越界写就发生在这里 —— 唯一的崩溃点
004040CB  83 C4 0C         add esp, 0xc
...     free / fclose ...
004040E2  68 0E 64 4E 00   push offset aTmpDat

004040EC  ... SEH 收尾 + ret                   ; 正常返回 —— 必须保留
```

`E8 49 EA 04 00`（`call 0x452B14`）在原版 `.text` 中唯一命中 `0x4040C6`。

修复：`warpc_base_refs` 的 `bytes_patches` 改为只 NOP 这一条解压调用——

- 模式 `8B 55 C4 52 E8 49 EA 04 00`，`expect_count=1`，把相对偏移 4..8 五个字节改为
  `90`（NOP）。
- 基址/字段锚定重定向先于字节补丁执行；被改写的是 `push` 立即数
  （`0x4040BD`），位于锚点起点 `0x4040C2` 之前，实测重定向前后该模式都唯一命中，
  不冲突。

效果：既消除已确认的越界写（解压被跳过），又保留 `tmp.dat` 消费与函数正常返回，
握手照常完成，因此不再卡死。启动器已注入 WarPC 缓冲区，回读本无数据语义，跳过
解压不影响进入场景后的数据。注入运行与生成 EXE 两条 GUI 链路都以相同语义应用该
`bytes_patches`（`patch_engine.apply_patch_bytes` 与
`generate_exe_dialog._build_data_section`→`ExeBuilder._apply_bytes_patch`，`replace`
键均为相对匹配起点的偏移）。

## 二十、进入游戏卡死的阶段性定位：init_battle_map 序言 Hook 自循环（2026-09-18）

> 本节保留当时的诊断与验证快照，不代表已找到全部阻断原因。其中 `0x3e8` 的清零长度仍有错误，列出的初始化访问违例也不能因为“并非当次改动引入”而排除；后续定位、修复与实机反馈见第二十一节。

第十九节的读回修复必要但不充分：实机仍卡死，日志（`tks_launcher_gui\logs\launcher_gui.log`
14:22 那次）确认读回补丁已生效（`8B 55 C4 52 E8 49 EA 04 00` 命中 1 处、NOP 于
`0x004040C2`），却仍“有声音但画面不动”。据此把范围收敛到统一技能扩展
`skill_ext_learn_state`（因 `TKSkill.dat` 为 351 条而被 `_ensure_skill_extension_for_extended_table`
强制启用）。

### 20.1 排除法：cave 本身无不可收敛循环、内存有哨兵

逐条反汇编 `patch.json` 内 9216 字节 cave 与全部 51 个位点后确认：

- 整个 cave 只有 8 处后向边，全部是 `rep`/`loop` 的定长循环或 CRC 的移位内层，
  均有界；`init_extension_defaults`、`load_append`、`save_append`、地址解析
  `0x1a00/0x1b00` 等入口都不含无限循环。
- 越界访问有哨兵：`0x1b00` 对 `base-0x757F08` 与 `base-0x9D707A` 都做范围判断，
  命中不了就返回固定哨兵 `0x6bc804`（落在 globals 内），不会野写。
- 被 hook 的原版循环都有界：`sub_4189BC`（学习扫描，`while v13<9 && v12<697`）、
  `sub_41E248`（关联传播，`while [ebp-2]<8`）都不因寄存器错配而失控。

因此卡死不是“cave 内死循环”，而是**注入的 hook 破坏了原版控制流**。

### 20.2 根因：`init_battle_map` 重建了错误的调用帧

位点 `0x307CC` 用注入 `call` 覆盖 `sub_4307CC` 的**序言** `55 8B EC 83 C4 C8`
（`push ebp; mov ebp,esp; add esp,-0x38`）。旧 cave 直接照抄这三条序言，但此刻栈顶
是注入 call 压入的合成返回地址（续点 `0x307D1`），其上是真正的调用者返回地址。
照抄序言后 `[ebp+4]` 变成**续点**而非调用者返回地址。`sub_4307CC` 自身尾声在
`0x43108F` 为 `mov esp,ebp; pop ebp; ret`，于是函数体跑完 `ret` 弹到续点
`0x307D1` → 再次进入函数体 → **无限重入**，主线程死循环、DirectSound 线程继续播放，
正是“有声音画面不动”。`sub_4307CC` 是战斗角色初始化，新游戏与读档进入开场战斗都触发它，
所以两条路径一致卡死。

修复后的 `init_battle_map`（cave `0x1cb0`）改为正确的序言 hook 跳板：

```text
pushad; pushfd; cld; mov edi,0x6b8000; xor eax,eax; mov ecx,0x3e8; rep stosb; popfd; popad
mov eax,[esp]        ; 取续点（注入 call 的合成返回）
add esp,4            ; 丢弃合成返回，真正的调用者返回地址升到 [esp]
push ebp; mov ebp,esp; add esp,-0x38   ; 忠实重放原序言，令 [ebp+4]=调用者返回地址
jmp eax              ; 跳回函数体续点
```

这样函数体尾声 `ret` 正确返回调用者，死循环消除。

### 20.3 附带修复：record_battle_map 的寄存器重放

位点 `0x450C7`（`sub_444FD4` 战斗角色复制）覆盖原两条 `movsx eax,[ebp-2];
movsx ecx,[ebp-4]`，紧随其后游戏用 `mov dl,[eax+0x953830]`。旧 cave 把 `eax`
覆写成 `movzx eax,[ebp-6]`（`[ebp-6]` 是源 WarPC 记录号），既破坏了游戏的标志字节
源地址，又没保存/恢复寄存器。修复后：`eax/ecx` 忠实重放为 `movsx[ebp-2]/movsx[ebp-4]`
交还游戏，battle map 用 `edx` 从 `[ebp-6]`（真正的源角色号）记录 `map[slot]=actor+1`
（`edx` 在续点之后由游戏 `movsx edx,[ebp-2]` 重载，可安全占用），长度不变。

## 二十一、持续卡死的补充根因与新游戏实机确认（2026-09-19）

### 21.1 现象与结论修正

第二十节修复后，用户仍报告：新游戏无法正常开始剧情，存档页加载后无法进入游戏，但音乐继续播放。原有 `init_battle_map` 返回测试已经通过，说明序言调用帧修复并不足以消除全部阻断，不能把该测试通过等同于游戏入口正常。

本轮继续检查未提交实现，复现并修复了下述三处确定错误。其中初始化入口错位与重定位误改指令会直接造成非法内存访问；战场清零越界则会破坏后续技能状态边界，不能单独据此断言发生死循环。

### 21.2 初始化模板代码错位一字节

`skill_ext_learn_state/patch.json` 中，`init_extension_defaults` 调用 cave 偏移 `0x2000`，但模板加载器的实际指令从 `0x2001` 才开始。调用落到了前面的填充字节，原本应执行的 `pushad; pushfd; cld` 被错位解码成 `add byte ptr [eax-0x64], ah`；模拟时 `eax=0`，因此访问 `0xFFFFFF9C` 并触发 `UC_ERR_READ_UNMAPPED`。

新游戏的 `init_new_game_state` 和没有 TKSX 尾块的旧档加载都会调用默认初始化，因此两条路径均受影响；错误发生在打开模板文件之前，与模板是否存在无关。第二十节中尚未解决的初始化测试访问违例正是必须继续追踪的证据，不能作为可忽略的既有失败。

修复将模板代码恢复到 `0x2000`，在末尾补齐填充，保持 cave 总长 `0x2400`（9216 字节）及其他入口偏移不变，同时恢复模板代码对 CRC 与错误处理入口的正确相对调用。

### 21.3 战场映射清零覆盖了技能数量

战场副本容量为 32 个槽，每个源角色映射占 2 字节，`0x006B8000` 起的映射区只需清理 `0x40`（64）字节；不能把 WarPC 的 500 角色容量当成同时在场的槽数。紧随映射区的是：

| 占位地址 | 含义 |
|---|---|
| `0x006B8040` | 已注册扩展技能数量，16 位 |
| `0x006B8044` | 技能编号上限，32 位 |

旧代码使用 `ecx=0x3e8` 清理 1000 字节，导致进入战场时把这两个字段一起清零。修复将默认初始化、扩展存档加载提交、战场初始化三处映射清零统一改为 64 字节，保留相邻元数据；外置学习矩阵仍按 `500 × 347` 初始化，并未缩减角色容量。

回归不再只检查映射区前几个字节为零，而是检查完整 64 字节及其后的边界，并连续执行新游戏/读档初始化与战场初始化，确认技能数量、上限和学习状态保持不变。

### 21.4 宽窗口重定位误把指令字节当成地址

裸 cave 测试通过后，实际生成 EXE 的读档入口仍在模拟中触发非法访问。原因是原重定位器逐字节扫描整个 `[0x00660000, 0x006C0000)` 地址窗口，没有区分指令与地址操作数，例如：

```text
6A 01 68 00 B0 68 00    ; push 1; push 0x0068B000
```

从首字节取四字节会得到 `0x0068016A`，恰好也在窗口内；将其重定位会改坏 `push` 指令，而真正的地址操作数在偏移 3。技能 cave 的 `load_append+0x09` 就存在这种伪命中，真实待重定位地址位于 `load_append+0x0C`。类似伪命中也存在于模板加载与其他文件读写代码中。

修复措施：

- 技能补丁声明 `globals_relocations`，列出从可达指令的真实地址操作数提取的 112 个 cave 偏移，不再对该补丁使用宽窗口字节猜测。
- 运行时注入与 EXE 生成共同使用 `core/memory.py` 的 `rebase_globals`；配置加载、补丁定义与 GUI 生成参数完整传递该表。
- 显式位点校验偏移范围和原始占位地址，只改写声明的四字节操作数；普通窄窗口补丁保留原有行为。
- 已计算完成的 `call` 相对位移与 `push_imm` 目标不再作为 globals 占位地址二次重定位。
- 回归从 cave 入口追踪可达指令，核对完整重定位表，并覆盖正负重定位偏移与跨指令伪命中，防止后续修改机器码后忘记同步该表。

## 二十二、技能列表空白与卡死的修复经验（2026-09-19，用户确认可用）

### 22.1 现象、证据与根因

进入游戏恢复后，角色 #0（未配置效果覆盖）打开技能列表为空，角色 #200（已配置附加技能）打开列表卡死。启动日志显示统一技能补丁 51 个位点全部写入成功，实际 WarPC、TKSkill 与 TKSX 模板也包含有效技能数据；因此“补丁应用成功”和“资源能够解析”仍不足以证明菜单正常。

对原版完整技能列表函数 `sub_4189BC` 的模拟确认两个错误：

1. **将相邻的两个 WORD 当成一个 DWORD。** `[ebp-4]` 是 16 位技能游标，`[ebp-2]` 是独立的 16 位列表末项索引，初始值为 `-1`。旧 cave 的 `mov ecx,[ebp-4]` 和返回指针计算中的 `add edx,[ebp-4]` 读取了四字节；游标为 0 时读到的是 `0xFFFF0000`，不是 0，进而错误偏移源地址和输出指针。
2. **把不同位点的寄存器约定混用。** `0x00418AE1` 原指令为 `lea edx,[eax+edx*2+0xB0]`，`0x00418C31` 则是 `lea eax,[ecx+eax*2+0xB0]`。两处共用只按第一种布局编写的扫描器，使第二处把角色偏移误当基址，触发非法读取；不能因为业务目的相同就复用同一个入口。

本轮修复首段扫描的 WORD 读取，并只回写其原指令的目标寄存器 EDX；第二段改用独立 `scan_followup` 入口，只按 16 位游标返回已合成缓冲区的地址到 EAX，不重复读取 WarPC。两段均保持其他寄存器与标志位，cave 总长和已有入口不变，显式 globals 重定位表同步更新为 113 项。

### 22.2 原有测试为何漏检

- 旧单入口测试把 `[ebp-4]` 写成四字节的 0，连带将真实游戏中应为 `-1` 的相邻列表索引清零，错误地掩盖了过宽读取。
- 测试只构造第一处入口的寄存器布局，没有覆盖第二处不同的原始 LEA 指令。
- 只断言合成缓冲区内容，没有验证完整列表函数、后续扫描、翻页与返回上一页；此前仅验证启动和进入战场也覆盖不到该路径。

### 22.4 后续维护规则

1. **位宽由字段定义及原版指令共同确定。** 16 位编号使用 `word ptr` 读取；是否符号扩展取决于原版约定与 `-1` 哨兵，不能把“目标寄存器为 32 位”理解为“源字段也要读 32 位”。
2. **每个 Hook 单独核对输入、输出及寄存器保持。** 指针是 32 位不代表指向的编号也是 32 位；栈参数占四字节也不代表其语义字段必然是 DWORD。
3. **相邻字段必须用非零、不同值测试。** 对 WORD 字段采用 `struct.pack("<hh", 游标, 相邻值)`，至少覆盖相邻值 `-1` 和正常非零值，禁止用整片零内存代替真实栈布局。
4. **断言完整控制流与边界。** 测试应从原版函数入口运行到真实返回位置，同时检查栈平衡、列表内容、容量和翻页标志；设置指令上限，将卡死转换为确定的测试失败。
5. **验证最终产物，不只验证模板。** 裸 cave、运行时重定位及生成 EXE 都要覆盖；机器码或入口变化时同步更新重定位表，不用旧脚本盲目重建覆盖已修补丁。
6. **不把宽读取一概判为错误。** 真实指针、DWORD 长度/版本、保存寄存器、合法的两 WORD 整体复制都可使用四字节；只有结合字段含义及后续用途，才能判断是否发生编号污染。
