# 数字列对齐补丁逆向与实现经验总结

> 对应补丁: `tks_launcher_gui/patches/num_column_align/` (fixed_layout_cave, 可选)
> 问题范围: 商店买卖页价格列、场品列表数量列、技能学习列表消耗列 (v3 纠正: 原记"装备列表数值列"实为菜单技能列表 sub_418C90, 装备页列表 sub_419A24 无数字列)
> 涉及函数: `sub_424A2C` (商店列表) / `sub_419458` (场品列表) / `sub_418C90` (装备列表) / `sub_4175D8` (文本绘制封装) / `sub_44E49C` (TextStep)

## 一、问题现象

MOD (子青版整合包) 给扩展物品的 TKT 名称加了颜色宏 (FCOLOR 绿色 + FRESET), 使其与原版物品区分。带宏物品出现在商店/列表中时, 行内的数字列 (价格、持有数、数量) 整体左移 48px, 与原版物品不对齐; 行尾固定坐标的小图标 (如商店的"1 5 金"三框) 不受影响。

像素实测 (商店页, 4 行商品):

| 物品 | 名称字节长 | 价格块 x | 持有数 x |
|---|---|---|---|
| 獅頭刀 #227 (原版) | 6 | 286-330 | 346 |
| 天妖戟 #234 (原版) | 6 | 275-330 | 346 |
| 青木弓 #604 (扩展) | 10 | 226-282 | 298 |
| 金烏劍 #605 (扩展) | 10 | 226-282 | 298 |

原版与扩展恰好差 48px = 4 个半角字符 —— 正是颜色宏的字节数 (`\x02\x15` + `\x01\x02` = 4 字节)。

## 二、根因: wvsprintfA 按字节对齐, 颜色宏字节占宽度却不渲染

商店列表每行的「名称 + 价格 + 持有数」是一次性格式化后整行绘制:

```c
// sub_424A2C (0x424B99 购买 / 0x424C18 出售, 出售分支价格已 /2)
sub_4175D8(obj, 285, 31*行+105, "%-16.16s%5dX%2d", TKT名称指针, 价格, 持有数);
```

`sub_4175D8` 内部用 Win32 **`wvsprintfA`** 格式化后再交给 TextStep (`sub_44E49C`) 渲染:

- `wvsprintfA` 是 ANSI 函数, `%-16.16s` 完全**按字节**处理: 名称不足 16 字节补空格、超过截断;
- TextStep 渲染时, TKT 控制字节 (`\x02`=FCOLOR、`\x01`=FRESET, 各跟 1 字节参数) 被解释为颜色切换, **不占像素**。

于是带宏名称 (10 字节) 只补 6 个空格, 可见的「名称→数字」间隔比原版 (6 字节补 10 空格) 少 4 个空格宽。全 EXE 共三处此类"名称补齐+数字"格式串:

| 格式串 | 地址 | 函数 | 界面 | 名称列字节 | 数字列 (字节/像素) |
|---|---|---|---|---|---|
| `%-16.16s%5dX%2d` | 0x4E9A49 / 0x4E9A59 | sub_424A2C 买/卖 | 商店 | 16 | 192px (x=477) |
| `%-24.24s%3d` | 0x4E9858 | sub_419458 | 场品列表 | 24 | 288px (x=573) |
| `%-10.10s%4d` | 0x4E9840 | sub_418C90 | 技能学习列表 (消耗列) | 10 | 120px (x=360) |

普通菜单不受影响: 它们画名称是单独一次 `sub_4175D8(obj, x, y, 名称指针)` 直绘 (无宽度补齐), 颜色宏照常生效且位置正确。

定位锚点: TKItem 全局表 `word_77CBCC` 的引用扫描 (0x419xxx 物品逻辑 + 0x424xxx 商店区), 格式串 strings 扫描, 反编译源码确认 (导出目录 `逆向工作区/decompile/`)。

## 三、字体度量: 字节对齐 = 像素对齐 (全角 = 2 × 半角)

FONT9696 字形 96×96, 引擎按 1/4 缩放渲染:

- 全角 (Big5 双字节) 步进 24px (墨迹 22px + 间隙);
- 半角 (ASCII, 经 word_4EC810 重编码) 步进 12px;
- **全角步进 = 2 × 半角步进**, 因此「N 字节名称 + (列宽-N) 空格」的渲染宽度 = 列宽×12px 恒定, 与名称字数无关 —— 这就是原版用字节补齐也能对齐的原因。

由此得到数字列固定坐标公式: `数字列 x = 名称列 x + 名称列字节宽 × 12`:
商店 285+16×12=477, 场品 285+24×12=573, 装备 240+10×12=360。

**坑: 页面态字体画布宽 640 是剪裁/换行边界。** 字体对象 +0x28 是字体画布宽度 (页面态 640、游戏态 856, `sub_44E290` 用作换行边界, 详见 widescreen_16_9 补丁注释④)。绘制文本越过 640 的部分被整体剪掉。商店 v1 补丁曾让价格段沿用原格式串并以空串作名称参数 (`%-16.16s` 输出 16 个前导空格), 数字起点落在 477+192=669 > 640 → **价格整列消失** (实测所有行价格不显示而名称正常)。所以数字段必须用无填充格式串直画。

## 四、修复方案: 一条 call 拆两段绘制

四个 hook 点 (商店买/卖 + 场品 + 装备) 的原版指令都是 `call sub_4175D8`, 参数已压好。cave 接管后拆成两段:

```asm
; 以商店入口为例 (进入时 [esp]=返回地址, 其后 7 参数: obj,x,y,fmt,name,price,cnt)
push esi                  ; callee-saved, 跨 call 保存 name
mov esi, [esp+0x18]       ; esi = name (原栈 [S0+0x14])
push 0x00643225           ; "%2d\0"  ← 立即数在栈上拼格式串, 不需要数据区
push 0x58643525           ; "%5dX"   → 栈上得到 "%5dX%2d\0"
lea eax, [esp]            ; eax = 栈上格式串地址
push cnt / price / eax(fmt) / y / 0x1DD(新x) / obj   ; 逆序压 6 参数
mov eax, 0x4175D8
call eax                  ; 数字段: "%5dX%2d" 只读 2 个变参, 多压无害
add esp, 0x20             ; 清栈 (含栈上字符串), 回到 push esi 之后
mov dword [esp+0x14], 0x4E9977  ; 原栈 fmt 槽 → "%s"
pop esi                   ; esp 回到进入时
mov eax, 0x4175D8
jmp eax                   ; 名称段 (尾调用): wvsprintf("%s", name) 画名称,
                          ; ret 弹出进入时的返回地址, 直达宿主 add esp 续接点
```

要点:

1. **多余的变参无害**: wvsprintfA 按 fmt 里的 `%` 个数读变参。统一压 6 参数即可同时服务商店 (fmt 读 2 个) 与场品/装备 (读 1 个);
2. **尾调用 jmp 复用宿主栈**: 数字段用 call (自己构造的参数自己清), 名称段用 jmp 直通 4175D8 的 ret 弹出宿主返回地址, 原参数栈由宿主自己的 `add esp,0x1C/0x18` 清理 —— cave 无需知道参数个数;
3. **fmt 槽可以覆写**: 栈上参数是副本, 覆写不影响宿主; 名称段不需要动 x 槽 (原 x 就是名称列起点);
4. **栈上拼格式串** (`push imm32` 两个 dword) 避免了"字符串常量地址依赖 cave_base 运行时分配"的重定位问题;
5. **全部地址都是 EXE 固定地址** (无 ASLR), cave 机器码可以完全静态生成。

## 五、引擎基建: cave_hook vs fixed_layout_cave

一个补丁要挂多个不同 pattern 的 hook 点时, 两者的差异是本次最大的坑源:

| | cave_hook | fixed_layout_cave |
|---|---|---|
| hook 数 | 1 个 pattern (可多命中, 共用同一 cave 入口) | `hooks[]` 数组, 每项独立 pattern + `cave_entry_offset` |
| 写入点 | pattern 起点 + **`hook_offset`** 字段修正 | **pattern 起点** (没有 hook_offset 概念!) |
| 冲突检测 | detect_hook_type + HookTable (按首字节判 E8/E9/68 → 原版 call rel32 会被误报「外部 MOD 占用」) | **无冲突检测, 直接覆盖** (对本场景反而合适) |
| pattern 通配 | 支持 `**`/`??` | **不支持** (`int('**',16)` 直接抛异常), 必须写死含 rel32 的完整字节; 可配 `fallback_rva` (写入点 RVA) 兜底 |
| cave 块 | 自动布局 (cave_code 长度申报) | cave_code.py 的 `build_cave_block(cave_base, n)` 运行时生成; 布局引擎按块内**非零区间**硬编码预留 |

fixed_layout_cave 的布局预留按"块内非零区间"硬编码 (`_fixed_layout_span` → `force_offset`), **先声明的先占**。`0x680` 起是 summon_extend 的惯例占用区 (其块 [0x680,0x7EB)), 新 fixed 补丁必须避让, 否则布局引擎会阻止**对方**应用 (本次实测 summon_extend 被 CAVE-LAYOUT-ERR 静默跳过, 日志可见)。

## 六、踩坑记录 (按时间序)

1. **hook_conflict_action 声明 skip 导致补丁整体跳过**。cave_hook 的冲突检测把原版 `call rel32` 误判为「外部 MOD 占用」(detect_hook_type 只看首字节 E8)。凡 hook 点原版就是 call/jmp 的补丁, 必须声明 `override` (先例: duel_self_target_fix)。教训: **补丁应用后必须看启动器日志确认** (`logs/launcher_gui.log`), 日志里 `按 skip 处理` 一行就是全部证据。

2. **16 空格前缀越过 640 画布剪裁, 价格整列消失**。空串名称 + 原格式串的方案 (v1) 数学上对齐、物理上被剪。教训: **数字段必须用无填充格式串直画**, 且新 x + 数字宽必须 < 640。修复手段是栈上拼 `"%5dX%2d"` 立即数。

3. **fixed_layout_cave 的 hooks[] 没有 hook_offset, pattern 必须等于写入点**。首版沿用 cave_hook 习惯在 pattern 前面带压参指令上下文, 引擎把 call cave 写到了 `push 0x11D` 上 (日志 `hook shop_buy @0x00424B90` 一眼可辨), cave 进入时栈中无 obj/x → 读参错位 → **打开商店黑屏**。修正: pattern 直接以 `E8 rel32 + add esp` 开头 (rel32 写死指向 0x4175D8, 四个写入点各自全 EXE 唯一)。

4. **手工推演栈偏移两次出错** (push esi 后 disp 差 4、y 槽 disp 0x18/0x1C 之误)。人肉算 disp8 不可靠, 最终以**符号栈模拟器** (capstone 逐指令 + dict 模拟栈槽) 收口: 模拟器自身也要先修正语义 (x86 `[esp+disp]` 不含 +4; call 压返回地址、jmp 不压; cdecl ret 后 esp 恢复), 然后 assert 每次调用的参数槽与返回路径。两次机器码 bug 都是它抓出来的。

5. **cave 块起点撞 summon_extend**。fixed 块的 0x680 起步是 summon_extend 的地盘, 布局引擎按声明顺序预留、后到者报 CAVE-LAYOUT-ERR 且**被跳过的可能是对方**。新 fixed 补丁的块起点要查现有 fixed 块占用 (日志 [CAVE-LAYOUT] 行) 后错开, 并保持 16 字节对齐。

6. **栈上格式串 immediate 手写十六进制字节序写反 (v3, 用户实测抓出)**。合并版 bag/equip 入口写成 `push 0x00336425`/`0x00346425` — 小端入栈后内存字节是 `25 64 33 00` = **"%d3\0"/"%d4\0"**, 宽度数字跑到 'd' 后面成了字面量: `wvsprintf("%d4", 50)` 输出 "504" 且无前导填充、从数字列起点左对齐 → 技能学习列表消耗显示 504/804/404 (角色悟性 50 时消耗恰为基础 jp_cost 50/80/40, 前两位"碰巧像对的"极具迷惑性)。正确值 `push 0x00643325`/`0x00643425` (内存 `25 33 64 00`="%3d\0"/`25 34 64 00`="%4d\0"); shop 入口两串 (`0x00643225`="%2d"、`0x58643525`="%5dX") 手写时恰好写对, 所以商店显示一直正常 — **同一次手写、三处只有一处对**, 印证"十六进制串接字符串"这种编码方式本身就是坑。教训: 栈上拼串的 immediate 必须用脚本从目标字符串生成并回读断言 (`imm.to_bytes(4,'little')` 应等于目标串), 不要手写 hex。

7. **sub_418C90 是技能列表, 不是装备列表 (v3 纠正误标)**。最初把 `%-10.10s%4d` @0x418DC4 判定为"装备数值列"——实际 sub_418C90 是菜单技能列表 (0x418DC4 处 `v4 = jp_cost×(250-悟性)/200` 后 `sub_4175D8(a1,240,31r+145,"%-10.10s%4d",名,消耗)`); 调度器 case 4 的真正装备页列表 sub_419A24 **只画名字无数字列**, 全 EXE 的补齐格式串也只有商店/场品/技能三处。equip_num 钩子实际服务的是技能学习消耗列 — 对无宏名字其渲染与原版逐位一致, 保留防未来技能名加宏 (MOD 现有 350 技能名 TKT raw 扫描无 \x01/\x02 宏)。教训: 判定"某格式串属于哪个界面"要以**取数语义**为准 (本例公式列就在同一调用点), 不能只看"名字+数字"的形状猜。

## 七、验证清单 (全部离线完成)

1. **pattern 全 EXE 唯一性**: 正则扫描原始文件, 核对命中 VA 与原 call 目标 (E8 位置 + 5 + rel32 = 0x4175D8);
2. **机器码反汇编核对**: capstone 逐条对照设计;
3. **符号栈模拟**: 模拟 push/pop/mov/lea/call/jmp 对栈槽的影响, assert 数字段参数 (obj/x/y/fmt/数字) 与名称段尾调用参数、返回路径;
4. **布局 dry-run**: `_build_cave_layout` 确认 fixed 块区间互不重叠、自动槽位避让;
5. **注入模拟**: 在 code_buf 副本上模拟写 cave 块 + 写 call rel32, 反汇编核对 call 目标与前后指令完整;
6. **启动器加载**: `load_patch_directory` 无 SCHEMA-FAIL;
7. **运行时日志**: 启动器日志逐行确认 4 个 hook 的写入地址是 E8 位置 (`@0x00424B99` 等), cave 块写入地址与布局声明一致;
8. **启动器测试**: 现有测试套件无回归 (test_patch_graph 的 import 错误为预存问题, 已用 git stash 对照确认)。

## 八、局限与遗留

- 名称段不再按 `%-N.Ns` 截断: 名称可见宽超过名称列 (商店 8 汉字 / 场品 12 汉字 / 装备 5 汉字) 会压到数字列。原版与常规 MOD 名称 (≤4 汉字) 不受影响; 若需要, 可在编辑器/整合包侧对名称长度做校验;
- `fixed_layout_cave` 的 apply 路径硬编码读取 `summon_limit` (2..8) 并传入 `build_cave_block` (summon_extend 的遗留特化), 非召唤补丁只能带着默认值 4 通过; 若后续再有 fixed 补丁, 可考虑把该参数泛化;
- 若 MOD 未来出现新的"名称+数字"对齐列表 (新的 `%-N.Ns` 格式串), 按同法追加 hooks[] 项与 cave 入口即可, 布局需重新避让。
