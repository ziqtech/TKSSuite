## 零、尺寸/布局调整速查

### v7.10：失效状态不占位（占位与绘制判定同源）

**用户实测反馈**：两个状态中一个到期失效后，剩余状态图标未重新居中。

**根因分析**（逆向原版状态机制确认）：v7.9 的位置计数（n1/k）只判 `st≠0`，而图标绘制还需通过帧号越界检查（`F=fbase+st-1 ≥ [obj+0x18]` → jae 跳过）。任何"st 残留非零但帧号无效"的数据状态都会造成**图标消失但位置占位**的不一致。

**原版状态机制**（逆向 442D44/4326CC/4431D4/4327A0）：

| 操作 | 行为 |
|---|---|
| 中状态（sub_442D44） | 从头找**第一个空槽**写入（低字节 statusID，高字节剩余回合数，无压缩） |
| 到期（sub_4326CC，回合结算） | 回合数递减到 0 → 清 statusID（`*v4=0`），同时清 byte_9E048E 标志 |
| 主动移除（sub_4431D4，如解药） | 清 statusID + 回合数 |
| 战斗重置（sub_4327A0） | 清临时状态 + **槽表压缩前移**（保留永久状态，负回合数） |
| 面板显示（sub_437664） | 低字节 statusID ≠ 0 即画，帧号 = `word_9D6F76+(char)statusID-1` |

**修复**：单位级计算 `maxst = [obj+0x18]总帧数 - fbase + 1`（statusID 有效上限，Mu2 = 107-76+1 = 32），有效性判定三处同源：

```
valid(st) = st != 0 && (unsigned)st < maxst
           ├─ n1 预扫描 (esi 持有 maxst)
           ├─ k 前缀计数 (ebx 持有)
           └─ 绘制跳过 (F≥total 双保险)
```

数学等价性：`F = fbase+st-1 < total ⟺ st < total-fbase+1`。**画不画与占不占位永远一致**；对正常数据（0=空、1..31=有效状态）行为完全不变。

**v7.10 首版栈槽覆写 bug（unicorn 用例 4/5 当场抓获，单槽用例测不出）**：maxst 首版存 V_BLOB 栈槽（0x64）——首个有效槽的 JVG 导航即覆写该槽为 blob 指针（无符号巨大）→ 后续槽的 k 计数把失效槽 0xFF 全判有效。修复 = maxst 一律**寄存器持有**（n1 预扫描用 esi，k 计数用 ebx；行基改在 k 完成后从 slot 重算 `mov ebx,eax; and ebx,4`）。教训：**跨 JVG 导航存活的值必须核对每个栈槽在槽内路径的写入点**，或干脆用寄存器。

### v7.9：行1 图标按激活数紧凑居中，行2 从左到右

| 激活数 n1 | offset1 = (124-31n)>>1 | 图标组范围 (相对 x0) | 组中心 |
|---|---|---|---|
| 1 | 46 | [46, 76] | 61（行中心 61.5，偏左 0.5px） |
| 2 | 31 | [31, 92] | 61.5（精确居中） |
| 3 | 15 | [15, 107] | 61（偏左 0.5px） |
| 4 | 0 | [0, 123] | 61.5（满行 = v7.7 原布局） |

**布局公式**（图标位置由「行内第 k 个激活状态」决定，空槽不占位）：

```
行1 (槽 0-3): xx = x0 + offset1 + k*31     (居中, 组宽 = 31n-1)
行2 (槽 4-7): xx = x0 + k*31               (超出 4 个后从左到右, 不居中)
yy = ytop + 31 - (slot>>2)*31               (不变)
```

**实现要点**：

- **单位级预扫描**：n1 = Σ(slot 0..3 的 st≠0)（4 次内存读），`offset1 = (124-31*n1)>>1` 存栈槽 V_OFF1（复用旧 V_UIDX 槽 0x6C——u 在 ytop/x0 计算后死亡，RLE 像素循环不触及）。
- **槽级前缀计数**：k = Σ_{i<slot, 同行}(st[i]≠0)（行基 = `slot&4`，≤3 次迭代小循环），st 提前到槽循环最前读取（空槽判定 + k 计数双依赖）。
- 状态分散（如 slot1+3）也紧凑排到中两格——视觉始终居中，与用户描述一致（1 个居中、2 个占第二三格、3 个居中、4 个占满）。
- 钳位不变：逐槽 xx≤610（最大 xx=x0+93 与 v7.7 一致）。

**v7.9 开发中被 capstone 抓到的编码 bug**（第 1 层验证的即时价值）：`movzx edx,byte[ecx+eax*2+0x56]` 的 modrm 误写 `0x14`（mod=00 无位移）→ capstone 全量解码立即暴露 `movzx edx,[ecx+eax*2] + push esi`（disp8 0x56 沦为独立指令）。正确为 `0x54`（mod=01|reg=edx|rm=100+SIB）。此为铁律 2 的变体：**disp8 操作数的 modrm mod 位必须 = 01**。

**unicorn 验证升级**：12 项检查（单状态居中×2 / 两状态连续+分散 / 三状态 / 四状态满行 / 行2 单+分散 / 行1+行2 混合 / 满两行 / 尾声双路径）。断言从「邻格全零」升级为「**全行区域 123×30 除图标矩形外全零**」（空槽透明 + 无幽灵块 + 步进/居中偏移正确三合一）。v7.10 再增 5 项**失效残留用例**（statusID=0xFF/超界值/边界 32 + 有效槽 → 剩余图标必须重新居中），共 17 项。

### v7.8：绘制层级修复（低于战斗菜单、高于角色）+ 空槽透明

| 项 | v7.7 | v7.8 |
|---|---|---|
| hook 点 | 0x43A8BD（面板尾部，菜单**之后**） | **0x43A7A6**（面板 switch bounds-ja，菜单**之前**） |
| 被替换指令 | `cmp word[0x9D6C88],0`（8B） | `ja 0x43A8BD`（6B：`0F 87 11 01 00 00`） |
| 尾声重放 | 逐字节重放 cmp 后 ret（jl 用其标志） | popad 后重放 `cmp edx,0x2b` 重新求值：未取→ret；取→`add [esp],0x112` 返回地址 0x43A7AB→0x43A8BD |
| 图标层级 | 高于一切（盖住菜单，已知局限） | **高于角色精灵、低于战斗菜单/信息面板/回合表** |
| 空槽 | 0x2104 暗灰 30×30 填充 | **透明不绘制**（st==0 直接跳下一槽） |
| cave 长度 | 893B | 845B（v7.9 居中布局后 944B；v7.10 失效不占位后 987B） |

层级依据：`sub_43A050` 的渲染顺序 = 单位格网循环（阴影+身体精灵，0x43A5D6..0x43A796）→ **hook 点 0x43A7A6** → 面板 switch（`sub_437664` 信息面板 / `sub_4393A8` / `sub_43844C` / `sub_439750` 菜单）→ `sub_439D34` 回合表。与 `war_hp_mp_bars` v5 的层级语义一致（该补丁同样因「v4.1 尾部 hook 盖住菜单」回移到 0x43A79C）。

**与血条补丁共存（零字节重叠）**：`war_hp_mp_bars` hook @0x43A79C（pattern 10B 止于 0x43A7A5，hook 写 0x43A79C..0x43A7A2）；本补丁 pattern 12B 始于 0x43A7A6，hook 写 0x43A7A6..0x43A7AB。两者无论应用顺序如何互不干扰（启动器预扫描统一在原始 code_buf 上进行，HookTable 按单偏移注册）。pattern 含后续 `mov dl,[edx+0x43a7b9]` 共 12 字节，全 exe 唯一（裸 6B `0F 87 11 01 00 00` 有 3 处命中，不唯一）。

**hook 条件跳转的尾声设计**（本次新增的架构模式）：被替换的 `ja` 依赖 `cmp edx,0x2b`（0x43A7A3）的标志位，而 cave 主体会破坏标志。解法：`popad` 恢复 edx（= `movsx word[9D6C88]` 的原值）后**重放 cmp 重新求值**，而非保存/恢复 EFLAGS。两条返回路径：

```
popad                    ; edx = movsx word[9D6C88]
cmp  edx, 0x2b           ; 重放 bounds 检查 → 重新求值标志
jbe  L_ret               ; edx ≤ 0x2B → 原 ja 未取
add  dword [esp], 0x112  ; edx > 0x2B → E8 返回地址 0x43A7AB → 0x43A8BD
L_ret: ret               ; 未取: 返回 0x43A7AB(NOP)→0x43A7AC 跳转表
                         ; 取:   返回 0x43A8BD (面板 default, 无菜单路径)
```

栈安全论证（与 v6 挂车式失败的本质区别）：被调整的返回地址是 **E8 自己压入的**（位于 esp0 之下，属 cave 所有），两路径 ret 后 esp 均严格回到 esp0；**绝不写调用者活跃栈帧**。v6.1 的「返回地址搬家」翻车在于把数据写到 esp0+0x44（调用者的活跃局部变量区）。调整自身返回地址是标准 trampoline 技术。

`word_9D6C88 = -1`（面板 default）时单位仍绘制但无菜单（战斗过场/背景渲染模式，见 43A8D8.c:37 先置 -1 再调 sub_43A050）——因此 hook 必须在 `ja` 的**公共路径**上（0x43A7AC/0x43A7B2 两处会被取跳过的路径绕过，不可用）。

## 一、补丁目标与最终效果

**目标**：战斗中，在每个存活单位的头顶（血条上方）显示**两行 8 个异常状态槽**（每行 4 槽、从下往上排列，各 30×30px 与战斗面板同尺寸，间隔 1px），活动槽显示 `Mu2.JVG` 中对应的状态图标（原尺寸直采），空槽透明不绘制；**行1 图标按激活数紧凑居中**（1 个居中、2 个占中两格、3 个居中、4 个占满，超出后行2 从左到右）；**图标层级高于角色精灵、低于战斗菜单/信息面板/回合表**。

**最终效果**（v7.10）：

- 状态图标以 **2 行 × 4 槽**区域显示在单位头顶血条上方（行1 紧贴血条、行2 在其上）；
- 行1 图标按激活数紧凑居中（单个状态不再偏在最左格）；状态到期失效后剩余图标即时重新居中（失效槽不占位）；
- 中状态后显示 Mu2.JVG 的真实彩色图标（RGB565 直写，30×30 原尺寸清晰）；
- 空槽透明（不绘制任何像素、不占位）；
- 图标被战斗菜单/信息面板正确遮挡，但不被角色精灵遮挡；
- 无崩溃、无幽灵块、无栈泄漏。

**原版行为参考**：原版游戏本身在「单位信息面板」（`sub_437664`）中显示状态图标，行布局为 8 槽、步进 37px、图标 30×30 原尺寸。本补丁将同样的数据以**同样的原尺寸**搬到单位头顶，并改为更紧凑的两行布局。

## 二、最终架构（v7.10）

### 2.1 Hook 点

```
sub_43A050 @ 0x43A7A6
替换指令: ja 0x43A8BD   (6 字节: 0F 87 11 01 00 00, 面板 switch 的越界检查)
pattern:  "0F 87 11 01 00 00 8A 92 B9 A7 43 00" (含后续 mov dl, 12B 全 exe 唯一)
```

该点位于单位精灵循环之后、面板 switch（`sub_437664`/`sub_4393A8`/`sub_43844C`/`sub_439750`）与回合表 `sub_439D34` 之前，**每帧必经一次**（含 `word_9D6C88=-1` 的无菜单路径）。cave 尾部 `popad` 后重放 `cmp edx,0x2b` 重新求值原 `ja` 条件，未取则 `ret` 返回 0x43A7AB(NOP)→0x43A7AC 跳转表，取则 `add dword[esp],0x112` 把 E8 返回地址调整为 0x43A8BD（default 路径）后 `ret`。

> ⚠ 此架构为 v4 起沿用、多轮实测无崩溃的安全模式（指令整体替换 + 尾部重放 + popad/ret），v7.8 仅将 hook 位置回移到菜单之前并扩展了「条件跳转重放」尾声（见零章 v7.8 节）。开发中期曾尝试「挂车式架构」（hook 到引擎精灵绘制点），连续 4 版白屏后彻底放弃，详见 [5.4 节](#54-失败实验挂车式架构-v60--v63)。

### 2.2 Cave 代码流程（987 字节，cave_offset=0x800 钉死）

```
pushad / sub esp,0x80            ; 序言
├─ 遍历战场格网 byte_951D42 (32×32)
│    格值=单位号 u；0xFF(空)/≥0x20 跳过   ← 与引擎绘制循环同源
├─ 对每个单位 u:
│    recordBase = u*1054 + 0x9D707A
│    HP = word[recordBase+0xA] ≤ 0 → 跳过
│    ytop = word[u*4+0x9DF804] - camY - 194 (imm32!)  钳位 [0,419]
│    x0 = word[u*4+0x9DF802] - camX - 55
│    fbase = word[0x9D6F76]      ; = 76 (Mu2.jvg 块44 起始帧)
│    maxst = [obj+0x18] - fbase + 1   ; v7.10 statusID 有效上限 (Mu2=32)
│    valid(st) = st≠0 且 st<maxst     ; 占位 ⇔ 绘制, 同源判定
│    n1 = Σ(slot 0..3 的 valid(st))  ; v7.10 行1 激活数预扫描 (esi 持 maxst)
│    offset1 = (124 - 31*n1) >> 1  ; 居中偏移 (46/31/15/0)
│    ├─ 对 8 个状态槽 slot (行1 居中 / 行2 左起):
│    │    st = byte[recordBase + 0x56 + slot*2]   (提前读取)
│    │    st == 0 → 空槽透明, 跳过 (不占位)
│    │    row = slot >> 2;  行基 = slot & 4
│    │    k = Σ_{i<slot, 同行} valid(st[i])   ; 行内激活序号 (ebx 持 maxst)
│    │    xx = x0 + k*31 + (行1 ? offset1 : 0)
│    │    yy = ytop + 31 - row*31   (行1: ytop+31; 行2: ytop)
│    │    xx > 610 (无符号) → 跳过该槽
│    │    F = fbase + st - 1
│    │    F ≥ [obj+0x18] 总帧数 → 跳过
│    │    ┌─ JVG 对象导航 (v7.5 修正版):
│    │    │  block = u16[*(obj+8)  + F*2]     ← 指针解引用!
│    │    │  sf    = u16[*(obj+0xC) + F*2]     ← 指针解引用!
│    │    │  rec   = *(obj) + block*64
│    │    │  sf ≥ [rec+0] 块帧数 → 跳过
│    │    │  blob  = [rec+0x2C]  (已由 45410C 预加载)
│    │    │  hdr   = blob + [ [rec+0x28] + sf*4 ]   (按 sf 索引)
│    │    │  W=word[hdr+4]  H=word[hdr+6]  N=word[hdr+14]
│    │    │  pal   = [rec+8 + 4*[rec+0x3C]]  回退 [rec+4]  (u16[256] RGB565)
│    │    └─ RLE 原尺寸直采 (ty 0..29 × tx 29..0):
│    │         每行复位游标 (wsrc/recleft/poscnt/runleft)
│    │         target = (H-1-⌊H*ty/30⌋)*640 + (W-1) - ⌊W*tx/30⌋
│    │         游标推进: target≥runEnd→开新记录; target<runbase→透明跳过;
│    │         命中→写 pal[runsrc[target-runbase]] 至 canvas+(yy+ty)*1280+2*(xx+tx)
└─ add esp,0x80 / popad / 重放 cmp edx,0x2b / jbe→ret
                                   └取→ add [esp],0x112 / ret (default 路径)
```

## 三、逆向知识库：JVG 精灵系统完整结构

### 3.1 JVG 文件格式（`sub_453BD0` 加载器逆向）

```
@JVG 总头 (32B): +8 = 块数
块结构 (两种):
  @JVM 块: [块头32B][偏移表 (帧数+1)*4B][调色板 512B (256×u16 RGB565)][数据 dz]
           块头+4 = 帧数, 块头+12 = 数据区大小
  @JVS 块: 每条 = [4B 大小][512B 调色板][数据], 单帧自成一块 (偏移恒 0)
帧头 (16B): +0/+2 = xmax/ymax (s16, 右下锚点偏移)
            +4 = W, +6 = H (u16)
            +14 = RLE 记录条数 (u16)
帧数据: [u16 skip][u16 run][run 字节调色板索引] × N
```

**RLE 渲染语义（`sub_4544EC`，反向线性扫描）**：

源单元格 `(row, col)` 在扫描流中的线性位置：

```
p640 = (H-1-row)*640 + (W-1-col)
```

- 记录流按 p640 递增方向排列；`skip` 段透明不写，`run` 段逐像素写入 `pal[idx]`；
- **行内单调，行间非单调**（行基准随 row 递增而减小）——逐行采样缩放时游标必须每行复位。

**实测 Mu2.JVG**：57 块 / 107 帧；状态图标帧 76..106 跨块 44..56（每块独立调色板）；块 44 帧 76 为 30×30、xmax=29 ymax=28。

### 3.2 JVG 运行时对象（内存布局，⚠ 偏移为字节）

`sub_453BD0` 加载后构造的对象（如 `dword_755AF4` = Mu2.jvg 对象）：

| 偏移 | 含义 |
|---|---|
| +0x00 | records 指针（组记录数组，每条 64B） |
| +0x08 | **帧→block 号表指针**（u16[]，独立 malloc） |
| +0x0C | **帧→块内子帧号表指针**（u16[]，独立 malloc） |
| +0x18 | **总帧数**（= IDR 反编译 `a2[6]`，下标×4！） |
| +0x10 | FILE*（用于按需加载） |

每条记录（64B）：

| 偏移 | 含义 |
|---|---|
| +0x00 | 块帧数 |
| +0x04 | 回退调色板指针（u16[256] RGB565） |
| +0x08 | 调色板指针数组起点（`[rec+8+4*序号]` 取当前调色板） |
| +0x28 | 子帧偏移表指针（**按 sf 索引**，相对数据块） |
| +0x2C | 数据块指针（`sub_45410C(obj,-1,0)` 全量加载后有效） |
| +0x30 | 数据块大小 |
| +0x3C | 当前调色板序号 |

> ⚠⚠ **本补丁最后两个 bug 都出在这里**：
> 1. `obj+8`/`obj+12` 是**指针**（loader 各自 malloc 数组后存指针），不能当内联数组读；
> 2. 总帧数在 `+0x18`（IDR 的 `_DWORD* a2[6]` = 字节 6×4），不是 `+0x24`。

### 3.3 帧号导航（`sub_4544EC` 原文语义）

```c
// a2 = JVG 对象 (_DWORD*), a5 = 帧号
word_A5AECC = *(_WORD *)(a2[3] + 2 * a5);            // sf = u16[*(obj+0xC) + 2F]
dword_A5AEB0 = *a2 + (*(unsigned __int16 *)(a2[2] + 2 * a5) << 6);  // rec = records + block*64
dword_A5AEBC = *(_DWORD *)(dword_A5AEB0 + 44)        // blob
             + *(_DWORD *)(*(_DWORD *)(dword_A5AEB0 + 40) + 4 * sf); // + 偏移表[sf]
```

注意 `a2[2]`/`a2[3]` 都是指针解引用（`a2` 是 `_DWORD*`，下标即 ×4 字节偏移）。

## 五、开发历程：七个真 Bug 与一次失败的架构

补丁从 v4（纯色矩形版）演进到 v7.5（真实图标版）、v7.9（居中布局）、v7.10（失效不占位），途中踩过的每一个坑都有教育意义。

### 5.1 Bug ①：空槽绘制漏 x 偏移（v4 就存在 → v7 修复）

**症状**：屏幕左边缘出现位置诡异的黑块（历代「画面外黑块」）。

**根因**：空槽绘制路径从未加过 x 偏移：

```asm
; 错误 (v4~v6.3):
imul edi, edx, 1280      ; 只有行偏移
lea  edi, [esi + edi]    ; canvas + y*1280 —— 完全没有 x!
rep  stosw               ; 画在屏幕左边缘 x=0
```

**修复**：`xx = slot*11 + x0` 提前到 st 判空之前计算，空槽/图标两条路径共用，空槽画在 `(xx, y0)`。

**误诊过程**：曾误诊为「屏外单位的幽灵槽」，先后加了锚点屏内守卫（v5.4）、格网遍历（v5.5）两轮**无效修复**——因为真正根因在绘制路径里，不在遍历源。**教训：出现「位置奇怪的图形」时，先逐指令审计绘制路径的坐标合成，不要急着改遍历源/过滤条件。**

### 5.2 Bug ②：y0 的 imm8 符号扩展（v5.0 引入 → v7.1 修复）

**症状**：格子出现在角色脚下很远的地方（x 正确、y 反向）。

**根因**：

```asm
83 EA 8F    sub edx, 0x8f   ← 143 = 0x8F 超出 imm8 有符号范围 ±127
```

CPU 把 0x8F 符号扩展成 -113，`sub edx, -113` 实际是 **+113** → `y0 = sy + 113`。而 x 用的 37 = 0x25 没超范围所以一直是对的。v4 原版用的是 `2D 8F 00 00 00`（imm32 形式），是正确的。

**修复**：`81 EA 8F 00 00 00`（imm32 形式）。

**讽刺之处**：历代 capstone dump 里都明明白白显示 `sub edx, -0x71`（负立即数 = 符号扩展 bug 的特征），却一直没有起疑。**教训：capstone 输出中出现「负的立即数」必须警惕 imm8 符号扩展。**

### 5.3 Bug ③：RLE 游标在透明空洞死推（v5.0 引入 → v7.3 修复）

**症状**：图标完全不显示（槽位在、颜色无）。

**根因**：游标推进逻辑中，采样目标落入**透明空洞**（skip 段）时错误地走「开新记录」分支死推游标到记录耗尽 → `row_exhaust` → 行内后续实心像素全部被丢弃：

```
错误 (v5.0~v7.2): target < runbase → 开新记录 → 越推越远 → 记录耗尽 → 整行黑
正确 (v7.3):     target < runbase → 该像素透明不写, 游标原地等待下一个更大的 target
```

图标每行只有零星几个实心像素，几乎每行都先踩到空洞 → 整行全灭。

### 5.4 失败实验：挂车式架构（v6.0 ~ v6.3）

为了「结构性消灭幽灵块」，曾把 hook 点从面板尾部移到引擎精灵绘制点（`sub_43A050` 格网循环内 `call sub_458020` 之后），连续 4 版白屏后**彻底放弃**：

| 版本 | 白屏原因 |
|---|---|
| v6.0 | hook 目标选在了 `call`（E8）指令上——启动器冲突检测扫描到 E8 首字节，误判「已被外部 MOD 占用」按 `skip` 处理，**补丁根本没应用** |
| v6.1 | 「返回地址搬家」写到 `esp0+0x44`——那是**调用者活跃栈帧**，每帧每单位写 8B 踩坏调用链 |
| v6.2 | 尾声恢复寄存器时 esp 已在局部帧，保存区实际在 `[esp+0x80..0x9C]` 而误读 `[esp+0x00..0x1C]`（读回局部变量垃圾）；且 `add esp` 常数应为 0xC4 误写 0x44（每次 esp 低 144B） |
| v6.3 | `mov r32,[esp+disp32]` 的 modrm 误用 mod=00（`0x04|reg<<3` = `[esp]` 无位移）→ 字节流解出 `mov r,[esp] + cwde + add [eax],al` 垃圾指令 → 访问违例 |

**结论**：E8 层多压 4B 返回地址导致的栈机巧（返回地址搬家/手动恢复寄存器/补 add esp）极易踩调用链。**安全模式 = 完整指令替换式 hook + 尾部重放 + popad/ret**——v4/v5.x/v7 长期验证无崩溃。v7.8 的 `add [esp],0x112` 调整自身 E8 返回地址是安全的边界案例：只改写 esp0 之下属于 cave 自己的返回地址槽，绝不触碰调用者活跃栈帧（v6.1 写的是 esp0+0x44）。

### 5.5 Bug ④：记录寻址 shl 目标错（v7.4 修复，后被证实非最终根因）

`sub_4544EC` 的记录定位是 `rec = records + u16[*(obj+8)+2F]*64`（按 **block 号**），v7.4 之前误把 `shl ebx,6` 作用在 `ebx=2F`（帧号×2，查表用字节偏移）上 → `rec = records + 128F`，F≥76 时远超记录数组 → 读堆外垃圾。同时 sf 载入 edi 后立即被 records 指针覆盖丢失，帧数比较误用 block、偏移表误按 block 索引。修复：sf 存栈槽、按 block 寻址、偏移表按 sf 索引。

### 5.6 Bug ⑤（最终根因）：JVG 对象导航双错（v7.5 修复，unicorn 定位）

**症状**：8 格中活动槽透明——图标路径在执行但零像素写入，而 Python 模拟却 31/31 一致（模拟与汇编实现存在语义差异）。

用 **unicorn 执行真实 cave 字节码**复现了 0 写入，然后在模拟器里挂指令/内存 hook 逐步定位到两个连环错误：

**⑤-1 总帧数偏移**：

```asm
cmp eax, [edx+0x24]   ← 错! 读的是字节 36 (loader 从未写入的堆垃圾 = 0)
                      → F(76) ≥ 0 恒真 → jae 跳过所有帧 → 图标永不绘制
cmp eax, [edx+0x18]   ← 对! IDR 反编译 sub_4544EC 的 a2 是 _DWORD*,
                          a2[6] = 字节偏移 6×4 = 24 = 0x18
```

**⑤-2 obj+8/obj+12 是指针**：

```asm
; 错 (把指针字段当内联数组):
movzx esi, word [edx + ebx*1 + 8]     ; 读到堆地址值附近的垃圾
; 对 (先解引用):
mov  ebx, [edx+8]                      ; 块号表指针
movzx esi, word [ebx + eax*2]          ; block
mov  ebx, [edx+0xC]                    ; 子帧号表指针
movzx ecx, word [ebx + eax*2]          ; sf
```

`sub_453BD0` 为两张表各自 malloc 独立数组，对象里存的是**指针**；`sub_4544EC` 的 `a2[2]`/`a2[3]` 均为指针解引用。

**为什么之前所有验证都没抓到**：Python 算法模拟直接用文件偏移构造数据，天然绕过了「指针解引用」这层汇编语义——这正是模拟与真实执行的盲区。unicorn 跑的是真实 x86 字节码，此类错误无处遁形。

### 5.7 Bug ⑥：modrm mod 位漏写（v7.9，capstone 即时拦截）

居中布局改造中，st 提前读取的 `movzx edx,byte[ecx+eax*2+0x56]` 的 modrm 误写 `0x14`（mod=00 无位移）——capstone 全量解码在构建当轮就暴露了 `movzx edx,[ecx+eax*2] + push esi`（disp8 `0x56` 被解为独立指令），正确为 `0x54`（mod=01|reg=edx|rm=100+SIB）。**与 v6.3 的 Bug 同族（铁律 2 的 disp8 变体）**。此 bug 未流入游戏实测——第 1 层验证（全量解码覆盖数 == 总长 + needle 断言）的即时价值：**每轮构建后立即跑 capstone，编码错误在写入 patch.json 之前被拦截**。

### 5.8 Bug ⑦：maxst 栈槽被 JVG 导航覆写（v7.10，unicorn 用例 4/5 抓获）

失效不占位改造中，maxst（statusID 有效上限）首版存 V_BLOB 栈槽（0x64）。**时序 bug**：首个有效槽进入 JVG 导航时 `mov [esp+0x64], eax` 写入 blob 指针（无符号巨大值）→ 同一单位后续槽的 k 前缀计数读到"maxst = 0x20xxxxx"→ 失效槽 0xFF 被 `cmp edi,ebx; jae` 判为有效 → 位置不重算。

**为什么单槽用例测不出**：只有 1 个有效槽时 k 计数发生在导航之前（maxst 未被覆写），一切正常；**第 2 个槽的 k 计数才踩到覆写后的值**。这正是用户实测场景（两个状态、一个失效）与单状态测试的差异。

修复：maxst 一律寄存器持有（n1 预扫描 esi、k 计数 ebx；行基改在 k 完成后从 slot 重算）。**教训：跨"槽循环 + JVG 导航"存活的值，必须逐一核对它在槽内所有路径的写入点——栈槽的"空闲"是相对于时间窗口的，不是静态属性。** unicorn 用例设计也要覆盖"多槽 + 失效残留"组合，单槽用例存在结构性盲区。

## 六、验证方法论（三层验证体系）

本次补丁最终建立了三层递进的交付前验证，每层覆盖前一层的盲区：

### 第 1 层：capstone 静态语义断言

`test_disassemble_clean` / `test_key_semantics_present`：

- 全量线性解码（覆盖字节数 == 总长，末条指令为 `ret`）；
- 关键语义 needle 断言（格网遍历、×4 坐标寻址、imm32 的 y0 偏移、指针解引用序列、v7.8 尾声的 `cmp edx,0x2b`/`add [esp],0x112` 等）；
- **bug 特征反向断言**：`sub edx, -0x71`（imm8 符号扩展特征）、`cwde`（modrm 编码垃圾指令特征）、v7.8 空槽透明后的 `rep`/`stos`/`0x2104`（灰块残留特征）等必须**不出现**。

> ⚠ 历史教训：`__main__` 必须强制调用这些测试函数——某版本曾因 `__main__` 不跑语义断言 + 测试资源路径少一层 parent 被**静默跳过**，`[OK]` 输出来自硬编码打印 = **假绿**。

### 第 2 层：Python 算法模拟

`test_icon_decode_matches_truth`：用与 cave **完全相同的控制流**（对象导航 + RLE 游标推进）解码真实 Mu2.JVG，逐像素对照直接解码（ground truth）的最近邻缩放结果。覆盖全部 31 个状态帧（76..106，跨块 44..56）。

**能抓**：算法层错误（游标推进逻辑、采样公式、行复位时机）。
**抓不到**：汇编编码错误、指针解引用语义（模拟直接用文件偏移构造，绕过了内存布局）。

### 第 3 层：unicorn 执行级验证（最终审判）

`test_war_status_icons_emu.py`：构造完整内存环境（JVG 对象/记录/偏移表/blob/调色板/格网/单位数据/相机/画布/栈），在 unicorn 里**执行真实 cave 字节码**。v7.8 共 **10 项检查**：帧 76/90 × 槽 0/3/4/7（两行四角）逐像素对照 ground truth + 邻格空槽全零（透明=零写入）+ **尾声双路径**（edx=0 → ret 落回返回地址原值且 esp 平衡；edx=0xFFFFFFFF → ret 落回返回地址+0x112 且 esp 平衡）。

**能抓**：一切——modrm/SIB/立即数符号扩展/跳转方向/寄存器生命周期/**指针解引用**/内存越界/返回地址调整错误。v7.5 的两个最终 bug 正是由此定位（unicorn 调试输出 `F=76 总帧数=0` 铁证）。

## 七、编码铁律（血泪教训）

手写 x86 机器码（尤其 cave 补丁）的硬规则，每一条都对应一次真实翻车：

1. **立即数 > 127 必须用 imm32 形式**（`81 /5 id`）；imm8（`83 /5 ib`）会**符号扩展**。
   capstone 输出中出现负立即数 = 符号扩展 bug 特征。
2. **`mov r32,[esp+disp32]` 的 modrm 必须 mod=10**（`0x84|reg<<3`）。
   mod=00（`0x04|reg<<3`）是 `[esp]` 无位移 → 字节流解出垃圾指令链。
   **变体（v7.9 实抓）**：带 disp8 的 `movzx r,byte[base+idx*2+disp8]` 的 modrm
   mod 位必须 = 01（如 `0x54` = mod01|reg(edx)|SIB）；误写 mod=00（`0x14`）
   会把 disp8 字节留给下一条指令解（`0x56` = push esi）。
3. **SIB scale 字段是 2^scale**：`0xBD`(scale=10b)=×4、`0xCD`(scale=11b)=×8。
   曾把 ×4 基线误读成 ×8 导致隔条取坐标。
4. **寄存器生命周期**：载入后又被后续指令覆盖 = 值丢失，需要栈槽保存。
5. **IDR 反编译下标语义**：类型化指针 `a2[k]` = 字节偏移 `k*sizeof(elem)`。
   `_DWORD*` 的 `a2[6]` = +0x18（不是 +0x24）；`int*`/`char*` 的 `p+k` 才是字节。
6. **结构体字段是指针还是内联数组，必须核对 loader**（malloc 后存指针 vs 直接写数组）。
   `sub_453BD0` 的两张帧表是 malloc + 存指针，读之前必须解引用。
7. **hook 目标不能选在 E8/E9 字节上**——启动器冲突检测会误判为外部 MOD 占用而 skip。
8. **hook 在 call 之后的位置（E8 层多压 4B 返回地址）时，严禁写 esp0 以上（调用者活跃栈帧）**；
   恢复寄存器注意 esp 已在局部帧内，保存区偏移 = 局部帧大小 + 原偏移。
9. **遍历战场单位必须用格网 `byte_951D42`**（与引擎渲染集合同源），不能用出战表。
10. **出现「位置奇怪的图形」时先审计绘制路径的坐标合成**（x/y 偏移逐项核对），不要急着改遍历源/过滤条件。
11. **hook 一条条件跳转时，标志位必须重放求值**（popad 恢复寄存器后重放其前的 cmp，
    而非假设标志存活）；需要改变返回目标时用 `add dword[esp],delta` 调整**自身** E8
    返回地址（esp0 之下、cave 所有），严禁写 esp0 以上的调用者活跃帧（v7.8）。
12. **多补丁共存时核对「pattern 字节区间 × hook 写入区间」的零重叠**，不能只看 hook
    地址不同——A 补丁的 pattern 可能覆盖 B 补丁的 hook 字节（v7.8 与血条补丁的共存分析）。

## 八、方法论教训：为什么错了这么多次

复盘整个开发过程，技术错误之外有三条更深层的方法论教训：

1. **先对比上一个正确的版本，再动手改。** 用户一句「你自己对比一下 v4 的代码不就清楚了」直接终结了坐标步长的争论——机械逐指令 diff 一分钟就能定谳的事，之前却在静态推演和实测之间来回摇摆。**当存在已验证正确的基线时，逐字节对齐它，而不是重新发明。**

2. **用执行级验证代替人肉审计。** v7.5 之前一直靠「读反编译 → 手写汇编 → capstone 反汇编核对」的流程，但人读反汇编会跳过 `a2[6]` 的类型语义、看不见 modrm 编码错误、注意不到寄存器被覆盖。unicorn 把字节码真实跑起来的那一刻，`F=76 总帧数=0` 的调试输出直接暴露了问题。**凡是手写的机器码，交付前必须在模拟器里执行过。**

3. **警惕「假绿」测试。** 两次严重的验证失效：①测试资源路径少一层 parent，`if not exists: return` 静默跳过，`[OK]` 来自 `__main__` 硬编码打印；②Python 模拟直接用文件偏移构造数据，天然测不出「指针解引用」类错误。**测试必须断言它真的测了东西（如帧数 ≥ 25 的下限检查），并且要意识到每层验证的覆盖盲区。**
