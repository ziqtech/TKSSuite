| 缩放采样除数 | `floor(W*tx/10)` / `floor(H*ty/10)` | `floor(W*tx/20)` / `floor(H*ty/20)` |
| tx / ty 迭代 | 9→0 / 0..9 | 19→0 / 0..19 |

| y0 偏移 | sy−143 | sy−153（⚠153>127 须 imm32） |

| y0 / xx 钳位 | [0,470] / ≤630 | [0,460] / ≤620 |
| 空槽色块 | 10×10 | 20×20 |

### v7.7：30×30 原尺寸 + 两行 × 4 槽布局（从下往上）

依据：战斗面板（`sub_437664`）的状态图标即 `sub_4544EC` 直绘 **30×30 原尺寸**（面板内步进 37px）。头顶版改用原尺寸直采（源即 30×30 → 采样恒等映射、无缩放损失），并改为两行布局：

```
        ┌────┬────┬────┬────┐
行2(顶): │槽4 │槽5 │槽6 │槽7 │  y = ytop      = sy−194
        ├────┼────┼────┼────┤
行1(底): │槽0 │槽1 │槽2 │槽3 │  y = ytop+31   = sy−163 (底边距HP条顶1px)
        └────┴────┴────┴────┘
          ↑ x0 = sx−55, 步进 31px, 行宽 123px, 中心 sx+6.5
```

| 参数 | 值 | 说明 |
|---|---|---|
| 图标尺寸 | **30×30** | 与面板同尺寸，源即 30×30 → 恒等采样 |
| col / row | `slot & 3` / `slot >> 2` | 8 槽拆为 2 行 × 4 列 |
| xx | `x0 + col*31` | 步进 31px（30+1 间隙），行宽 4×31−1=123px |
| yy | `ytop + 31 − row*31` | 行1：ytop+31；行2：ytop |
| ytop | `sy − 194` | ⚠194=0xC2>127 必须 imm32 |
| x0 | `sx − 55` | 行中心保持 sx+6.5（123/2=61.5） |
| 钳位 | ytop∈[0,419]（总高 61px）/ xx≤610 | 无符号比较同时挡负值 |
| 空槽色块 | 30×30 | |
| 栈布局 | V_YY 复用旧 V_F 槽 0x1C | F 仅在寄存器内使用从不回读 |

**unicorn 验证增强**：从「单槽抽查」升级为 **8 项检查**（帧 76/90 × 槽 0/3/4/7 = 两行四角），每项同时验证图标逐像素一致 + 邻格空槽灰块 `0x2104`（验证步进与空槽绘制）。期间还发现并修正了测试自身的逻辑错误：邻格断言最初要求「干净」，但**空槽会合法地画灰块**——断言应验证灰块存在而非不存在。

## 一、补丁目标与最终效果

**目标**：战斗中，在每个存活单位的头顶（血条上方）显示**两行 8 个异常状态槽**（每行 4 槽、从下往上排列，各 30×30px 与战斗面板同尺寸，间隔 1px），活动槽显示 `Mu2.JVG` 中对应的状态图标（原尺寸直采），空槽显示暗灰占位色块 `0x2104`。

**最终效果**（v7.7，用户实测确认）：

- 8 个槽位以 **2 行 × 4 槽**显示在单位头顶血条上方（行1 紧贴血条、行2 在其上）；
- 中状态后对应槽显示 Mu2.JVG 的真实彩色图标（RGB565 直写，30×30 原尺寸清晰）；
- 空槽显示暗灰色块；
- 无崩溃、无幽灵块、无栈泄漏。

**原版行为参考**：原版游戏本身在「单位信息面板」（`sub_437664`）中显示状态图标，行布局为 8 槽、步进 37px、图标 30×30 原尺寸。本补丁将同样的数据以**同样的原尺寸**搬到单位头顶，并改为更紧凑的两行布局。

## 二、最终架构（v7.7）

### 2.1 Hook 点

```
sub_43A050 @ 0x43A8BD
替换指令: cmp word ptr [0x9D6C88], 0   (8 字节: 66 83 3D 88 6C 9D 00 00)
pattern:  "66 83 3D 88 6C 9D 00 00 7C 0A" (含后续 jl, 增强唯一性)
```

该点位于面板 switch 之后、回合表 `sub_439D34` 之前，**每帧必经一次**。cave 尾部逐字节重放这条 `cmp` 后 `ret`（`popad` 不影响标志位，后续 `jl` 使用重放指令设置的标志）。

> ⚠ 此架构为 v4 起沿用、多轮实测无崩溃的安全模式。开发中期曾尝试「挂车式架构」（hook 到引擎精灵绘制点），连续 4 版白屏后彻底放弃，详见 [5.4 节](#54-失败实验挂车式架构-v60--v63)。

### 2.2 Cave 代码流程（893 字节，cave_offset=0x800 钉死）

```
pushad / sub esp,0x80            ; 序言
├─ 遍历战场格网 byte_951D42 (32×32)
│    格值=单位号 u；0xFF(空)/≥0x20 跳过   ← 与引擎绘制循环同源
├─ 对每个单位 u:
│    recordBase = u*1054 + 0x9D707A
│    HP = word[recordBase+0xA] ≤ 0 → 跳过
│    ytop = word[u*4+0x9DF804] - camY - 194 (imm32!)  钳位 [0,419]
│    x0 = word[u*4+0x9DF802] - camX - 55
│    fbase = word[0x9D6F76]      ; = 76 (Mu2.jvg 块44 起始帧)
│    ├─ 对 8 个状态槽 slot (v7.7: 2 行 × 4 槽):
│    │    col = slot & 3;  row = slot >> 2
│    │    xx = x0 + col*31          (行宽 4*31-1 = 123px)
│    │    yy = ytop + 31 - row*31   (行1: ytop+31; 行2: ytop)
│    │    xx > 610 (无符号) → 跳过该槽
│    │    st = byte[recordBase + 0x56 + slot*2]
│    │    st == 0 → 画空槽色块 30x30 (在 xx,yy)
│    │    F = fbase + st - 1
│    │    F ≥ [obj+0x18] 总帧数 → 跳过
│    │    ┌─ JVG 对象导航 (v7.5 修正版):
│    │    │  block = u16[*(obj+8)  + F*2]     ← 指针解引用!
│    │    │  sf    = u16[*(obj+0xC) + F*2]     ← 指针解引用!
│    │    │  rec   = *(obj) + block*64
│    │    │  sf ≥ [rec+0] 块帧数 → 跳过
│    │    │  blob  = [rec+0x2C]  (已由 45410C 预加载)
│    │    │  hdr   = blob + [ [rec+0x28] + sf*4 ]   (按 sf 索引)
│    │    │  W=word[hdr+4]  H=word[hdr+6]  N=word[hdr+14]
│    │    │  pal   = [rec+8 + 4*[rec+0x3C]]  回退 [rec+4]  (u16[256] RGB565)
│    │    └─ RLE 原尺寸直采 (ty 0..29 × tx 29..0):
│    │         每行复位游标 (wsrc/recleft/poscnt/runleft)
│    │         target = (H-1-⌊H*ty/30⌋)*640 + (W-1) - ⌊W*tx/30⌋
│    │         游标推进: target≥runEnd→开新记录; target<runbase→透明跳过;
│    │         命中→写 pal[runsrc[target-runbase]] 至 canvas+(yy+ty)*1280+2*(xx+tx)
└─ add esp,0x80 / popad / 重放 cmp / ret
```

## 三、逆向知识库：JVG 精灵系统完整结构

### 3.1 JVG 文件格式（`sub_453BD0` 加载器逆向）

```
@JVG 总头 (32B): +8 = 块数
块结构 (两种):
  @JVM 块: [块头32B][偏移表 (帧数+1)*4B][调色板 512B (256×u16 RGB565)][数据 dz]
           块头+4 = 帧数, 块头+12 = 数据区大小
  @JVS 块: 每条 = [4B 大小][512B 调色板][数据], 单帧自成一块 (偏移恒 0)
帧头 (16B): +0/+2 = xmax/ymax (s16, 右下锚点偏移)
            +4 = W, +6 = H (u16)
            +14 = RLE 记录条数 (u16)
帧数据: [u16 skip][u16 run][run 字节调色板索引] × N
```

**RLE 渲染语义（`sub_4544EC`，反向线性扫描）**：

源单元格 `(row, col)` 在扫描流中的线性位置：

```
p640 = (H-1-row)*640 + (W-1-col)
```

- 记录流按 p640 递增方向排列；`skip` 段透明不写，`run` 段逐像素写入 `pal[idx]`；
- **行内单调，行间非单调**（行基准随 row 递增而减小）——逐行采样缩放时游标必须每行复位。

**实测 Mu2.JVG**：57 块 / 107 帧；状态图标帧 76..106 跨块 44..56（每块独立调色板）；块 44 帧 76 为 30×30、xmax=29 ymax=28。

### 3.2 JVG 运行时对象（内存布局，⚠ 偏移为字节）

`sub_453BD0` 加载后构造的对象（如 `dword_755AF4` = Mu2.jvg 对象）：

| 偏移 | 含义 |
|---|---|
| +0x00 | records 指针（组记录数组，每条 64B） |
| +0x08 | **帧→block 号表指针**（u16[]，独立 malloc） |
| +0x0C | **帧→块内子帧号表指针**（u16[]，独立 malloc） |
| +0x18 | **总帧数**（= IDR 反编译 `a2[6]`，下标×4！） |
| +0x10 | FILE*（用于按需加载） |

每条记录（64B）：

| 偏移 | 含义 |
|---|---|
| +0x00 | 块帧数 |
| +0x04 | 回退调色板指针（u16[256] RGB565） |
| +0x08 | 调色板指针数组起点（`[rec+8+4*序号]` 取当前调色板） |
| +0x28 | 子帧偏移表指针（**按 sf 索引**，相对数据块） |
| +0x2C | 数据块指针（`sub_45410C(obj,-1,0)` 全量加载后有效） |
| +0x30 | 数据块大小 |
| +0x3C | 当前调色板序号 |

> ⚠⚠ **本补丁最后两个 bug 都出在这里**：
> 1. `obj+8`/`obj+12` 是**指针**（loader 各自 malloc 数组后存指针），不能当内联数组读；
> 2. 总帧数在 `+0x18`（IDR 的 `_DWORD* a2[6]` = 字节 6×4），不是 `+0x24`。

### 3.3 帧号导航（`sub_4544EC` 原文语义）

```c
// a2 = JVG 对象 (_DWORD*), a5 = 帧号
word_A5AECC = *(_WORD *)(a2[3] + 2 * a5);            // sf = u16[*(obj+0xC) + 2F]
dword_A5AEB0 = *a2 + (*(unsigned __int16 *)(a2[2] + 2 * a5) << 6);  // rec = records + block*64
dword_A5AEBC = *(_DWORD *)(dword_A5AEB0 + 44)        // blob
             + *(_DWORD *)(*(_DWORD *)(dword_A5AEB0 + 40) + 4 * sf); // + 偏移表[sf]
```

注意 `a2[2]`/`a2[3]` 都是指针解引用（`a2` 是 `_DWORD*`，下标即 ×4 字节偏移）。

## 四、战场数据结构速查

| 地址 | 含义 |
|---|---|
| `byte_951D42` | 战场格网 32×32，格值=单位号，空格 0xFF。**引擎画精灵前判格值有符号 ≥0**（@0x43A659）——遍历单位必须用它，与引擎渲染集合同源 |
| `byte_9D705A` | 出战表（⚠ 含隐藏/未部署/已离场单位，坐标为残留值，**不能**用它画头顶 UI，否则产生屏幕边缘幽灵块） |
| `word_9DF802/804` | 单位像素坐标 X/Y，**WORD 数组、字节步长 4**（`[u*4+addr]`，原版 exe @0x43A694/0x43A6AB 实测） |
| `dword_8242A8/AC` | 相机 X/Y |
| `0x9D707A + u*1054` | 单位记录基址；+0xA = HP 当前值（word）；**+0x56 + i*2 = 8 个状态槽**（低字节 statusID 非 0 即画，高字节剩余回合数不参与显示判定） |
| `dword_755AF4` | Mu2.jvg 对象指针（战斗初始化 `sub_42FEE0` 加载） |
| `word_9D6F76` | 状态图标基准帧号 = `sub_45408C(Mu2obj, 44)` = 76 |
| `word_9D6C88` | 面板状态字（hook 重放指令的操作数） |

**状态图标帧号公式**（逆向自 `sub_437664.c:127-142/:186-202` 信息面板绘制）：

```
frame = word_9D6F76 + statusID - 1
```

**几何**（v7.7，30×30 原尺寸 + 两行布局）：`ytop = sy_cam - 194`（行2/顶行顶；行1 = ytop+31，底边距血条顶 sy−132 上方 1px）、`x0 = sx_cam - 55`（行宽 4×31−1=123px，中心 sx+6.5 与历代一致）、槽步进 31px（图标 30px + 间隔 1px）；`col = slot&3`、`row = slot>>2`，`yy = ytop + 31 − row*31`。

## 五、开发历程：五个真 Bug 与一次失败的架构

补丁从 v4（纯色矩形版）演进到 v7.5（真实图标版），途中踩过的每一个坑都有教育意义。

### 5.1 Bug ①：空槽绘制漏 x 偏移（v4 就存在 → v7 修复）

**症状**：屏幕左边缘出现位置诡异的黑块（历代「画面外黑块」）。

**根因**：空槽绘制路径从未加过 x 偏移：

```asm
; 错误 (v4~v6.3):
imul edi, edx, 1280      ; 只有行偏移
lea  edi, [esi + edi]    ; canvas + y*1280 —— 完全没有 x!
rep  stosw               ; 画在屏幕左边缘 x=0
```

**修复**：`xx = slot*11 + x0` 提前到 st 判空之前计算，空槽/图标两条路径共用，空槽画在 `(xx, y0)`。

**误诊过程**：曾误诊为「屏外单位的幽灵槽」，先后加了锚点屏内守卫（v5.4）、格网遍历（v5.5）两轮**无效修复**——因为真正根因在绘制路径里，不在遍历源。**教训：出现「位置奇怪的图形」时，先逐指令审计绘制路径的坐标合成，不要急着改遍历源/过滤条件。**

### 5.2 Bug ②：y0 的 imm8 符号扩展（v5.0 引入 → v7.1 修复）

**症状**：格子出现在角色脚下很远的地方（x 正确、y 反向）。

**根因**：

```asm
83 EA 8F    sub edx, 0x8f   ← 143 = 0x8F 超出 imm8 有符号范围 ±127
```

CPU 把 0x8F 符号扩展成 -113，`sub edx, -113` 实际是 **+113** → `y0 = sy + 113`。而 x 用的 37 = 0x25 没超范围所以一直是对的。v4 原版用的是 `2D 8F 00 00 00`（imm32 形式），是正确的。

**修复**：`81 EA 8F 00 00 00`（imm32 形式）。

**讽刺之处**：历代 capstone dump 里都明明白白显示 `sub edx, -0x71`（负立即数 = 符号扩展 bug 的特征），却一直没有起疑。**教训：capstone 输出中出现「负的立即数」必须警惕 imm8 符号扩展。**

### 5.3 Bug ③：RLE 游标在透明空洞死推（v5.0 引入 → v7.3 修复）

**症状**：图标完全不显示（槽位在、颜色无）。

**根因**：游标推进逻辑中，采样目标落入**透明空洞**（skip 段）时错误地走「开新记录」分支死推游标到记录耗尽 → `row_exhaust` → 行内后续实心像素全部被丢弃：

```
错误 (v5.0~v7.2): target < runbase → 开新记录 → 越推越远 → 记录耗尽 → 整行黑
正确 (v7.3):     target < runbase → 该像素透明不写, 游标原地等待下一个更大的 target
```

图标每行只有零星几个实心像素，几乎每行都先踩到空洞 → 整行全灭。

### 5.4 失败实验：挂车式架构（v6.0 ~ v6.3）

为了「结构性消灭幽灵块」，曾把 hook 点从面板尾部移到引擎精灵绘制点（`sub_43A050` 格网循环内 `call sub_458020` 之后），连续 4 版白屏后**彻底放弃**：

| 版本 | 白屏原因 |
|---|---|
| v6.0 | hook 目标选在了 `call`（E8）指令上——启动器冲突检测扫描到 E8 首字节，误判「已被外部 MOD 占用」按 `skip` 处理，**补丁根本没应用** |
| v6.1 | 「返回地址搬家」写到 `esp0+0x44`——那是**调用者活跃栈帧**，每帧每单位写 8B 踩坏调用链 |
| v6.2 | 尾声恢复寄存器时 esp 已在局部帧，保存区实际在 `[esp+0x80..0x9C]` 而误读 `[esp+0x00..0x1C]`（读回局部变量垃圾）；且 `add esp` 常数应为 0xC4 误写 0x44（每次 esp 低 144B） |
| v6.3 | `mov r32,[esp+disp32]` 的 modrm 误用 mod=00（`0x04|reg<<3` = `[esp]` 无位移）→ 字节流解出 `mov r,[esp] + cwde + add [eax],al` 垃圾指令 → 访问违例 |

**结论**：E8 层多压 4B 返回地址导致的栈机巧（返回地址搬家/手动恢复寄存器/补 add esp）极易踩调用链。**安全模式 = 面板尾部 hook + 尾部逐字节重放 + popad/ret**——v4/v5.x/v7 长期验证无崩溃。

### 5.5 Bug ④：记录寻址 shl 目标错（v7.4 修复，后被证实非最终根因）

`sub_4544EC` 的记录定位是 `rec = records + u16[*(obj+8)+2F]*64`（按 **block 号**），v7.4 之前误把 `shl ebx,6` 作用在 `ebx=2F`（帧号×2，查表用字节偏移）上 → `rec = records + 128F`，F≥76 时远超记录数组 → 读堆外垃圾。同时 sf 载入 edi 后立即被 records 指针覆盖丢失，帧数比较误用 block、偏移表误按 block 索引。修复：sf 存栈槽、按 block 寻址、偏移表按 sf 索引。

### 5.6 Bug ⑤（最终根因）：JVG 对象导航双错（v7.5 修复，unicorn 定位）

**症状**：8 格中活动槽透明——图标路径在执行但零像素写入，而 Python 模拟却 31/31 一致（模拟与汇编实现存在语义差异）。

用 **unicorn 执行真实 cave 字节码**复现了 0 写入，然后在模拟器里挂指令/内存 hook 逐步定位到两个连环错误：

**⑤-1 总帧数偏移**：

```asm
cmp eax, [edx+0x24]   ← 错! 读的是字节 36 (loader 从未写入的堆垃圾 = 0)
                      → F(76) ≥ 0 恒真 → jae 跳过所有帧 → 图标永不绘制
cmp eax, [edx+0x18]   ← 对! IDR 反编译 sub_4544EC 的 a2 是 _DWORD*,
                          a2[6] = 字节偏移 6×4 = 24 = 0x18
```

**⑤-2 obj+8/obj+12 是指针**：

```asm
; 错 (把指针字段当内联数组):
movzx esi, word [edx + ebx*1 + 8]     ; 读到堆地址值附近的垃圾
; 对 (先解引用):
mov  ebx, [edx+8]                      ; 块号表指针
movzx esi, word [ebx + eax*2]          ; block
mov  ebx, [edx+0xC]                    ; 子帧号表指针
movzx ecx, word [ebx + eax*2]          ; sf
```

`sub_453BD0` 为两张表各自 malloc 独立数组，对象里存的是**指针**；`sub_4544EC` 的 `a2[2]`/`a2[3]` 均为指针解引用。

**为什么之前所有验证都没抓到**：Python 算法模拟直接用文件偏移构造数据，天然绕过了「指针解引用」这层汇编语义——这正是模拟与真实执行的盲区。unicorn 跑的是真实 x86 字节码，此类错误无处遁形。

## 六、验证方法论（三层验证体系）

本次补丁最终建立了三层递进的交付前验证，每层覆盖前一层的盲区：

### 第 1 层：capstone 静态语义断言

`test_disassemble_clean` / `test_key_semantics_present`：

- 全量线性解码（覆盖字节数 == 总长，末条指令为 `ret`）；
- 关键语义 needle 断言（格网遍历、×4 坐标寻址、imm32 的 y0 偏移、空槽 x 偏移、指针解引用序列等）；
- **bug 特征反向断言**：`sub edx, -0x71`（imm8 符号扩展特征）、`cwde`（modrm 编码垃圾指令特征）等必须**不出现**。

> ⚠ 历史教训：`__main__` 必须强制调用这些测试函数——某版本曾因 `__main__` 不跑语义断言 + 测试资源路径少一层 parent 被**静默跳过**，`[OK]` 输出来自硬编码打印 = **假绿**。

### 第 2 层：Python 算法模拟

`test_icon_decode_matches_truth`：用与 cave **完全相同的控制流**（对象导航 + RLE 游标推进）解码真实 Mu2.JVG，逐像素对照直接解码（ground truth）的最近邻缩放结果。覆盖全部 31 个状态帧（76..106，跨块 44..56）。

**能抓**：算法层错误（游标推进逻辑、采样公式、行复位时机）。
**抓不到**：汇编编码错误、指针解引用语义（模拟直接用文件偏移构造，绕过了内存布局）。

### 第 3 层：unicorn 执行级验证（最终审判）

`test_war_status_icons_emu.py`：构造完整内存环境（JVG 对象/记录/偏移表/blob/调色板/格网/单位数据/相机/画布/栈），在 unicorn 里**执行真实 cave 字节码**，跨块抽查 5 帧（76/80/90/100/106）逐像素对照 ground truth。

**能抓**：一切——modrm/SIB/立即数符号扩展/跳转方向/寄存器生命周期/**指针解引用**/内存越界。v7.5 的两个最终 bug 正是由此定位（unicorn 调试输出 `F=76 总帧数=0` 铁证）。

> 环境备注：unicorn 2.1.4（`pip install unicorn`）。调试时可挂 `UC_HOOK_CODE` 指令断点 dump 栈槽/寄存器、`UC_HOOK_MEM_WRITE` 监控内存改写，比人肉审计高效得多。

## 七、编码铁律（血泪教训）

手写 x86 机器码（尤其 cave 补丁）的硬规则，每一条都对应一次真实翻车：

1. **立即数 > 127 必须用 imm32 形式**（`81 /5 id`）；imm8（`83 /5 ib`）会**符号扩展**。
   capstone 输出中出现负立即数 = 符号扩展 bug 特征。
2. **`mov r32,[esp+disp32]` 的 modrm 必须 mod=10**（`0x84|reg<<3`）。
   mod=00（`0x04|reg<<3`）是 `[esp]` 无位移 → 字节流解出垃圾指令链。
3. **SIB scale 字段是 2^scale**：`0xBD`(scale=10b)=×4、`0xCD`(scale=11b)=×8。
   曾把 ×4 基线误读成 ×8 导致隔条取坐标。
4. **寄存器生命周期**：载入后又被后续指令覆盖 = 值丢失，需要栈槽保存。
5. **IDR 反编译下标语义**：类型化指针 `a2[k]` = 字节偏移 `k*sizeof(elem)`。
   `_DWORD*` 的 `a2[6]` = +0x18（不是 +0x24）；`int*`/`char*` 的 `p+k` 才是字节。
6. **结构体字段是指针还是内联数组，必须核对 loader**（malloc 后存指针 vs 直接写数组）。
   `sub_453BD0` 的两张帧表是 malloc + 存指针，读之前必须解引用。
7. **hook 目标不能选在 E8/E9 字节上**——启动器冲突检测会误判为外部 MOD 占用而 skip。
8. **hook 在 call 之后的位置（E8 层多压 4B 返回地址）时，严禁写 esp0 以上（调用者活跃栈帧）**；
   恢复寄存器注意 esp 已在局部帧内，保存区偏移 = 局部帧大小 + 原偏移。
9. **遍历战场单位必须用格网 `byte_951D42`**（与引擎渲染集合同源），不能用出战表。
10. **出现「位置奇怪的图形」时先审计绘制路径的坐标合成**（x/y 偏移逐项核对），不要急着改遍历源/过滤条件。

## 八、方法论教训：为什么错了这么多次

复盘整个开发过程，技术错误之外有三条更深层的方法论教训：

1. **先对比上一个正确的版本，再动手改。** 用户一句「你自己对比一下 v4 的代码不就清楚了」直接终结了坐标步长的争论——机械逐指令 diff 一分钟就能定谳的事，之前却在静态推演和实测之间来回摇摆。**当存在已验证正确的基线时，逐字节对齐它，而不是重新发明。**

2. **用执行级验证代替人肉审计。** v7.5 之前一直靠「读反编译 → 手写汇编 → capstone 反汇编核对」的流程，但人读反汇编会跳过 `a2[6]` 的类型语义、看不见 modrm 编码错误、注意不到寄存器被覆盖。unicorn 把字节码真实跑起来的那一刻，`F=76 总帧数=0` 的调试输出直接暴露了问题。**凡是手写的机器码，交付前必须在模拟器里执行过。**

3. **警惕「假绿」测试。** 两次严重的验证失效：①测试资源路径少一层 parent，`if not exists: return` 静默跳过，`[OK]` 来自 `__main__` 硬编码打印；②Python 模拟直接用文件偏移构造数据，天然测不出「指针解引用」类错误。**测试必须断言它真的测了东西（如帧数 ≥ 25 的下限检查），并且要意识到每层验证的覆盖盲区。**
