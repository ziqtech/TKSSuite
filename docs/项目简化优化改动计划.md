# TKSSuite 项目简化与优化改动计划

> 制定日期：2026-09-06
> 计划来源：对全项目 497 个 git 跟踪文件、约 9.5 万行 Python 的四路系统探查（跨编辑器重复代码 / 死代码与无用文件 / 构建系统与启动器 / 共享层质量与巨型文件），关键结论均经 file:line 级验证与抽查复核。
> 执行原则：与根目录 `CLAUDE.md` 一致——最小改动、手术式修改、每项改动可验证、不动与本次目标无关的代码。

---

## 一、总体结论

1. **项目底子是健康的**：共享层 `editor_utils/` 已系统性收敛（main 样板、主题、表格、线程、搜索框、最近目录均已统一），`configs_editor/panels/` 是注册表驱动的好范本，`build_all.py` 已表驱动，依赖清单无冗余，无大块注释掉的死代码。
2. **剩余可简化空间集中在业务编排层**：16 个编辑器主体约 3.4 万行中，存在约 **2500～3200 行（8～9%）**复制粘贴式重复，主要是 MOD 导出/导入编排、表单编辑骨架、缩放画布类、.bak 保存骨架四大块。
3. **另有一批零风险的纯删除项**：15 个全项目零调用的函数、LZSS 算法双胞胎、patch_engine 死代码、生成产物重复提交等，合计约 **700～800 行**可直接删除。
4. **量化目标**：净删/收敛 **3500～4500 行（约 4～5%）**，其中第一梯队约 750 行为无风险删除；同时把"改一处要动 N 个文件"的热点（MOD 导出弹窗文案等）收敛为单点维护。

---

## 二、改动原则

- **删除优先于新增**：能用删除解决的绝不重构；能用参数化统一的绝不发明新抽象。
- **每个任务独立提交**：一个任务一个 commit，commit message 注明任务编号，便于单独回滚。
- **行为零变更**：本计划全部是等价重构与死代码清除，不改任何用户可见行为；凡需要改变行为的（仅 T5 可选），单独说明。
- **先验证后删除**：标记"零调用"的函数，删除前用全项目 word-boundary grep 复核一次（含字符串字面量，防 getattr/信号字符串派发）。
- **每梯队结束跑一次全量冒烟**（见第六节），不把验证攒到最后。

#### T1. LZSS 双胞胎合并

- **现状**：同一逆向算法存在两份实现。
  - `editor_utils/lzss.py`（276 行）：统一三变体版，导出 `lzss_decompress_dat / lzss_compress_dat / lzss_decompress_save / lzss_compress_save / lzss_decompress_stream / lzss_compress_stream`。
  - `tks_launcher_gui/core/lzss.py`（116 行）：自述"从 tks_launcher.py 提取的最小化版"，导出通用 `lzss_compress(data)` / `lzss_decompress(data)`。
  - core 版调用方共 3 处：`tks_launcher_gui/core/mod_loader.py:26`、`tks_launcher_gui/core/warpc_expander.py:15`、`tks_launcher_gui/patches/tkkon_expand/script.py:30`。
- **注意（关键）**：两版**函数签名不同**（通用版 vs 三变体版），不能直接换 import。需先确定 core 版的格式对应哪个变体（mod_loader 用于 tkd/tkt 类 DAT 文件，大概率对应 `_dat` 变体，**必须实证确认**）。
- **方案**：
  1. 写一次性比对脚本：取 3 个调用方实际处理的样本文件（游戏目录下的 DAT / 展开产物），分别用两版实现 compress→decompress 往返，比对字节级一致；同时用 `lzss_decompress_dat` 等变体各试一遍，确认 core 版语义与哪个变体等价。
  2. 若等价于 `_dat` 变体：在 `editor_utils/lzss.py` 不新增任何东西，3 个调用点改为 `from editor_utils.lzss import lzss_decompress_dat as lzss_decompress`（或直接改调用名），删除 `tks_launcher_gui/core/lzss.py`。
  3. 若不等价（存在格式差异）：保留 core 版但在其文件头注明差异与原因，本任务降级为"仅记录，不合并"。
- **涉及文件**：`tks_launcher_gui/core/lzss.py`（删）、`core/mod_loader.py`、`core/warpc_expander.py`、`patches/tkkon_expand/script.py`（改 import）。
- **验收标准**：比对脚本证明等价后，launcher 正常加载 MOD（补丁应用流程走通）；`grep -rn "core.lzss\|from .lzss"` 全项目无残留。
- **收益**：−116 行，消除"改压缩算法只改一半"的隐患。

#### T5. entry 产物与 EDITORS 清单单源化

- **现状**：
  - `build/entries/entry_*.py` 共 19 个文件 361 行，为 `build/gen_entries.py` 生成产物（文件头写明"自动生成，请勿手动编辑"，gen_entries.py:52），且 `build_all.py:1305` 每次构建前重新生成。已验证相邻两个 entry 文件**互异仅 2 行**（sys.path 目录名 + import 模块名）。
  - gen_entries.py:99-101 专门写了"内容未变则不重写、保留 mtime"的保鲜逻辑，其存在理由正是文件被 git 跟踪、checkout 会刷新 mtime 干扰 `build_all.py:722` 的增量判断。
  - **同一份 19 条编辑器清单存在两份手抄副本**：`gen_entries.py:25-45` 与 `build_all.py:69-89`（格式不同），新增编辑器时需要改两处，漏一处即构建失败或入口缺失。
- **方案**（两步独立，可分别提交）：
  1. **单源化 registry（必做）**：新建 `build/editors_registry.py`，承载 19 条编辑器元数据（文件名/模块名/目录/是否 bootstrap/打包名），`gen_entries.py` 与 `build_all.py` 均从它 import。删除两份手抄副本。
  2. **产物是否出库（二选一，团队自决）**：
     - 方案 A（保守，推荐先做）：保持 entry 文件入库，在 `.gitignore`/README 注明"刻意提交的生成产物，勿手改"；registry 单源化后 gen_entries 逻辑不变。
     - 方案 B（彻底）：entry 文件移出 git（加入 .gitignore），构建时生成；运行期场景改用单一参数化入口（按产品名分发到对应编辑器 main）。可删掉 19 个文件与 mtime 保鲜特判（gen_entries.py:99-101）。**注意**：方案 B 影响构建流程与可能的 CI/文档引用，执行前 grep 所有引用 `entry_` 的文档与脚本。
- **验收标准**：registry 单源化后，`python build/gen_entries.py` 生成的 19 个文件与现有文件**逐字节一致**（证明等价）；新增一个测试编辑器条目走通"只改 registry 一处"的验证。
- **收益**：−360 行仓库体积（方案 B）或 0（方案 A）；两份清单合一，消除"改一处漏一处"。
