# 追加式MOD与剧本分离方案可行性分析

> 分析日期：2026-05-31
> 分析范围：游戏脚本系统 + 数据文件容量 + MOD架构设计
> 核心原则：**不改变原有游戏内容，所有MOD只能追加**

## 一、核心设计理念

### 1.1 追加式MOD原则

```
┌─────────────────────────────────────────────────────────────────┐
│                    追加式MOD设计原则                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ✅ 允许：                                                       │
│  ├── 新增记录（使用空闲槽位）                                     │
│  ├── 新增DEFINE块（使用空闲ID）                                   │
│  ├── 新增资源文件（不覆盖原有）                                   │
│  └── 扩展缓冲区（如WarPC从143→200）                              │
│                                                                 │
│  ❌ 禁止：                                                       │
│  ├── 修改原有记录内容                                             │
│  ├── 覆盖原有DEFINE块                                            │
│  ├── 替换原有资源文件                                             │
│  └── 改变原有游戏逻辑                                             │
│                                                                 │
│  🎯 目标：                                                       │
│  ├── 100%保留原游戏内容                                          │
│  ├── MOD可叠加、可卸载                                           │
│  └── 不同MOD互不干扰（除非显式依赖）                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 MOD分类体系

```
┌─────────────────────────────────────────────────────────────────┐
│                      MOD分类体系                                 │
├─────────────────────────────────────────────────────────────────┤

│                                                                 │

│                                                                 │

```

## 二、数据文件容量分析

### 2.1 各文件容量现状

| 文件 | 记录大小 | 总记录数 | 已使用 | 空闲 | 使用率 | 可新增 |
|------|----------|----------|--------|------|--------|--------|
| **TKD.dat** | 变长 | 5000(上限) | 1539 | 3461 | 31% | ✅ 3461个DEFINE块 |
| **TKMat.Dat** | 384B | 6000 | ~500 | ~5500 | 8% | ✅ 5500条实体 |
| **TKDefUnit.Dat** | 16B | 5000 | ~500 | ~4500 | 10% | ✅ 4500条DefUnit |
| **TKSkill.dat** | 94B | 350 | 344 | 6 | 98% | ⚠️ 仅6条（需扩展） |
| **TKItem.dat** | 64B | 600 | ~300 | ~300 | 50% | ✅ 300条物品 |
| **TKShop.dat** | 8B | 240 | ~20 | ~220 | 92% | ✅ 220条商店 |
| **TKKon.dat** | 40B | 650 | ~50 | ~600 | 92% | ✅ 600条陷阱 |
| **WarPC.dat** | 1054B | 143(可扩展) | 143 | 0→57 | 100% | ✅ 扩展后57条 |

### 2.2 关键发现

**TKD.dat（脚本文件）**：
- 游戏引擎硬编码上限：5000个DEFINE块
- 当前使用：1539个（31%）
- **剩余空间：3461个DEFINE块** ← 剧本MOD的黄金资源
- 每个DEFINE块独立，可自由新增

**TKMat.Dat（实体表）**：
- 总共6000条记录
- 当前使用约500条（8%）
- **剩余空间：约5500条** ← 新增NPC/场景实体

**WarPC.dat（角色数据）**：
- 原始143条，已实现扩展到200条
- 扩展后新增57条角色槽位
- **需配合启动器补丁使用**

**TKSkill.dat（技能数据）**：
- 350条记录，已使用344条（98%）
- **仅剩6条**，需要扩展才能新增技能
- 扩展方案：修改游戏引擎的循环上限

### 3.2 开局脚本机制

**当前实现**：
- 已经可以修改新游戏开始时执行的DEFINE块
- 通过修改TKD.dat中的初始DEFINE块实现

**剧本选择方案**：

```javascript
// 开局DEFINE块示例 (ID: 100000)
DEFINE 100000
{
  // 显示剧本选择菜单
  MenuChoice(0, 0, 0, &result)  // result存储玩家选择
  
  // 根据选择跳转到不同剧本
  CheckResult(result, 0, +5)    // 选择0 → 跳到原版剧本
  CheckResult(result, 1, +10)   // 选择1 → 跳到MOD剧本A
  CheckResult(result, 2, +15)   // 选择2 → 跳到MOD剧本B
  
  // 原版剧本入口
  ChangeScene(1, 400, 384, 1)
  End(0)
  
  // MOD剧本A入口
  ChangeScene(100, 400, 384, 1)  // 使用新场景ID
  End(0)
  
  // MOD剧本B入口
  ChangeScene(200, 400, 384, 1)  // 使用新场景ID
  End(0)
}
```

## 六、降低实现成本的策略

### 6.1 MOD类型分离的优势

```
┌─────────────────────────────────────────────────────────────────┐
│                    MOD分离的成本优势                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  【传统方案】所有功能打包在一起                                   │
│  ├── 实现复杂度：O(n²) - 功能间耦合                              │
│  ├── 测试复杂度：高 - 需要测试所有组合                           │
│  └── 维护成本：高 - 修改一处影响全局                             │
│                                                                 │
│  【分离方案】按类型拆分                                          │
│  ├── 实现复杂度：O(n) - 功能独立                                 │
│  ├── 测试复杂度：低 - 每个MOD独立测试                            │
│  └── 维护成本：低 - 修改只影响单个MOD                            │
│                                                                 │
│  成本对比：                                                      │
│  ├── 美化MOD：只需资源替换，实现成本 ⭐☆☆☆☆                     │
│  ├── 剧本MOD：只需追加DEFINE块，实现成本 ⭐⭐☆☆☆                 │
│  ├── 数据MOD：只需追加记录，实现成本 ⭐⭐⭐☆☆                     │
│  └── 代码补丁：需要逆向工程，实现成本 ⭐⭐⭐⭐⭐                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 6.2 分阶段实现路线

**第一阶段：追加式数据MOD**（1-2周）

```
目标：支持新增WarPC/TKSkill/TKItem记录
任务：
```

## 七、关键问题与解决方案

### 7.1 ID冲突检测

**问题**：多个MOD可能使用相同的ID范围

**解决方案**：

```json
// mod.json中声明ID使用范围
{
  "id_ranges": {
    "defines": {"start": 2000, "end": 2999},
    "tkmat": {"start": 500, "end": 1999},
    "warpc": {"start": 143, "end": 159}
  }
}

// 启动器检测冲突
if (mod1.id_ranges.defines.end > mod2.id_ranges.defines.start) {
  Log("[ERROR] MOD ID范围冲突: defines");
}
```

### 7.2 剧本变量管理

**问题**：多个剧本MOD可能使用相同的脚本变量

**解决方案**：

```json
// 每个MOD声明使用的变量范围
{
  "variable_ranges": {
    "script_vars": {"start": 90, "end": 99},  // word_755E80[90-99]
    "switches": {"start": 28, "end": 31},     // word_755E10[28-31]
    "flags": {"start": 900, "end": 999}        // word_756080[900-999]
  }
}
```

### 7.3 存档兼容性

**问题**：追加式MOD的存档是否与原版兼容

**解决方案**：

```
原版存档加载MOD后：
├── 新增角色：WarPC记录为空（默认值）
├── 新增实体：TKMat记录为空（默认值）
└── 新增脚本：DEFINE块已加载，可正常执行

MOD存档加载原版后：
├── 新增角色：数据丢失（WarPC扩展部分）
├── 新增实体：数据保留（TKMat空闲槽位）
└── 新增脚本：不存在，调用时跳过
```

### 7.4 技能扩展的限制

**问题**：TKSkill.dat只剩6条记录

**解决方案**：

```
方案A：扩展TKSkill上限
├── 修改游戏引擎的循环上限（350→500）
├── 需要新的启动器补丁
└── 实现成本：⭐⭐⭐☆☆

方案B：复用现有技能槽位
├── 使用空闲的技能ID（344-349）
├── 仅适用于少量新增技能
└── 实现成本：⭐☆☆☆☆

方案C：技能组合系统
├── 通过组合现有技能实现新效果
├── 不需要新增技能ID
└── 实现成本：⭐⭐⭐⭐☆
```

## 八、总结

### 8.1 可行性评估

| 维度 | 评估 | 说明 |
|------|------|------|
| **追加式数据** | ⭐⭐⭐⭐⭐ | 所有数据文件都有大量空闲槽位 |
| **剧本分离** | ⭐⭐⭐⭐⭐ | DEFINE块独立，可自由新增 |
| **美化分离** | ⭐⭐⭐⭐⭐ | 资源文件完全独立 |
| **降低成本** | ⭐⭐⭐⭐☆ | 分离后每个MOD实现简单 |
| **向后兼容** | ⭐⭐⭐⭐☆ | 原版存档可加载MOD数据 |

### 8.2 核心优势

1. **100%保留原游戏内容**：所有MOD只追加，不修改
2. **MOD可叠加**：多个MOD可同时使用
3. **MOD可卸载**：删除MOD文件即可恢复原版
4. **降低实现成本**：分离后每个MOD实现简单
5. **提高可维护性**：每个MOD独立，互不影响

### 8.3 实施建议

1. **先做数据扩展MOD**：最简单，验证追加式机制
2. **再做剧本MOD**：利用数据扩展，创建完整剧本
3. **最后做美化MOD**：独立于数据，可随时添加
4. **逐步完善管理器**：根据需求迭代

### 8.4 预期效果

```
用户视角：
├── 下载MOD包（.tksmod文件）

```
