## 一、问题现象

启用启动器（含 WarPC 缓冲区扩展）后保存存档，再次进入读档界面看到：

- **6 个完全相同的主角头像**（应该按队伍实际成员显示）
- **`Lv 0` × 6**（应该显示真实等级）
- **`70 年 01 月 01 日 08:00:00`**（应该显示真实保存时间）
- **`大地图`**（应该显示真实场景名）
- **金钱显示 `0`**（应该显示真实金钱）

特征：每个槽位看起来都像 28 字节"全 0"被渲染出来。

## 二、误诊与正确诊断的曲折过程

### 2.1 误诊一：「0 字节损坏文件」（[补丁十一]）

**初始假设**：`save\N.sav` 是 0 字节空文件，`sub_41B1A8` 读 0 字节文件后 buffer 保留 BSS 初始 0 → 渲染全 0。

**修补**：`EnsureSaveDirectoryHealthy()` 启动前清理 0 字节 `.sav` 文件。

**结果**：用户实测发现 `save\N.sav` 是 14 字节、20 字节（非 0），假设错误。但**修补保留**——可作为防御性清理。

### 2.2 真因一：sub_41CE10 写入越界（[补丁十二]）

通过字节级分析 `5.sav` (14B) 和 `9.sav` (20B)：

```
5.sav (14B): 00 FF FF FF FF FF | F4 01 | 2C 4E 0F 6A | 01 00
              ^^队员            ^^金钱  ^^时间戳     ^^第1个等级 → 写到这里中断
9.sav (20B): 00 8F 90 91 FF FF | F4 01 | 5E 4E 0F 6A | 01 00 01 00 01 00 01 00
              ^^[0,143,144,145] ^^500   ^^时间戳     ^^前4个等级写完 → 中断
```

**根因定位**：`sub_41CE10` 写等级循环：

```c
v6 = word_75688C;
do {
    sub_41DAC4(v21, &word_757F0C[527 * *v6], 2);
    ++v11; ++v6;
} while (v11 <= 5);
```

当队员 ID = -1（空槽位）时，地址计算 = `&word_757F0C[527*(-1)]` = `newBuf+4-1054` = **`newBuf-1050`**。

> **逆向核对**：`sub_41CE10` 写索引循环（`word_75688C` 队伍 / `word_757F0C[527*id]` 等级，`v11<=5`）与 `sub_41B1A8` 9 槽读取循环均已在 `../save_editor/TKS存档系统硬编码分析报告.md` 逐行核对（41CE10.c:116-124 / 41B1A8.c:74-84）；此处 `id=-1 → newBuf-1050` 越界推导与该验证一致。

- **原始游戏**：`word_757F0C = 0x757F0C`，越界访问 `0x756AFE` 落在 `unk_756880`（Block B）区域内 → 合法内存
- **启动器修补 WarPC 后**：`word_757F0C → newBuf+4`，`newBuf` 之前是 **VirtualAllocEx 未分配区** → 触发**页错误** → `sub_41DAC4` 内部 SEH 截断写入流 → 索引文件被截断

**修补**：在 `newBuf` 之前预留 **64 KB GUARD 区**（VirtualAllocEx 多分配，逻辑起点 +GUARD_SIZE），让负偏移访问落在合法已分配区内（默认填 0）。

**效果**：所有索引文件现在写满完整 28 字节。

### 2.3 真因二：sub_4C33FC「已打开」标志阻止循环（[补丁十三]）

补丁十二让索引文件完整写入后，依然全部异常显示。通过启动器添加诊断 dump 所有 `N.sav` 字节，**确认文件内容完全正确**：

```
slot 8: team=[0,-1,-1,-1,-1,-1] money=500 ts=2026-05-22 02:36 scene=6 levels=[Lv1,...]
slot 9: team=[0,143,144,145,-1,-1] money=500 ts=2026-05-22 02:36 scene=214 levels=[Lv1×4,...]
```

→ 问题转移到**游戏读取流程**。

**根因定位**：`sub_41B1A8` 9 次循环复用同一个 `v24` 文件结构：

```c
do {
    sub_4C352C(v24, "save\\%d.sav", 12);  // ← 9 次复用 v24
    ...
    sub_41C984(v23);  // ← 关闭 stream（但 v24+12 不一定被清零）
} while (v19 <= 9);
```

而 `sub_4C33FC`（被 sub_4C352C 调用）入口：

```c
if (*(_BYTE *)(a1 + 12)) return 0;   // 已打开就拒绝
```

执行链：
- `v19=1` 打开 `save\1.sav` 成功 → `v24+12 = 1`
- `v19=2..9` 时 `v24+12` 仍为 1 → sub_4C33FC 直接 `return 0` → 后续槽位读取失败

**修补**：扫描 sub_4C33FC 入口前 32 字节的 `cmp byte [reg+0Ch], 0` + 分支指令，把 **`je short → jmp short`**（无条件跳到 continue）：

```
原: 80 7B 0C 00       cmp byte [ebx+0Ch], 0
    74 07             je 0x1A (continue)
    33 C0             xor eax, eax
    E9 0E 01 00 00    jmp return_0

修补: 80 7B 0C 00       cmp（保留，无副作用）
      EB 07             jmp 0x1A (无条件跳到 continue)
```

**效果**：能看到所有存档内容了，但**第 3 页 slot 7/8/9 仍异常**。

### 2.4 真因三：sub_41C120「stream error」标志污染（[补丁十四]）

**根因定位**：`sub_41B1A8` 中 `if (!v1)` 分支：

```c
if (!v1) {  // sub_4C352C 失败（文件不存在）
    v17 = *(_DWORD *)(v22[0] + 8) | 4;   // ← 设置 stream error 位 (EOF)
    *(_DWORD *)(v18 + 8) = v2;
    ...
}
```

执行链：

| Slot | 文件状态 | sub_4C352C | stream+8 | 结果 |
|---|---|---|---|---|
| 1-3 | 存在 | 成功 | = 0 | ✓ 正常读取 |
| 4-6 | **不存在** | 失败 → `stream+8 \|= 4` | = 4 (EOF) | 空槽（fill -1） |
| 7-9 | 存在 | 成功，但 stream+8 仍是 4 | = 4 | ❌ `sub_41C120` 检测错误返回 false → 跳读 → buffer 保留 0 |

`sub_41C120` 实际汇编（不是 cmp，是 mov+test+sete+and+test+je 链）：

```
8B 4A 08         mov ecx, [edx+8]      ← 加载 stream+8
85 C9            test ecx, ecx
0F 94 C0         sete al               ← al = (error == 0)
83 E0 01         and eax, 1
84 C0            test al, al
0F 84 E5 00 00 00 je near set_fail     ← ZF=1 时跳到 set_fail
```

**修补**：把 13 字节替换为「真正清零」逻辑：

```
原 13 字节: 8B 4A 08 85 C9 0F 94 C0 83 E0 01 84 C0
新 13 字节: C7 42 08 00 00 00 00  mov dword [edx+8], 0  ← 真正清零 stream+8
            B0 01                  mov al, 1
            84 C0                  test al, al           ← ZF=0
            90 90                  NOP × 2
（保留后面的 0F 84 E5 00 00 00，因 ZF=0 不跳）
```

**效果**：所有槽位（包括 5/6/7/8/9）正常显示队伍、金钱、时间、地图、等级。✓

## 四、关键经验教训

### 4.1 字节级验证胜过任何推理

最初我多次基于反编译代码做"逻辑推理"：
- 误判 0 字节文件 → 实际是 14/20 字节
- 误判反编译的 `cmp dword [reg+8], 0` → 实际汇编是 `mov + test + sete` 链
- 误判 `if (a1+12) return 0` 是 jne → 实际是 je

**正确做法**：让启动器把目标函数的真实机器码 **dump 到日志**，再做精确分析。每一处误判都因为依赖反编译伪代码而不是真实字节。

### 4.2 BSS 邻接区域的"隐式契约"

原始游戏中 `word_757F0C[-527] = 0x756AFE` 落在 `unk_756880` Block B 内部。游戏作者**默认依赖** WarPC 区域前面有 BSS 内存可访问。当启动器把 WarPC 重定向到 VirtualAllocEx 分配的独立内存后，这种"隐式契约"被打破。

**通用对策**：用 VirtualAllocEx 替代原 BSS 内存时，必须考虑**前后相邻区域**的可达性，预留 GUARD 区填零。

### 4.3 stream 错误状态在循环内的"污染"

C++ stream 类的设计中，一旦设置 fail/eof 标志，**后续操作全部短路返回**，直到显式 `clear()`。原始游戏 `sub_41B1A8` 循环中没有调用 clear，可能是依赖 `sub_4C352C` 内部清理（但实际并没有）。

**通用对策**：循环复用 stream 对象时，必须在每轮开头**显式重置 error 标志**。本次修补在 sub_41C120 入口强制写 0 到 stream+8，相当于隐式 clear。

### 4.4 增量诊断 + 增量修补

整个修复经历了 4 轮：
1. 假设 0 字节 → 修 → 失败
2. 加诊断发现 14/20 字节截断 → 修 GUARD 区 → 部分修复
3. 加诊断发现 sub_4C33FC 标志位 → 修 je → 进一步修复
4. 加诊断发现 sub_41C120 stream error → 修清零 → 完全修复

**关键**：每次失败都让启动器**多输出诊断到日志**（hex dump、字节级解析），用真实数据驱动下一步修补。
