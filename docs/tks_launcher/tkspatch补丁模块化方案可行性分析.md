## 二、当前架构的模块化障碍

### 障碍 1：Cave 区域共享

`BuildPatches()` 将所有动态 cave 打包在同一个 `VirtualAllocEx` 分配的 512 字节区域内：

```
caveAddr (512B)：
  +0:   CaveTemplate       (51B) ← 补丁二 PATH1
  +64:  PortraitCave1      (41B) ← 补丁三 PATH1
  +128: PortraitCave2      (42B) ← 补丁三 PATH2
  +192: ArchivePortraitCave(48B) ← 补丁十五
  +256: HistoryTextCave    (38B) ← 补丁十七
```

**解决**：如果拆分成独立文件，每个 cave 补丁需要各自独立分配 `VirtualAllocEx` 几十字节即可，无技术难度。

### 障碍 2：统一的生命周期管理

`Main()` 函数是单一大函数，按固定顺序执行：

```
Main()
  ├─ LogInit()
  ├─ EnsureSaveDirectoryHealthy()    ← 补丁十一
  ├─ PrepareWarPcForGame()           ← 补丁五/八的前置处理
  ├─ Process.Start("TKS.exe")
  ├─ 检测子进程
  ├─ 分配 WarPC 缓冲区               ← 补丁五的一部分
  ├─ BuildPatches() + ApplyPatches() ← 补丁一~四,十五~十七
  ├─ ExpandWarPcBuffer()             ← 补丁五~九,十二
  ├─ Patch4C33FC()                   ← 补丁十三
  ├─ Patch41C120()                   ← 补丁十四
  ├─ PatchArchivePortrait()          ← 补丁十五(hook扫描)
  └─ InjectWarPCData()               ← 数据注入
```

**解决**：可重构为补丁生命周期事件模型，每个补丁声明自己的执行阶段，启动器按阶段分组执行。

### 障碍 3：补丁十五的特殊性

补丁十五（`PatchArchivePortrait`）需要在**已运行的进程**中扫描 `sub_41AB94` 函数体来找到 hook 点。这不适合在静态的 `.tkspatch` 文件中预先描述——必须运行时扫描。

**解决**：作为 cave 类型补丁，声明"需要运行时代码扫描"，不影响模块化。

## 三、.tkspatch 文件格式设计

### 3.1 完整格式示例

```json
{
  "format": "TKSPATCH",
  "version": 1,
  "patch": {
    "id": "patch_team_limit",
    "name": "入队数量限制扩展",
    "version": "1.0",
    "author": "author",
    "description": "将队伍最大人数从 30 扩展到 200，同时修复有符号比较问题",
    "category": "gameplay",
    "game_version": "1.0",
    
    "requires": [],
    "conflicts": [],
    
    "actions": [
      {
        "type": "static_patch",
        "rva": "0xDA15",
        "data": "C887",
        "desc": "TeamMember: cmp 0x1E->0xC8, jg->ja"
      },
      {
        "type": "static_patch", 
        "rva": "0xE6C1",
        "data": "C876",
        "desc": "CheckTeam: cmp 0x1E->0xC8, jle->jbe"
      }
    ]
  }
}
```

### 3.2 支持的 action 类型

| action 类型 | 用途 | 对应补丁 |
|-------------|------|----------|
| `static_patch` | 固定地址写字节（RVA + hex data） | 补丁一、二PATH2、四、十六 |
| `dynamic_cave` | 分配 cave 内存 + 写 hook 跳转 | 补丁二PATH1、三、十五、十七 |
| `code_scan` | 扫描代码段查找模式并替换 | 补丁六、八、十三、十四 |
| `file_operation` | 启动前文件操作（检查/创建/删除） | 补丁十一 |
| `buffer_expand` | 缓冲区重分配 + 全引用修复 | 补丁五（需特殊处理） |
| `data_inject` | 向指定内存地址写入 WarPC 数据 | InjectWarPCData |

### 3.3 Cave 补丁格式

```json
{
  "type": "dynamic_cave",
  "id": "awk_sprite_path1",
  "cave_bytes": "50510FBF45FA6685C0742569C01E04000005087F75000FB788080200006685C9750485C0EB0A83E90666894DFA6685C95958C3",
  "cave_size": 51,
  "hook": {
    "rva": "0x309A6",
    "instruction_length": 5,
    "desc": "AwkSprite: hook cmp [ebp-6],0 -> cave"
  },
  "requires_warpc": true
}
```

### 3.4 代码扫描补丁格式

```json
{
  "type": "code_scan",
  "id": "sub_4C33FC_fix",
  "target_function_rva": "0xC33FC",
  "scan_length": 32,
  "pattern": "80780C00",
  "pattern_type": "cmp_byte_reg_plus_offset",
  "replace": {
    "je_short_to_jmp": true
  }
}
```

### 3.5 WarPC 扩展包格式（原子补丁）

```json
{
  "id": "warpc_expand",
  "name": "WarPC 缓冲区扩展 (143→N 角色)",
  "version": "1.0",
  "category": "core",
  "requires": [],
  "atomic": true,
  
  "includes": ["补丁五", "补丁六", "补丁九", "补丁十二"],
  
  "warpc_config": {
    "target_count": 200,
    "base_rvas": [29个地址列表],
```

## 五、补丁执行阶段分类

| 阶段 | 时机 | 补丁类型 | 示例 |
|------|------|----------|------|
| **阶段 1** | 游戏启动前 | `file_operation` | 补丁十一 |
| **阶段 2** | 进程创建后、代码解密后 | `buffer_expand` | 补丁五/六/九/十二 |
| **阶段 3** | 缓冲区扩展完成后 | `static_patch`、`dynamic_cave`、`data_inject` | 补丁一~四、十五、十七 |

.tkspatch 文件中的每个 action 需声明 `stage` 字段，启动器按阶段分组执行。

## 六、可行性总结

| 维度 | 评估 | 说明 |
|------|------|------|
| **静态补丁拆分** | ⭐⭐⭐⭐⭐ | 补丁一/二PATH2/四/十六：每个只有 1-2 个固定字节，天然独立 |
| **Cave补丁拆分** | ⭐⭐⭐⭐☆ | 需要各自独立分配 cave 内存（十几字节每次），无技术难度 |
| **代码扫描补丁拆分** | ⭐⭐⭐⭐☆ | 每个扫描函数是独立的，只需在正确的时机调用 |
| **WarPC扩展包** | ⭐⭐⭐☆☆ | 补丁五/六/九/十二不可分割，需保持为原子单元，但可以整个包作为一个 .tkspatch |
| **GUI改造** | ⭐⭐⭐⭐☆ | C# WinForms 是成熟技术，当前代码可直接复用。但需处理异步（游戏启动后要做内存补丁） |
| **依赖解析** | ⭐⭐⭐⭐⭐ | 依赖关系清晰（只有 WarPC 扩展包有硬依赖），JSON 声明 + 拓扑排序即可 |
| **整体可行性** | ⭐⭐⭐⭐⭐ | 非常可行 |

### 需要注意的关键问题

1. **WarPC 扩展包拆不出来**：`ExpandWarPcBuffer()` 做了太多操作（29个基址引用 + 5个大小常量 + 7个 word_757F0C 引用 + 字段级盲扫 + 159922 存档缓冲 + 新角色备份），分布在同一个代码段扫描中，强行拆分会降低效率（重复扫描）。建议将整个 WarPC 扩展作为 **一个不可分割的补丁包**。

2. **Cave 地址的动态性**：Cave 补丁中的 hook 指令（`call rel32`）依赖 cave 的运行时地址。如果补丁按用户选择的顺序逐个应用，需要先统一分配所有 cave 空间，再逐个写 hook → 两阶段执行。

3. **执行时机顺序错误**：补丁必须在正确的时间点执行。若补丁 A 在阶段 3 依赖阶段 2 分配的缓冲区，顺序错误会导致崩溃。启动器需严格执行阶段顺序。

4. **兼容性检测**：静态补丁依赖原始字节值。如果多个 .tkspatch 修改同一 RVA，需要冲突检测。

### 建议实施路径

1. 先定义 `.tkspatch` 文件格式规范（JSON schema）
2. 将现有的 17 个补丁按上述分类拆分为独立的 `.tkspatch` 文件
3. 重构 `Main()` 为模块化的补丁加载器（解析 JSON → 拓扑排序 → 分阶段执行）
4. 在此基础之上加 WinForms GUI
