# 补丁十六深度分析：skill_learn 扩容方案

> 分析日期：2026-05-29
> 分析范围：`tks_launcher.cs` 补丁十六 + WarPC 内存布局 + sub_4189BC 逆向

---

## 一、补丁十六的本质

### 1.1 它修复了什么

补丁十六修改的是 `sub_4189BC`（RVA 0x189BC）中的两处循环上限比较指令：

```
RVA 0x18BB5: cmp word [ebp-04], 0x015E  → 0x015E = 350 → 改为 0x0158 = 344
RVA 0x18C3F: cmp word [ebp-04], 0x015E  → 0x015E = 350 → 改为 0x0158 = 344
```

### 1.2 为什么需要修

WarPC 每条记录 1054 字节，关键内存区间：

```
偏移         大小      含义
─────────────────────────────────────────────
[0..175]     176B     基础属性（名称、肖像、等级、经验、属性等）
[176..519]   344B     skill_learn[344] ← 每个字节跟踪一个技能的学会状态
[520..521]     2B     WORD[260] ← 补丁二：自定义战场精灵索引 (awk_sprite_id)
[522..523]     2B     WORD[261] ← 补丁三/十五：自定义队伍头像帧 (portrait_menu_id)
[524..525]     2B     WORD[262] ← 补丁十七：自定义历史文本ID (history_text_id)
[526..1053]  528B     其他字段（部分被游戏使用，部分为死空间）
```

原始游戏中 `sub_4189BC` 的循环：

```c
for (v12 = 0; v12 < 350; v12++) {
    byte status = warPC_record[176 + v12];  // skill_learn[v12]
    if (status 在有效区间内) {
        // 加入可装备列表
    }
}
```

当 `v12 ∈ [344, 349]` 时，`byte[176+v12]` 访问的是 `byte[520..525]`——即补丁二/三/十七的自定义字段：

| v12 | 访问地址 | 实际内容 |
|-----|----------|----------|
| 344 | byte[520] | WORD[260] 低字节（awk_sprite_id） |
| 345 | byte[521] | WORD[260] 高字节（awk_sprite_id） |
| 346 | byte[522] | WORD[261] 低字节（portrait_menu_id） |
| 347 | byte[523] | WORD[261] 高字节（portrait_menu_id） |
| 348 | byte[524] | WORD[262] 低字节（history_text_id） |
| 349 | byte[525] | WORD[262] 高字节（history_text_id） |

当新角色设置了自定义战场形象（如 WORD[260] = 某个值），其低字节若恰好落在 `[20, 39]` 区间（技能的"20-组技能学会"或"30-子技能学会"范围），`sub_4189BC` 就会误判为"已学会 TKSkill[344~349]"：

```
误判链:
  sub_4189BC 读到 byte[520] = 25（例如 WORD[260] = 0x??19）
  → 25 在 [20, 40) → 判为"20-组技能学会"
  → 加入可装备列表
  → sub_418C90 调用 sub_4067E8(TKSkill[id].name_id) 查 TKT
  → TKSkill[344~349] 的 name_id = 0
  → sub_4067E8(0) 兜底返回 TKT 字符串首条 "啊！"
  → 技能列表显示 "啊！"
```

**补丁十六将循环上限从 350 改为 344，让 v12 永远不进入 [344, 349]，从而 byte[520+] 永远不被当作 skill_learn 读取。**

### 1.3 补丁十六不是限制的根源

```
┌───────────────────────────────────────────────────────────────┐
│                                                               │
│  真正限制技能数量的：                                          │
│    1. WarPC.skill_learn 数组大小 = 344 字节                   │
│    2. byte[520~525] 已被 WORD[260/261/262] 占用               │
│    3. 游戏代码 sub_4189BC 通过 byte[176+v12] 访问技能状态     │
│                                                               │
│  补丁十六只是：                                                │
│    ✅ 阻止了 [344..349] 的越界误读                             │
│    ❌ 没有创造任何新限制                                       │
│                                                               │
│  344 上限是原始游戏设计的一部分。                              │
│  补丁十六只是让你看清了这个天花板。                            │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

## 二、约束分析

### 2.1 硬约束：WarPC 字段顺序不可动

作为 MOD 开发者而非游戏作者，绝对不能调整 WarPC 记录内部的字段顺序。原因：

1. **游戏引擎中每个字段的偏移都是硬编码的立即数**：
   ```
   sub_41762C:  mov ax, [ecx + 2]      ; WORD[1] 肖像
   sub_406864:  mov eax, [esi + 520]   ; 如果有的话
   ```

2. **MOV 指令的偏移是编译时计算好的**，调整字段顺序意味着需要修补游戏中所有访问 WarPC 的指令——这不仅是 29 个基址引用的问题，而是**每个字段的每次访问都是独立编译的偏移量**。

3. **现有 17 个补丁都依赖于 fix offset**（补丁二的 `[eax+0x208]`、补丁三的 `[eax+0x20A]`、补丁十七的 `[eax+0x20C]`）。

### 2.2 软约束：344 是否够用

原始游戏 TKSkill.dat 有 350 条记录，其中 idx 344~349 是空记录。这说明游戏设计者预期：
- 最多 344 个技能需要"学会"机制
- 额外 6 个可能是预留或系统用途

对于 MOD 开发：
- 如果只是增加敌人/BOSS 专用技能（不需要角色"学会"）→ **344 够用，不需扩容**
- 如果需要新增角色可学技能（超出 344）→ **必须扩容 skill_learn**
- 如果角色和敌人的技能数据都通过 WarPC 配置 → **344 就是硬瓶颈**

## 三、扩容方案：Cave Hook 双路径技能读取

### 3.1 核心思路

```
sub_4189BC 原始逻辑:
  for (v12 = 0; v12 < 350; v12++)
      byte status = warPC_record[176 + v12];  // ← Hook 这里

Hook 后逻辑:
  for (v12 = 0; v12 < 344 + K; v12++)
      if (v12 < 344)
          byte status = warPC_record[176 + v12];        // 原始路径
      else
          byte status = ext_skill_buf[char_idx][v12 - 344];  // 扩展路径
```

### 3.2 两个技术方向对比

| | 方向 A：独立扩展缓冲区 | 方向 B：扩 WarPC 记录尾部 |
|---|---|---|
| **做法** | 额外分配 `ext_skill_buf[N][K]`，hook sub_4189BC 分叉读取 | 改 `WARPC_REC_SIZE = 1054+K`，新字节追加在记录末尾 |
| **WarPC 字段顺序** | ✅ 不动，1054 不变 | ✅ 不动，新字段在 1054+ |
| **现有 17 个补丁** | ✅ 零影响，所有 offset 不变 | ⚠️ 所有 `imul reg, 1054` 需重扫描修补 |
| **现有 cave 代码** | ✅ 不变：`[eax+0x208]` 等 offset 不动 | ⚠️ WORD[260/261/262] offset 不变，但记录大小变了 |
| **存档/读档** | ❌ 需要自行 hook 存档/读档函数，单独序列化扩展区 | ✅ 游戏自动读写完整记录（大小常量已被修补） |
| **实现复杂度** | 中等，需 hook 3~4 个函数 | 较高，需全面扫描修补所有 1054 引用 |
| **风险** | 低——改动集中在已知函数 | 中——可能有遗漏的 1054 引用（如 `shl+add` 组合） |

### 3.3 推荐方向 A：独立扩展缓冲区

选择理由：

1. **不碰 WARPC_REC_SIZE**，现有 17 个补丁全部不受影响
2. 补丁五的 `ExpandWarPcBuffer()` 已有成熟的双缓冲区管理模式：
   - 补丁九：新角色备份缓冲区
   - 补丁十二：GUARD 安全垫
   - → 再加一块扩展技能区只是多一次 `VirtualAllocEx`
3. 只需要在 `BuildPatches()` 中加一个新 cave，在 `ExpandWarPcBuffer()` 中加一块内存分配
4. 存档序列化可复用已有思路：在 Frame 2 的 WarPC 数据段后面追加 `K * 角色数` 字节

### 3.4 扩展技能缓冲区布局

```
进程内存布局:
  ┌──────────────────────┐ ← GUARD 区 (64KB, 补丁十二)
  │                      │
  ├──────────────────────┤ ← newBuf (WarPC 完整数据)
  │  WarPC[0..N-1]       │
  │  (N × 1054 字节)     │
  ├──────────────────────┤ ← backupBuf (补丁九: 新角色数据备份)
  │  备份数据             │
  ├──────────────────────┤ ← extSkillBuf (新增: 扩展技能区)
  │  ext_skill[0][0..K-1]│
  │  ext_skill[1][0..K-1]│
  │  ...                 │
  │  ext_skill[N-1][0..K-1]│
  └──────────────────────┘
     总共 = GUARD + N×1054 + extraSize + N×K
```

### 3.5 Cave 汇编实现

需要 hook `sub_4189BC` 中读取 `skill_learn[v12]` 的精确指令。典型的汇编模式：

```asm
; 循环体内，v12 在某寄存器（如 ecx），warPC_record 基址在另一个（如 esi）
movzx eax, byte [esi + ecx + 0xB0]   ; 0xB0 = 176, 读取 skill_learn[v12]
```

Cave 替换为：

```asm
; ─── Cave: SkillLearnReader ───
; 入口:
;   ecx = v12 (技能索引, 0-based)
;   esi = warPC_record 基址 (当前角色)
;   edi = char_idx            (需从上层传入或从某全局读取)
;   ext_buf_base = 扩展区基址 (编译时 patched 为实际地址)

push edx                    ; 保存 edx

cmp ecx, 344                ; v12 < 344 ?
jl .original_path           ; 是 → 走原始路径

; === 扩展路径 ===
sub ecx, 344                ; ecx = v12 - 344
mov eax, edi                ; eax = char_idx
imul eax, eax, K            ; eax = char_idx * K
add eax, dword [ext_buf_base] ; eax = &ext_skill_buf[char_idx][0]
movzx eax, byte [eax + ecx] ; eax = ext_skill[char_idx][v12-344]
pop edx
ret

.original_path:
movzx eax, byte [esi + ecx + 176] ; eax = warPC_record[176+v12]
pop edx
ret
```

### 3.6 需要涉及的函数

| 函数 | RVA | 作用 | 改动说明 |
|------|-----|------|----------|
| `sub_4189BC` | 0x189BC | 构建可装备技能列表 | Hook 循环体内的 `movzx` 指令，v12≥344 走扩展路径 |
| `sub_4189BC` | 0x18BB5 | 主循环上限比较 | `0x015E`(350) → `0x0158+K`（344+K） |
| `sub_4189BC` | 0x18C3F | 第二段翻页上限比较 | 同上 |
| `sub_410ED4` | 0x10ED4 | 存档写入 Frame 2 | 在 WarPC 数据段后追加 `N×K` 字节扩展技能区 |
| `sub_41103C` | 0x1103C | 读档读取 Frame 2 | 在 WarPC 数据段后读取 `N×K` 字节到扩展区（旧存档不足时填 0） |
| `sub_412688` | 0x12688 | 新游戏初始化 WarPC | 清零扩展技能区（全部填 0 = 未学会） |

### 3.7 编辑器侧改动

`warpc_editor.py` 需要：

1. **WarPC 记录结构扩展**：在内存中的记录字典里增加 K 个扩展技能字节字段
2. **编辑界面**：新增"扩展技能"标签页，列出 TKSkill[idx 344..343+K] 供勾选
3. **保存格式**：WarPC.dat 的 LZSS 数据中，每条记录末尾追加 K 字节扩展数据：
   ```
   原格式: [1054B 记录 0] [1054B 记录 1] ... [1054B 记录 N-1]
   新格式: [1054+K B 记录 0] [1054+K B 记录 1] ... [1054+K B 记录 N-1]
   ```
4. **加载格式**：兼容旧 WarPC.dat（无扩展区时自动补 0）

### 3.8 存档格式

Frame 2 存档结构：

```
原存档:
  [9200B 队伍/背包/金币等] [N×1054B WarPC 数据]
  
扩展后:
  [9200B 队伍/背包/金币等] [N×1054B WarPC 数据] [N×K B 扩展技能区]
```

旧存档加载时，扩展技能区不存在 → 自动填充 0（所有扩展技能为"未学会"状态），兼容。

## 四、是否需要扩容的判断

### 4.1 当前 344 够用的场景

- TKSkill 条目数 ≤ 344
- 新增的技能是敌人/BOSS 专用（不需要角色学会）
- 没有新增"角色可学会"的技能类别

### 4.2 需要扩容的场景

- 需要新增角色可学技能，使总数超过 344
- 需要给每个角色配置超过 344 个技能的学会状态

### 4.3 扩容多少合适

```
建议 K = 30 ~ 50:
  - 覆盖 TKSkill 当前 350 条记录 → K ≥ 6
  - 给未来 MOD 预留空间       → K ≥ 20
  - 保守估计                  → K = 30
```

`v12` 用 word 类型比较（`cmp word [ebp-04], 0x015E`），理论上可以扩到 65535，但实际受存档大小和 WarPC.dat 文件大小限制。

## 五、总结

| 问题 | 答案 |
|------|------|
| **补丁十六是否限制了技能上限？** | 否。限制来自 WarPC 的 `skill_learn[344]` 数组大小。补丁十六只是修复了 byte[520~525] 被误读为技能状态的 bug。 |
| **能否无限扩展技能？** | 理论上可以扩展到 65535（word 上限），但受存档大小和 WarPC.dat 文件大小限制。实际建议 K=30~50。 |
| **怎么扩容？** | 推荐方案 A：独立扩展缓冲区 + Cave hook 双路径读取。不动 WarPC 记录大小，不动现有字段偏移。 |
| **影响哪些补丁？** | 零影响现有 17 个补丁。新增补丁约 4 个 hook 点（技能读取 + 存档 + 读档 + 初始化）。 |
| **存档兼容吗？** | 兼容。旧存档加载时扩展区自动填 0（未学会），新存档包含完整扩展数据。 |
| **编辑器需要改吗？** | 需要。WarPC 记录增加扩展字段，保存/加载格式兼容处理。 |
