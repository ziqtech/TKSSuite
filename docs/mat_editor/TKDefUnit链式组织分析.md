# TKDefUnit.dat f6 链式组织分析

严格依据反编译代码 `sub_4066F0`, `sub_40EBD4` case 0, 及实测 267 条链的数据分析。

---

## 一、核心结论

**f6 链 = 单个 NPC 的脚本阶段状态机。** 链链接的不是地图位置、不是事件、不是资源文件，而是**同一个 NPC 在故事推进过程中依次进入的各个脚本配置阶段**。

`sub_4066F0` 是状态机的推进函数，根据子场景计数器的当前值，沿链步进到对应的阶段节点。

---

## 二、反编译代码机制

### 2.1 sub_40EBD4 case 0 — 脚本块结束处理

当脚本执行到操作码 0（脚本块结束）时，根据下一个 uint16 参数选择子场景：

```
操作码 0x0000, 参数 = 子类型:

  参数值    Hex     实体表操作                      含义
  ───────  ──────  ──────────────────────────────  ──────
  1        0xFFFF  cur_A += 1; 若 > max_A: cur_A=0  推进子场景A
  2        0xFFFE  cur_B += 1; 若 > max_B: cur_B=0  推进子场景B
  3        0xFFFD  cur_C += 1; 若 > max_C: cur_C=0  推进子场景C
  4        0xFFFC  cur_A = 0                         重置子场景A
  5        0xFFFB  cur_B = 0                         重置子场景B
  6        0xFFFA  cur_C = 0                         重置子场景C
  0        0x0000  (不操作计数器)                    仅结束当前块
```

**证据**: `sub_40EBD4.c` 第 31-77 行。

计数器更新后，进入 LABEL_16：
1. `PC = saved_PC`（恢复保存的程序计数器）
2. `saved_PC = -1`
3. 调用 `sub_4066F0(entity, 0)` — 沿子场景A的链步进

### 2.2 sub_4066F0 — 链步进函数

```
sub_4066F0(entity_ptr, sub_scene):

  参数 a2 选择子场景:
    0 → max[30], cur[33], head[39]  (子场景A)
    1 → max[31], cur[34], head[40]  (子场景B)
    2 → max[32], cur[35], head[41]  (子场景C)

  逻辑:
    1. 若 max <= 0 或 cur <= 0 或 max < cur:
       → 实体表[44] = -1  (无脚本, 实体休眠)
       → 返回
    2. 从 head 开始
    3. 循环 (cur - 1) 次:
       v7 = *(DWORD*)(DefUnit_buf + 16 × v7 + 12)  // 沿 f6 链步进
    4. 实体表[44] = v7  (到达的节点成为新的脚本入口)
```

**证据**: `sub_4066F0.c` 第 18-58 行。

> **已核对**：`4066F0.c:18-58` 与本节完全一致——`a2=0/1/2` 选 `max=[30/31/32] / cur=[33/34/35] / head=[39/40/41]`；`if(max<=0||cur<=0||max<cur){[44]=-1; [42]=-1}` 否则自 head 循环 (cur-1) 次沿 `f6`(偏移 +12) 步进，末节点写 `[44]`。与 sub_40EBD4 case 0 的子场景 A/B/C 计数（TKMat [33-35]）配套。

### 2.3 关键实体表字段

| 索引 | 字节偏移 | 含义 | 使用 |
|------|---------|------|------|
| 30 | +120 | max_A | 子场景A最大阶段数 |
| 31 | +124 | max_B | 子场景B最大阶段数 |
| 32 | +128 | max_C | 子场景C最大阶段数 |
| 33 | +132 | cur_A | 子场景A当前阶段 |
| 34 | +136 | cur_B | 子场景B当前阶段 |
| 35 | +140 | cur_C | 子场景C当前阶段 |
| 39 | +156 | head_A | 子场景A链头 (DefUnit记录号) |
| 40 | +160 | head_B | 子场景B链头 |
| 41 | +164 | head_C | 子场景C链头 |
| 42 | +168 | script_PC | 脚本程序计数器 |
| 43 | +172 | saved_PC | 保存的程序计数器 |
| **44** | **+176** | **DefUnit索引** | **当前激活的DefUnit记录号** |

## 三、实测数据分析（267条链）

### 3.1 链内实体一致性

绝大多数链（~99%）所有节点 **f1 值相同** — 链属于单个 NPC：

```
链#51 (f1=305): f0=[256,257,258,259] 长度=4  (左慈住所)
链#61 (f1=312): f0=[256,257,258]     长度=3  (天師塚括蒼穴)
链#66 (f1=715): f0=[256,257]         长度=2  (常见二阶段)
```

极少数例外 — 链#1294: 含 6 个不同实体ID, 可能为共享终局脚本。

### 3.2 链长度分布

| 长度 | 数量 | 占比 | 含义 |
|------|------|------|------|
| 2节点 | 157条 | 59% | 二阶段 NPC（最常见, 初遇→后续） |
| 3节点 | 69条 | 26% | 三阶段 NPC |
| 4节点 | 18条 | 7% | 较复杂 NPC |
| 5-7节点 | 20条 | 7% | 重要 NPC |
| 10-11节点 | 3条 | 1% | 核心故事线 NPC |

### 3.3 链内 f0 变化规律

f0 在链中逐节点递增（数据观察, 非代码逻辑）：

```
链#51 (4节点): f0: 256→257→258→259
  对应: 匈奴民帳 → 匈奴王主帳 → 黃河南岸渡口 → 黃河北岸渡口
```

大多数 2 节点链的模式：f0: 256→257

## 四、运行机制图解

```
NPC #305 (左慈住所) 的故事线 ── 4个阶段:

实体表[44] = 51 ──────────────── 阶段0入口
       │
       ▼
   ┌─────────────────────┐
   │ DefUnit #51         │  f0=256, f1=305, f6=52
   │ [+4]=脚本A (初次对话) │
   └─────────┬───────────┘
             │ 脚本A执行完毕
             │ opcode=0, param=1 (推进子场景A)
             │ cur_A: 0 → 1
             │ sub_4066F0(entity, 0): 步进1步 → #52
             ▼
   ┌─────────────────────┐
   │ DefUnit #52         │  f0=257, f1=305, f6=53
   │ [+4]=脚本B (二次对话) │
   └─────────┬───────────┘
             │ 脚本B执行完毕, cur_A: 1 → 2
             │ 步进 → #53
             ▼
   ┌─────────────────────┐
   │ DefUnit #53         │  f0=258, f1=305, f6=54
   │ [+4]=脚本C           │
   └─────────┬───────────┘
             │ cur_A: 2 → 3, 步进 → #54
             ▼
   ┌─────────────────────┐
   │ DefUnit #54         │  f0=259, f1=305, f6=0
   │ [+4]=脚本D (最终对话) │  ← f6=0 链终止
   └─────────────────────┘
```

### 三子场景并行示意

```
NPC 的三个独立推进线:

  子场景A (主线):  head_A → 节点→节点→节点→...
                  cur_A=0  cur_A=1 cur_A=2 cur_A=3

  子场景B (分支):  head_B → 节点→节点→...
                  cur_B=0  cur_B=1 cur_B=2

  子场景C (分支):  head_C → 节点→节点
                  cur_C=0  cur_C=1
```

脚本通过 end-mode 参数选择推进哪条线：
- 参数=1: 推进 A 线 (主线对话)
- 参数=2: 推进 B 线 (分支对话/支线)
- 参数=3: 推进 C 线 (另一分支)

## 五、生命周期中的链操作

```
1. 场景加载 (sub_40C044 → sub_402E88):
   - 重新加载 TKDefUnit.dat
   - 遍历所有记录, 为有效实体创建脚本对象
   - 实体表[44] 被设置为初始 DefUnit 索引
   - 实体表[39/40/41] 被设置为链头 (由 TKMat.Dat 初始化)
   - cur_A/B/C 和 max_A/B/C 从场景数据初始化

2. 脚本执行 (sub_40EBD4):
   - 读取实体表[44] → 获取当前 DefUnit 记录
   - 读取 DefUnit[+4] → 获取脚本字节码
   - 执行操作码

3. 脚本块结束 (sub_40EBD4 case 0):
   - 根据参数更新 cur_A/B/C
   - sub_4066F0 沿链步进
   - 实体表[44] 更新为链中到达的节点
   - 下次脚本执行将使用新节点的脚本

4. 场景切换 (sub_40C044):
   - sub_4119CC 释放所有脚本对象
   - sub_402E88 重新加载 TKDefUnit.dat
   - 链和计数器重新初始化
```

## 六、总结

| 问题 | 答案 |
|------|------|
| 链组织的是什么？ | **单个 NPC 的脚本阶段序列** |
| 每个节点代表什么？ | NPC 在故事推进中的一个阶段, 有独立的脚本字节码 |
| 如何推进阶段？ | 脚本执行 opcode 0 时, 子场景计数器+1, sub_4066F0 沿链步进 |
| 3个子场景的作用？ | 3条独立的阶段推进线, 支持对话分支/并行任务线 |
| f0/f4 在链中的角色？ | 数据中随阶段变化, 但链遍历代码不使用它们；可能被各阶段脚本引用 |
| f6=0 的含义？ | 链终止, NPC 不再有后续阶段 |
