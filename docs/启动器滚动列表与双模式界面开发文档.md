# TKS 启动器滚动列表与双模式界面开发文档

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 文档类型 | 产品、交互与开发设计文档 |
| 适用模块 | `tks_launcher_gui` |
| 目标用户 | 以游玩游戏为主、不了解补丁和注入技术的普通玩家 |
| 核心目标 | 让玩家能够清楚选择启动模式、游戏功能和 MOD，并在项目数量较多时保持可用 |
| 当前状态 | 已实施；实施期间的用户调整见 §29，与前文冲突处以 §29 为准 |

## 2. 背景与问题

当前启动器已经具备以下能力：

- 读取并显示 `.tkspatch` 补丁。
- 区分必选补丁和可选补丁。
- 扫描并勾选 `.tksmod` / `.tksmodpak`。
- 应用资源型 MOD、数据型 MOD 和 TKS.exe 替换型 MOD。
- 选择辅助工具。
- 保存补丁、MOD 和辅助工具的勾选状态。
- 通过 GUI 和 CLI 启动游戏。

但是，当前界面更接近 MOD 制作者工具，普通玩家会遇到以下问题：

1. “启动并注入”属于技术术语，玩家不确定它是否会修改游戏文件。
2. “补丁”“必选补丁”“可选补丁”和“MOD”的关系不直观。
3. 顶部工具栏放置了过多低频 MOD 制作功能，启动游戏这一核心操作不够突出。
4. 当游戏功能或 MOD 数量增加时，固定表格会变得拥挤，玩家难以查找项目。
5. 当前界面没有清晰表达“只加载 MOD、不使用启动器游戏功能补丁”的使用场景。
6. 技术日志、补丁失败和 MOD 加载失败混在一起，普通玩家难以判断实际结果。

## 3. 设计目标

### 3.1 必须达到的目标

- 玩家打开启动器后，能够在几秒内回答三个问题：
  - 当前使用什么启动模式？
  - 哪些 MOD 会被加载？
  - 点击哪里启动游戏？
- 支持大量游戏功能和 MOD，列表不会撑破窗口。
- 支持搜索、分类、状态筛选和滚动浏览。
- 启动模式与 MOD 选择相互独立。
- 标准模式保持现有默认行为。
- 兼容模式可以跳过启动器游戏功能补丁，但仍加载玩家选择的 MOD。
- 低频的 MOD 制作功能进入菜单栏，不干扰日常启动流程。
- 旧配置和旧状态文件可以平滑升级。

### 3.2 不在本阶段解决的问题

- 不重新设计补丁引擎的二进制定位逻辑。
- 不改变 `.tkspatch` 文件格式。
- 不改变 `.tksmod` 文件格式。
- 不自动判断所有 MOD 的真实兼容性。
- 不在界面层承诺任何第三方 MOD 一定兼容。
- 不把所有技术日志删除；技术日志改为高级查看模式。

## 4. 核心概念重新定义

界面文案应优先使用玩家语言，内部代码仍可保留现有术语。

| 内部概念 | 玩家界面建议名称 | 说明 |
|---|---|---|
| 必选补丁 | 启动器游戏功能 | 启动器提供的游戏功能扩展和运行时修改 |
| 可选补丁 | 可选游戏功能 | 玩家可以单独启用或关闭的功能 |
| MOD | 我的 MOD | 玩家安装的头像、音乐、图片、剧情、功能等内容 |
| 注入 | 应用 / 加载 | 避免直接暴露实现细节 |
| 辅助工具 | 画面兼容工具 | cnc-ddraw 等辅助运行工具 |
| 补丁失败 | 部分功能未应用 | 避免让玩家误以为整个游戏启动失败 |

界面中应明确区分：

```text
启动模式决定是否使用启动器游戏功能。
我的 MOD 决定玩家自己的内容修改是否加载。
两者可以独立选择。
```

## 5. 启动模式设计

### 5.1 标准模式

显示名称：

```text
标准模式
```

玩家说明：

```text
使用启动器游戏功能，并加载已勾选的 MOD。
推荐原版游戏使用。
```

行为定义：

- 应用启动器游戏功能补丁。
- 应用玩家勾选的可选游戏功能。
- 加载玩家勾选的 MOD。
- 可选择辅助工具。
- 保持现有启动器默认行为。

### 5.2 兼容模式

显示名称：

```text
兼容模式
```

玩家说明：

```text
不使用启动器游戏功能，只加载已勾选的 MOD。
适合其他作者的游戏版本或其他启动器制作的 MOD。
```

行为定义：

- 不应用启动器游戏功能补丁。
- 仍然扫描并加载玩家勾选的 MOD。
- 仍然支持头像、音乐、图片、文本等资源型 MOD。
- 仍然支持 TKS.exe 替换型 MOD，但必须明确提示可能存在版本兼容问题。
- 仍然执行 MOD 文件备份和退出后的恢复流程。
- 辅助工具选择独立生效。
- 依赖启动器游戏功能的 MOD 可能无法工作，界面需要提示这一点。

### 5.3 模式选择控件

推荐使用分段按钮或单选按钮，不建议只放一个“是否使用必选补丁”复选框。

推荐表现：

```text
启动模式：  [● 标准模式]  [○ 兼容模式]
```

模式控件必须同时显示当前说明：

```text
当前：标准模式
将使用启动器游戏功能，并加载已勾选的 MOD。
```

切换到兼容模式后，说明更新为：

```text
当前：兼容模式
将跳过启动器游戏功能，但仍加载已勾选的 MOD。
```

第一次切换到兼容模式时可以显示一次确认对话框：

```text
切换到兼容模式？

兼容模式不会使用启动器游戏功能，但仍会加载你勾选的 MOD。
部分依赖启动器游戏功能的 MOD 可能无法正常工作。

[取消] [切换到兼容模式]
```

## 6. 信息架构与菜单调整

### 6.1 顶部工具栏只保留高频操作

建议保留：

```text
[▶ 启动游戏] [刷新 MOD] [存档管理]
启动模式：[标准模式]
已启用 MOD：3 个
```

“启动游戏”是唯一的主操作按钮，应使用明显的主按钮样式。

“启动并注入”改为“启动游戏”，技术解释放到 Tooltip 或启动说明中。

### 6.2 文件菜单

```text
文件(F)
├── 启动游戏                 Ctrl+Enter
├── 选择游戏程序
├── 刷新 MOD
├── 存档管理
├── ─────────────
└── 退出
```

### 6.3 MOD 工具菜单

低频功能全部移动到这里：

```text
MOD 工具(M)
├── 制作头像 MOD
├── 制作音乐 MOD
├── 打包 MOD
├── 合并 MOD
├── 拆分 MOD
├── 编辑 MOD 内容
├── 编辑 MOD 信息
└── 将 TKS.exe 打包为 MOD
```

### 6.4 设置菜单

```text
设置(S)
├── 画面兼容工具
├── 启动模式设置
├── 日志显示设置
└── 切换主题
```

辅助工具可以从主界面移入设置，但如果玩家经常需要切换，也可以在启动模式旁保留一个紧凑选择控件。

### 6.5 帮助菜单

```text
帮助(H)
├── 使用说明
├── 标准模式与兼容模式
├── 常见问题
└── 关于
```

### 7.2 三个主面板职责

#### 游戏功能

用于选择启动器提供的功能补丁。标准模式下可用；兼容模式下整体折叠或置灰。

#### 我的 MOD

用于选择玩家安装的 `.tksmod` 和 `.tksmodpak`。无论标准模式还是兼容模式，都保持可用。

#### 启动状态

用于显示当前模式、已启用数量、启动结果和重要警告。技术日志通过“查看详细日志”打开。

## 8. 大量项目的列表方案

### 8.1 不采用下拉列表承载多选项目

下拉列表适合：

- 启动模式单选。
- 分类筛选。
- 状态筛选。
- 排序方式。

下拉列表不适合承载大量需要同时勾选的功能或 MOD，因为玩家看不到已选项目全貌，也不方便比较。

### 8.2 采用固定面板加滚动列表

每个主面板内部使用：

```text
面板标题
搜索框
分类筛选 + 状态筛选
可滚动分组列表
批量操作
选中项目详情
```

列表必须具备：

- 垂直滚动条。
- 固定表头或固定列标题。
- 项目数量较多时不改变主窗口整体尺寸。
- 滚动位置可在刷新时尽量保留。
- 搜索时只过滤当前列表，不修改启用状态。
- 清空搜索后恢复原列表和原勾选状态。

### 8.3 分组列表

游戏功能建议分组：

```text
推荐功能
游戏扩展
显示与美化
存档相关
战斗相关
高级功能
```

MOD 建议分组：

```text
美化
头像
音乐
剧情
功能
存档
TKS.exe 替换
其他
```

分类名称必须面向玩家，不显示内部类型名，例如 `cave_hook`、`patch_imm32`、`patch_bytes`。

### 8.4 项目行设计

游戏功能行：

```text
☑ 字体显示                         推荐
```

MOD 行：

```text
☑ 小乔头像美化      美化      作者：玩家A
```

可在鼠标悬停或选中后显示详细描述，不建议在列表中同时铺开过多字段。

## 9. 搜索、筛选与排序

### 9.1 搜索

搜索范围包括：

- 显示名称。
- 作者。
- 简介。
- ID（高级搜索时可用）。

搜索框占位符：

```text
搜索游戏功能...
搜索 MOD 名称、作者或说明...
```

无匹配时显示：

```text
没有找到匹配项目
请尝试其他关键词或清除筛选条件
```

### 9.2 状态筛选

建议提供：

```text
全部
已启用
未启用
推荐
可能冲突
```

MOD 额外提供：

```text
兼容模式可用
需要游戏功能
作者未声明
```

如果当前项目没有可靠的兼容性元数据，不得伪造“兼容”结论。

### 9.3 排序

默认排序建议：

1. 推荐项目。
2. 已启用项目。
3. 分类顺序。
4. 名称。

高级用户可以按名称、作者、加载顺序排序，但加载顺序不应成为普通玩家的主要概念。

## 10. 批量操作

批量操作应以当前分类或当前筛选结果为范围，避免误操作整个列表。

推荐按钮：

```text
[启用当前分类] [关闭当前分类]
```

不建议默认提供无确认的全局“全部启用”，因为大量 MOD 可能产生冲突。

当批量启用项目较多时显示确认：

```text
即将启用当前筛选结果中的 24 个 MOD。
部分 MOD 可能存在冲突。

[取消] [继续]
```

## 11. 选中项目详情

点击项目时，在面板底部或右侧显示简要详情。

### 游戏功能详情

```text
名称：动画速度
分类：游戏扩展
说明：调整部分战斗动画的播放速度。
状态：推荐
```

### MOD 详情

```text
名称：小乔头像美化
作者：玩家A
版本：1.0
类型：美化
说明：替换小乔相关头像图片。
兼容提示：作者未声明兼容模式。
```

内部 ID、文件路径、加载顺序等信息放入“高级信息”折叠区。

## 12. 兼容模式下的显示策略

切换到兼容模式后，不建议删除游戏功能面板，否则玩家可能认为配置丢失。

推荐显示：

```text
游戏功能
兼容模式下未启用                         [展开查看]
```

展开后：

```text
兼容模式不会应用以下启动器游戏功能。
切换回标准模式后将恢复当前选择。
```

游戏功能的勾选状态应被保留，切换模式只改变“本次是否应用”，不清空玩家选择。

MOD 面板不变，并在标题下显示：

```text
兼容模式下仍可加载已勾选的 MOD。
```

## 13. 启动流程与状态反馈

### 13.1 启动前摘要

玩家点击启动前，在主界面显示摘要：

```text
准备启动
模式：兼容模式
游戏功能：不使用
MOD：3 个
画面兼容工具：cnc-ddraw
```

### 13.2 启动过程

普通状态文案建议：

```text
正在检查游戏文件...
正在加载 MOD...
正在准备游戏...
正在应用游戏功能...
游戏已启动
```

详细技术信息进入日志面板，不直接替代普通状态文案。

### 13.3 启动结果

不要只显示“补丁应用成功”或“补丁应用失败”，改为分项结果。

标准模式成功：

```text
游戏已启动

游戏功能：已应用
MOD：3 个已加载
辅助工具：未使用
```

兼容模式成功：

```text
游戏已启动

游戏功能：未使用
MOD：2 个已加载
辅助工具：cnc-ddraw
```

部分失败：

```text
游戏已启动，但部分内容未加载

游戏功能：已应用
MOD：2 个成功，1 个失败

[查看详细日志]
```

## 14. 状态持久化

### 14.1 需要保存的状态

```text
启动模式：standard / compatible
可选游戏功能的启用状态
MOD 的启用状态
辅助工具选择
```

### 14.2 默认值

旧状态文件没有启动模式字段时，默认：

```text
standard
```

这样升级后不会改变原有用户的默认启动行为。

### 14.3 切换模式时的状态规则

- 切换模式不清空游戏功能勾选状态。
- 切换模式不清空 MOD 勾选状态。
- 兼容模式下暂时不应用游戏功能，但保留玩家下次切回标准模式的选择。
- 搜索、分类和滚动位置可以保存，也可以只在当前运行周期内保留；启用状态必须保存。

## 15. 存档备份与恢复

如果启动器已有补丁和 MOD 状态快照，备份元数据应增加：

```text
启动模式
可选游戏功能状态
MOD 状态
辅助工具状态
```

恢复备份时，如果启动模式不同，应在确认提示中明确显示：

```text
备份使用：兼容模式
当前使用：标准模式

是否同时恢复启动模式、游戏功能和 MOD 状态？
```

旧备份没有启动模式字段时，按标准模式处理。

## 17. 兼容性与风险提示

兼容模式并不等于所有 MOD 都兼容。界面应使用谨慎文案：

```text
兼容模式适合只需要资源替换或内容 MOD 的情况。
依赖启动器游戏功能的 MOD 可能无法正常工作。
请以 MOD 作者说明为准。
```

以下情况需要提示但不应阻止玩家尝试：

- MOD 作者未声明兼容模式。
- MOD 需要特定游戏版本。
- 检测到重复 ID。
- 检测到多个 MOD 修改同一资源。
- MOD 需要某个游戏功能但当前处于兼容模式。

提示应尽量说明解决方式：

```text
该 MOD 可能需要标准模式。
你可以切换到标准模式后再次启动，也可以继续尝试兼容模式。
```

## 18. 需要补充的 MOD 元数据

为了支持分类和兼容提示，建议逐步扩展 MOD 元数据：

```json
{
  "type": "avatar",
  "category": "美化",
  "compatibility": {
    "standard": true,
    "compatible": true
  },
  "requires_features": [],
  "conflicts_with": [],
  "description": "替换小乔相关头像图片"
}
```

建议字段：

| 字段 | 说明 |
|---|---|
| `category` | 玩家可理解的分类 |
| `compatibility.standard` | 是否声明支持标准模式 |
| `compatibility.compatible` | 是否声明支持兼容模式 |
| `requires_features` | 依赖的游戏功能 ID |
| `conflicts_with` | 已知冲突 MOD ID |
| `type` | 头像、音乐、功能、剧情等类型 |

旧 MOD 没有这些字段时：

- `category` 归入“其他”。
- 兼容性显示“作者未声明”。
- 不自动判定为不兼容。

## 19. 启动模式与流水线执行契约

启动模式不是单纯的界面筛选条件，而是一次启动任务的执行策略。界面、GUI Worker 和核心流水线必须使用同一个模式值，禁止仅通过“清空补丁选择”来模拟兼容模式。

### 19.1 模式值

内部只允许使用以下稳定值：

```text
standard    标准模式
compatible  兼容模式
```

未知值、空值或旧状态文件缺少该字段时，一律按 `standard` 处理，并记录一次迁移日志。

### 19.2 各阶段执行矩阵

| 执行阶段 | 标准模式 | 兼容模式 |
|---|---:|---:|
| 检查游戏程序和游戏目录 | 执行 | 执行 |
| 扫描并解析 MOD | 执行 | 执行 |
| 检测 MOD 依赖和冲突 | 执行 | 执行 |
| 备份并应用纯资源 MOD | 执行 | 执行 |
| 应用 MOD 携带的启动器配置 | 按依赖决定 | 默认跳过，记录原因 |
| WarPC/TKAct 等启动器数据扩展准备 | 按补丁需求执行 | 跳过 |
| 启动游戏进程 | 执行 | 执行 |
| 检测游戏进程和窗口 | 执行 | 执行 |
| 应用启动器内存补丁 | 执行 | 跳过 |
| 应用依赖运行时补丁的 MOD 数据 | 执行 | 跳过或标记失败 |
| TKS.exe 替换型 MOD | 执行 | 执行，但显示版本风险 |
| 辅助工具注入 | 执行 | 执行 |
| 游戏退出后恢复文件 | 执行 | 执行 |

兼容模式仍然需要启动器监控游戏进程，以保证 MOD 文件、TKS.exe 和辅助工具能够恢复。兼容模式不应调用会修改目标进程内存的补丁阶段。

### 19.3 MOD 按运行时依赖分层

不能仅依据 `type` 或 `category` 决定兼容模式行为。启动器应根据元数据和实际内容，将 MOD 分为：

| 分层 | 典型内容 | 兼容模式处理 |
|---|---|---|
| `resource_only` | 图片、头像、音乐、文本资源替换 | 允许加载 |
| `data_replace` | 普通 DAT 数据替换，且不需要扩容或运行时 Hook | 默认允许，记录未验证状态 |
| `runtime_required` | `requires_features`、`warpc_expand`、启动器配置或内存 Hook | 不应用，显示明确原因 |
| `exe_replace` | `type == "tks_exe"` | 允许尝试，必须确认版本风险 |
| `mixed` | 同时包含多个层级 | 按组件拆分；不能拆分时按最高风险层级处理 |

若旧 MOD 没有足够元数据，不能自动判定为安全。启动器可以根据内容推断风险，但必须显示“自动识别”或“未声明”。

### 19.4 模式切换与本次启动快照

点击启动后，应创建不可变的 `LaunchContext` 快照，至少包括：

```json
{
  "mode": "compatible",
  "exe_path": "...",
  "game_dir": "...",
  "enabled_patch_ids": [],
  "enabled_mod_ids": [],
  "selected_tool": "cnc-ddraw"
}
```

启动过程只使用快照，不直接读取正在变化的界面控件。游戏运行期间禁止切换模式、刷新 MOD 或修改启用状态；游戏退出并完成清理后才恢复这些操作。

## 20. 结构化启动结果与状态反馈

启动结果不得只使用一个成功/失败布尔值。核心流水线应返回可序列化的分项结果：

```json
{
  "process_started": true,
  "mode": "standard",
  "patches": {"status": "partial", "applied": 8, "failed": 1, "skipped": 0},
  "mods": {"loaded": 3, "failed": 1, "skipped": 0},
  "tool": {"name": "cnc-ddraw", "status": "applied"},
  "cleanup": {"status": "pending"},
  "warnings": []
}
```

### 20.1 状态定义

普通状态至少区分：

```text
准备启动
正在准备文件
正在加载 MOD
正在启动游戏
游戏运行中
游戏已退出，正在恢复文件
已完成
启动失败
启动成功但部分内容未应用
恢复失败
```

兼容模式下跳过补丁是预期行为，必须显示“未使用”，不能显示“补丁失败”。

### 20.2 错误分类

错误至少分为：

```text
preflight_failed       启动前检查失败
mod_load_failed        MOD 解析或加载失败
patch_failed           补丁应用失败
process_launch_failed  游戏进程启动失败
tool_apply_failed      辅助工具应用失败
cleanup_failed         退出后的恢复失败
```

状态面板显示面向玩家的摘要，详细日志保留原始路径、MOD ID、补丁 ID、异常信息和堆栈。一个分项失败不应覆盖其他分项的实际结果。

## 21. 文件修改、备份与异常恢复

凡是启动器写入游戏目录的文件，都必须在本次启动上下文中登记：

```text
目标路径
原始文件是否存在
备份路径
写入来源（MOD / TKS.exe / 辅助工具）
写入前校验值
写入后校验值
是否已恢复
```

### 21.1 恢复规则

- 只有确认文件仍是本次启动写入的版本时，才自动覆盖恢复。
- 文件在游戏运行期间被用户或其他程序修改时，不应静默覆盖，应提示人工处理。
- 原文件不存在时，恢复动作是删除启动器新建文件。
- 多种来源修改同一路径时，必须按逆序恢复，并记录来源链。
- 恢复失败不能被普通“游戏已退出”状态掩盖。

### 21.2 异常退出

启动器崩溃、游戏强制结束或启动流程中途失败时，都应进入统一清理入口。启动器下次打开时，应扫描未完成的启动快照并提示：

```text
检测到上次启动未完成恢复。
是否尝试恢复游戏文件？
```

恢复快照必须使用唯一任务 ID，不能只依赖固定的 `.bak` 文件名。原有备份文件不得被新的启动任务覆盖。

## 22. 状态文件版本与游戏目录作用域

GUI 状态文件应增加 schema 版本和最近使用的游戏目录信息。建议格式：

```json
{
  "schema_version": 2,
  "last_game_path": "C:/Games/TKS/TKS.exe",
  "mode": "standard",
  "patches": {},
  "mods": {},
  "tool": ""
}
```

### 22.1 迁移规则

- 旧文件没有 `schema_version` 时按版本 1 读取。
- 旧文件没有 `mode` 时写入 `standard`。
- 迁移前先保留原文件副本，迁移成功后再原子替换。
- 字段类型错误时只丢弃错误字段，不应导致整个状态文件失效。
- 未知字段必须保留，避免未来版本降级时丢失数据。
- MOD 勾选状态至少按游戏目录隔离；不同游戏目录不能默认共享同一套状态。

补丁选择还应考虑 EXE 版本或配置 profile。无法确认适用版本时，启动前显示警告，而不是静默应用。

## 23. `.tksmodpak` 元数据与资源规则

合集根元数据用于概览和默认值，子 MOD 元数据用于实际执行。合并优先级固定为：

```text
子 MOD 明确声明
    > 合集根明确声明
    > 启动器内容推断
    > 未分类 / 未声明
```

规则如下：

- 子 MOD 的 `type`、`category`、`tags`、`compatibility` 和 `requires_features` 必须被完整解析。
- 合集根标签只能补充子 MOD 缺失字段，不能覆盖子 MOD 的明确声明。
- `tags` 合并时去重；`requires_features` 合并时保留全部依赖。
- 任一子 MOD 明确不支持兼容模式时，合集只能显示“包含不支持项”，不能标记为整体兼容。
- 合集内的 `TKS.exe` 替换资源必须通过嵌套 ZIP 读取，不能假定资源位于外层 ZIP 根目录。
- 多个子 MOD 提供 `TKS.exe` 时，默认阻止无确认启动，并要求玩家明确选择一个。
- 合集显示的“已加载数量”应区分合集数量和展开后的子 MOD 数量。

## 25. 验收标准

### 25.1 普通玩家可理解性

- 首屏能看到“启动游戏”按钮。
- 首屏能看到当前启动模式。
- 首屏能看到已启用 MOD 数量。
- 不需要阅读开发文档即可理解标准模式和兼容模式的区别。
- 不需要理解“注入”“Cave”“RVA”等技术词汇即可完成启动。

### 25.2 大量项目

- 至少数十个游戏功能和 MOD 时窗口不发生横向溢出。
- 列表可以滚动。
- 搜索可以快速定位名称、作者或说明。
- 分类和状态筛选不会丢失勾选状态。
- 批量操作只作用于当前筛选范围。

### 25.3 模式功能

- 默认模式仍为标准模式。
- 标准模式可以应用游戏功能和 MOD。
- 兼容模式不会应用启动器游戏功能。
- 兼容模式仍可以应用资源型 MOD。
- 切换模式不会清空游戏功能和 MOD 选择。
- 旧状态文件升级后仍然可用。

### 25.4 错误反馈

- 游戏启动失败、游戏功能失败和 MOD 加载失败可以区分。
- 兼容模式下不应显示误导性的“补丁应用失败”。
- 技术排错信息可以通过详细日志获取。
- MOD 文件、TKS.exe 和辅助工具的恢复结果可以单独查看。
- 启动器中途退出后再次打开，能够检测并处理未完成的恢复任务。
- 文件被外部程序修改后，恢复流程不会静默覆盖用户修改。

### 25.5 启动与持久化

- 首次启动时可以选择游戏程序，之后能够使用最近一次有效路径。
- 游戏程序不存在、路径变化或版本变化时，启动前给出明确提示。
- 启动前摘要使用本次 `LaunchContext` 的实际内容，而不是界面当前的临时显示值。
- 启动期间不能刷新列表、切换模式或修改勾选状态。
- 旧状态文件迁移失败时不会覆盖原文件。
- 不同游戏目录的模式、补丁和 MOD 状态不会互相污染。

### 25.6 合集与元数据

- `.tksmodpak` 的子 MOD 标签优先于合集根标签。
- 子 MOD 的 `TKS.exe` 资源可以从嵌套 ZIP 正确读取。
- 合集内存在不支持兼容模式的子 MOD 时，不会显示为整体兼容。
- 多个 `TKS.exe` 替换源不会被静默选择。
- 旧 MOD 缺少新字段时仍可加载，并显示“未声明”或“自动识别”。

## 26. 最终设计结论

推荐采用以下整体方案：

```text
顶部：高频操作 + 当前启动模式 + 已启用数量
主区域：固定面板 + 搜索框 + 分类筛选 + 可滚动多选列表
菜单栏：低频 MOD 制作工具、设置、帮助
启动模式：标准模式 / 兼容模式
兼容模式：跳过启动器游戏功能，但仍加载玩家选择的 MOD
详细日志：默认隐藏，发生问题时再查看
```

关键产品原则是：

> 先让玩家选择“怎么玩”，再让玩家选择“使用哪些 MOD”，最后点击“启动游戏”。

对于项目数量较多的情况，滚动列表是主方案；“更多”只用于打开完整管理或高级设置，不应成为玩家每次启动都必须打开的隐藏入口。

## 27. MOD 标签与编辑器导出设计

### 27.1 设计结论

按照滚动列表、分类筛选和双启动模式的规划，编辑器导出 `.tksmod` 时应增加标签选择。

但是不应直接改变现有 `type` 字段的含义，也不应要求以前发布的 MOD 重新打包。推荐采用向后兼容的扩展：

```text
保留 type
新增 category
新增 tags
新增 compatibility
新增 requires_features
旧 MOD 使用回退和自动推断
```

### 27.2 字段职责

```json
{
  "type": "data",
  "category": "gameplay",
  "tags": ["data", "gameplay"],
  "compatibility": {
    "standard": true,
    "compatible": null,
    "requires_features": [],
    "notes": "作者未声明兼容模式支持情况"
  }
}
```

字段定义：

| 字段 | 用途 | 兼容要求 |
|---|---|---|
| `type` | 现有内部结构或特殊行为，例如 `tks_exe`、`data`、`mixed` | 保留原有语义 |
| `category` | 玩家看到的主分类，单值 | 新字段，可缺省 |
| `tags` | 玩家筛选用的多值标签 | 新字段，可缺省 |
| `compatibility` | 标准模式和兼容模式的支持声明 | 新字段，可缺省 |
| `requires_features` | 依赖的启动器游戏功能 ID | 新字段，可缺省 |
| `notes` | 面向玩家的兼容性说明 | 新字段，可缺省 |

### 27.3 推荐分类与标签

内部值使用稳定英文，界面显示中文：

| 内部值 | 界面名称 |
|---|---|
| `visual` | 美化 |
| `avatar` | 头像 |
| `music` | 音乐 |
| `story` | 剧情 |
| `gameplay` | 功能 |
| `save` | 存档 |
| `tks_exe` | TKS.exe 替换 |
| `config` | 配置 |
| `mixed` | 综合 |
| `other` | 其他 |

推荐标签包括：

```text
visual
avatar
music
story
gameplay
save
config
resource
data
requires_patch
compatible_mode
```

### 27.4 兼容性状态

兼容模式支持不能只用一个布尔值表示。建议区分三种状态：

```text
true  = 作者明确声明支持
false = 作者明确声明不支持
null  = 作者没有声明
```

示例：纯资源头像 MOD：

```json
{
  "category": "avatar",
  "tags": ["avatar", "visual", "resource"],
  "compatibility": {
    "standard": true,
    "compatible": true,
    "requires_features": [],
    "notes": "纯资源替换类 MOD"
  }
}
```

示例：依赖启动器功能的游戏扩展 MOD：

```json
{
  "category": "gameplay",
  "tags": ["gameplay", "requires_patch"],
  "compatibility": {
    "standard": true,
    "compatible": false,
    "requires_features": ["summon_extend"],
    "notes": "需要启动器召唤扩展功能"
  }
}
```

### 27.5 公共导出对话框

大多数 `EDITORS` 对应的编辑器都复用公共模块：

```text
editor_utils/mod_exporter.py
```

因此标签控件应集中放入公共 `ModMetadataDialog`，不要在每个编辑器中重复实现。

建议增加：

```text
MOD 分类：[美化 ▼]

标签：
☐ 美化
☐ 头像
☐ 音乐
☐ 剧情
☐ 功能
☐ 配置
☐ TKS.exe 替换
☐ 需要启动器游戏功能

兼容模式：
(●) 支持
(○) 不支持
(○) 未声明

兼容性说明：[________________]
```

编辑器通过 `defaults` 传入默认值，作者可以在导出时调整。

### 27.6 各编辑器默认分类建议

| 编辑器 | 默认分类 | 默认标签 |
|---|---|---|
| `TKSItemEditor` | 功能 | `data` |
| `TKSWarpcEditor` | 功能 | `data`, `gameplay` |
| `TKSSkillEditor` | 功能 | `data`, `gameplay` |
| `TKSShopEditor` | 功能 | `data` |
| `TKSMatEditor` | 功能 | `data`, `gameplay` |
| `TKSJvgEditor` | 美化 | `visual`, `resource` |
| `TKSGrpEditor` | 美化 | `visual`, `resource` |
| `TKSTktEditor` | 剧情 | `story`, `text` |
| `TKSKonEditor` | 功能 | `data` |
| `TKSActEditor` | 功能 | `data`, `gameplay` |
| `TKSWardataEditor` | 功能 | `data`, `gameplay` |
| `TKSGxpEditor` | 美化 | `visual`, `resource` |
| `TKSConfigsEditor` | 配置 | `config` |
| `TKSFontEditor` | 美化 | `font`, `visual`, `resource` |
| 自定义头像导出 | 头像 | `avatar`, `visual`, `resource` |
| 自定义音乐导出 | 音乐 | `music`, `visual`, `resource` |
| TKS.exe 替换导出 | TKS.exe 替换 | `tks_exe` |
| 综合打包/合并 | 综合 | 根据来源 MOD 合并 |

默认值只是减少作者操作，不应阻止作者修改分类。

### 27.7 旧 MOD 的兼容策略

启动器读取新字段时必须使用缺省值：

```python
category = mj.get("category")
tags = mj.get("tags", [])
compatibility = mj.get("compatibility")
```

旧 MOD 没有新字段时：

- 继续正常加载，不拒绝启动。
- 分类显示“未分类”。
- 兼容性显示“作者未声明”。
- 不自动判定为不兼容。
- 允许玩家在兼容模式中尝试。
- 对明显的纯资源 MOD 可以显示“通常可用”，但必须标记为自动识别。

建议在启动器内部记录：

```text
inferred_metadata = true
```

用于区分作者声明和启动器推断，界面可以显示：

```text
美化（自动识别）
兼容模式：未声明
```

### 27.8 旧 MOD 的分类推断

自动推断只能用于分类建议和提示，不能替代真实兼容性验证。

推荐规则：

| 检测依据 | 推断结果 |
|---|---|
| `type == "tks_exe"` | TKS.exe 替换 |
| 资源路径包含 `Sound/`、`BGM/` 或音频扩展名 | 音乐 |
| 资源路径包含头像/图片目录或 `.JVG`、`.GRP`、图片扩展名 | 美化或头像 |
| 目标文件为 `TKT.dat`、`TKD.dat` | 剧情或文本 |
| 携带白名单 `configs/*.json` | 配置 |
| 只有 `data/*.json` | 功能或其他 |
| 无法判断 | 其他 |

推断结果必须能在界面中被识别为“自动识别”，不能冒充作者明确声明。

### 27.9 `.tksmodpak` 合集规则

合集根 `mod.json` 可以携带自己的分类和兼容声明，但不能覆盖子 MOD 的明确声明。

优先级：

```text
子 MOD 明确标签
    > 合集根标签
    > 根据内容推断
    > 未分类 / 未声明
```

如果合集内包含未声明或明确不支持兼容模式的子 MOD，兼容模式提示应为：

```text
合集内包含部分未声明或不支持兼容模式的 MOD
```

不能因为合集内存在一个纯美化 MOD，就把整个合集标记为完全兼容。

### 27.10 打包、合并和元数据编辑

以下工具需要同步处理新字段：

```text
tks_launcher_gui/ui/mod_packer_dialog.py
tks_launcher_gui/ui/mod_merger_dialog.py
tks_launcher_gui/ui/mod_meta_editor_dialog.py
tks_launcher_gui/core/mod_packer.py
tks_launcher_gui/core/mod_merger.py
```

规则：

- 打包工具允许选择分类和兼容性。
- 合并工具合并来源 MOD 的标签并去重。
- 合并后无法确定单一兼容性时使用“未声明”。
- 元数据编辑器可以补充旧 MOD 缺少的标签。
- 重写 `mod.json` 时必须保留未知字段，避免破坏未来扩展。
- `type == "tks_exe"` 的现有特殊行为必须保持不变。

### 27.11 启动器列表显示

推荐行显示：

```text
☑ 小乔头像美化       美化 · 头像       作者：玩家A
☑ 战斗音乐包         音乐             作者：玩家B
☐ 召唤扩展           功能 · 需要补丁   作者：玩家C
☐ 未知 MOD           未分类 · 未声明   作者：未知
```

兼容性状态应同时使用文字和颜色：

- 绿色：明确支持兼容模式。
- 黄色：作者未声明，需要注意。
- 红色：明确要求标准模式或依赖游戏功能。
- 灰色：未分类或信息不足。

颜色不能作为唯一信息来源。

## 28. 标签设计验收标准

- 新导出的 MOD 包含所选择的 `category`、`tags` 和 `compatibility`。
- `type` 的原有语义和 `tks_exe` 识别不受影响。
- 所有使用公共导出对话框的编辑器都能使用默认分类。
- 旧 MOD 没有新字段时仍可正常加载和应用。
- 旧 MOD 不会因缺少标签被自动判定为不兼容。
- 旧 MOD 的自动推断结果明确显示为自动识别。
- `.tksmodpak` 子 MOD 和合集根元数据按规定优先级处理。
- MOD 打包、合并和元数据编辑不会丢失新字段或未知字段。
- 分类筛选、标签筛选和兼容模式筛选不会改变 MOD 实际启用状态。
- 标签提示不会替代运行时冲突检测和实际启动结果。

- 左面板定名“补丁列表”，Dock 标题栏右侧为 可选补丁/必选补丁 互斥切换按钮（显示各自数量），切换仅显隐对应子集；兼容模式下整体置灰、勾选保留。

- 状态栏不再放置 设置/帮助 按钮（菜单栏已有入口）；设置菜单不再单列“画面兼容工具”（面板常驻可见）。

### 29.2 列表简化（覆盖 §8 / §9 / §10）

- 两列表均移除：搜索框、分类/状态/兼容性筛选下拉、分组标题行、批量操作按钮；改为扁平滚动列表。

- 补丁列表列：启用 / 功能名称 / 类型。类型列使用玩家友好标签：数值修改、指令修补、代码注入、外部脚本、召唤表、字体配置、动画速度、掉落概率、经验锁定、地址重定位、额外段修补（未知类型回退原始 type）。面板底部详情框显示 名称/类型/状态(必选·推荐·可选)/说明。
- MOD列表列：启用 / 模组名称 / 分类 / 作者。分类列使用彩色 Tag 标签；列表不显示“（自动识别）”字样（仅保留在悬浮提示中）。
- Tag 组件：PySide6 (Qt Widgets) 无可嵌入表格的原生 Tag/Chip 组件，自定义 `_CategoryTag`（居中 QLabel + 主题 QSS `Tag*` 规则按分类着色），经 `setCellWidget` 嵌入。

### 29.3 分类体系扩展（覆盖 §27.3 分类表）

新增三个分类：`font`=字体、`interface`=界面、`map`=地图。同步点：模组信息编辑弹窗、导出为MOD 弹窗的分类下拉，MOD列表标签映射，双主题 `TagFont/TagInterface/TagMap` 配色。

### 29.4 弹窗字段精简（覆盖 §27.5）

模组信息编辑 与 导出为MOD 弹窗移除字段：游戏版本、依赖、冲突、兼容模式、兼容说明。保存采用 `orig.update(new_meta)` 合并，mod.json 中这些键的原值保留不丢失。

- 移除首次切换兼容模式的确认对话框。
- 兼容模式说明文案从面板顶部移至状态栏常驻标签（仅兼容模式可见，`probe="warn"` 语义色）：“兼容模式：跳过启动器游戏功能（勾选已保留），仍可加载已勾选的 MOD”。

### 29.6 玩家可见文案（覆盖 §13 文案示例）

状态时间线（状态栏右下角 + 启动状态面板）：

```text

游戏已退出 → 右下角回落到 就绪；状态栏小结：游戏已退出。本次：{模式}，游戏功能 {已应用|未使用|部分未应用}，MOD {N 个已加载|X 成功，Y 失败}
```

### 29.7 主题规范对齐（editor_themes）

- 双主题对齐 Godot 4.7 Modern 默认色板（源码 `theme_modern.cpp` / `editor_theme_manager.cpp` 推导）：
  - 深色：chrome `#292929`、accent `#569EFF`、内容面板 `#141414`、表格内嵌层 `#171717`、DockHeader 标题带 `#1f1f1f`。
  - 浅色：chrome `#E6E6E6`、accent `#2E80FF`、内容面板 `#FDFDFD`、表格内嵌层 `#F6F6F6`、DockHeader 标题带 `#D4D4D4`。
- `window_theme.py` DWM 标题栏颜色同步上述色板。
- Qt QSS 类型选择器 `QWidget { background }` 会匹配子类，导致裸 QWidget/QRadioButton/QCheckBox 被染成灰块。统一处理：Dock 内容容器使用 `#TransparentBg`；`QRadioButton`/`QCheckBox` 规则加 `background-color: transparent`；详情框 `QTextBrowser#detailBox` 透明无边框。所有 Dock 内容面色调统一，仅表格保留内嵌层色差。
- 历史教训：表格合并区（setSpan）只渲染左上角单元格，分组标题项必须放在第 0 列，否则呈现为空行（分组功能已按用户要求移除，此结论适用于今后任何合并区用法）。
