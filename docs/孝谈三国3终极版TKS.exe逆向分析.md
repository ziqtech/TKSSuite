# 孝谈三国3终极版 TKS.exe 逆向分析报告

> 对比基准：`逆向工作区/TKS.exe`（原版）
> 分析对象：`MOD文档/第三方MOD\孝谈三国3终极版\TKS.exe`
> 分析方法：字节级二进制对比 + x86 反汇编

---

## 一、PE 结构变化

| 项目 | 原版 | MOD |

| PE 节数量 | 8 | 11 |

### 新增 PE 节

| 节名 | RVA | VSize | RawSize | 用途 |
|------|-----|-------|---------|------|

## 二、.text 段代码修改总览

共 **93 处**代码修改，分为两大类：

- **Cave Hook（~30处）**：用 `E9 rel32`（JMP）替换原指令，跳到 `.test` 节执行新逻辑后返回
- **内联修改（~63处）**：直接修改指令字节（立即数、条件码、NOP 等）

## 六、技能222 Cave 代码反汇编

cave 入口 VA 0xA7D2A8（.test 节 offset 0x2A8）：

```asm
; 技能222 虎威震南天 → rand(3) 三选一
push 3                      ; 0xA7D2A8: 6A 03
call sub_452AC0             ; 0xA7D2AA: E8 11 58 9D FF  (rand函数)
pop ecx                     ; 0xA7D2AF: 59              (cdecl清栈)
cmp ax, 0                   ; 0xA7D2B0: 66 83 F8 00
je .case0                   ; 0xA7D2B4: 74 1E  → 0xA7D2D4
cmp ax, 1                   ; 0xA7D2BA: 66 83 F8 01
je .case1                   ; 0xA7D2BE: 74 1F  → 0xA7D2DF
cmp ax, 2                   ; 0xA7D2C4: 66 83 F8 02
je .case2                   ; 0xA7D2C8: 74 20  → 0xA7D2EA

.case0:                     ; rand==0
mov word [ebp-2], 58        ; i=58, WarPC 94 = 祝融夫人 (原版)
jmp 0x444CCF                ; 返回合流点

.case1:                     ; rand==1
mov word [ebp-2], 59        ; i=59, WarPC 95 = (MOD角色)
jmp 0x444CCF

.case2:                     ; rand==2
mov word [ebp-2], 60        ; i=60, WarPC 96 = 大鹏金翅鸟
jmp 0x444CCF
```

## 七、技能251 分析结论

**技能251（閃閃生光）完全未被修改**。字节级对比确认 VA 0x444CB3-0x444CCE 区间与原版完全一致：

```asm
; 原版逻辑保持不变:
push 100                    ; 0x444CB3
call sub_452AC0             ; rand(100)
pop ecx
cmp ax, 50                  ; >= 50?
jae .if_branch
mov word [ebp-2], 96        ; else: i=96, WarPC 132 = 大鹏金翅鸟
jmp .merge
mov word [ebp-2], 98        ; if:   i=98, WarPC 134 = 五爪金龙
```

合流点（0x444CCF）之后的 `rand(4)` 参与战斗位参数计算的代码也是原版就有的，非 MOD 新增。

## 九、与启动器补丁框架的关系

该 MOD 的修改方式为**直接修改 TKS.exe 二进制文件**（静态补丁），与我们的启动器运行时内存补丁框架不同：

| 对比项 | 孝谈三国3终极版 | 我们的启动器 |
|--------|----------------|-------------|
| 修改方式 | 静态修改 EXE 文件 | 运行时内存补丁 |
| 生效时机 | 永久 | 运行时（关闭失效） |
| 版本耦合 | 硬编码地址，不可跨版本 | 模式扫描，版本无关 |
| 可逆性 | 需备份原文件 | 天然可逆 |
| 扩展方式 | 新增 PE 节(.test) | VirtualAllocEx 分配 cave |

如果需要让启动器兼容此 MOD 版本，需注意：
1. 技能222的 hook 点已被占用（原指令被替换为 JMP）
2. 模式扫描 `66 C7 45 FE 3A 00 EB 2B`（skill_222）将匹配失败
3. `.test` 节的 cave 代码可能与启动器的内存补丁产生地址冲突

### 10.2 需处理项及适配措施

| 项 | 性质 | 适配措施 |
|----|------|---------|
| **召唤表 skill_222 盲写**（`code_addrs` RVA 0x44CA0） | **危险**：MOD 已把 `mov word[ebp-2],imm16`（0x444C9C）整条改成 `E9 rel32`（JMP 到 0xA7D2A8 的 rand(3) cave），启动器旧逻辑会盲写 imm16 覆盖 JMP 偏移 → 破坏 MOD 跳转 → 崩溃 | 在 `patch_engine.apply_summon_table` 增加**版本无关守卫**：仅当目标前导字节确为 `66 C7 45 FE` 时才写入，否则 `[SKIP]`。对原版无副作用，对 MOD 自动放弃 222 定制（保留 224~231/251 定制） |
| exp_cap_unsigned_fix（**必选**） | MOD 金钱系统重写波及 0x43BADF，经验上限特征码不存在 | `profile_rules: {"xiaotansanguo3":"skip"}` |

| lusu_intel_duration_x4_fix | MOD 改写鲁肃技能代码 | 同上 |
| shanhai_map_unlock | MOD 改写物品使用判定 | 同上 |

| enter_key_item_fix | MOD 改写 0x420C8A 附近代码 | 同上 |

> 上述 6 条中 exp_cap_unsigned_fix 为必选、其余 5 条为默认勾选，若不处理会因特征码失配触发「部分补丁未应用成功」假失败。改为 `profile_rules` 主动跳过后，孝谈版下这些补丁以清晰日志略过，`all_ok` 保持为真 → 启动器显示「补丁应用成功」。

### 10.3 无需处理项（实测确认良性）

- **summon skill_222 多随机 hook**（`66 C7 45 FE ** ** EB 2B`）：默认关闭的高级功能；MOD 已硬编码 222 为 rand(3)，此子功能在本 MOD 下不可用，属既定限制，不影响其余召唤定制。
- **engine.load_hook_points（存档加载 Move 调用点）**：用启动器真实函数实测，**原版与 MOD 结果完全一致**（静态镜像下均为 0，运行期由 500ms 轮询看门狗兜底重注入头像），非 MOD 引入的回归。
- **engine.gold_display（存档界面金钱 movsx→movzx）**：MOD 改写金钱显示代码，该内置补丁扫描 0 处、静默跳过、零写入，仅影响存档界面金钱显示的符号性，无损坏。

### 10.4 版本识别与策略

启动器 `detect_exe_profile` 通过 PE 节名集合识别：本 MOD 含 `.test` + `.Silvana` → 判定为 `xiaotansanguo3`（显示名「孝谈三国3终极版」）。策略为**启动器补丁最高优先级**：cave hook 一律 `override` 覆盖 MOD 已有修改；仅上述 6 条特征码已消失的原版 BUG 修复通过 `profile_rules` 主动跳过。失败提示文案现也会在 `profile.name != "original"` 时给出「检测为孝谈三国3终极版，部分补丁不适用属正常」的说明。

## 十一、BUG 修复：战斗“防御”误触发魔将发光特效

### 11.1 现象

使用孝谈三国3终极版时，战斗中对任意角色选择**防御**，该角色立即被套上“魔将发光特效”（角色渲染走发光/亮度 alpha 混合），**即使未勾选「开启魔将特效」补丁**。

### 11.2 根因（逆向定位）

防御状态由 `sub_43E958` 写入每单位渲染标志 `word_9DF7C2[当前行动者]`。

- **原版**（`0x43E95F`）：`or word[eax*2+9DF7C2], 1000h` —— 仅**追加**防御状态位 `0x1000`，保留其它位。
- **MOD**：在 `0x43E95F` 处 hook 跳转到 `.test` 段 cave `0xA7D260`，cave 内被改成 `mov word[eax*2+9DF7C2], 7530h`。

`0x7530`(=30000，恰为 MOD 各处 HP/经验上限常量) 的位分解为 `0x4000 | 0x2000 | 0x1000 | 0x400 | 0x100 | 0x20 | 0x10`——其中 **`0x4000` 正是发光/魔将渲染位**（`word_9DF7C2 & 0x4000 → sub_459168`，见 §十/`十魔将特效补丁分析`）。因此防御会：①把当前角色写上 `0x4000` → 发光；②用 `mov` **覆盖**而非 `or`，抹掉该单位原有状态位。这是 MOD 自身的 cave 代码错误（疑似把 `or 0x1000` 误写成了 `mov 30000`）。

> 该 cave 位于 `.test` 段（VA≈`0xA7D262`），落在启动器 `code_buf`（`base+0x1000`, 3MB）扫描窗口之外，常规 JSON 特征码补丁无法触及，故需专门扫描额外 PE 段处理。

### 11.3 修复

`patch_defend_glow_xiaotan`（仅在 `profile==xiaotansanguo3` 时由 worker 调用）读取 MOD 额外 PE 段，扫描全局唯一指令并还原为原版语义：

```
0xA7D262:  C7 04 45 C2 F7 9D 00 30 75   mov word[eax*2+9DF7C2],7530h   ← MOD(BUG)
0xA7D262:  81 0C 45 C2 F7 9D 00 00 10   or  word[eax*2+9DF7C2],1000h   ← 修复后(=原版)
```

- 指令等长（9 字节，`66 3E` 前缀保留），`mov→or`(`C7 04→81 0C`) + imm16 `7530→1000`；
- 修复后防御仅置 `0x1000`，**不再置 `0x4000`（及 `0x2000` 等伪造位）**，与原版逐字节一致；
- 幂等（重复应用安全）；真正的魔将角色/「开启魔将特效」补丁在 `sub_4307CC` 初始化置位，与本修复互不影响；
- 全局唯一命中，`.test` 段内 1 处，带 `read→verify→write` 校验，未命中则安全跳过。

## 十二、全面差异重扫与“错误修改”排查（2026-07）

> 工具：`逆向工作区/scan_mod_diff.py`（字节级 diff .text + capstone 反汇编）与 `scan_cave.py`（全量反汇编 .test cave + 入口映射）。
> 目标：在全部代码改动中找出是否还有“已修改但错误”（如防御误触发魔将特效）的情况。

### 12.1 扫描覆盖

- **`.text` 字节级 diff**：517 个差异字节 → 合并为 **65 个改动区**（**25 处 cave hook** E9/E8→.test，**40 处内联修改**）。
- **`.test` cave 全量反汇编**：30 个 cave 入口逐一与 hook 源地址匹配、逐条比对原版逻辑。
- 覆盖了逆向文档所述全部“93 处代码改动”与 .test/.Newdata/.Silvana 三节。

### 12.2 结论：未发现其他同类错误

逐一核对 65 处改动 + 全部 cave 后，**防御→魔将特效（cave 0xA7D260）是唯一一处“修改错误导致可见异常行为”的缺陷（已修复）**。其余均为有意图的平衡/公式/系统改动：

- **cave hook**：移动/行动力公式、伤害×1.5/×2、属性加算（武力+35/智力+30等，受 `byte_523078` 门控）、召唤222三选一、存档/金钱特殊值替换、战斗速度计数限 9999 等——均逻辑自洽。
- **内联 40 处**：金钱上限/地址引用、经验阈值、移动×16→×18、阈值 3000→1800、回合计量重写等，均与逆向文档已记录的改动一致。

重点排除的两个“可疑点”（经核实为正常）：

| 位置 | 改动 | 结论 |
|------|------|------|
| `0x422644` / `0x422655` | `mov`→`or`（`a2[67]`/`a2[68]`，即单位结构 +0x86/+0x88 的 word 位域） | **有意/修正**：两字段循环前已置 0，且同循环内 `a2[33] |= v9[20]` 本就用 OR；MOD 改为 `|=` 使装备标志从 4 件装备累加（而非只取最后一件），与零初始化意图一致，无可见异常 |
| `0x431F6E` | `push 100`→`push 0`（rand(100)→rand(0)） | **安全**：`sub_452AC0` 首行 `if(!a1) return 0`，rand(0) 固定返回 0（无除零崩溃），仅等价于禁用某随机事件 |

### 12.3 重要发现：MOD 内置“伴随进程/保护”机制（非 gameplay 缺陷）

`.Silvana` 新增导入 **`WinExec`（kernel32）+ `ShellExecuteA`（shell32）**；`.Newdata` 含字符串 `system.exe` / `closesystem.exe` / `open` / `YinShiXing2013`，以及提示文案“亲,请把辅助程序放在游戏目录下!!!”“未检测到辅助程序运行!!!游戏退出!!!”。桥函数：`0x4E542C=FindWindowExA`、`0x4E55B2=MessageBoxA`、`0x4E57C2=ShellExecuteA`、`0x4E57C8=ExitProcess`。

**实测控制流（关键）**：

- **反篡改检查已被 MOD 自己“阉割”**：三处 `FindWindowExA("YinShiXing2013")`（cave `0xA7D544/0xA7D586/0xA7D5CD`）之后均为 `test eax,eax` + **无条件 `jmp`**，结果被丢弃；四处 `MessageBoxA(...)+ExitProcess` 响应块（`0xA7D4E7/0xA7D551/0xA7D593/0xA7D5DA`）均为**死代码**（永不到达）。
- **`system.exe` / `closesystem.exe` 实际并不存在于 MOD 目录**，游戏却正常运行——正因检查被丢弃、退出响应是死代码。
- **唯一活跃的伴随调用**：启动 cave `0xA7D609`（源 `0x403587`）的 `ShellExecuteA("open","closesystem.exe")`（`0xA7D626`）。文件缺失时该调用静默失败。

### 12.4 处理：可选“纯净运行”修复（已实现）

应用户要求，新增 `patch_defend_glow_xiaotan` 的姊妹函数 **`patch_disable_companion_xiaotan`**（仅 `profile==xiaotansanguo3` 时由 worker 调用）：扫描 `.test` 段中唯一活跃的 `ShellExecuteA` 启动调用（anchor `68 D0 E0 A7 00 6A 00 E8` + 校验 call 目标 `==0x4E57C2`），将 5 字节 `call` 替换为 `add esp,0x18` + 2×`NOP`：

```
0xA7D626:  E8 xx xx xx xx        call ShellExecuteA            ← MOD
0xA7D626:  83 C4 18 90 90        add esp,0x18; nop; nop        ← 修复后(跳过启动)
```

- **栈平衡**：`pushal` 后 6×`push`（+24B），`add esp,0x18`（-24B），`popal` 前净变化 0；
- 原相对指令 `mov edx,[0x4FA514]`（cave 首条，位于 `pushal` 之前）保留，被 hook 的原函数逻辑不受影响；
- **只中和唯一活跃的 ShellExecuteA**，已死的反篡改检查（FindWindowExA/MessageBox/Exit）不动，避免无谓风险；
- 幂等（`E8` 被清除后目标校验不再命中），未命中安全跳过。

> 效果：在我们的启动器下运行孝谈三国3终极版时，TKS.exe 不再尝试启动任何外部伴随进程（纯净运行）。因 `closesystem.exe` 本就不存在、检查已死，本修复对现有可玩性零影响，仅为“防御性净化”。
