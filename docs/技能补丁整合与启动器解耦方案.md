# 技能补丁整合与启动器解耦方案

## 目标与边界

将技能和存档相关的八个独立补丁定义收敛为三个职责包。玩家只选择“扩展技能支持”，长度补丁和存档支持由依赖自动加入，不再要求玩家判断扫描、菜单、学习状态、效果解析之间的组合。

本次是组织结构与执行架构重构，不调整技能容量、学习规则、效果规则或 TKSX 文件格式。以实施开始时 Git HEAD 的机器码、位点和重定位表为静态对照基线，不把已有代码或测试通过视为游戏流程正确的证明。

游戏逆向资料实际目录：`反编译产物`。不启动游戏、不运行废弃 CLI、不将 `tks_launcher_gui/tests` 作为游戏流程验收依据。

## 三个职责包

| 补丁包 | 职责 | 选择方式 |
| --- | --- | --- |
| `tkskill_size` | 技能数据加载长度的唯一写入者 | 内部依赖，不单独勾选 |
| `tkskill_expand` | 定义表重定位、学习和装备状态、扫描与菜单保护、效果解析、敌我及召唤战斗映射 | 对外入口“扩展技能支持” |
| `tksave_expand` | 原存档缓冲区扩容、TKSX 读写和完整性校验、存档流兼容处理 | 自动基础支持，包内保留高级选项 |

`tkskill_expand` 启用完整扩展时依赖 `tkskill_size`、`tksave_expand` 及现有 WarPC 扩容能力。`tksave_expand` 不反向强制开启技能扩展，只有技能扩展生效时才接入对应 TKSX 数据。

不能只修改 TKSkill 加载长度而继续使用旧静态缓冲区。长度修改、定义表重定位和状态保护必须作为完整计划一起校验；继续保留当前扩容时的 64 KiB 最低加载容量，不把本次重构变成容量语义变更。

未启用完整技能扩展时，原有扫描限制和菜单溢出保护仍作为包内基础操作执行。存档流错误修复保持原有默认启用行为；全局性更强的流重开修复保持默认关闭，仅作为存档包的高级选项保留。

## 通用补丁计划

### 包与内部操作分离

增加通用 `bundle` 载体。一个补丁包通过包内 `prepare.py` 输出已有类型的操作：字节修改、立即数修改、数据扩容或位点注入。内部操作具有稳定 ID 和所属包，供日志定位，但不成为玩家列表中的独立补丁。

包内的 `detect(context)` 只读取数据并给出自动启用原因；`prepare(context)` 只构建操作，不访问或写入游戏进程。记录长度、容量上限、文件名、存档布局等业务知识全部留在包内。启动器只提供数据读取、资源访问、依赖解析和操作链接能力。

处理顺序：

1. 读取最终 MOD 数据，迁移旧选择键，执行包内数据检查和自动检测。
2. 解析必选项、用户选择、依赖和替代，得到唯一有效选择。
3. 展开包内操作，链接共享代码和状态区域。
4. 校验位点、冲突和资源需求，再分配、重定位和应用。

GUI 与 EXE 生成器均消费相同的计划接口。运行时不得在依赖闭包之后再次按原始勾选集合过滤。

### 共享状态与固定布局链接

现有技能 cave 中的存读档、模板读取、CRC 和学习逻辑存在相对调用，共用一块 globals。不能把原 blob 复制两份，也不能仅剪掉存读档入口后各自分配内存。

本轮采用构建期固定布局片段链接：

- 技能包持有学习、效果和映射代码以及唯一 globals 布局声明。
- 存档包持有存读档、校验及模板文件读取代码片段。
- 片段声明同一逻辑链接组、原偏移、入口和显式重定位位置。
- 通用链接器检查覆盖范围、重叠、入口冲突和唯一所有者，合成一个可执行 `patch_sites` 操作。
- 合成后的原始 cave 字节、入口、位点及重定位集合必须与迁移前基线一致；保留既有相对偏移，不同时重写汇编算法。

物理上仍只有一份运行时状态，源码职责已经分包。未来调整算法时也必须维护链接布局契约，不能在启动器中增加技能专用分支。

### 源码目录与发行包一致

源码目录和 ZIP `.tkspatch` 使用相同的包内资源接口；资源路径不得越出包根目录。打包器收集实际运行需要的嵌套资源，排除缓存文件。不能仅在开发目录能导入脚本，而发行包缺失资源。

## 需要迁出的启动器业务

- `launcher_pipeline.py` 中按 TKSkill 大小直接补选旧技能 ID 的逻辑，替换为通用计划准备。
- `config_loader.py` 中技能补丁 ID 特判、94 字节与 350/697 上限校验，迁入技能包。
- `patch_engine.py` 中旧技能 ID 状态标志，移除或由通用操作状态替代。
- `warpc_expander.py` 中存档缓冲区 `9200 + WarPC大小` 的修改，迁入存档包，避免再次旁路改写。
- EXE 生成对 `WarPC.dat.tksx` 的专用部署处理，替换为包声明的部署资源。

无关补丁不重写；不重做整个启动器，不修改废弃 CLI 的功能。

## 旧配置与源码迁移

- 旧统一技能开关映射为新技能包；新键优先，不能用旧必选定义表补丁的缺失推断用户关闭扩展。
- 旧存档流重开开关映射到存档包高级选项，默认值不改变。
- 迁移规则由包声明，通用逻辑同时用于 GUI 初始状态、配置恢复和运行计划。
- 被替代的扫描、菜单和效果原型移入包内，不继续发行同级旧包。
- 旧汇编生成辅助工具与当前产物并不一致，不允许直接运行后覆盖新包。收编为包内构建流程，以当前片段为准，先校验再生成。
- 必须保留近期敌方映射修复：RVA `0x30D24` 继续调用 `record_battle_map_player`。

## 验收

### 可以在本轮执行

- Python 语法检查和纯数据计划构建。
- 原版数据、扩展数据、显式选择、旧选择键、依赖缺失和禁用组合检查。
- 归并前后 cave、位点、入口、重定位集合对照。
- 共享 globals 唯一性、片段越界或重叠拒绝、存档长度唯一写入者检查。
- 源码目录与 ZIP 计划一致性，以及不写真实进程的定向补丁计划验证。
- GUI 组件检查不触发启动游戏；如果环境无法交互验证，明确记录限制。

### 留给用户实机复测

新游戏、旧档与扩展档读取、保存后重读、学习和装备、菜单容量、我方/敌方/召唤单位施法。静态检查不能替代这些游戏流程。

## 实施记录

### 已实现

- 八个技能/存档相关定义已归并为三个包；旧独立定义清退，基础菜单的带注释机器码也迁入技能包。
- 通用计划准备、旧选择键迁移、固定布局片段链接及包内高级选项已接入 GUI、运行流水线和 EXE 生成器。
- 启动器不再按旧技能补丁 ID 决策；技能容量校验与自动启用条件在包内，存档总长修改从 WarPC 扩容函数迁入存档包。
- `.orig` 残留恢复提前到 MOD 合并与计划准备之前；随后才执行临时截断，避免按截断数据生成错误计划。
- 包内关键位点预检失败、写入句柄获取失败、缓冲区分配/写入失败或代码洞/挂钩短写，均阻止继续恢复游戏进程。
- 包资源支持嵌套目录；原有固定布局代码生成器也通过相同接口从 ZIP 加载。无 `patch.json` 的资料目录不作为补丁打包，不删除其中内容。
- 当前构建入口为 `tks_launcher_gui/patches/tkskill_expand/build.py`，只读链接固定片段；失配的旧辅助脚本退役，不使用旧模板重新汇编并覆盖当前修复。

### 已执行的检查

1. `python -m unittest tests.test_patch_bundles -v`：18 项新建的定向检查通过，覆盖基础保护、自动依赖、旧配置迁移、长度唯一写入者、记录边界、片段链接、失败阻断、恢复顺序和 ZIP 加载。未运行原有启动器流程测试。
2. 归并后 cave 为 9216 字节，包含 38 个命名入口、52 个位点和 113 个显式重定位位置，与迁移前逐项一致。SHA-256：`e5dad11b34a7cab81458d74e841abeb11eff58cc9434935760361e9d8d0cfcc7`。
3. 使用游戏导出的 `.text` 镜像预检扩展计划，位点校验通过。在完全隔离的 Python 内存模型中，以 351 条技能/500 条角色的临时数据比较旧定义与新三包加 WarPC 依赖：代码、cave、globals 和数据缓冲区最终字节完全一致；只分配一块技能 globals，敌方 `0x30D24` 的调用目标保持一致。未取得或操作真实游戏进程句柄。
4. 当前 60 个补丁完成源码目录到临时 ZIP 的往返，包内资源字节一致；完整目录的 GUI 生成计划在源码和 ZIP 模式下一致。构建产物仅位于临时目录。
5. 使用 PySide6 离屏控件点击高级选项，检查旧选择恢复、明确关闭值、全选不改变高级选项、兼容模式禁用及隐藏内部依赖；另检查了中文界面截图。未启动完整游戏流程，未以浏览器测试替代原生界面验证。
6. 改动 Python 文件语法检查及 `git diff --check` 通过。

游戏原版的存档缓冲区总长由几个分块长度累加，不一定存在独立的 159922 立即数；存档包保留对此常量零命中的允许行为，不能把它误设为必需命中三处。

### 使用与剩余验证边界

玩家选择“扩展技能支持”即可；扩展数据或技能模板要求完整支持时，运行前计划会自动启用并记录原因。存档流重开修复仍默认关闭，在“存档扩展支持”的详情下调整。

若补丁计划在进程启动后失败，游戏进程保持挂起，启动器不会把半应用的补丁继续运行，也不会擅自还原仍被进程使用的数据；请确认关闭该游戏进程后，再使用启动器恢复快照。

以上检查不证明游戏流程已经正确。新游戏、旧档续玩、扩展档保存重读、学习与装备、菜单容量以及敌我和召唤单位施法，仍需用户实机复测。

## GUI 战斗白屏复验补记（2026-09-22，用户确认解决）

### 根因与最小修复

`python main.py` GUI 注入启动在入战时白屏，而已有生成 EXE 正常。实际战斗 #1 包含角色 #200，其移动技能槽为 `-1`；原版 `sub_422794` 未排除该空槽，仍读取 `TKSkill[-1]` 的属性字段。GUI 的独立技能表分配从 `0x001E0000` 开始，隔离执行在 `0x00422A26` 读取 `0x001DFFDE` 时失败；生成 EXE 的表前恰好有可读零填充，掩盖了同一负索引访问。

修复在 [技能包 table.json](../tks_launcher_gui/patches/tkskill_expand/table.json#L19) 声明 `front_pad: 94`：两条路径共用已有通用机制，显式保留一条表前零记录。游戏加载地址和全部表引用指向前置记录之后，逻辑容量仍为 65536 字节；不改磁盘技能文件、技能编号、WarPC 布局、TKSX 协议或已链接 cave 字节，也不向核心引擎添加技能专用分支。

GUI 重启即可重载定义；已有生成 EXE 需要重新生成，不能把旧产物碰巧可用当成长期边界保障。

### 排查与架构维护经验

- **计划等价不等于运行环境等价。** 54 项补丁应用成功、cave 基线一致及地址归一化比对，都不足以证明表前、表后访问安全；还必须比较独立内存分配与 PE 映像的可读边界。
- **声明完整的访问需求，而不只是数据大小。** `-1` 空槽、前置零记录、逻辑容量与实际分配大小是不同概念；由业务包声明需求，通用注入器和生成器一致执行。
- **数据准备也属于两条路径的一致性。** 本次另修复了 TKAct 654 条临时截成 650 条后未恢复就注入的问题，并提前恢复异常退出遗留备份；用户确认该修复后仍白屏，因此它是独立缺陷，不能代替最终根因。美化模组因素亦已被用户排除。
- **验证模型不能替越界兜底。** 用真实资源、真实函数入口及未映射的相邻区复现；不能把所有分配塞入一块大零内存，使错误负索引看起来正常。

### 实际验证与剩余边界

修复前，实际战斗 #1 在 GUI 布局失败、已有 EXE 布局通过；修复后，四场战斗 × 两种队伍 × 两条路径的 16 组隔离初始化均正常返回。GUI 的实际计划转换及临时 EXE 构建、前置零记录与 350/351/697 条边界等 5 项定向检查、语法及差异检查通过。

隔离执行对图像加载、随机数和 `memset` 使用受控替代，属于临时诊断，不是完整游戏测试；已入库检查位于 `tests/test_patch_bundles.py`。代理未启动游戏或 CLI、未运行 `tks_launcher_gui/tests`、未修改测试目录，用户最终明确确认“战斗白屏问题解决了”。验收只覆盖此前 GUI 白屏场景，不扩大到所有技能、存读档或两条路径的完整闭环。

详细调用链、地址计算与验证说明见[《技能扩展与存档兼容设计方案》第二十三节](技能扩展与存档兼容设计方案.md)。
