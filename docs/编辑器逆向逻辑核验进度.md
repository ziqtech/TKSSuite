# 编辑器逆向逻辑核验进度

> **核验原则**：一切以 `反编译产物` 的反编译源码（`decompile/*.c`、`disassembly/`、`function_index.txt`、`strings.txt`、`memory/`）为唯一权威依据。`docs/` 下既有分析文档只作线索，不得直接采信。
>
> **核验对象**：`` 各编辑器的业务逻辑（字段语义、读写布局、计算规则、容量限制、交叉引用）。
>
> **判定等级**：
> - **符合** — 有反编译/反汇编直接证据，编辑器实现与之一致
> - **存疑** — 证据不完整，或既有文档与反编译存在张力
> - **误判** — 反编译证据明确与编辑器/既有文档不一致
> - **遗漏** — 反编译中存在但编辑器未覆盖的业务逻辑
> - **无法验证** — 当前导出资料不足以断言，禁止瞎猜

## 1. shop_editor（商店编辑器）

### 1.1 核验范围

- 源码：`shop_editor/shop_editor.py`
- 主要反编译：`4233C4.c`（打开商店）、`4244CC.c`（出现条件过滤）、`4246D8.c`（购买页过滤）、`42485C.c`（出售页过滤）、`424ECC.c`（买卖切换）
- 既有文档：`docs/shop_editor/商店系统逆向分析报告.md`（**仅作线索，已逐项对照源码**）

### 1.2 反编译证据（权威）

#### TKShop.dat 布局

- 加载：`sub_45343C("TKShop.dat", &unk_9508A0, 1920)` → 1920 字节 = 240 × 8 字节
- 记录寻址：`9767072 + 8*index`（`unk_9508A0` 的整型别名）
- 字段（`4244CC.c` / `4246D8.c` 交叉确认）：
  - offset 0 / int16：`area_id`
  - offset 2 / int16：`item_ref`（TKItem 数组下标）
  - offset 4 / int16：`condition`
  - offset 6 / byte：`display`（运行时显示标志，由 `sub_4244CC` 写入）
  - offset 7 / byte：未在反编译中出现读写（保留）

#### area_id → tab_code 硬编码映射（`4233C4.c:28-54`）

```c
switch ( a1[28] ) {  // a1[28] = 打开商店时的 area_id 参数 a3
  case 0: v7=0; v6=-1; break;  // 药店 → 主分类0，无副分类
  case 1: v7=1; v6=-1; break;  // 道具店 → 主分类1
  case 2: v7=2; v6=3;  break;  // 武器防具 → 主2 副3
  case 3: v7=0; v6=1;  break;  // 杂货店 → 主0 副1
  case 4: v7=4; v6=-1; break;  // 饰品店 → 主分类4
  default: break;              // 未初始化 v7/v6 → 未定义
}
a1[31] = v7; a1[32] = v6;
```

#### 出现条件过滤（`4244CC.c`）

1. 计算“参照幸运值” `v19`：
   - 若 `a1[28] != 0`：遍历 `word_75688C` 起的队伍成员索引，取 `word_757F34[527 * member]` 的最大值
   - 若 `a1[28] == 0`：直接取全局 `word_75688A`
2. 遍历 240 条记录，`area_id` 匹配时：
   - `condition == 1`：随机抽选。`sub_452AC0(50000)` 取随机数，最多保留 5 件（`v14 >= 5` 时替换概率最低者）
   - `condition != 1`：`v9 = clamp(max_luck - condition, 0, +∞)`；`rand = sub_452AC0(50000)/500`（0–99）；`rand < v9` 则 `display=1`，否则 `display=0`

**关键纠正（相对既有文档）**：
- 既有文档写“`condition > 1` 幸运门槛、`≤0` 始终”——**不准确**。源码中**只有 `condition==1` 走随机抽选**；其余一律走幸运差值公式。`condition≤0` 只是更易满足（差值更大），并非无条件“始终”。只有当 `max_luck - condition ≥ 100` 时才必现。
- “幸运值”在 area_id=0 与 area_id≠0 时**数据源不同**（全局量 vs 队伍扫描），既有文档未记录。

#### 购买页过滤（`4246D8.c`）

同时满足才进入当前页商品列表：

```text
shop.area_id == a1[28]
AND shop.display == 1
AND TKItem[shop.item_ref].field[1] == 当前 tab_code
```

- 单页最多 8 件（`while (v6 < 7 && v5 < 240)`）
- `word_77CBCC[32 * item_ref]` 即 TKItem 第 2 个 int16（分页类别码）

#### area_id 参数序号（重要）

```text
40EBD4 case 50:
  sub_40D804(script[+2], script[+4], script[+6])   // param1, param2, param3
40D804:
  sub_4233C4(&unk_82444C, a1, a2, a3)
4233C4:
  a1[28] = a3   // = sub_40D804.a2 = script param2
```

因此 **area_id 是 Shop 指令的第 2 个参数**（opcode 后的第 2 个 int16）。既有 `商店系统逆向分析报告.md` 写“第3个参数”以及编辑器注释 `a3=area_id → 脚本第3参数` 均属误判。`param1` 在 `4233C4` 中作过滤缓存键；`param3` 写入 `a1[29]`，本次核验未在已读函数中看到后续业务用途（标为无法验证）。

#### area_id==0 的“幸运”来源（重要纠正）

```text
4244CC:
  if (a1[28] != 0)  // 非药店
      v19 = max( word_757F34[527 * member] )  // 队伍当前 LUK
  else              // 药店 area_id==0
      v19 = word_75688A
```

`41E40C` 中 `word_75688A += v15[25]`，而 field[25] 是物品“增加医术”。故 **`word_75688A` 是全局医术，不是幸运**。  
药店（area_id=0）的出现概率基准是 **医术**；其它商店才是 **队伍最大幸运**。既有文档与编辑器帮助文案统一写成“幸运”属于误判。

### 1.4 结论

- **数据布局、240 条容量、area↔tab 映射、condition 二分逻辑与幸运差值公式：符合反编译。**
- **三处文档/注释级误判**（不影响当前读写二进制，但会误导修改与 MOD 说明）：
  1. condition 语义写成“等级门槛 / ≤0 始终”
  2. Shop 脚本 area_id 写成第 3 参数
  3. 药店基准写成幸运（实为医术 `word_75688A`）
- UI 把 `condition=-100` 当“始终”是合理工程约定，与源码公式兼容。
- `area_id=9` 不可依赖（落入 default，v7/v6 未初始化）。

#### equip_type

- 出售过滤（`42485C`）：`item.equip_type & 角色权限掩码 == 0` 则不可卖 —— **位掩码语义成立**。
- 武器菜单（`41F318`）：对 1/2/4/8/16/32 等做 **等值比较**（武器大类），单件武器通常只置一个 bit，与位掩码兼容。
- 编辑器按页面切换的选项表属于 UI 约定；位定义本身与源码不冲突。

#### HP/MP 百分比细节

```text
inc > 1000: delta = (inc-1000) * max / 100 + 1   // 注意 +1
heal > 1000: delta = (heal-1000) * max / 100     // 按上限百分比，无 +1
heal <= 1000: 仅当 >0 时才加
```

编辑器注释写“≤1000 固定、>1000 百分比”正确，但未写 inc 路径的 `+1`（次要）。

#### field[21] 双用途

- 装备重算 `42234C`：施加技能被动（`sub_422BBC`）——编辑器文档覆盖。
- 使用物品 `41E40C`：`word_757F46 += v15[21]`，与 field[19] 同目标（JP）。若物品 `attach_skill` 填了较大技能 ID，使用时会按数值加 JP。编辑器未说明使用路径，属**遗漏/存疑**，不得擅自改语义。
