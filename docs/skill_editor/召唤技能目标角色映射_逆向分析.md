# 召唤类技能如何决定召唤什么角色 — 逆向分析

> 验证源：`反编译产物` 反编译代码 + `TKSkill.dat` / `WarPC.dat` / `TKT.dat` 数据解码
> 双重印证（反编译逻辑 + 实测数据），最后更新：2026-06-25

---

## 一、核心结论

**召唤目标角色并不存储在 TKSkill.dat 的任何字段中**，而是以**硬编码方式**写在 TKS.exe 里，按"技能记录索引"查表得出。

这是技能编辑器目前无法编辑"召唤谁"的根本原因——该信息不在技能数据文件内，游戏运行时直接从 exe 数据段读取。

技能数据中只有召唤的"消耗"是可编辑的（字段[40] `cost_res2` 獸元、字段[43] `mp_cost` 内力）；"召唤谁"由 exe 内硬编码映射表决定。

## 二、触发条件

### 2.1 atk_type 字段（TKSkill.dat 字段[46]）

| atk_type | 含义 | sub_447DAC 中 byte_9D6C78 值 |
|----------|------|------------------------------|
| -1 | 近战攻击 | 0 |
| 0 | 物理攻击 | 1 |
| 1 | 术法攻击 | 2 |
| **10** | **召唤攻击** | **11** |

`sub_447DAC` 计算：
```c
byte_9D6C78 = LOBYTE(word_786226[47 * word_9D6C7C]) + 1;
// 召唤技能 atk_type=10 → LOBYTE(10)+1 = 11
```

### 2.2 召唤分支入口（sub_4458B0:670-672）

```c
LOBYTE(v0) = byte_9D6C78;
if ( byte_9D6C78 == 11 )                  // 11 = 召唤
    LOBYTE(v0) = sub_444BB0(word_9D6F58); // 进入召唤角色选择
```

## 三、完整调用链

```

   │  byte_9D6C78 = LOBYTE(atk_type)+1 = 11
   ▼
sub_4458B0  (战斗效果处理, case 11 分支)

   ▼

   ▼
召唤角色出现在战场, 阵营归属玩家方
```

## 四、角色选择逻辑（sub_444BB0:35-54）

按技能记录索引 `word_9D6C7C` 分三路决定召唤目标 `i`：

```c
v4 = dword_4EB7D8;
v5 = byte_4EB7DC;
if ( byte_9DF88E[0] >= 0 && byte_9DF88F >= 0 )
{
    // 战斗槽已满 (两个备用槽都占用) → 召唤失败
    sub_451780(1);
    sub_451C38(0);
    return sub_433A38(a1, (int)&unk_4EBBDC, 18);  // 失败提示
}

if ( word_9D6C7C < 224 || word_9D6C7C > 231 )
{
    if ( word_9D6C7C == 222 )
    {
        i = 58;                       // 特例: 祝融夫人 (硬编码)
    }
    else
    {
        if ( word_9D6C7C != 251 )
            return result;            // 非召唤技能, 直接返回
        if ( (unsigned __int16)sub_452AC0(100) >= 0x32u )
            i = 98;                   // 特例: 随机 50% → 五爪金龍
        else
            i = 96;                   // 特例: 随机 50% → 大鵬金翅鳥
    }
}
else
{
    i = *((char *)&stru_4EB6F0 + word_9D6C7C);  // 查表 0x4EB6F0
}

// 等级计算: 以召唤者为基础 ± 4 级 (222 虎威震南天用召唤者原等级)
if ( word_9D6C7C == 222 )
    v8 = word_9D707E[527 * a1];                        // 召唤者等级
else
    v8 = word_9D707E[527 * a1] + sub_452AC0(4) - 4;    // ±4 级随机
    if ( v8 < 0 ) v8 = 1;

v7 = sub_431094(i, v8, word_9D6F7C, word_9D6F7E);  // 落场
```

**三路逻辑说明：**

| 技能索引范围 | 选择方式 | 说明 |
|---|---|---|
| == 222 | 硬编码 `i = 58` | 虎威震南天，固定召唤祝融夫人 |
| == 251 | 随机 `i = 96 或 98`（各50%） | 閃閃生光，随机召唤神兽 |
| 224 ~ 231 | 查表 `stru_4EB6F0[skill_idx]` | 8 种野兽召唤，按索引查字节表 |
| 其他 | 直接 return（不召唤） | 非召唤技能不走此路径 |

## 五、召唤索引数据（stru_4EB6F0 区域内的 8 字节片段）

> ⚠️ **修正**：早期版本曾把 `stru_4EB6F0` 描述为"以技能索引为下标的字节数组查表"。经 PE 段解析 + 文件偏移验证，这一描述不准确。实际真相见下文。

### 5.1 数据的真实位置与性质

**所在文件：`TKS.exe` 本身（不是任何 .dat 文件）**

| 项 | 值 |
|---|---|
| 所在文件 | **`TKS.exe`** |
| PE 段 | `.data`（VirtAddr=0xE6000, FileOff=0xE5200, RawSize=0x13A00） |
| ImageBase | 0x400000 |
| `stru_4EB6F0` 虚拟地址 | 0x4EB6F0 |
| **`stru_4EB6F0` 在 TKS.exe 中的文件偏移** | **0x0EA8F0** |
| **召唤角色索引 8 字节 文件偏移** | **0x0EA9D0**（= 0x4EB7D0 在文件中的位置） |

**验证**：从 `TKS.exe` 文件偏移 0xEA9D0 直接读取的字节 = `68 64 5D 63 66 65 62 60 1C 16 11 0B 06 1C 16 11`，与运行时内存转储 `0x4EB7D0` 完全一致 → **该数据静态写死在 exe 文件内，未加密未压缩**。

### 5.2 为什么不是"一张字节数组表"

`stru_4EB6F0` 只是 IDA 给虚拟地址 0x4EB6F0 处某个结构起的名字。dump 出 0x4EB6F0 起偏移 0–255 的原始内容可以看到，该区域是**一堆混合的全局数据**，并非一张独立数组：

```
偏移   地址        原始字节
0x00   4EB6F0     00 00 00 00 D4 FF FF FF  00 00 05 00 00 00 00 00   ← int32 -44 等
0x10   4EB700     00 00 00 00 08 00 05 00  00 00 00 00 D0 B6 4E 00   ← 指针 0x4EB6D0（自引用）
0x20   4EB710     00 00 05 00 00 00 00 00  00 00 00 00 20 00 05 00
0x30   4EB720     00 00 00 00 E0 B6 4E 00  FF FF 01 00 0A 50 14 CE   ← 指针 0x4EB6E0（自引用）
0x40   4EB730     F6 E2 C9 DD EC 00 F3 EA  E2 E7 F1 00 F8 00 FC 00
0x50   4EB740     FE 00 FF FF 00 00 00 00  01 00 02 00 04 00 08 00   ← 位掩码 1/2/4/8…
0x60   4EB750     10 00 00 00 00 00 01 00  10 00 40 00 80 00 00 01   ← 位掩码 0x10/0x40/0x80…
0x70   4EB760     00 02 00 08 02 00 04 00  08 00 20 00 00 04 00 10
0x80   4EB770     00 00 20 00 40 00 80 00  00 01 00 10 00 40 00 00
0x90   4EB780     01 00 00 00 00 00 01 00  FF FF 00 00 00 00 FF FF
```

区域里混杂着：int32（`D4 FF FF FF`=-44）、回指指针（`D0 B6 4E 00`=0x4EB6D0、`E0 B6 4E 00`=0x4EB6E0，自引用链式结构）、位掩码表（0x50–0x90 段的 `01 02 04 08 10 20 40 80`）、int16 数组（0xA0–0xDF 段），以及紧跟其后的 ASCII 错误串 `"FindPCxy Type [%d] error on pc..."`。

**结论**：`stru_4EB6F0` 是 IDA 对 0x4EB6F0 处上层结构的命名，区域内大部分字节与召唤无关。代码 `*((char*)&stru_4EB6F0 + word_9D6C7C)` 写成"基址+技能索引"的形式，但因 `sub_444BB0` 在前面用 `if (idx<224 || idx>231) return;` 把入口卡死，**实际只有偏移 0xE0–0xE7（=索引 224–231）这 8 个字节会被读取**。它本质是"嵌在 .data 全局数据中间的 8 字节召唤索引片段"，而非一张独立数组。

### 5.3 召唤索引 8 字节（偏移 0xE0 / 索引 224–231）

从 `memory/004E6000--00566000.txt` 提取（= TKS.exe 文件偏移 0x0EA9D0）：

```
00000000004EB7D0 | 68 64 5D 63 66 65 62 60  1C 16 11 0B 06 ... |
                   ↑  ↑  ↑  ↑  ↑  ↑  ↑  ↑
                  [224]...                [231]
```

| 技能索引 | 偏移 | 字节 | 十进制 | 召唤角色（见第六节验证） |
|---|---|------|--------|------------------------|
| 224 | 0xE0 | 0x68 | 104 | 野狼 |
| 225 | 0xE1 | 0x64 | 100 | 翼蛇 |
| 226 | 0xE2 | 0x5D | 93 | 老虎 |
| 227 | 0xE3 | 0x63 | 99 | 巨象 |
| 228 | 0xE4 | 0x66 | 102 | 麒麟 |
| 229 | 0xE5 | 0x65 | 101 | 毒蜘蛛 |
| 230 | 0xE6 | 0x62 | 98 | 五爪金龍 |
| 231 | 0xE7 | 0x60 | 96 | 大鵬金翅鳥 |

> 紧随其后的字节 `1C 16 11 0B 06`（28, 22, 17, 11, 6）位于偏移 0xE8+，对应技能索引 232+（降獸擊等非召唤技能），但因 `sub_444BB0` 的 `idx>231 return` 守卫，**这些字节在召唤路径中从不被读取**；它们属于相邻全局数据，不参与召唤。

### 5.4 直接修改召唤目标的方法（改 exe）

由于召唤索引静态写在 `TKS.exe` 文件内，修改召唤目标只能直接改 exe：

| 召唤技能 | 修改位置 | 修改内容 |
|---|---|---|
| 224–231（8 种野兽） | TKS.exe 文件偏移 **0x0EA9D0**（共 8 字节） | 改对应字节为新角色索引 i（WarPC 索引 = i+36） |
| 222（祝融夫人，固定 58） | `sub_444BB0` 代码段（字面量 `i = 58`） | 改代码段指令，非数据段 |
| 251（随机神兽，96/98） | `sub_444BB0` 代码段（字面量 `i = 96/98`） | 改代码段指令，非数据段 |

> 注：222 和 251 的目标是写在代码段里的指令立即数，不是 .data 数据，故需改代码段。只有 224–231 的 8 字节是纯数据，可仅用十六进制编辑器改文件偏移 0x0EA9D0。

`sub_431094:16`：`v7 = a1 + 36`（a1 即召唤角色 `i`），随后 `qmemcpy` 从 `WarPC[v7]` 拷贝 1054 字节。

## 七、落场机制（sub_431094）

```c
__int16 __cdecl sub_431094(__int16 a1, unsigned __int8 a2, __int16 a3, __int16 a4)
// a1 = 召唤角色 i, a2 = 等级, a3/a4 = 落点坐标
{
    v7 = a1 + 36;                              // WarPC 索引

    // 选择空战斗槽 (两个备用槽 byte_9DF88E[0], byte_9DF88F)
    if ( byte_9DF88E[0] == -1 ) { v6 = byte_9DF883;     v5 = 0; }
    else if ( byte_9DF88F == -1 ) { v6 = byte_9DF883+1; v5 = 1; }

    qmemcpy(battle_slot[v6], WarPC[v7], 0x41C);   // 复制角色数据 (1054字节)
    word_9D7496[527*v6] = word_758324[527*v7];
    byte_9DF781[v6] = 0;                           // AI 编组 = 0
    sub_430578(&word_9D707A[527*v6], 0, a2, a2, 0); // 应用等级

    // 精灵/立绘资源加载 (v7==36 特例 → word_9D6C84+42)
    if ( v7 == 36 ) v8 = word_9D6C84 + 42;
    else            v8 = v7 + 12;
    dword_9DF43A[5*v6] = sub_45410C(dword_951928, v8, 0);  // 精灵资源1
    byte_9DF447[20*v6] = sub_4540E8(dword_951928, v8) / 4; // 帧数1
    dword_9DF43E[5*v6] = sub_45410C(dword_95192C, v8, 0);  // 精灵资源2
    byte_9DF44B[20*v6] = sub_4540E8(dword_95192C, v8) / 4; // 帧数2

    byte_9DF761[v6] = 20;                          // 初始行动槽 = 20
    word_9DF7C2[v6] = 0;                           // 阵营 = 0 (玩家方)
    word_9DF6BA[v6] = 260 - word_9D70A2[527*v6] + 120; // 行动时序
    byte_9D705A[byte_9DF882++] = v6;               // 加入行动队列

    word_9DF802[2*v6] = a3;                        // 落点 X
    word_9DF804[2*v6] = a4;                        // 落点 Y
    byte_951D42[32*a4 + a3] = v6;                  // 战场占位表
    sub_42F9C8(&word_9DF802[2*v6], &word_9DF804[2*v6]); // 寻路初始化
    byte_9DF88E[v5] = v6;                          // 标记备用槽已占用
    return v6;
}
```

**关键设定：**
- **阵营**：`word_9DF7C2[slot] = 0`（无阵营 bit → 玩家方，与可操控角色一致）
- **AI 编组**：`byte_9DF781[slot] = 0`
- **行动槽**：`byte_9DF761[slot] = 20`（初始较高，很快可行动）
- **战斗槽上限**：受 `byte_9DF88E[0]` / `byte_9DF88F` 两个备用槽限制，若都已占用则召唤失败（`sub_433A38` 提示）

## 八、与事件驱动增援的关系

游戏存在两条召唤入口，**共用同一套硬编码表 `stru_4EB6F0`**：

| 入口 | 触发 | 选择依据 | 落场函数 |
|---|---|---|---|
| **技能召唤**（本主题） | 玩家施放 atk_type=10 技能 | 技能记录索引 `word_9D6C7C` | sub_431094 |
| 事件增援 | 战斗事件/脚本 | 事件ID `word_9D6C7C`（同一变量） | sub_444FD4 → sub_431094 |

> `sub_444FD4`（callers: 0x445564）是事件增援路径：从已有敌方槽位中随机选一个复制，阵营按 `word_953992[v13]` 设定（可能含 bit13/14/15，即敌方）。与技能召唤（强制阵营=0 玩家方）不同。
>
> 两条路径都引用了 `stru_4EB6F0` 这个符号，但如第五节所述，`sub_444BB0` 实际只读取其中偏移 0xE0–0xE7 的 8 字节（技能 224–231）；事件增援路径 `sub_444FD4` 走的是另一套逻辑（从战场现存槽位 `word_9537FA`/`byte_953830` 随机挑选），并不读取这 8 字节。两条路径并非"共用一张表"，只是恰好都落在 IDA 命名为 `stru_4EB6F0` 的同一全局数据区域内。

## 九、对技能编辑器的影响

### 9.1 可编辑 vs 不可编辑

| 属性 | 是否在 TKSkill.dat | 编辑器可编辑性 |
|---|---|---|
| 召唤消耗·獸元 | 字段[40] `cost_res2` | ✅ 可编辑 |

### 9.2 若需在编辑器中展示召唤目标

由于游戏运行时硬编码读取 `stru_4EB6F0` + 两个特例字面量，编辑器无法从数据文件获知映射。若要展示，需在编辑器内**内置这张硬编码映射表**（Python 常量），例如：

```python
# 召唤技能 → 召唤角色 映射（逆向自 TKS.exe sub_444BB0 + stru_4EB6F0）
# WarPC 索引 = i + 36
SUMMON_TARGET_MAP = {
    222: ("祝融夫人",    58),   # 硬编码
    224: ("野狼",        104),  # stru_4EB6F0[224]
```
