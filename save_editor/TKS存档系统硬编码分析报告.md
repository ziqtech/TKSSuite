# TKS 存档系统硬编码大小分析报告

> 基于 PE 逆向反编译代码直接验证，所有结论均附源码行号证据。
> 验证日期: 2026-05-21

---

## 一、核心发现摘要

存档系统存在**大量硬编码大小常量**，分布在 6 个关键函数中。TKSLauncher 通过运行时内存修补覆盖了 WarPC 相关的大小常量，但 **TKMat (2304000)、unk_755B18 (3432)、unk_756880 (5768)、9200 偏移量** 等常量未被修补。

## 二、存档数据文件格式 (sav.{1..9})

### 2.1 整体结构

**源码证据**: `410ED4.c` (写入), `41103C.c` (读取)

```
┌─ Frame 1 ─────────────────────────────────────┐
│  [4B: frame_total_size]                       │ ← int32 LE
│  [4B: original_size = 2304000]                │ ← int32 LE, 硬编码
│  [N B: LZSS compressed TKMat data]            │
├─ Frame 2 ─────────────────────────────────────┤
│  [4B: frame_total_size]                       │ ← int32 LE
│  [4B: original_size = 159922]                 │ ← int32 LE, 硬编码
│  [M B: LZSS compressed global state]          │
└───────────────────────────────────────────────┘
```

### 2.2 Frame 1: TKMat 实体表

- **原始大小**: `2304000` 字节 (= 6000 × 384)
- **源地址**: `dword_51AF40`
- **写入**: `410ED4.c:21` — `v6 = 2304000;`
- **读取**: `41103C.c:26` — `sub_452B14(v5, &v8, dword_51AF40);` (解压到固定地址)

### 2.3 Frame 2: 全局游戏状态 (三块拼接)

**源码证据**: `410ED4.c:25-29`

```c
v3 = sub_4AEB18(159922);                    // 硬编码总大小
sub_4B008C(v3,        &unk_755B18, 3432);   // Block A: 3432 字节
sub_4B008C(v3 + 3432, &unk_756880, 5768);   // Block B: 5768 字节
sub_4B008C(v3 + 9200, word_757F08, 150722); // Block C: 150722 字节 (WarPC)
//                    ↑ 9200 = 3432 + 5768  硬编码偏移量
```

| 子块 | 源地址 | 偏移 | 大小 | 内容 |
|------|--------|------|------|------|
| Block A | `unk_755B18` | 0 | **3432** | SCE 脚本全局变量/标志位 |
| Block B | `unk_756880` | 3432 | **5768** | 物品背包/任务/队伍/金币等 |
| Block C | `word_757F08` | 9200 | **150722** | WarPC 角色数据 (143×1054) |
| **合计** | | | **159922** | = 3432 + 5768 + 150722 |

**加载时同样硬编码**: `41103C.c:28,34-36`

```c
v4 = sub_4AEB18(159922);                        // 硬编码分配
sub_4B008C(&unk_755B18, v4, 3432);              // 硬编码恢复 Block A
sub_4B008C(&unk_756880, v4 + 3432, 5768);       // 硬编码恢复 Block B
sub_4B008C(word_757F08, v4 + 9200, 150722);     // 硬编码恢复 Block C
```

## 三、存档索引文件格式 ({1..9}.sav, 28字节)

**源码证据**: `41CE10.c:103-124` (写入), `41B1A8.c:74-84` (读取)

### 3.1 写入流程 (`sub_41CE10`)

```c
// 队伍成员 ID × 6 (1字节/人)
v7 = (char *)word_75688C;
do { sub_41D750(v21, *v7); ++v13; v7 += 2; } while ( v13 <= 5 );

// 游戏时间 (2字节)
sub_41DAC4(v21, &word_756882, 2);        // L111

// Unix 时间戳 (4字节)
sub_4B9284(v12);
sub_41DAC4(v21, v12, 4);                 // L112-113

// 6 队员等级 (每项 2字节)
v6 = word_75688C;
do { sub_41DAC4(v21, &word_757F0C[527 * *v6], 2); ++v11; ++v6; } while ( v11 <= 5 );

// 当前场景/角色 ID (4字节)
sub_41DAC4(v21, &dword_755B58, 4);       // L124
```

### 3.2 字段结构 (28 字节)

| 偏移 | 大小 | 数据源 | 说明 |
|------|------|--------|------|
| 0x00 | 6×1B | `word_75688C[0..5]` | 队伍成员 ID (-1=空) |
| 0x06 | 2B | `word_756882` | 游戏时间计数 |
| 0x08 | 4B | `sub_4B9284` (当前时间) | Unix 时间戳 |
| 0x0C | 6×2B | `word_757F0C[527*id]` | 队员等级 (读取 WORD[0]=等级) |
| 0x18 | 4B | `dword_755B58` | 当前角色/场景 ID |

**6 + 2 + 4 + 12 + 4 = 28** ✓

> ⚠️ **重要限制**: L103 将 `word_75688C` (int16*) 强制转为 `char*` 后逐字节写入 (`sub_41D750(v21, *v7)`)，仅写入每个队员 ID 的**低字节**。这意味着如果队伍成员 ID ≥ 256，索引文件中的 ID 会被截断，导致存档列表显示错误的角色名。同理，L119 的等级写入使用 `word_757F0C[527 * *v6]` 是完整的 2 字节写入，无截断问题。

### 3.3 读取流程 (`sub_41B1A8`)

```c
// 循环读取 9 个槽位 (v19 = 1..9)
do {
    sub_4B2ECC(v5, "save\\%d.sav", v19);  // 构建路径
    sub_4C352C(v24, v5, 12);              // 检查文件存在
    if ( v24[12] ) {
        // 读 6 个队伍成员 → a1 + 6*v19 + 664
        sub_41BF48(v22, v15++ + a1 + 6 * v19 + 664);  // ×6
        // 读游戏时间 → a1 + 2*v19 + 722
        sub_41C2B8(v22, a1 + 2 * v19 + 722, 2);
        // 读时间戳 → a1 + 4*v19 + 738
        sub_41C2B8(v22, a1 + 4 * v19 + 738, 4);
        // 读 6 个等级 → a1 + 12*v19 + 766
        sub_41C2B8(v22, 2 * v14++ + a1 + 12 * v19 + 766, 2);  // ×6
        // 读当前角色 → a1 + 4*v19 + 882
        sub_41C2B8(v22, a1 + 4 * v19 + 882, 4);
    } else {
        // 文件不存在 → 填充 -1
    }
} while ( v19 <= 9 );
```

## 四、存档写入流程 (`sub_410ED4`)

**调用链**: `sub_42131C:111-112` → `sub_410ED4` (SaveTKMat)

```
1. fopen(path, "wb")                              → v7
2. v6 = 2304000;                                  — 硬编码
3. v4 = sub_4530A8(dword_51AF40, &v6, 0);        — LZSS 压缩 TKMat
4. fwrite(&v6, 4, 1, v7);                        — 写 Frame 1 大小
5. fwrite(v4, v6, 1, v7);                        — 写 Frame 1 数据
6. v3 = malloc(159922);                           — 硬编码分配
7. memcpy(v3,        &unk_755B18, 3432);          — 硬编码
8. memcpy(v3 + 3432, &unk_756880, 5768);          — 硬编码
9. memcpy(v3 + 9200, word_757F08, 150722);        — 硬编码
10. v5 = 159922;                                   — 硬编码
11. v2 = sub_4530A8(v3, &v5, 0);                  — LZSS 压缩
12. fwrite(&v5, 4, 1, v7);                        — 写 Frame 2 大小
13. fwrite(v2, v5, 1, v7);                        — 写 Frame 2 数据
14. fclose / free
```

## 五、存档加载流程 (`sub_41103C`)

**调用链**: `sub_42131C:158` 或 `sub_426164:58` → `sub_41103C` (LoadTKMat)

```
1. fopen(path, "rb")                              → v9
2. fread(&v8, 4, 1, v9);                         — 读 Frame 1 大小
3. v5 = malloc(v8);                               — 动态分配
4. fread(v5, v8, 1, v9);                         — 读 Frame 1 数据
5. sub_452B14(v5, &v8, dword_51AF40);            — 解压到 TKMat 实体表

7. fread(&v8, 4, 1, v9);                         — 读 Frame 2 大小
8. v6 = malloc(v8);                               — 动态分配
9. fread(v6, v8, 1, v9);                         — 读 Frame 2 数据
10. sub_452B14(v6, &v8, v4);                      — 解压到临时缓冲
11. memcpy(&unk_755B18, v4, 3432);                — 硬编码
12. memcpy(&unk_756880, v4 + 3432, 5768);         — 硬编码
13. memcpy(word_757F08, v4 + 9200, 150722);       — 硬编码
14. dword_755B58 = -1;                             — 强制场景重载
15. sub_40C044(...) → sub_406E18(...) → sub_405B98()
```

## 八、LZSS 压缩/解压 (无硬编码大小)

**压缩**: `sub_4530A8` (0x4530A8)
- 窗口大小: 4096 字节 (`byte_A2C8A0[4096]`)
- 初始填充: 0x20
- 初始位置: 4078 (`v23 = 4078`)
- 最小匹配: 3 字节 (`dword_A2D8B8 > 2`)
- 最大匹配: 18 字节
- 标志位编码: bit=1→原文字节, bit=0→(12-bit offset, 4-bit length)
- **输出上限检查**: `if ( 2 * v16 <= v17 )` — 压缩率不低于 50%，否则返回失败

**解压**: `sub_452B14` (0x452B14)
- 同上窗口参数
- 从参数读取大小，**无硬编码大小限制**

**LZSS 文件加载包装**: `sub_45343C` (0x45343C)
- 安全检查: `if ( v5 <= a3 )` — 文件解压大小不超过传入的缓冲区大小
- 但 `a3` 由调用者硬编码传入

## 九、TKSLauncher 修补机制分析

### 9.1 补丁五: WarPC 缓冲区动态扩展

**常量定义** (`tks_launcher.cs:382-386`):
```csharp
const int WARPC_BASE = 0x757F08;
const int WARPC_REC_SIZE = 1054;
const int WARPC_ORIG_COUNT = 143;
const int WARPC_ORIG_SIZE = 150722;       // = 143 × 1054
const int WARPC_TOTAL_ORIG_SIZE = 159922;  // = 9200 + 150722
```

**修补的常量**:
- `WarpcAddrRVAs` (29 处): 修补 `word_757F08` 基址引用 → 新缓冲区地址
- `WarpcAddr0CRVAs` (7 处): 修补 `word_757F0C` 引用 → 新缓冲区+4
- `WarpcSizeRVAs` (5 处): 修补 `150722` 大小常量 → `newSize`
- 字段级盲扫: 修补 `[0x757F08, 0x758326)` 范围内所有预计算偏移地址

### 9.2 补丁六: 存档/读档缓冲区扩展

**修补的常量**: `159922` (Frame 2 总大小)
- 盲扫代码段中所有匹配 `0x000270D2` 的 4 字节值
- 替换为 `9200 + newSize` (新 WarPC 大小 + 固定开销)

**修补位置**: `410ED4.c:25` 和 `410ED4.c:29` 中的 `159922`

### 9.3 未修补的硬编码常量

以下常量**未被 TKSLauncher 修补**：

| 常量 | 原因 | 风险评估 |
|------|------|---------|
| **2304000** | TKMat 大小不应改变 | 低风险 — 除非修改 TKMat 结构 |
| **3432** | Block A 大小 | 低风险 — 除非修改 SCE 全局变量区 |
| **5768** | Block B 大小 | 低风险 — 除非修改游戏状态区 |
| **9200** | WarPC 偏移量 | **中风险** — 如果 Block A 或 B 扩展会出错 |
| **38400/32900/1920/26000** | 其他数据文件 | 低风险 — 通常不需要修改 |

### 9.4 9200 偏移量风险详解

`9200 = 3432 + 5768` 是 WarPC 数据在 Frame 2 中的固定偏移。TKSLauncher 修补了:
- `159922` → `9200 + newSize` (总大小)
- `150722` → `newSize` (WarPC 大小)

但 `9200` 本身**保持不变**。这是因为:
- `sub_4B008C(v3 + 9200, word_757F08, 150722)` 中的 `9200` 是 `v3+9200`，其中 `v3` 已通过 `159922→newTotal` 扩展
- 只要 Block A (3432) 和 Block B (5768) 不改变大小，9200 偏移就是正确的

但如果未来 Block A 或 Block B 需要扩展（例如增加新物品类型），则需要同步修补 `9200` 常量。

## 十、sub_412688 清零导致存档界面异常分析

### 10.1 问题确认

`412688.c:27,61`:
```c
sub_4B00FC(&unk_755B18, 0, 3432);    // 清零 Block A (含队伍/金币/统计)
// ...
sub_4B00FC(&unk_756880, 0, 5768);    // 清零 Block B
```

清零后恢复不完整:
- `word_75688C` (队伍数组) 在 `412688.c:63-70` 仅恢复为 `[0, -1, -1, -1, -1, -1]`
- `word_756888` (金钱) 在 `412688.c:73` 从 WarPC[0] 恢复
- `word_757EBA/BC` (胜负统计) **未恢复**，保持为 0

### 10.2 验证: 与旧文档一致

旧文档 `存档界面显示异常分析.md` 中的分析与反编译代码**完全一致**:
- 清零范围: 3432 + 5768 = 9200 字节 ✓
- 队伍恢复为 `[0,-1,-1,-1,-1,-1]` ✓
- 金钱从 WarPC[0].field_29 恢复 ✓
- `word_757EBA`/`word_757EBC` 未恢复 ✓

### 10.3 与存档格式的关系

`sub_412688` 仅在**新游戏初始化**时调用（caller: `sub_412BE8` WinMain），存档界面异常是初始化问题，**不是存档 I/O 问题**。存档文件本身的读写逻辑 (`sub_410ED4`/`sub_41103C`) 是正确的。

1. **存档系统存在大量硬编码大小常量**，分布在 `sub_410ED4`、`sub_41103C`、`sub_412688`、`sub_4173F8` 四个函数中。
