# TKS 事件系统完整语义分析

> 基于 `TKS.exe` 反编译源码 + `TKD.dat` 脚本 + 实际存档数据的三方交叉验证

---

## 一、总体架构

游戏事件系统是一个 **脚本虚拟机 (Script VM)**，以 `sub_40EBD4` 为核心执行引擎，解析 TKD.dat 中的脚本字节码驱动剧情。

### 数据流

```
TKD.dat (XOR 0xFF 加密)
  └─ DEFINE 块 → DEFCMD.LST 操作码 → sub_40EBD4 (脚本VM, 67个操作码)
                                          │
         ┌────────────────────────────────┘
         ▼
存档 SEG1 (Block A, 3432B) 中的四个事件数组:

  word_755E10[32]   ← SetSwitch(49)                         事件开关
  word_755E50[24]   ← MenuTalk(7)        → CheckResult(60)  事件结果
  word_755E80[250]  ← SetVar(36)/Random(37)                  事件变量
                        ↓ (SetFlagVar/AddFlagVar 中转)
  word_756080[1024] ← SetFlag(32)/AddFlag(33)
                    ← SetFlagVar(38)/AddFlagVar(39)
                    → CheckFlag(61)                           事件标志
```

### 存档布局

```
SEG1 (0x755B18, 3432 字节):
  +0x000 ~ +0x2F7: 基本状态、地图、编成槽、同伴标志等
  +0x2F8 ~ +0x337: 事件开关  word_755E10[32]   (64B)
  +0x338 ~ +0x367: 事件结果  word_755E50[24]   (48B)
  +0x368 ~ +0x567: 事件变量  word_755E80[250]  (500B, 存档预留256×2=512B)
  +0x568 ~ +0xD67: 事件标志  word_756080[1024] (2048B)
  +0xD68 = 3432 = SEG1_SIZE
```

## 二、事件标志 (Flags) — `word_756080[1024]` ⭐ 核心

### 基本属性

| 属性 | 值 |
|---|---|
| 存档偏移 | SEG1 +0x568 |
| 元素数量 | 1024 个 int16 (索引 0-1023) |
| 总大小 | 2048 字节 (0x800) |
| 范围检查 | `if (flag_id >= 0x400u)` → 报错 (反编译: `sub_40CB08.c`, `sub_40CB4C.c`) |

### 读写操作码

| 操作码 | DEFCMD 名称 | 参数 | 逆向函数 | 行为 |
|---|---|---|---|---|
| 32 | SetFlag | (flag_id, value) | `sub_40CB08` | `word_756080[id] = value` |
| 33 | AddFlag | (flag_id, value) | `sub_40CB4C` | `word_756080[id] += value` |
| 38 | SetFlagVar | (flag_id, var_slot) | case 38 → `sub_40CB08` | `word_756080[id] = word_755E80[var]` |
| 39 | AddFlagVar | (flag_id, var_slot) | case 39 → `sub_40CB4C` | `word_756080[id] += word_755E80[var]` |
| 61 | CheckFlag | (flag_id, value, op) | `sub_40E40C` | 比较 `word_756080[id]` 与期望值 |

### CheckFlag 比较运算符 (`sub_40E40C`)

| 操作码值 | 运算符 | TKD 脚本写法 | 典型场景 |
|---|---|---|---|
| -2 | `<` (小于) | `CheckFlag(id, val, -2)` | 极少使用 |
| -1 | `<=` (小于等于) | `CheckFlag(id, val, -1)` | 极少使用 |
| 0 | `==` (等于) | `CheckFlag(503, 1, 0)` | **最常用**：精确匹配状态 |
| 1 | `>=` (大于等于) | `CheckFlag(503, 1, 1)` | **常用**：检查"至少达到"某状态 |
| 2 | `>` (大于) | `CheckFlag(id, val, 2)` | 极少使用 |
| 3 | `!=` (不等于) | `CheckFlag(id, val, 3)` | 极少使用 |

### 标志值的游戏语义

从 TKD.dat 脚本和实际存档分析得出：

| 值 | 语义 | 实际存档证据 |
|---|---|---|
| 0 | 事件未触发/未开始 (默认值) | 存档1: 1019/1024 个标志为0；存档2: 1013/1024 个标志为0 |
| 1 | 事件已触发/进行中 | 存档1有3个, 存档2有8个值为1的标志 |
| 2 | 事件已完成 (某分支结果) | 存档2: flag[107]=2, flag[1004]=2 |
| 3+ | 多分支结果 (如随机位置) | 存档1和2: flag[354]=3, flag[999]=3 |

**随游戏进度，激活的标志数量递增：存档1(早期) 5个 → 存档2(后期) 11个。**

### 标志使用的三种模式

**模式 A：开关型 (二值)**

```
// 激活某事件
CheckFlag(503, 1, 0)   // 检查是否已激活 (==1)
{
    SetFlag(503, 1)     // 未激活则激活
    // ... 事件逻辑 ...
}
```

值域 `{0, 1}`，用于简单的"是否已触发"判断。

**模式 B：阶段型 (多值)**

```
// 多阶段剧情进度
CheckFlag(303, 1, 0)   // 阶段1
{ ... SetFlag(303, 2) }
CheckFlag(303, 2, 0)   // 阶段2
{ ... SetFlag(303, 5) }
```

值域 `{0, 1, 2, 3, 5...}`，跳过某些值，用于多阶段剧情追踪。

**模式 C：随机型**

```
// 随机NPC/物品位置
Random(0, 0, 4)        // var[0] = rand(0..4)
SetFlagVar(999, 0)     // flag[999] = var[0]
CheckFlag(999, 0, 0)   // flag==0 → 位置A
{ Enable(A); SetPos(A, ...) }
CheckFlag(999, 1, 0)   // flag==1 → 位置B
{ Enable(B); SetPos(B, ...) }
...
```

值域 `{0..4}` 或其他小范围，用于不可预测的游戏内容。

## 三、事件开关 (Switches) — `word_755E10[32]`

### 基本属性

| 属性 | 值 |
|---|---|
| 存档偏移 | SEG1 +0x2F8 |
| 元素数量 | 32 个 int16 (索引 0-31) |
| 总大小 | 64 字节 (0x40) |
| 范围检查 | `if (slot >= 0x20)` → 报错 (反编译: case 49 in `40EBD4.c`) |

### 读写操作

| 操作码 | DEFCMD 名称 | 逆向函数 | 行为 |
|---|---|---|---|
| 49 | SetSwitch | case 49 in `sub_40EBD4` | `word_755E10[slot] = value` |
| (读) | — | `sub_408E5C` | 检查 `word_755E10` 是否为非零 (决定是否允许对话激活) |

### 反编译证据

```c
// 40EBD4.c case 49 — 写:
dword_755AA0 = *(__int16 *)(dword_755A94 + 2 * word_755AB2 + 2);
if ((unsigned int)dword_755AA0 >= 0x20)  // 最多32个
{
    sub_452478(0, "[%d] event SetSwitch slot [%d] error !!", ...);
    return -1;
}
word_755E10[dword_755AA0] = *(_WORD *)(dword_755A94 + 2 * word_755AB2 + 4);

// 408E5C.c — 读 (对话激活检查):
if (!word_755E10)   // switch[0] 为0则拒绝激活
    return 0;
```

### 游戏语义

**开关是"全局功能控制"，与标志的"持久剧情进度"不同。**

| 开关索引 | 推测语义 | 证据 |
|---|---|---|
| switch[0] | **主事件/对话系统启用** | TKD 几乎所有 DEFINE 开头都调 `SetSwitch(0,1)`；`sub_408E5C` 以此为对话激活前提 |
| switch[1-30] | 未观察到使用 | 两个存档中均为0 |
| switch[31] | **脚本交互模式切换** | TKD: `SetSwitch(31,1)` 配合 `PlayerAct(1)` 使用 |

### 与标志 (Flags) 的核心区别

| 维度 | 开关 (Switches) | 标志 (Flags) |
|---|---|---|
| 数量 | 32 | 1024 |
| 用途 | 全局功能控制 (对话启用/交互模式) | 剧情进度追踪 |
| 检查方式 | 仅检查是否为非零 | 支持6种比较运算符 (==, >=, <, <=, >, !=) |
| TKD使用频率 | 低 (通常只在开头 SetSwitch(0,1)) | 极高 (大量 CheckFlag/SetFlag) |
| 存档值 | 几乎只有 switch[0]=1 | 随进度递增, 值域丰富 |

## 四、事件变量 (Variables) — `word_755E80[250]`

### 基本属性

| 属性 | 值 |
|---|---|
| 存档偏移 | SEG1 +0x368 |
| 代码上限 | 250 个 int16 (索引 0-249) |
| 存档大小 | 256 × 2 = 512 字节 (索引 250-255 为保留空间, 脚本VM不访问) |
| 范围检查 | `if (slot > 0xF9)` → 报错 (反编译: case 36 in `40EBD4.c`) |

> **注意 (第五轮修正)**: 变量上限**因操作码而异**, 不是一个统一值:
> - **case 36 SetVar**: `if (slot > 0xF9)` → max index **249** (250 个)
> - **case 37 Random / case 38 SetFlagVar / case 39 AddFlagVar**: `if (slot >= 0x100)` → max index **255** (256 个)
>
> 存档预留 256 槽 (0x368-0x567, 512B)。`save_editor_v2.py` 编辑 0-249 (250 个), 覆盖最严格的 SetVar 上限。槽 255 (word_755E80[255]) = `word_75607E` (last_acq 字段) 的内存别名。TKD 脚本实际仅使用 var[0] (17 次 Random 全部写入 var[0])。

### 读写操作

| 操作码 | DEFCMD 名称 | 参数 | 行为 |
|---|---|---|---|
| 36 | SetVar | (var_slot, value) | `word_755E80[slot] = value` |
| 37 | Random | (var_slot, min, max) | `word_755E80[slot] = rand(min, max)` |
| 38 | SetFlagVar | (flag_id, var_slot) | `word_756080[id] = word_755E80[var]` (读变量→写标志) |
| 39 | AddFlagVar | (flag_id, var_slot) | `word_756080[id] += word_755E80[var]` (读变量→累加标志) |

### 反编译关键代码

```c
// case 36 SetVar:
dword_755AA0 = *(__int16 *)(dword_755A94 + 2 * word_755AB2 + 2);
if ((unsigned int)dword_755AA0 > 0xF9)    // max index 249
    return -1;
word_755E80[dword_755AA0] = *(_WORD *)(dword_755A94 + 2 * word_755AB2 + 4);

// case 37 Random:
dword_755AA0 = range = max - min + 1;
dword_755AA0 = sub_452AC0(range);   // 随机数生成
dword_755AA0 += min;
word_755E80[slot] = dword_755AA0;   // 存回变量
```

### 游戏语义

**变量是"脚本运行时工作区"，用于临时计算和值传递。**

核心作用：**Random → 变量 → SetFlagVar → 标志** 的值传递链。

```
为什么需要变量？
  SetFlag(32) 只能设置脚本中的固定常量值
  但 Random(37) 的结果是运行时确定的
  所以必须: Random → var → SetFlagVar → flag
  变量是实现"运行时值→持久存储"的桥梁
```

**实际存档数据：** var[0]=3 (两个存档均为最后一次 Random 的结果)

**在 TKD 脚本中 SetVar 极少单独使用** (搜索结果显示几乎没有独立的 SetVar 调用)，变量主要通过 Random 写入，然后立即被 SetFlagVar 消费。

## 五、事件结果 (Results) — `word_755E50[24]`

### 基本属性

| 属性 | 值 |
|---|---|
| 存档偏移 | SEG1 +0x338 |
| 元素数量 | 24 个 int16 (索引 0-23) |
| 总大小 | 48 字节 (0x30) |
| 范围检查 | `if (slot >= 0x18u)` → 报错 (反编译: case 60 in `40EBD4.c`) |

### 读写操作

| 操作码 | DEFCMD 名称 | 逆向函数 | 行为 |
|---|---|---|---|
| 7 | MenuTalk | `sub_40B710` → `word_755E50[slot] = i` | 显示菜单, 将玩家选择的菜单项索引写入 |
| 60 | CheckResult | case 60 in `sub_40EBD4` | 检查 `word_755E50[slot] == expected`，仅支持 `==` 比较 |

### 反编译关键代码

```c
// sub_40B710.c:163 — MenuTalk 结束时写入:
word_755E50[a3] = i;   // i = 玩家选中的菜单项 (0-based 索引)

// 40EBD4.c case 60 — CheckResult:
if (*(_WORD *)(dword_755A94 + 2 * word_755AB2 + 2) < 0x18u)  // slot < 24
{
    if (word_755E50[slot] == expected_value)
        word_755AB2 += 4;         // 匹配 → 继续执行
    else
        word_755AB2 += skip;      // 不匹配 → 条件跳转
        dword_755AAC = 2;         // 标记跳转发生
}
```

### 游戏语义

**结果存储玩家的菜单/对话选择，专用于对话分支。**

```
TKD 脚本典型用法:

MenuTalk(28639, 0)       // 显示文本#28639, 选择结果存 result[0]
CheckResult(0, 0)         // 玩家选了第0项 (如"是")
{
    FadeOut(0,0,0,100)    // 执行对应逻辑
    ...
}
CheckResult(0, 1)         // 玩家选了第1项 (如"否")
{
    End(0)                 // 直接结束对话
}
```

**CheckResult 与 CheckFlag 的区别：**

| 维度 | CheckResult(60) | CheckFlag(61) |
|---|---|---|
| 数据源 | `word_755E50` (菜单选择) | `word_756080` (持久标志) |
| 比较方式 | 仅支持 `==` | 支持6种运算符 (`<`, `<=`, `==`, `>=`, `>`, `!=`) |
| 写入者 | MenuTalk (用户交互) | SetFlag/AddFlag (脚本逻辑) |
| 生命周期 | 菜单选择后立即消费 | 跨存档持久 |

**实际存档数据：两个存档的 results 均为 0** — 菜单选择在脚本执行期间消费完毕，存档时通常无残留。

## 十三、场景名称显示机制 (参考 mat_editor_v2.py)

### TKT 场景名查找

mat_editor_v2.py 通过 `scene_name()` 函数获取场景名：

```python
SCENE_NAME_TKT_BASE = 300

def scene_name(tkt, sid):
    if sid == -1: return "全局(所有场景)"
    txt = tkt.get(SCENE_NAME_TKT_BASE + sid, "")
    return txt.split('\n')[0].strip() if txt else f"场景{sid}"
```

**原理**: TKT.dat 中 ID=300+scene_id 的文本就是场景名。取第一行（`\n` 分割）。

### DEFINE→实体→场景 追踪链

mat_editor 通过三层数据关联 DEFINE 块到场景：

```
DEFINE块 (TKD.dat)
  → DEFINE ID = (TKDefUnit.f1 << 16) | TKDefUnit.f0
  → TKDefUnit 属于某条链 (A/B/C)
  → 实体 (TKMat) 的 d39/d40/d41 指向链头 DefUnit
  → 实体的 d1 = scene_id
  → TKT[300 + scene_id] = 场景名
```

### save_editor_v2.py 已添加的场景名支持

1. **`_scene_name()` 方法**: 使用已加载的 `self.tkt` 查找场景名
2. **语义标注中含场景名**: 116条明确标注中，大部分包含 TKT 场景名
   - 例如: `flag[100]: "计数A — 场景25「成都王殿」NPC 实体666-669"`
3. **场景名格式**: `场景ID「场景名」` (与 mat_editor 一致)

## 十四、第四轮：逆向工程源码验证 (2024-06-26)

### 核心结论：标志语义完全由TKD脚本定义，游戏引擎中无硬编码引用

对全部反编译C代码 (`decompile/*.c`) 和反汇编 (`disassembly/`) 的搜索确认：

1. **`word_756080[1024]`** — 仅在 `sub_40CB08`(SetFlag)、`sub_40CB4C`(AddFlag)、`sub_40E40C`(CheckFlag) 中被参数化访问，**无任何硬编码索引引用**
2. **`word_755E10[32]`** — 仅在 `sub_40EBD4`(case49 SetSwitch) 和 `sub_408E5C`(检查switch[0]) 中被访问
3. **`word_755E80[250]`** — 仅在 `sub_40EBD4`(case36-39) 和文本格式化引擎 `sub_409C60` 中被访问
4. **`word_755E50[24]`** — 仅在 `sub_40EBD4`(case60 CheckResult) 和 `sub_40B710`(MenuTalk) 中被访问

**这意味着：剩余的未标注标志无法从逆向源码中进一步挖掘语义，它们的含义只能在TKD脚本中通过DEFINE上下文推断。**

### 新发现的语义细节

#### 文本格式化引擎 `sub_409C60` — 变量在对话中的使用

#### Note数组 `sub_40DBF4` — `word_7568D8[1000]`

Note是脚本状态标记数组，存储在SEG2中(偏移0x58, 1000×2=2000B)。由opcode 46写入，供脚本内部跟踪状态使用，**不影响游戏逻辑**。

#### 遭遇战旗标 `dword_755C80` — 战斗系统控制

```c
// sub_4084E0 (战斗区触发):
if ((dword_755C80 & 4) != 0)  // bit2=禁止遇敌
    return 0;

// 随机判定时:

    cooldown += base / 2;
else if ((dword_755C80 & 1) != 0)  // bit0=减半

```

**位域定义（修正）**：
- **bit0** (0x1): 遇敌率减半
- **bit1** (0x2): 遇敌率降低
- **bit2** (0x4): **禁止遇敌** (完全跳过战斗判定)
- **bit3**: 反击相关

### 第五轮修正 (4 处)

#### 1. 变量上限: 因操作码而异 (非统一 250)

第四轮据 case 36 的 `>0xF9` 将变量上限统一记为 250，复核发现 case 37/38/39 用的是更宽松的 `>=0x100`：

| 操作码 | 范围检查 | max index | 来源 |
|---|---|---|---|
| 36 SetVar | `> 0xF9` | 249 | `40EBD4.c:304` |
| 37 Random | `>= 0x100` | 255 | `40EBD4.c:314` |
| 38 SetFlagVar | `>= 0x100` | 255 | `40EBD4.c:330` |
| 39 AddFlagVar | `>= 0x100` | 255 | `40EBD4.c:340` |

存档预留 256 槽 (0x368-0x567, 512B)。编辑器维持编辑 0-249 (覆盖最严格的 SetVar 上限)；槽 250-254 无脚本使用；槽 255 与 last_acq 别名 (见下条)。

#### 2. last_acq 字段 = 变量槽 255 的内存别名

`word_75607E` (SEG1+0x566, last_acq) 地址 = `word_755E80 + 255*2` = `word_755E80[255]`。即"事件变量槽255"与"last_acq 字段"是同一内存单元，反编译器只是给了两个符号名。

`sub_40CE30` (opcode 40) 写入语义 (`40CE30.c`):
- 金币获取 (`a1==10000`): `word_75607E = a2` (获取的数量) — `40CE30.c:37`
- 物品获取: `word_75607E = word_77CBCE[32*v12]` (物品某属性) — `40CE30.c:92`

故原标注"最后获得金币"不完整，已改为"最后获得量(金币/物品)"。

#### 3. battle_flags (dword_755C80) 位定义修正

第四轮仅记 bit0-3 且 bit3 标"反击"。复核 `sub_4084E0` / `sub_431E70` / `sub_43B7FC` / `sub_41F784` 后修正：

| 位 | 语义 | 证据 |
|---|---|---|
| bit0 (0x1) | 遇敌冷却 +30% (随机阈值 140) | `4084E0.c:42,60-62` |
| bit1 (0x2) | 遇敌冷却 +50% (随机阈值 200) | `4084E0.c:36,56-58` |
| bit2 (0x4) | **禁止遇敌** (直接 return 0) | `4084E0.c:19` |
| bit3 (0x8) | 战斗数值修正 (sub_431E70，对 byte_9DF761==100 者 1-3 次扣减 word_9DF6BA) | `431E70.c:35-51` |
